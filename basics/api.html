컴퓨터끼리 대화하는 법 — API · REST의 역사

4장에서 "HTTP로 요청하고 JSON으로 답받는다"까지 봤습니다. 이 장은 한 걸음 물러나서 묻습니다. 컴퓨터끼리는 원래 어떻게 대화했고, 왜 지금은 REST가 기본이 됐을까? REST · RESTful · REST API가 각각 무슨 뜻인지, REST 말고는 어떤 방식이 있는지, 데이터 엔지니어가 실제로 마주치는 방식은 무엇인지 역사 순서로 정리합니다.

먼저 단어 정리 — API · REST · RESTful · REST API

말품사한 문장 뜻비유
API명사 (넓음)"이렇게 요청하면 이렇게 답한다"는 프로그램끼리의 약속 목록. 방식은 무엇이든 됨가게의 주문 창구
REST명사 (설계 스타일)웹이 잘 굴러가는 원리를 정리한 설계 규칙 묶음. 기술 · 프로그램 · 규격 문서가 아님"메뉴판을 보고 말로 주문한다"는 주문 예절
RESTful형용사"REST 규칙을 지키는". RESTful한 설계, RESTful한 주소"예절 바른"
REST API (RESTful API)명사REST 스타일로 만든 API. 실무에서는 "HTTP 주소 + 메서드 + JSON"이면 대개 이렇게 부름예절대로 운영되는 주문 창구

REST API와 RESTful API는 사실상 같은 말입니다. 차이가 생기는 곳은 따로 있습니다. REST를 만든 사람이 말하는 엄격한 REST와, 업계가 부르는 느슨한 REST API 사이입니다. 이 차이는 아래에서 다룹니다.

🧸 비유

"API"가 교통수단이라면 REST는 그중 버스입니다. 버스가 제일 흔하다고 해서 교통수단 = 버스는 아니죠. 기차(gRPC), 택시(GraphQL), 화물차(파일 전달)도 있습니다. "REST"는 버스 운행 규칙(정류장 · 노선 · 요금 체계), "RESTful"은 "규칙대로 다니는"이라는 형용사입니다.

한 줄로 줄이면 이렇습니다. "남의 컴퓨터를 내 함수처럼 부르고 싶다"는 욕심이 계속 무거워지다가, 웹의 단순함(REST)이 이겼고, 그다음엔 REST가 약한 곳을 GraphQL · gRPC가 메웠다.

1막 · 선을 잇는다 — 소켓 (1960s ~ 1980s)

1969년 ARPANET에서 처음으로 멀리 떨어진 컴퓨터끼리 메시지가 오갔습니다. 1983년에는 ARPANET 전체가 TCP/IP로 넘어가면서 "주소(IP) + 문(포트) + 순서 보장(TCP)"이라는 지금의 기초가 섰습니다. 같은 해 BSD 유닉스에 소켓(socket)이라는 프로그래밍 창구가 들어갔습니다.

  프로그램 A ──[소켓]── 바이트들 ──▶ ──[소켓]── 프로그램 B
                "0x48 0x45 0x4C 0x4C 0x4F ..."
  소켓이 해 주는 것: 선을 잇고, 바이트를 순서대로 보내 준다
  소켓이 안 해 주는 것: 그 바이트가 무슨 뜻인지 (→ 양쪽이 알아서 약속해야 함)

소켓은 전화선입니다. 통화는 되지만 무슨 말로 대화할지는 정해 주지 않습니다. 그래서 프로그램마다 자기만의 대화 규칙(프로토콜)을 만들었습니다. 메일은 SMTP, 파일은 FTP, DB는 각 DB 회사의 자체 규칙을 썼습니다. 지금도 PostgreSQL · MySQL은 이 시절 방식처럼 자기만의 이진 규칙(와이어 프로토콜)으로 대화합니다.

2막 · 남의 함수를 내 것처럼 — RPC · CORBA · ODBC (1980s ~ 1990s)

바이트를 직접 주무르는 건 너무 힘들었습니다. 그래서 1984년 Birrell과 Nelson이 RPC(원격 프로시저 호출) 구현 논문을 냈습니다. 아이디어는 간단합니다. "다른 컴퓨터의 함수를, 내 코드 안의 함수 부르듯 부르자."

# 내 코드에서는 그냥 함수 호출처럼 보이지만
spend = ads_server.get_campaign_spend("C001", "2026-11-01")
# 실제로는: 인자를 바이트로 포장 → 네트워크로 전송 → 저쪽에서 함수 실행 → 결과를 포장해 돌려받음

이 꿈은 여러 표준으로 커졌습니다. 기업용 CORBA(1991)는 언어가 달라도 서로 부를 수 있게 했고, 마이크로소프트의 DCOM(1996)과 자바의 RMI(1997)도 나왔습니다. 그런데 공통 문제가 있었습니다.

  • 네트워크는 함수가 아니다: 내 함수는 실패하지 않지만, 네트워크는 느려지고 끊깁니다. "함수처럼 보이게" 숨긴 탓에 오히려 실패 처리가 어려웠습니다.
  • 양쪽이 단단히 묶임: 서버 함수 모양이 바뀌면 클라이언트를 다시 빌드해야 했습니다.
  • 방화벽을 못 넘음: 각자 쓰는 포트와 규칙이 달라서 회사 밖으로 나가기 어려웠습니다.
SQL 감각으로 옮기면 — ODBC · JDBC

같은 시기에 DB 쪽에도 "어느 DB든 같은 방식으로 부르자"는 표준이 생겼습니다. 1992년 ODBC, 1997년 자바의 JDBC입니다. 엑셀 · BI 도구가 오라클 · SQL Server · PostgreSQL에 똑같이 붙는 이유가 이것입니다. 각 DB의 와이어 프로토콜 차이는 드라이버가 숨겨 줍니다. 지금 쓰는 Metabase도 JDBC 드라이버로 DB에 붙습니다. 그래서 Cube가 "나는 PostgreSQL이야"라고 말하는 SQL API를 열어 두면, Metabase는 진짜 PostgreSQL인 줄 알고 붙습니다.

3막 · 웹이 이긴다 — HTTP와 SOAP (1990s ~ 2000s 초)

1989년 CERN의 팀 버너스리가 웹을 제안했고, 1991년부터 HTTP 위에서 문서가 오가기 시작했습니다. HTTP는 단순했습니다. 텍스트로 된 요청 한 번, 응답 한 번이고, 문은 80번(나중에 HTTPS 443번) 하나였습니다. 무엇보다 방화벽이 이미 열어 둔 문이었습니다.

그러자 "함수 호출도 HTTP에 실어 보내자"는 흐름이 생겼습니다. 1998년 XML-RPC, 이어서 마이크로소프트 등이 키운 SOAP입니다. 함수 호출을 XML 봉투에 담아 HTTP로 보냈고, WSDL(서비스 설명서) · UDDI(서비스 전화번호부) 같은 표준이 줄줄이 붙었습니다.

POST /AdService HTTP/1.1
Content-Type: text/xml; charset=utf-8
SOAPAction: "GetCampaignSpend"

<soap:Envelope xmlns:soap="http://schemas.xmlsoap.org/soap/envelope/">
  <soap:Header><Auth><Token>abc123</Token></Auth></soap:Header>
  <soap:Body>
    <GetCampaignSpend>
      <CampaignId>C001</CampaignId>
      <Date>2026-11-01</Date>
    </GetCampaignSpend>
  </soap:Body>
</soap:Envelope>

SOAP은 엄격하고 기업 시스템에 잘 맞았지만 무거웠습니다. 봉투가 크고, 도구 없이는 읽고 쓰기 어려웠고, 모든 요청이 POST 하나로 같은 주소에 몰려서 웹의 장점(캐시, 주소로 구분)을 못 썼습니다. 오래된 은행 · 공공 · 일부 광고 시스템에는 지금도 남아 있습니다.

4막 · "웹처럼 만들자" — REST의 탄생 (2000)

2000년, 로이 필딩(Roy Fielding)이 UC 어바인 박사 논문 「Architectural Styles and the Design of Network-based Software Architectures」의 5장에서 REST를 정리했습니다. 필딩은 HTTP/1.1 규격을 직접 쓴 사람 중 하나입니다. 그래서 질문이 남달랐습니다. "웹은 왜 이렇게 크게 커지고도 안 무너졌나? 그 원리를 규칙으로 뽑아 보자."

이름은 REpresentational State Transfer, 풀면 "자원의 상태를 JSON · HTML 같은 표현으로 주고받는다"입니다.

REST의 제약 6개

REST는 기술이 아니라 "이 6가지를 지키면 웹처럼 커져도 버틴다"는 제약 조건의 묶음입니다.

#제약뜻지키면 얻는 것
1클라이언트-서버화면(요청하는 쪽)과 데이터(답하는 쪽)를 나눈다각자 따로 바꿀 수 있음
2무상태 (stateless)요청마다 필요한 걸 다 담아 보낸다. 서버는 "아까 그 사람"을 기억하지 않는다서버를 여러 대로 늘리기 쉬움 (아무 서버나 받아도 됨)
3캐시 가능응답에 "이건 10분간 다시 써도 됨" 같은 표시를 붙인다같은 요청을 서버까지 안 보내도 됨
4균일한 인터페이스모든 자원을 같은 방식으로 다룬다 (아래 4개 세부 규칙)처음 보는 API도 읽는 법이 같음
5계층 구조중간에 프록시 · 로드밸런서 · CDN이 끼어도 클라이언트는 모른다보안 · 속도 장치를 사이에 넣기 쉬움
6코드 온 디맨드 (선택)서버가 실행할 코드(자바스크립트)를 보내 줄 수도 있다웹 페이지의 동작

4번 "균일한 인터페이스"가 REST의 핵심이고, 세부 규칙이 넷입니다.

  1. 자원은 주소로 가리킨다: /campaigns/C001. 주소는 명사입니다.
  2. 표현으로 다룬다: 서버 안의 실제 데이터가 아니라, 그걸 JSON으로 표현한 것을 주고받습니다.
  3. 메시지가 스스로 설명한다: 메서드(GET), 상태 코드(404), 헤더(Content-Type: application/json)만 보고도 무슨 일인지 압니다.
  4. 하이퍼미디어 (HATEOAS): 응답 안에 "다음에 갈 수 있는 링크"가 들어 있어서, 클라이언트가 링크를 따라가며 움직입니다. 웹 페이지에서 링크를 누르며 돌아다니는 것과 같습니다.
하고 싶은 일REST 스타일함수 호출(RPC) 스타일
캠페인 조회GET /campaigns/C001POST /getCampaign + {"id":"C001"}
예산 수정PATCH /campaigns/C001POST /updateCampaignBudget + {"id":"C001", ...}
캠페인 삭제DELETE /campaigns/C001POST /deleteCampaign + {"id":"C001"}
특징주소 = 명사, 행동 = HTTP 메서드주소에 동사가 들어감, 거의 다 POST

"진짜 REST"와 "실무 REST API" — 리처드슨 성숙도 모델

2000년대 중반부터 JSON을 HTTP로 주고받는 API가 폭발했고, 다들 그걸 "REST API"라고 불렀습니다. 그런데 2008년 필딩은 블로그에 "REST API는 하이퍼텍스트로 움직여야 한다"는 글을 써서, HATEOAS가 없으면 REST라고 부르지 말라고 했습니다. 실무 API 대부분이 여기에 해당했습니다.

이 간극을 정리한 것이 레너드 리처드슨의 성숙도 모델(2008년 발표, 2010년 마틴 파울러의 글로 널리 알려짐)입니다.

단계모양예
0단계주소 하나에 POST만. HTTP를 "운반용 관"으로만 씀SOAP, XML-RPC
1단계자원마다 주소가 생김POST /campaigns/C001
2단계HTTP 메서드와 상태 코드를 제대로 씀GET /campaigns/C001 → 200, 없으면 404 · 실무 "REST API" 대부분이 여기
3단계응답에 다음 행동 링크(HATEOAS)"links": {"pause": "/campaigns/C001/pause"} · 필딩이 말하는 진짜 REST
실무에서는

"REST API"라고 하면 거의 항상 2단계를 뜻합니다. 주소는 명사, 행동은 메서드, 결과는 상태 코드와 JSON입니다. 엄밀하게 말하고 싶은 사람은 이걸 "HTTP API"나 "JSON API"라고 부르기도 합니다. 면접이나 문서에서는 "엄밀한 REST는 HATEOAS까지 포함하지만, 보통 말하는 REST API는 리소스 주소 + HTTP 메서드 + JSON 수준"이라고 한 문장 덧붙이면 정확합니다.

5막 · REST의 시대 — JSON · OAuth · 웹훅 · OpenAPI (2000s ~ 2010s)

REST가 이긴 데는 같이 자란 도구들이 큰 몫을 했습니다.

시기일왜 중요했나
2000 전후Salesforce · eBay 등이 웹 API를 공개"API를 열어 남이 우리 서비스 위에 무언가 만들게 하자"는 사업 모델의 시작
2001 ~ 2006더글러스 크록퍼드가 정리한 JSON이 퍼지고, 2006년 RFC 4627로 문서화XML보다 훨씬 가볍고, 자바스크립트가 바로 읽음 → 웹 API 기본 형식이 됨
2005AJAX라는 말 등장 (페이지 새로고침 없이 데이터만 요청)브라우저가 API를 직접 부르는 시대
2007웹훅(webhook)이라는 말 등장"다 됐니?"를 계속 묻는 대신, 일이 생기면 서버가 먼저 알려 줌
2007 · 2012OAuth 1.0 → OAuth 2.0 (RFC 6749)비밀번호를 넘기지 않고 "이 앱이 내 광고 계정 읽어도 됨"만 위임. 광고 매체 API는 거의 다 이 방식
2011 · 2015Swagger → OpenAPI 표준REST API 설명서를 기계가 읽는 형식으로. 문서 · 테스트 화면 · 클라이언트 코드 자동 생성
2015JWT (RFC 7519)서명된 토큰 안에 "누구 · 언제까지"를 담음 → 서버가 기억할 필요 없음 (무상태와 잘 맞음)

6막 · REST가 약한 곳을 메운다 — GraphQL · gRPC · 실시간 (2010s ~)

REST가 표준이 되자 약점도 보였습니다.

  • 너무 많이 받거나 너무 적게 받음: 모바일 화면 하나를 그리려고 주소 5개를 부르고, 각각 필요 없는 필드까지 받았습니다.
  • 서버끼리의 대량 통신엔 느림: 텍스트 JSON을 매번 만들고 해석하는 비용이 컸습니다.
  • 실시간에 약함: 요청해야만 답이 오므로, 채팅 · 주가처럼 계속 바뀌는 데이터에 안 맞았습니다.

결국 2막의 "함수 호출(RPC)"과 4막의 "자원 주소(REST)"는 둘 중 하나가 이긴 게 아니라 쓰임새가 나뉘었습니다. 밖에 공개하는 API는 REST, 회사 안 서버끼리는 gRPC, 화면 데이터는 GraphQL을 많이 씁니다.

대화의 모양 — 누가 먼저 말하나

방식(REST · gRPC…)과 별개로, 언제 · 누가 먼저 말하는지도 고를 수 있습니다. 데이터 엔지니어에게는 이쪽이 더 자주 문제가 됩니다.

  ① 요청응답   me ---request--->  server ---response--->  me
                "지금 줘" (REST 기본)

  ② 폴링       me ---"done?"---> (no) ... me ---"done?"---> (yes, here)
                큰 리포트 생성을 기다릴 때

  ③ 웹훅       server ---"done, here it is"--->  my URL
                서버가 먼저 연락 (결제 완료 알림)

  ④ 스트리밍   me <=== keeps flowing ===  server
                연결을 열어 둠 (실시간 · AI 답변)

  ⑤ 메시지 큐  sender --->  [ mailbox: Kafka · Pub/Sub ]  ---> receiver
                서로 몰라도 됨 · 나중에 읽어도 됨

  ⑥ 파일 전달  server drops a file (S3 · GCS · SFTP)  ---> I pick it up
                대용량 · 하루 한 번

손으로 해 보기

아래 실습은 내 PC에 띄운 연습용 Cube(http://localhost:4000)를 씁니다. Docker Desktop을 켜고 cube-playground 폴더에서 docker compose up -d로 띄웁니다. 브라우저 주소창에 주소를 넣는 것 = GET 요청입니다.

1. 가장 작은 REST API — 서버 살아 있니?
http://localhost:4000/readyz

{"health":"HEALTH"}가 보이면 됩니다. 주소(자원) + GET(가져와) + JSON(표현), REST의 세 요소가 다 들어 있습니다.

2. 메뉴판 받기 — 무엇을 물어볼 수 있나
http://localhost:4000/cubejs-api/v1/meta

meta_ads.spend, meta_ads.roas 같은 지표 목록이 나옵니다. 챗봇은 이 목록 안에서만 지표를 골라야 계산법이 흔들리지 않습니다.

3. 숫자 받기 — GET과 POST 둘 다로

브라우저(GET): 주문서를 주소 뒤 ?query=에 붙입니다.

http://localhost:4000/cubejs-api/v1/load?query={"measures":["meta_ads.spend","meta_ads.roas"],"dimensions":["meta_ads.brand"]}

PowerShell(POST): 같은 주문서를 바디에 담습니다.

$body = '{"query":{"measures":["meta_ads.spend","meta_ads.roas"],"dimensions":["meta_ads.brand"]}}'
(Invoke-RestMethod http://localhost:4000/cubejs-api/v1/load -Method Post -ContentType 'application/json' -Body $body).data
왜 같은 일을 두 방법으로?

GET은 주소에 다 담겨서 브라우저로 쉽게 확인할 수 있지만, 주소 길이 한계가 있고 기록(방문 기록 · 서버 로그)에 그대로 남습니다. 긴 주문서나 민감한 조건은 POST 바디로 보냅니다. Cube는 둘 다 받아 줍니다.

4. 상태 코드로 대화하기 — 400과 404
try { Invoke-WebRequest 'http://localhost:4000/cubejs-api/v1/load?query={"measures":["meta_ads.nope"]}' -UseBasicParsing }
catch { [int]$_.Exception.Response.StatusCode }        # 400 : 주문서가 잘못됨 (없는 지표)
try { Invoke-WebRequest http://localhost:4000/cubejs-api/v1/nothing -UseBasicParsing }
catch { [int]$_.Exception.Response.StatusCode }        # 404 : 그런 주소(자원) 없음

"메시지가 스스로 설명한다"는 규칙입니다. 본문을 읽지 않아도 숫자만으로 "내 잘못(4xx)인지, 서버 잘못(5xx)인지"를 압니다.

정리

💡 한 줄 요약 컴퓨터끼리의 대화는 선 잇기(소켓) → 함수 흉내(RPC) → 무거운 웹 표준(SOAP) → 웹처럼 단순하게(REST) → 목적별 특화(GraphQL · gRPC · 스트리밍)로 왔습니다. REST는 기술이 아니라 설계 규칙이고, 실무의 "REST API"는 대개 주소는 명사 · 행동은 HTTP 메서드 · 결과는 상태 코드와 JSON을 뜻합니다.

퀴즈

REST를 가장 정확하게 설명한 것은?

  1. JSON을 주고받는 통신 프로토콜
  2. 웹이 크게 커져도 버티는 원리를 정리한 설계 제약(스타일)의 묶음
  3. 구글이 만든 고속 API 프레임워크
  4. HTTP의 새 버전 이름
REST는 로이 필딩이 2000년 논문에서 정리한 아키텍처 스타일입니다. JSON도 HTTP 버전도 아니고, 구글의 프레임워크는 gRPC입니다.

다음 중 가장 REST다운(RESTful) 설계는?

  1. GET /deleteCampaign?id=C001
  2. POST /campaignService 바디 {"action":"delete","id":"C001"}
  3. DELETE /campaigns/C001
  4. POST /campaigns/C001/delete-now
주소는 자원(명사), 행동은 HTTP 메서드로 나눕니다. 1번은 주소에 동사가 있고 GET으로 지우기까지 합니다(위험). 2번은 리처드슨 0단계(SOAP 스타일)입니다.

REST의 "무상태(stateless)" 제약을 지켰을 때 얻는 가장 큰 이점은?

  1. 어느 서버가 요청을 받아도 처리할 수 있어 서버를 늘리기 쉽다
  2. 응답이 항상 JSON이 된다
  3. 토큰을 보낼 필요가 없어진다
  4. HTTPS가 필요 없어진다
요청마다 필요한 정보(토큰 · 조건)를 다 담아 보내므로 서버가 "아까 그 사람"을 기억할 필요가 없습니다. 그래서 오히려 토큰은 매번 보내야 합니다.

회사 안 서버끼리 초당 수만 건을 빠르게 주고받아야 하고, 주고받는 형식을 엄격하게 고정하고 싶다. 가장 알맞은 선택은?

  1. SOAP
  2. 웹훅
  3. GraphQL
  4. gRPC
gRPC는 HTTP/2 위에서 Protocol Buffers(이진 형식)로 미리 정한 함수를 호출해 빠르고 형식이 엄격합니다. GraphQL은 "필요한 필드만"이 강점이고, 웹훅은 알림 방식입니다.

Metabase가 Cube를 "PostgreSQL처럼" 연결할 수 있는 이유는?

  1. Cube가 내부에 진짜 PostgreSQL을 품고 있어서
  2. Cube의 SQL API가 PostgreSQL과 같은 와이어 프로토콜로 대화해서, Metabase의 PostgreSQL 드라이버가 그대로 붙어서
  3. Metabase가 REST API를 SQL로 자동 번역해서
  4. 둘 다 JSON을 써서
"같은 말로 대화하면 상대가 누구인지 몰라도 된다"는 2막 ODBC · JDBC의 아이디어입니다. Cube는 PostgreSQL처럼 말할 뿐, 실제 계산은 자기 정의대로 해서 BigQuery(또는 DuckDB)에 보냅니다.
