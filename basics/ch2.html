코드가 돌아가는 원리

1장에서 CPU는 "더해라·비교해라·건너뛰어라" 같은 아주 단순한 명령만 안다고 했습니다. 그런데 우리는 total = sum(prices)나 SELECT ... GROUP BY처럼 사람 말에 가까운 코드를 씁니다. 이 장은 그 사이에서 무슨 일이 일어나는지를 봅니다. 그리고 에러 메시지(트레이스백)를 겁내지 않고 읽는 법까지 익힙니다.

이 장을 마치면
  • 소스 코드가 기계어가 되는 두 가지 길(컴파일·인터프리트)을 설명하기
  • Python이 .py 파일을 실행할 때 거치는 단계와 __pycache__ 폴더의 정체를 말하기
  • 변수가 "값을 담는 상자"가 아니라 "값에 붙인 이름표"라는 것을 예로 보이기
  • 트레이스백을 아래에서부터 읽어 원인 줄을 찾기
  • SQL이 선언형이라는 말의 뜻과, 옵티마이저가 무엇을 대신해 주는지 설명하기
  • import가 모듈을 어디서 찾는지, 순서대로·동시에·병렬 실행이 어떻게 다른지 말하기

사람 말에서 기계어까지

CPU가 실제로 실행하는 것은 기계어(machine code), 즉 명령어 번호와 데이터가 담긴 바이트입니다. 사람이 그걸 직접 쓰기는 너무 힘들어서, 위로 갈수록 사람 말에 가까운 층을 쌓아 왔습니다.

  사람에 가까움
       ▲   SQL            SELECT city, SUM(amount) FROM sales GROUP BY city
       │                  "무엇을 원하는지"만 적는다 (선언형)
       │   Python · Java  for r in rows: totals[r.city] += r.amount
       │                  "어떻게 할지"를 순서대로 적는다 (명령형)
       │   C · Rust       포인터·메모리를 직접 다룬다
       │   어셈블리        ADD  RAX, RBX      ← 기계어를 글자로 적은 것
       │   기계어          48 01 D8           ← CPU가 실제로 읽는 바이트
       ▼
  기계에 가까움          위의 어떤 코드든 결국 맨 아래 형태가 되어야 실행된다
🧸 비유 — 통역

CPU는 아주 좁은 사투리만 알아듣는 일꾼입니다. 우리가 표준어(Python·SQL)로 말하면 누군가 그 사투리로 옮겨 줘야 합니다. 옮기는 방법은 두 가지입니다. 책 한 권을 미리 통째로 번역해 두거나(컴파일), 옆에서 한 문장씩 바로바로 통역하거나(인터프리트).

컴파일 vs 인터프리터

컴파일 방식인터프리터 방식
언제 옮기나실행 전에 전체를 기계어로 번역해 실행 파일(.exe 등)을 만든다실행하는 동안 한 줄(한 덩이)씩 읽어 처리한다
대표C, C++, Rust, GoPython, JavaScript, 셸 스크립트(PowerShell·bash)
장점빠르다. 실행 파일만 있으면 언어 없이도 돈다. 오타·타입 오류를 실행 전에 많이 잡는다고치고 바로 돌려 볼 수 있다. 같은 코드가 여러 OS에서 돈다
단점OS·CPU마다 따로 번역해야 한다. 번역 시간이 든다느리다. 오류가 그 줄에 도착해야 드러난다

실제로는 둘이 섞여 있습니다. Java와 C#은 먼저 바이트코드(bytecode)라는 중간 언어로 번역해 두고, 실행할 때 가상 머신이 그걸 처리합니다. 자주 쓰는 부분은 실행 중에 기계어로 번역해 두는데, 이걸 JIT(Just-In-Time) 컴파일이라고 합니다. Python(정확히는 표준 구현인 CPython)도 사실은 바이트코드로 한 번 바꾼 다음 실행합니다.

데이터 엔지니어에게는
  • pandas·numpy·DuckDB·Polars가 Python인데도 빠른 이유: 겉은 Python이지만 무거운 계산은 C·C++·Rust로 미리 컴파일된 코드가 합니다. 그 컴파일된 부품이 윈도에서는 .dll·.pyd 파일입니다.
  • 그래서 "Python에서 for문으로 행을 하나씩 도는 코드"와 "라이브러리 함수 한 번 호출"은 속도가 수십~수백 배 차이 날 수 있습니다. 행 단위 반복은 되도록 라이브러리나 SQL에 맡기세요.
  • 회사 보안 정책이 처음 보는 .dll을 막으면 "설치는 됐는데 import에서 에러" 가 납니다. 컴파일된 부품이 실행을 거부당한 것입니다.

Python은 실제로 어떻게 실행되나

python main.py를 치면 이런 일이 일어납니다.

  main.py (글자)
      │ ① 읽기 + 문법 검사        → 괄호 빠짐 등은 여기서 SyntaxError (한 줄도 실행 안 됨)
      ▼
  구문 트리 (AST)               "이건 함수 정의, 이건 대입, 이건 곱셈"으로 구조화
      │ ② 컴파일
      ▼
  바이트코드                     LOAD_FAST, BINARY_OP … 같은 Python 전용 명령
      │   (import 된 모듈은 __pycache__/*.pyc 로 저장해 두고 다음에 재사용)
      ▼ ③ 실행
  Python 가상 머신(인터프리터)     바이트코드를 하나씩 읽어 처리
      │                         (여기 자체는 C로 짜서 미리 컴파일된 python.exe)
      ▼
  CPU                           결국 python.exe 의 기계어가 돈다

바이트코드는 dis 모듈로 직접 볼 수 있습니다(Python 3.12 결과).

>>> import dis
>>> def add_tax(price):
...     return price * 1.1
...
>>> dis.dis(add_tax)
  1           0 RESUME                   0

  2           2 LOAD_FAST                0 (price)     # price 값을 꺼낸다
              4 LOAD_CONST               1 (1.1)       # 상수 1.1을 꺼낸다
              6 BINARY_OP                5 (*)         # 둘을 곱한다
             10 RETURN_VALUE                           # 결과를 돌려준다

바이트코드 모양은 Python 버전마다 조금씩 다릅니다. 내 PC 결과가 조금 달라도 괜찮습니다.

__pycache__의 정체

프로젝트 폴더에 저절로 생기는 __pycache__/helper.cpython-312.pyc는 import된 모듈의 바이트코드를 저장해 둔 것입니다. 이름의 312는 Python 3.12용이라는 뜻입니다. 다음 실행 때 원본 .py가 안 바뀌었으면 ②단계를 건너뛰어 빨라집니다. 지워도 다시 만들어지므로 안전하고, git에는 올리지 않습니다(.gitignore에 넣음). 직접 실행한 파일(python main.py의 main.py)은 저장하지 않고 import된 쪽만 저장합니다.

SQL 감각으로 옮기면 DB도 비슷한 일을 합니다. SQL 글자를 받으면 ① 문법 검사(파싱) → ② 실행 계획 만들기 → ③ 실행 순서로 처리하고, 자주 쓰는 실행 계획은 캐시해 둡니다. 프로시저를 "컴파일한다"고 할 때도 이렇게 미리 검사하고 계획을 만들어 두는 일을 말합니다. 문법 오류가 실행 시작 전에 나는 것도 같습니다.

변수·값·참조 — 이름표 이야기

처음 배울 때 "변수는 값을 담는 상자"라고 듣지만, Python에서는 "메모리 어딘가에 있는 값(객체)에 붙인 이름표"라고 이해해야 헷갈리지 않습니다.

a = [1, 2, 3]      # 메모리에 리스트 하나를 만들고 'a' 이름표를 붙인다
b = a              # 같은 리스트에 'b' 이름표를 하나 더 붙인다 (복사가 아님!)
b.append(4)        # b가 가리키는 리스트에 4를 넣으면…
print(a)           # [1, 2, 3, 4]  ← a도 바뀌었다. 같은 리스트니까
print(a is b)      # True          ← 정말로 같은 객체

c = a.copy()       # 새 리스트를 만들어 복사한다
c.append(5)
print(a, c)        # [1, 2, 3, 4] [1, 2, 3, 4, 5]  ← 이제 따로 논다
  b = a 일 때                         c = a.copy() 일 때

   a ──┐                               a ──▶ [1, 2, 3, 4]
       ├──▶ [1, 2, 3, 4]
   b ──┘                               c ──▶ [1, 2, 3, 4, 5]   (다른 객체)

그런데 숫자·문자열은 다르게 보입니다.

x = 10
y = x
y = y + 1          # 10을 바꾸는 게 아니라, 11이라는 새 값에 y 이름표를 옮겨 붙인다
print(x, y)        # 10 11

숫자·문자열·튜플은 바꿀 수 없는(immutable) 값이라 "고친다"는 게 항상 "새 값을 만들어 이름표를 옮긴다"입니다. 리스트·딕셔너리·집합은 바꿀 수 있는(mutable) 값이라 이름표 여러 개가 같은 값을 공유하면 한쪽 변경이 다른 쪽에도 보입니다.

🧸 비유 — 공유 문서와 첨부 파일

b = a는 구글 시트 링크를 공유한 것입니다. 누가 고치든 모두에게 바뀐 게 보입니다. a.copy()는 엑셀 파일을 첨부로 보낸 것이라, 받은 사람이 고쳐도 내 원본은 그대로입니다.

SQL 감각으로 옮기면 b = a는 뷰(VIEW), a.copy()는 CREATE TABLE b AS SELECT * FROM a와 비슷합니다. 뷰는 원본을 가리키기만 해서 원본이 바뀌면 같이 바뀌고, CTAS로 만든 테이블은 그 순간의 복사본이라 따로 놉니다.

Python은 실행 중에 타입을 확인합니다. "1" + "1"은 "11"(문자열 이어 붙이기), 1 + 1은 2입니다. CSV에서 읽은 값은 전부 문자열이라, 숫자로 바꾸지 않고 더하면 이런 일이 생깁니다.

함수와 호출 스택

함수가 다른 함수를 부르면, 컴퓨터는 "어디까지 하다 왔는지"를 차곡차곡 쌓아 둡니다. 이 더미를 호출 스택(call stack)이라고 합니다. 함수가 끝나면 맨 위에서 하나를 꺼내 원래 자리로 돌아갑니다.

  f() 가 g() 를, g() 가 h() 를 부른 순간의 스택

        ┌───────────────┐  ← 맨 위: 지금 실행 중
        │ h()  6번째 줄    │
        ├───────────────┤
        │ g()  4번째 줄    │  h 가 끝나면 여기로 돌아옴
        ├───────────────┤
        │ f()  3번째 줄    │
        ├───────────────┤
        │ <module> 7번째 줄 │  ← 맨 아래: 파일 자체 (가장 먼저 시작)
        └───────────────┘
🧸 비유 — 접시 쌓기

일을 맡길 때마다 접시를 하나 위에 올리고, 일이 끝나면 맨 위 접시부터 치웁니다. 함수가 자기 자신을 끝없이 부르면(무한 재귀) 접시가 천장까지 쌓여 무너지는데, 그게 RecursionError(다른 언어에서는 stack overflow)입니다. Python은 기본으로 약 1,000층에서 멈춥니다.

각 함수 호출은 자기만의 지역 변수 칸을 스택에 갖습니다. 그래서 함수 안의 s = 0은 바깥의 s와 다른 변수입니다. 함수가 끝나면 그 칸도 사라집니다.

에러와 트레이스백 읽는 법

에러가 나면 Python은 그 순간의 호출 스택을 그대로 출력합니다. 이걸 트레이스백(traceback)이라고 합니다. 길어 보여도 읽는 순서만 알면 쉽습니다.

def parse_amount(text):
    return int(text)

def total(rows):
    s = 0
    for r in rows:
        s += parse_amount(r["amount"])
    return s

rows = [{"amount": "1000"}, {"amount": "2,000"}]
print(total(rows))
Traceback (most recent call last):
  File "...\shop.py", line 11, in <module>
    print(total(rows))
          ^^^^^^^^^^^
  File "...\shop.py", line 7, in total
    s += parse_amount(r["amount"])
         ^^^^^^^^^^^^^^^^^^^^^^^^^
  File "...\shop.py", line 2, in parse_amount
    return int(text)
           ^^^^^^^^^
ValueError: invalid literal for int() with base 10: '2,000'
읽는 순서 — 아래에서 위로
  1. 맨 마지막 줄부터: 에러종류: 설명. 여기서는 ValueError, "'2,000'은 int로 바꿀 수 없다". 이 한 줄이 답의 80%입니다.
  2. 바로 위 블록: 에러가 실제로 터진 곳(2번째 줄 int(text)). ^^^^는 그 줄에서 문제가 된 부분을 가리킵니다(Python 3.11+).
  3. 더 위로: 누가 그 함수를 불렀는지 거슬러 올라갑니다. 7번째 줄 total → 11번째 줄 파일 본문. "most recent call last"는 가장 최근 호출이 맨 아래라는 뜻입니다.
  4. 내 코드의 줄을 찾기: 라이브러리 내부 경로(site-packages\...)가 길게 이어져도, 그중 내 파일 이름이 나오는 가장 아래 줄이 보통 고칠 곳입니다.
여기서는 원천 데이터에 천 단위 쉼표가 섞여 있었습니다. int(text.replace(",", ""))로 고치거나, 더 좋게는 수집 단계에서 숫자 형식을 정해 두면 됩니다.

SQL 감각으로 옮기면 BigQuery의 Bad int64 value: 2,000, Unrecognized name: amout가 각각 Python의 ValueError, NameError입니다. SQL 에러는 보통 한 줄이지만, Python은 "누가 누구를 불러서 여기까지 왔는지"를 전부 보여 준다는 점만 다릅니다. 프로시저 안에서 프로시저를 부르다 난 에러를 추적하는 것과 같습니다.

명령형 Python, 선언형 SQL

같은 일 — "1,000원 이상 주문만, 도시별 합계" — 을 두 방식으로 적어 보겠습니다.

SQL: "무엇을" 원하는지만
SELECT city, SUM(amount) AS total
FROM sales
WHERE amount >= 1000
GROUP BY city;
Python: "어떻게" 할지 순서대로
totals = {}                       # 결과 테이블 (GROUP BY 결과)
for r in rows:                    # FROM sales — 한 행씩
    if r["amount"] >= 1000:       # WHERE amount >= 1000
        city = r["city"]          # GROUP BY city 의 키
        # SUM(amount): 없으면 0에서 시작해 더하기
        totals[city] = totals.get(city, 0) + r["amount"]
print(totals)                     # {'서울': 3000}

Python 쪽은 "한 행씩 돌고, 조건을 보고, 딕셔너리에 더하라"는 절차를 사람이 다 정했습니다. SQL 쪽은 원하는 결과의 모양만 말했고, 절차는 DB가 정합니다. DB 안에서 그 일을 하는 것이 옵티마이저(optimizer)입니다.

  SQL 글자 ──▶ 파서 ──▶ 옵티마이저 ──────────────▶ 실행 계획 ──▶ 실행 엔진
                         │ 고민하는 것들                   (EXPLAIN 으로 볼 수 있음)
                         ├ 인덱스를 쓸까, 전체를 읽을까
                         ├ 어느 테이블부터 조인할까, 해시 조인? 중첩 반복?
                         ├ WHERE 를 먼저 적용해 읽을 양을 줄일 수 있나
                         └ 몇 조각으로 나눠 동시에 돌릴까 (분산 DB)
🧸 비유 — 내비게이션

명령형은 "300m 직진, 우회전, 두 번째 골목 좌회전"을 내가 정하는 것이고, 선언형은 목적지만 찍고 내비게이션에 맡기는 것입니다. 내비게이션(옵티마이저)은 그날 교통(데이터 크기·인덱스·통계)을 보고 길을 고릅니다. 데이터가 커져도 SQL은 그대로 두고 DB가 더 좋은 길을 찾아 주는 이유입니다.

데이터 엔지니어에게는
  • 선언형이라도 옵티마이저가 고를 수 있는 길을 막으면 느려집니다. 예: 파티션 컬럼에 함수를 씌워 WHERE DATE(ts) = ...처럼 쓰면 일부 DB는 파티션을 건너뛰지 못합니다. 실행 계획(EXPLAIN, BigQuery의 실행 그래프)을 보는 습관이 필요합니다.
  • dbt·Spark·pandas도 이 생각을 따릅니다. Spark DataFrame은 바로 실행하지 않고 계획을 모았다가 한 번에 최적화해서 돌립니다(지연 실행).
  • Python은 "정해진 절차가 필요할 때"(API 호출, 파일 옮기기, 재시도), SQL은 "집합 계산"에 씁니다. 집계를 Python 반복문으로 하는 건 대부분 손해입니다.

순서대로·동시에·병렬로

프로그램이 느린 이유는 크게 두 가지입니다. 계산할 게 많거나(CPU 바쁨), 기다리는 시간이 길거나(I/O 대기) — 네트워크 응답, 디스크 읽기, DB 쿼리 결과를 기다리는 시간입니다. 해결책이 다릅니다.

방식무엇잘 맞는 일Python 도구
순서대로(동기)하나 끝나면 다음단순한 스크립트평범한 코드
동시에(concurrency)기다리는 동안 다른 일을 시작API 여러 개 호출, 파일 여러 개 다운로드스레드(ThreadPoolExecutor), asyncio
병렬로(parallelism)코어 여러 개가 정말 같은 순간에 계산큰 계산, 이미지 처리프로세스(ProcessPoolExecutor, multiprocessing)
분산컴퓨터 여러 대가 나눠서 계산한 대에 안 들어가는 데이터Spark, BigQuery 같은 웨어하우스
🧸 비유 — 라면 다섯 개

라면 다섯 개를 끓일 때 하나 끓이고 다 먹고 다음 걸 올리면 순서대로입니다. 냄비 다섯 개를 동시에 올리고 물 끓는 동안 기다리면 동시에(혼자서도 됨, 대부분 기다리는 시간이니까)입니다. 요리사 다섯 명이 각자 끓이면 병렬, 식당 다섯 곳에 나눠 주문하면 분산입니다.

CPython에는 GIL(Global Interpreter Lock)이 있어서, 스레드를 여러 개 만들어도 Python 바이트코드는 한 순간에 하나의 스레드만 실행합니다. 그래서 스레드는 "기다리는 일"에는 효과가 크지만 "계산이 많은 일"은 빨라지지 않습니다. 계산을 나누려면 프로세스를 여러 개 쓰거나, C로 된 라이브러리·DB에 맡깁니다. (Python 3.13부터 GIL 없는 빌드가 실험적으로 나왔지만, 아직 일반적인 기본 설치는 GIL이 있는 쪽입니다.)

메모리는 누가 치우나 — 가비지 컬렉션

값(객체)을 만들면 메모리를 차지합니다. C 같은 언어는 다 쓴 메모리를 사람이 직접 돌려줘야 하고, 깜빡하면 메모리가 계속 새는(memory leak) 버그가 생깁니다. Python·Java·JavaScript는 가비지 컬렉션(GC)이 자동으로 치웁니다.

  • CPython은 기본으로 참조 카운트를 씁니다. 객체마다 "나를 가리키는 이름표가 몇 개인지"를 세다가 0이 되면 바로 메모리를 돌려줍니다.
  • 서로가 서로를 가리키는 고리(순환 참조)는 카운트가 0이 안 되므로, 가끔 따로 고리를 찾아 치우는 순환 GC가 돕니다.
>>> import sys
>>> a = [1, 2]
>>> sys.getrefcount(a)   # 2 — a 하나 + 이 함수에 넘기느라 잠깐 생긴 것 하나
2
>>> b = a
>>> sys.getrefcount(a)   # 3 — b 이름표가 늘었다
3
>>> del b                # 이름표를 떼면
>>> sys.getrefcount(a)
2
데이터 엔지니어에게는 GC가 있어도 이름표가 붙어 있는 동안에는 치우지 않습니다. 큰 데이터를 리스트에 계속 쌓아 두거나, 전역 변수에 담아 두면 메모리가 계속 늘어 결국 OOM(1장)으로 죽습니다. 큰 데이터는 처리한 뒤 이름표를 떼고(del), 애초에 나눠서(청크) 처리하는 것이 기본입니다.

4. 순서대로 vs 동시에 — 기다리는 일 다섯 개

wait.py를 만들어 실행합니다. time.sleep(1)은 "API 응답을 1초 기다린다"는 흉내입니다.

import time
from concurrent.futures import ThreadPoolExecutor   # 스레드 여러 개로 동시에 일 시키는 도구

def fetch(n):          # API 하나 호출하는 척
    time.sleep(1)      # 응답 기다리는 1초
    return n

t = time.time()
[fetch(n) for n in range(5)]                 # 하나씩 순서대로 5번
print(f"순서대로: {time.time() - t:.1f}초")

t = time.time()
with ThreadPoolExecutor(max_workers=5) as pool:   # 일꾼 5명
    list(pool.map(fetch, range(5)))               # 5개를 나눠 맡김
print(f"동시에: {time.time() - t:.1f}초")
python wait.py

결과:

순서대로: 5.0초
동시에: 1.0초

기다리는 일이라 스레드로 5배 빨라졌습니다. 같은 실험을 time.sleep(1) 대신 sum(range(30_000_000))처럼 계산만 하는 일로 바꾸면 스레드로는 거의 빨라지지 않습니다(GIL). 시간이 되면 직접 비교해 보세요.

퀴즈

CPython이 .py 파일을 실행하는 방식으로 가장 정확한 것은?

  1. 실행 전에 전체를 기계어 .exe로 컴파일한다
  2. 소스 코드 글자를 CPU가 직접 읽는다
  3. 바이트코드로 바꾼 뒤, 인터프리터(Python 가상 머신)가 그 바이트코드를 실행한다
  4. SQL로 바꿔서 DB에 보낸다
CPython은 소스를 바이트코드로 컴파일한 뒤 가상 머신이 그걸 하나씩 실행합니다. 기계어 실행 파일을 만드는 것은 C·Go 같은 컴파일 언어 방식이고, CPU는 소스 글자를 직접 읽지 못합니다.

프로젝트 폴더의 __pycache__ 폴더에 대한 설명으로 맞는 것은?

  1. import된 모듈의 바이트코드를 저장해 둔 것이라 지워도 다시 만들어진다
  2. 실행 기록(로그)이라 지우면 안 된다
  3. 내가 직접 실행한 파일만 저장된다
  4. git에 꼭 올려야 한다
.pyc는 바이트코드 캐시라서 지워도 다음 import 때 다시 만들어집니다. 직접 실행한 스크립트가 아니라 import된 모듈 쪽이 저장되고, 버전마다 다르게 생기므로 git에는 올리지 않습니다.

a = [1, 2]; b = a; b.append(3) 다음 print(a)의 결과는?

  1. [1, 2]
  2. [3]
  3. 에러
  4. [1, 2, 3]
b = a는 복사가 아니라 같은 리스트에 이름표를 하나 더 붙인 것입니다. 리스트는 바꿀 수 있는(mutable) 값이라 b로 바꾼 것이 a로도 보입니다. 따로 쓰려면 a.copy()를 씁니다.

긴 트레이스백에서 가장 먼저 봐야 할 곳은?

  1. 맨 첫 줄 Traceback (most recent call last):
  2. 맨 마지막 줄의 에러 종류와 설명
  3. 가장 긴 줄
  4. 라이브러리 내부(site-packages) 경로가 나오는 줄
"most recent call last"라는 말대로 가장 최근(에러가 난) 호출이 맨 아래에 있고, 마지막 줄이 에러 종류와 이유를 알려 줍니다. 그다음 위로 올라가며 내 파일 이름이 나오는 가장 아래 줄을 찾습니다. 라이브러리 내부 줄은 보통 고칠 곳이 아닙니다.

같은 폴더에 csv.py를 만들었더니 import csv 후 csv.reader가 없다는 에러가 납니다. 원인은?

  1. csv 라이브러리를 pip로 설치하지 않았다
  2. Python 버전이 너무 낮다
  3. sys.path에서 스크립트 폴더가 표준 라이브러리보다 먼저라, 내 csv.py가 import됐다
  4. 윈도에서는 csv 모듈을 쓸 수 없다
import는 sys.path를 앞에서부터 찾아 처음 찾은 것을 씁니다. 스크립트 폴더가 맨 앞이라 표준 라이브러리 csv 대신 내 빈 파일이 잡혔습니다. csv는 표준 라이브러리라 설치가 필요 없습니다. 파일 이름을 바꾸면 해결됩니다.

API 200개를 호출해 응답을 저장하는 스크립트가 느립니다. 대부분의 시간이 응답 대기라면 가장 알맞은 개선은?

  1. 스레드나 asyncio로 여러 요청을 동시에 보내고 기다린다
  2. CPU가 더 빠른 PC로 바꾼다
  3. for문을 while문으로 바꾼다
  4. Spark 클러스터로 옮긴다
기다리는 일(I/O 대기)은 기다리는 동안 다른 요청을 보내면 되므로 스레드·asyncio가 잘 맞습니다. 계산이 병목이 아니므로 CPU를 바꿔도 거의 안 빨라지고, 반복문 종류는 상관없습니다. 데이터가 크지 않은 API 호출에 Spark는 과합니다. 다만 API 쪽의 호출 횟수 제한(rate limit)은 지켜야 합니다.
