데이터는 어떻게 저장되나

SELECT 한 줄을 날리면 그 뒤에서 무슨 일이 일어날까요? 이 장에서는 데이터가 디스크 위에 어떤 모양으로 놓이는지를 봅니다. 이걸 알면 "왜 이 쿼리는 느리지?", "왜 BigQuery 요금이 이렇게 나왔지?", "왜 Parquet을 쓰라고 하지?"에 스스로 답할 수 있습니다.

이 장을 마치면

  • 웨어하우스가 열 저장을 쓰는 이유와, 그게 요금·속도에 어떻게 이어지는지 설명하기
  • 인덱스·파티션·클러스터링이 "덜 읽기 위한 장치"라는 걸 설명하기

파일과 데이터베이스

데이터를 담는 방법은 크게 두 가지입니다.

  • 파일: 디스크에 바이트를 늘어놓은 것. CSV, JSON, 엑셀, Parquet 모두 파일입니다. 파일 자체는 아무 일도 하지 않습니다. 읽는 프로그램이 알아서 해석해야 합니다.
  • 데이터베이스: 파일들 위에서 돌아가는 프로그램입니다. 결국 데이터베이스도 디스크에 파일로 저장하지만, 그 위에 "누가 동시에 써도 안 깨지게", "원하는 행을 빨리 찾게", "SQL로 물어보면 답하게" 같은 기능을 얹습니다.
  파일만 있을 때                       데이터베이스가 있을 때

  내 프로그램 ──읽기/쓰기──▶ orders.csv   내 프로그램 ──SQL──▶ ┌─────────────────────┐
  다른 프로그램 ──쓰기────▶ (동시에 쓰면   다른 프로그램 ─SQL─▶ │ DB 엔진               │
                           깨질 수 있음)                       │ · 동시 접근 순서 정리 │
                                                               │ · 인덱스로 빨리 찾기  │
                                                               │ · 실패하면 되돌리기   │
                                                               │ · 권한 확인           │
                                                               └──────────┬──────────┘
                                                                          ▼
                                                               디스크의 데이터 파일들
🧸 비유

파일은 창고에 쌓아 둔 상자입니다. 필요하면 내가 직접 들어가서 뒤져야 합니다. 두 사람이 동시에 같은 상자를 고치면 엉망이 됩니다.

데이터베이스는 창고 관리인이 있는 창고입니다. "3번 고객 주문 줘"라고 말하면 관리인이 색인 장부를 보고 바로 가져옵니다. 두 사람이 동시에 고치려 하면 관리인이 순서를 정합니다.

SQL 감각으로 옮기면

DuckDB의 read_csv('data/raw_orders.csv')나 BigQuery의 외부 테이블은 "파일을 데이터베이스처럼 SQL로 읽게 해 주는 다리"입니다. 다만 파일에는 관리인이 없으니, 인덱스·트랜잭션 같은 기능은 기대하면 안 됩니다.

텍스트 포맷과 바이너리 포맷

파일 포맷은 "바이트를 어떤 규칙으로 늘어놓느냐"입니다. 사람이 메모장으로 열어 읽을 수 있으면 텍스트 포맷, 프로그램만 읽을 수 있으면 바이너리 포맷이라고 합니다.

포맷모양좋은 점아쉬운 점주로 쓰는 곳
CSV쉼표로 나눈 줄어디서나 열림, 엑셀로 확인 가능타입 정보 없음(숫자인지 글자인지 모름), 쉼표·줄바꿈이 값 안에 있으면 골치, 인코딩 문제사람끼리 주고받기, 작은 원천 데이터
JSON{"키": 값} 중첩 구조중첩·배열 표현 가능, API 응답의 기본키 이름이 행마다 반복돼 크다API, 설정 파일
JSONL (NDJSON)한 줄에 JSON 하나줄 단위로 이어 쓰고 나눠 읽기 쉬움JSON처럼 크다로그, 수집 데이터 적재(BigQuery 적재 포맷으로도 흔함)
Parquet바이너리, 열 단위로 묶음작고 빠름, 타입 정보 포함, 필요한 컬럼만 읽음메모장으로 못 봄, 한 행씩 고치기 어려움데이터 레이크, 분석용 저장
ORC바이너리, 열 단위Parquet과 비슷Hive 생태계 밖에서는 덜 쓰임Hadoop·Hive 계열
Avro바이너리, 행 단위 + 스키마스키마가 파일에 같이 들어감, 한 건씩 쓰기 좋음, 스키마 변경 규칙이 명확분석 쿼리에는 열 포맷보다 느림Kafka 같은 스트리밍 메시지

같은 주문 10만 건을 CSV와 JSONL로 저장하면 크기가 이렇게 다릅니다(아래 "손으로 해 보기"에서 직접 재 봅니다).

orders.csv    2062 KB     order_id,status,amount  ← 컬럼 이름은 맨 위에 한 번
orders.jsonl  5773 KB     {"order_id": 0, "status": "shipped", "amount": 5816}  ← 줄마다 키 이름 반복
⚠️ CSV의 함정 세 가지
  • 타입이 없다: 00123은 우편번호일까 숫자 123일까? 읽는 쪽이 추측하다 앞자리 0을 날려 먹습니다.
  • 인코딩: 한국 윈도우 엑셀은 CSV를 CP949로 저장하는 경우가 많고, 대부분의 도구는 UTF-8을 기대합니다. 한글이 깨지면 먼저 인코딩을 의심하세요(1장 참고).
  • 구분자가 값 안에: 주소에 쉼표가 들어가면 큰따옴표로 감싸야 합니다. 직접 split(",") 하지 말고 csv 라이브러리를 쓰세요.

행 저장 vs 열 저장 — 웨어하우스가 빠른 진짜 이유

표를 디스크에 쓸 때, 한 행씩 이어 쓸 수도 있고 한 열씩 이어 쓸 수도 있습니다.

  표                         행 저장 (MySQL·PostgreSQL 기본)         열 저장 (BigQuery·Snowflake·Parquet)
  ┌────┬─────────┬───────┐
  │ id │ status  │ amount│    [1,shipped,5816][2,placed,86459]...   [1,2,3,4,...]
  ├────┼─────────┼───────┤                                           [shipped,placed,shipped,...]
  │ 1  │ shipped │ 5816  │    한 행이 디스크에 붙어 있다              [5816,86459,...]
  │ 2  │ placed  │ 86459 │    → "주문 1번 전부 줘" 에 빠름           한 열이 디스크에 붙어 있다
  │ 3  │ shipped │ 1200  │                                           → "amount 합계" 에 빠름
  └────┴─────────┴───────┘

분석 쿼리는 대부분 컬럼 몇 개만, 행은 아주 많이 읽습니다. SELECT status, SUM(amount) FROM orders GROUP BY status는 컬럼이 50개인 테이블에서도 딱 2개만 필요합니다. 열 저장이면 그 2개 열만 디스크에서 읽고 나머지 48개는 건드리지도 않습니다.

게다가 같은 열에는 비슷한 값이 모여 있어서 압축이 잘 됩니다. status 열은 shipped, shipped, placed, shipped...처럼 몇 가지 값의 반복이라, "shipped가 3번" 식으로 줄여 쓸 수 있습니다.

🧸 비유

반 학생 30명의 성적표가 있습니다. 행 저장은 학생마다 한 장씩, 국어·영어·수학이 다 적힌 종이 30장입니다. "철수 성적 보여 줘"에는 한 장만 꺼내면 돼서 빠릅니다.

열 저장은 과목마다 한 장, "수학 점수 30개"가 적힌 종이입니다. "수학 평균"을 구할 때 수학 종이 한 장만 보면 됩니다. 행 저장이면 30장을 다 넘기며 수학 칸만 골라 봐야 하죠.

데이터 엔지니어에게는
  • BigQuery가 "읽은 바이트"로 요금을 매기는 이유가 바로 이것입니다. 열 저장이라 쿼리에 쓴 컬럼만 읽으니, 쓴 컬럼 크기만큼만 받는 거죠. 그래서 SELECT *는 비싸고, LIMIT 10을 붙여도 요금은 거의 줄지 않습니다(LIMIT은 읽은 뒤에 자르는 것이라서).
  • 반대로 운영 시스템(주문 접수, 회원 가입)은 "한 건 넣고 한 건 고치기"가 대부분이라 행 저장 DB를 씁니다.

인덱스 — 책 뒤의 색인

인덱스가 없으면 DB는 WHERE customer_id = 42를 찾으려고 모든 행을 처음부터 끝까지 봅니다. 이걸 풀 스캔(full scan)이라고 합니다. 인덱스는 "42번 고객의 행은 어디어디에 있다"를 정렬해서 따로 적어 둔 장부입니다.

  B-tree 인덱스 (customer_id) — 정렬된 나무

                     [ 5000 ]
                    /        \
           [ 2500 ]            [ 7500 ]
           /      \            /      \
     [1~2499]  [2500~4999] [5000~7499] [7500~10000]
        │
        └─ 42 → 행 위치: 3번 페이지, 812번 페이지 ...

  50만 행이어도 위에서 3~4번만 갈림길을 고르면 도착

대부분의 DB가 쓰는 인덱스는 B-tree라는 정렬된 나무 모양입니다. 사전에서 단어를 찾을 때 가운데를 펴고 "앞쪽이네" 하고 범위를 반씩 줄이는 것과 같습니다. 100만 건이어도 20번 정도만 반으로 나누면 찾습니다.

🧸 비유

두꺼운 교과서에서 "광합성"을 찾을 때, 첫 페이지부터 넘기면 풀 스캔이고, 책 뒤 색인에서 "광합성 → 132쪽"을 보면 인덱스입니다. 대신 색인도 종이를 차지하고, 본문을 고칠 때마다 색인도 고쳐야 합니다.

⚠️ 인덱스는 공짜가 아니다
  • INSERT·UPDATE 때마다 인덱스도 갱신하니 쓰기는 느려집니다.
  • 디스크를 더 씁니다.
  • 결과가 전체의 큰 비율이면(예: status가 3종류뿐이라 3분의 1씩) 인덱스보다 그냥 다 읽는 게 빠를 수 있어 DB가 인덱스를 안 쓰기도 합니다.
  • BigQuery·Snowflake 같은 열 저장 웨어하우스는 이런 B-tree 인덱스를 거의 쓰지 않습니다. 대신 아래의 파티션·클러스터링으로 "덜 읽기"를 합니다.

트랜잭션과 ACID — "다 되거나, 하나도 안 되거나"

계좌 이체를 생각해 봅시다. A에서 3만 원 빼고, B에 3만 원 넣는 두 단계입니다. 첫 단계만 되고 서버가 꺼지면 돈이 사라집니다. 그래서 DB는 여러 작업을 트랜잭션이라는 한 묶음으로 처리합니다.

글자뜻쉬운 말
A · Atomicity (원자성)묶음 전체가 성공하거나 전체가 취소된다반만 되는 일은 없다
C · Consistency (일관성)규칙(제약 조건)을 깨는 상태로는 끝나지 않는다잔액이 음수가 되는 일은 없다
I · Isolation (격리성)동시에 도는 트랜잭션끼리 서로 중간 상태를 보지 않는다남이 고치는 중인 값을 읽지 않는다
D · Durability (지속성)COMMIT 된 것은 전원이 나가도 남는다"저장됨"이라고 했으면 진짜 저장된 것

격리 수준은 "동시에 돌 때 얼마나 철저히 떼어 놓을까"를 고르는 설정입니다. 철저할수록 안전하지만 서로 기다리는 일이 늘어 느려집니다. 대표적으로 READ COMMITTED(커밋된 것만 읽기, 많은 DB의 기본), REPEATABLE READ, SERIALIZABLE(한 줄로 차례차례 돈 것과 같은 결과) 순으로 엄격해집니다.

SQL 감각으로 옮기면

프로시저에서 쓰던 BEGIN TRANSACTION ... COMMIT, 오류 나면 ROLLBACK이 바로 이것입니다. "그날 것 지우고(DELETE) 다시 넣기(INSERT)"를 한 트랜잭션으로 묶지 않으면, 지운 직후 실패했을 때 마트가 텅 빈 채로 남습니다. dbt가 테이블을 "임시 테이블에 만들고 → 이름 바꿔치기" 하는 것도 같은 걱정에서 나온 방식입니다.

OLTP와 OLAP — 가게 계산대와 본사 분석실

OLTP (온라인 트랜잭션 처리)OLAP (온라인 분석 처리)
예주문 접수, 회원 가입, 재고 차감월별 매출, 매체별 전환율
한 번에 다루는 양몇 행수백만~수십억 행
주로 하는 일INSERT·UPDATE 아주 많이, 아주 빨리SELECT + GROUP BY, 큰 JOIN
저장 방식행 저장 + 인덱스열 저장 + 파티션
모델링정규화(중복 없이 쪼개기)스타 스키마(분석하기 쉽게 다시 묶기)
대표 제품PostgreSQL, MySQL, Oracle, SQL ServerBigQuery, Snowflake, Redshift, DuckDB

데이터 엔지니어의 일은 크게 보면 OLTP에 쌓인 데이터를 OLAP으로 옮겨 분석하기 좋게 다시 만드는 것입니다. 운영 DB에서 바로 큰 분석 쿼리를 돌리면 계산대가 멈추니까요.

정규화는 "같은 정보는 한 곳에만 적는다"는 원칙입니다. 고객 주소를 주문마다 적지 않고 고객 테이블에 한 번만 적는 것이죠. 정규화·반정규화와 스타 스키마는 필수 정리의 모델링 주차에서 자세히 다룹니다.

🧸 비유

OLTP는 편의점 계산대입니다. 손님 한 명씩, 빨리빨리. OLAP은 본사 분석실입니다. 전국 매장 1년 치 영수증을 쌓아 놓고 "어느 지역에서 뭐가 잘 팔리지?"를 봅니다. 계산대에서 분석을 하면 줄이 끝없이 길어집니다.

파티션·클러스터링 — 덜 읽는 기술

열 저장 웨어하우스에서 속도와 요금을 줄이는 핵심은 안 읽어도 되는 부분을 아예 건너뛰는 것입니다.

  • 파티션: 테이블을 날짜 같은 기준으로 칸막이를 친 것. WHERE order_date = '2026-10-21'이면 그날 칸만 읽습니다(파티션 가지치기, partition pruning).
  • 클러스터링: 칸 안에서 특정 컬럼(예: customer_id) 순서로 정렬해 두는 것. 블록마다 "이 블록은 customer_id 100~200"이라는 최솟값·최댓값이 적혀 있어서, 해당 없는 블록을 건너뜁니다.
  orders (order_date로 파티션, customer_id로 클러스터링)

  ┌ 2026-10-19 ┐ ┌ 2026-10-20 ┐ ┌ 2026-10-21 ┐ ┌ 2026-10-22 ┐
  │ 블록 1~99  │ │ 블록 1~99  │ │ 블록  1~120│ │ 블록 1~80  │
  │ 블록100~.. │ │ ...        │ │ 블록121~250│ │ ...        │
  └────────────┘ └────────────┘ └────────────┘ └────────────┘
       건너뜀          건너뜀       ▲ 이 칸만 열고       건너뜀
                                    │ 그 안에서도 customer_id 범위 맞는 블록만

  WHERE order_date = '2026-10-21' AND customer_id = 42
데이터 엔지니어에게는

파티션 컬럼에 함수를 씌우면(예: 문자열로 바꿔 비교) 가지치기가 안 되는 경우가 있습니다. 대용량 테이블은 파티션 필터를 필수로 거는 옵션도 있습니다. dbt에서는 모델 설정의 partition_by, cluster_by로 지정합니다.

분산 저장·복제·샤딩, 그리고 CAP

데이터가 컴퓨터 한 대에 안 들어가거나, 한 대가 고장 나도 서비스가 멈추면 안 될 때 여러 대에 나눠 담습니다.

  • 복제(replication): 같은 데이터를 여러 대에 똑같이 둔다. 한 대가 죽어도 나머지가 답한다. 읽기를 나눠 받을 수도 있다.
  • 샤딩(sharding)·파티셔닝: 데이터를 나눠서 여러 대에 둔다. 고객 1~100만은 1번 서버, 100만~200만은 2번 서버 식. 저장 용량과 처리량을 늘린다.
  복제 (같은 것 여러 벌)          샤딩 (나눠 담기)

  ┌ 서버1 ┐ ┌ 서버2 ┐ ┌ 서버3 ┐     ┌ 서버1 ┐ ┌ 서버2 ┐ ┌ 서버3 ┐
  │ A B C │ │ A B C │ │ A B C │     │  A    │ │  B    │ │  C    │
  └───────┘ └───────┘ └───────┘     └───────┘ └───────┘ └───────┘
  고장에 강함                        용량·속도를 늘림
  실제로는 둘을 같이 씀: 나눈 조각마다 복제본을 둔다

CAP 정리는 분산 시스템에서 네트워크가 끊겼을 때(P, 분할) 일관성(C, 모두가 같은 최신 값을 봄)과 가용성(A, 일단 응답은 함) 중 하나를 포기해야 한다는 이야기입니다. 은행 잔액은 "틀린 답보다 잠깐 멈추는 게 낫다"(C 우선), SNS 좋아요 수는 "잠깐 덜 정확해도 계속 보여 주는 게 낫다"(A 우선)처럼 서비스마다 고릅니다.

🧸 비유

지점이 두 곳인 가게에서 두 지점 사이 전화가 끊겼습니다. 재고를 서로 확인할 수 없어요. "확인될 때까지 판매 중지"(일관성)할지, "일단 팔고 나중에 맞추자"(가용성)할지 골라야 합니다. 전화가 끊기지 않았다면 고민할 필요가 없죠.

객체 저장소·데이터 레이크·레이크하우스

객체 저장소(Amazon S3, Google Cloud Storage, Azure Blob Storage)는 "아주 싸고 거의 무한한 클라우드 파일 창고"입니다. 폴더처럼 보이지만 실제로는 버킷/경로/파일이름이라는 키로 파일 하나(객체)를 통째로 넣고 빼는 구조입니다. 파일 중간만 고치는 건 안 되고, 통째로 다시 씁니다.

  • 데이터 레이크: 원천 데이터를 가공 전 모양 그대로(CSV·JSON·Parquet) 객체 저장소에 몽땅 쌓아 두는 방식. 싸고 유연하지만, 관리를 안 하면 "뭐가 뭔지 모르는 늪(data swamp)"이 됩니다.
  • 문제: 파일만 있으니 트랜잭션이 없습니다. 누가 파일을 쓰는 중에 읽으면 반쯤 쓴 데이터를 봅니다. UPDATE·DELETE도 어렵고, 어느 파일들이 "지금 버전의 테이블"인지도 모호합니다.
  • 테이블 포맷(Apache Iceberg, Delta Lake, Apache Hudi): Parquet 파일들 옆에 "지금 이 테이블은 이 파일들로 이뤄져 있다"는 메타데이터(목록·스냅숏)를 같이 관리해서, 파일 더미를 트랜잭션 되는 테이블처럼 쓰게 해 줍니다. 과거 버전 조회(time travel), 스키마 변경, 안전한 동시 쓰기가 됩니다.
  • 레이크하우스: 레이크(싼 객체 저장소 + 열린 파일 포맷) 위에 웨어하우스 기능(트랜잭션·SQL·권한)을 얹은 구조. 여러 엔진(Spark, Trino, Snowflake, BigQuery 등)이 같은 테이블을 읽을 수 있다는 게 장점입니다.
  레이크하우스의 층

  ┌────────────────────────────────────────────┐
  │ 엔진: Spark · Trino · DuckDB · 웨어하우스  │  ← SQL로 읽고 씀
  ├────────────────────────────────────────────┤
  │ 테이블 포맷: Iceberg / Delta / Hudi        │  ← "지금 버전은 파일 a,b,c" 스냅숏·트랜잭션
  ├────────────────────────────────────────────┤
  │ 파일 포맷: Parquet (열 저장)               │  ← 실제 데이터
  ├────────────────────────────────────────────┤
  │ 객체 저장소: S3 · GCS · Azure Blob         │  ← 싸고 큰 창고
  └────────────────────────────────────────────┘
🧸 비유

Parquet 파일 더미는 사진이 잔뜩 든 상자, 테이블 포맷은 그 옆의 앨범 목차입니다. "2026년 앨범은 이 사진 120장"이라고 목차에 적혀 있어서, 상자에 사진을 새로 넣는 중이어도 목차를 고치기 전까지는 다들 예전 앨범을 봅니다. 목차를 한 번에 바꾸는 순간 새 앨범이 됩니다.

1. CSV와 JSONL 크기 비교

fmt.py로 저장하고 python fmt.py로 실행합니다.

import csv, json, os, random   # 표준 라이브러리만 사용

# 주문 10만 건 만들기 (SQL로 치면 INSERT 10만 번 할 데이터)
rows = [{"order_id": i,
         "status": random.choice(["placed", "shipped", "completed"]),
         "amount": random.randint(1000, 90000)} for i in range(100000)]

# CSV로 저장: 컬럼 이름은 맨 위 한 줄에만
with open("orders.csv", "w", newline="", encoding="utf-8") as f:
    w = csv.DictWriter(f, fieldnames=rows[0].keys())
    w.writeheader()
    w.writerows(rows)

# JSONL로 저장: 한 줄에 JSON 하나 (키 이름이 줄마다 반복)
with open("orders.jsonl", "w", encoding="utf-8") as f:
    for r in rows:
        f.write(json.dumps(r) + "\n")

for name in ["orders.csv", "orders.jsonl"]:
    print(name, os.path.getsize(name) // 1024, "KB")

2. 행으로 압축 vs 열로 압축

1번에서 만든 orders.csv를 행 묶음과 열 묶음으로 각각 압축해 봅니다.

import csv, zlib   # zlib = 압축 라이브러리 (zip과 같은 계열)

with open("orders.csv", encoding="utf-8") as f:
    rows = list(csv.reader(f))[1:]          # 머리글 빼고 전부 읽기

# 행 저장 흉내: 한 행씩 이어 붙이기
row_bytes = "\n".join(",".join(r) for r in rows).encode()

# 열 저장 흉내: zip(*rows) = 표를 90도 돌려 열 단위로 모으기
cols = list(zip(*rows))
col_bytes = ["\n".join(c).encode() for c in cols]

print("행 저장 압축", len(zlib.compress(row_bytes)) // 1024, "KB")
print("열 저장 압축", sum(len(zlib.compress(c)) for c in col_bytes) // 1024, "KB")
print("status 열만", len(zlib.compress(col_bytes[1])) // 1024, "KB")

결과 예시:

행 저장 압축 588 KB
열 저장 압축 512 KB
status 열만 38 KB

열로 모으면 비슷한 값끼리 붙어 압축이 더 잘 되고, status만 필요한 쿼리라면 38KB만 읽으면 됩니다. BigQuery가 쓴 컬럼만큼만 요금을 매기는 원리가 이것입니다. 실제 Parquet은 사전 인코딩 같은 기법을 더 써서 차이가 훨씬 큽니다.

3. 인덱스 전후 실행 계획 비교 (sqlite3)

50만 행 테이블에서 같은 쿼리를 인덱스 없이, 그리고 인덱스를 만든 뒤 돌려 봅니다. EXPLAIN QUERY PLAN은 "DB가 이 쿼리를 어떻게 풀 계획인지" 보여 주는 명령입니다.

import sqlite3, random, time

con = sqlite3.connect(":memory:")   # 메모리 안에 임시 DB 만들기
con.execute("CREATE TABLE orders (order_id INTEGER, customer_id INTEGER, amount INTEGER)")
rows = [(i, random.randint(1, 10000), random.randint(1000, 90000)) for i in range(1, 500001)]
con.executemany("INSERT INTO orders VALUES (?, ?, ?)", rows)   # 50만 행 INSERT

q = "SELECT SUM(amount) FROM orders WHERE customer_id = 42"

print(con.execute("EXPLAIN QUERY PLAN " + q).fetchall())
t = time.perf_counter(); con.execute(q).fetchone()
print("인덱스 전", round((time.perf_counter() - t) * 1000, 1), "ms")

con.execute("CREATE INDEX ix_orders_customer ON orders (customer_id)")

print(con.execute("EXPLAIN QUERY PLAN " + q).fetchall())
t = time.perf_counter(); con.execute(q).fetchone()
print("인덱스 후", round((time.perf_counter() - t) * 1000, 2), "ms")

결과 예시:

[(3, 0, 216, 'SCAN orders')]
인덱스 전 9.8 ms
[(4, 0, 62, 'SEARCH orders USING INDEX ix_orders_customer (customer_id=?)')]
인덱스 후 0.12 ms

SCAN(전부 훑기)이 SEARCH ... USING INDEX(색인으로 찾기)로 바뀌고 수십 배 빨라집니다. 이번엔 WHERE customer_id = 42를 WHERE amount > 1000으로 바꿔 보세요. amount에는 인덱스가 없으니 다시 SCAN이 됩니다.

4. 트랜잭션 — 반만 되는 이체는 없다
import sqlite3

con = sqlite3.connect(":memory:")
# CHECK 제약: 잔액은 0 미만이 될 수 없다 (ACID의 C)
con.execute("CREATE TABLE account (name TEXT PRIMARY KEY, balance INTEGER CHECK (balance >= 0))")
con.executemany("INSERT INTO account VALUES (?, ?)", [("A", 10000), ("B", 0)])
con.commit()

try:
    with con:   # with con: 블록 = BEGIN ... 끝나면 COMMIT, 오류 나면 ROLLBACK
        con.execute("UPDATE account SET balance = balance + 30000 WHERE name = 'B'")  # 성공
        con.execute("UPDATE account SET balance = balance - 30000 WHERE name = 'A'")  # 잔액 부족 → 실패
except sqlite3.IntegrityError as e:
    print("실패:", e)

print(con.execute("SELECT * FROM account").fetchall())

결과:

실패: CHECK constraint failed: balance >= 0
[('A', 10000), ('B', 0)]

B에 3만 원을 넣는 첫 UPDATE는 성공했지만, 두 번째가 실패하자 첫 번째까지 통째로 취소되어 B는 여전히 0원입니다. 이게 원자성(A)입니다. with con:을 빼고 두 줄을 따로 돌리면 어떻게 되는지도 해 보세요.

퀴즈

컬럼이 60개인 큰 테이블에서 SELECT region, SUM(revenue) ... GROUP BY region을 돌릴 때 열 저장이 유리한 가장 큰 이유는?

  1. 행 단위로 잠금을 걸 수 있어서
  2. 필요한 두 컬럼만 디스크에서 읽으면 되고, 같은 열 값끼리 압축이 잘 되어서
  3. B-tree 인덱스가 자동으로 만들어져서
  4. 트랜잭션 격리 수준이 더 높아서
열 저장은 열마다 따로 모여 있어 쿼리에 쓴 열만 읽고, 비슷한 값이 붙어 있어 압축률도 높습니다. 잠금·격리 수준은 트랜잭션 이야기이고, 열 저장 웨어하우스는 B-tree 인덱스를 거의 쓰지 않습니다.

다음 중 Avro에 대한 설명으로 맞는 것은?

  1. 사람이 메모장으로 읽기 좋은 텍스트 포맷이다
  2. 열 단위 저장이라 분석 쿼리에 가장 빠르다
  3. 엑셀이 기본으로 저장하는 포맷이다
  4. 행 단위 바이너리 포맷이고 스키마가 함께 들어가 스트리밍 메시지에 자주 쓰인다
Avro는 행 단위 + 스키마 포함 바이너리 포맷이라 한 건씩 쓰고 주고받기 좋아 Kafka 메시지에 많이 씁니다. 열 단위로 분석에 강한 쪽은 Parquet·ORC입니다.

이체 중 두 번째 UPDATE가 실패했는데 첫 번째 UPDATE도 취소되었습니다. ACID 중 무엇 덕분인가요?

  1. Atomicity (원자성)
  2. Isolation (격리성)
  3. Durability (지속성)
  4. Partitioning (분할)
"다 되거나 하나도 안 되거나"가 원자성입니다. 격리성은 동시에 도는 트랜잭션끼리 간섭하지 않는 것, 지속성은 커밋된 것이 사라지지 않는 것입니다. 분할(P)은 ACID가 아니라 CAP에 나오는 말입니다.

날짜로 파티션된 테이블에서 요금을 줄이는 쿼리 습관으로 가장 알맞은 것은?

  1. 쿼리 끝에 LIMIT 100을 붙인다
  2. SELECT *로 한 번에 다 가져와 재사용한다
  3. 파티션 컬럼에 대한 WHERE 조건을 걸어 필요한 날짜 칸만 읽게 한다
  4. ORDER BY를 추가해 정렬된 결과를 받는다
파티션 필터가 있으면 해당 칸만 읽어 읽은 바이트가 줄어듭니다. LIMIT은 읽은 뒤에 자르므로 읽는 양을 거의 줄이지 않고, SELECT *는 모든 열을 읽어 오히려 비쌉니다. ORDER BY는 계산만 늘립니다.

Iceberg·Delta Lake 같은 테이블 포맷이 해결하려는 문제로 가장 알맞은 것은?

  1. CSV 파일의 한글 인코딩 문제
  2. 객체 저장소의 파일 더미를 트랜잭션·버전 관리가 되는 테이블처럼 쓰지 못하는 문제
