데이터 엔지니어링의 역사 — 천공카드에서 레이크하우스까지

지금 쓰는 도구는 거의 다 "그 전 도구로는 안 되던 문제"의 답입니다. 이 장은 130년을 여덟 장면으로 나눠, 각 장면에서 무슨 문제가 있었고 → 무엇이 나왔고 → 그게 지금 내 일에 어떻게 남아 있는지를 봅니다.

읽기 약 40분 · 퀴즈 7문제 · 함께 보면 좋은 페이지: 이야기로 보는 데이터 역사 (SQL · 인먼 · 킴볼 · dbt 부분을 더 자세히)

이 장을 마치면
  • 배치 · ETL · 데이터 웨어하우스 · 빅데이터 · ELT · 레이크하우스가 각각 어떤 문제 때문에 생겼는지 설명하기
  • "SQL은 왜 몇 번이나 버려졌다가 다시 돌아왔나"를 말하기
  • DBA → ETL 개발자 → 데이터 엔지니어 → analytics engineer 로 이어지는 직업의 계보 그리기
  • 새 도구가 나왔을 때 "이건 어떤 옛 문제의 새 답인가"로 읽는 눈 갖기
이 페이지의 성격 널리 알려진 연도와 사건을 제 말로 이어 붙인 이야기입니다. 연도는 "발표", "공개", "정식 출시"에 따라 1~2년씩 다르게 적히는 경우가 많습니다. 발표나 글에 인용할 때는 원문을 한 번 확인하세요.

1장 · 천공카드와 메인프레임 — "배치"라는 생각

1880년 미국 인구조사는 사람이 손으로 세서 집계에 7~8년이 걸렸습니다. 그러다 다음 조사가 돌아올 판이었습니다. 1890년 조사에는 허먼 홀러리스의 천공카드 집계기가 쓰였습니다. 한 사람 = 카드 한 장, 성별·나이 같은 항목 = 구멍 위치. 기계가 카드를 읽으며 구멍 위치별로 숫자를 세었습니다. 홀러리스의 회사는 몇 번 합병을 거쳐 1924년 IBM이 됩니다.

  카드 한 장 = 행(row) 한 줄         구멍 위치 = 컬럼(column)
  ┌──────────────────────────────┐
  │ ▮ ▯ ▯ ▮ ▯ ▯ ▯ ▮ ▯ ▯ ▯ ▯ ▮ ▯ │   ← 성별 | 나이대 | 지역 ...
  └──────────────────────────────┘
  카드 묶음(덱)을 한꺼번에 기계에 넣는다  →  "배치(batch)" 처리

1950~60년대 메인프레임 시대에도 방식은 같았습니다. 낮 동안 쌓인 카드·테이프를 밤에 한꺼번에 돌리고, 아침에 결과 보고서를 받았습니다. 어떤 작업을 어떤 순서로 돌릴지는 JCL(Job Control Language) 같은 작업 제어 언어로 적었습니다.

🧸 비유

배치는 빨래를 모아 뒀다가 밤에 세탁기를 한 번 돌리는 것입니다. 옷 한 벌 나올 때마다 세탁기를 돌리면(실시간) 편하지만 비쌉니다. 모아서 돌리면 싸고 단순하지만, 아침까지 기다려야 합니다.

데이터 엔지니어에게는 "매일 새벽 6시에 어제 데이터를 처리한다"는 지금의 일 대부분이 이 시절 생각 그대로입니다. 바뀐 건 카드가 파일이 되고, JCL이 크론 · Airflow 가 됐다는 것뿐입니다. 배치냐 스트리밍이냐는 60년 넘게 이어지는 질문입니다.

2장 · 데이터베이스의 탄생 — 길을 따라가는 DB에서 표로

1956년 IBM이 하드디스크(RAMAC)를 내놓으면서 "테이프를 처음부터 감지 않고 원하는 데이터로 바로 가는 것"이 가능해졌습니다. 그러자 데이터를 어떻게 정리해 둘지가 문제가 됐습니다.

  • 계층형(IMS, IBM, 1960년대 후반) — 아폴로 계획의 부품 목록 관리에서 출발. 데이터가 나무 모양(고객 → 주문 → 주문상세)으로 연결돼 있고, 위에서부터 가지를 따라 내려가야 찾을 수 있습니다.
  • 네트워크형(CODASYL) — 나무보다 자유로운 그물 모양. 그래도 여전히 "포인터를 따라 이 레코드에서 저 레코드로" 가는 방식입니다.

문제는 질문이 바뀌면 프로그램을 다시 짜야 한다는 것이었습니다. "고객별 주문"은 쉬운데 "상품별로 어떤 고객이 샀나"를 물으려면 길을 거꾸로 가는 코드를 새로 짜야 했습니다.

1970년 IBM의 에드거 코드가 관계형 모델을 냅니다. 데이터는 그냥 표로 두고, 연결은 같은 값을 가진 컬럼(키)으로 하고, 사용자는 무엇을 원하는지만 말하면 시스템이 길을 찾게 하자는 생각입니다. 여기서 SQL이 나왔고(1974 SEQUEL), 1979년 오라클이 첫 상용 SQL DB를 냈습니다. 버클리의 Ingres 프로젝트는 훗날 Postgres → PostgreSQL 로 이어집니다.

SQL 감각으로 옮기면

우리가 JOIN 한 줄로 "상품별 구매 고객"을 뽑을 수 있는 건 당연한 게 아니라 1970년의 발명입니다. 그 전에는 그 질문 하나에 프로그램 하나가 필요했습니다. 그리고 "어떻게 찾을지"는 옵티마이저가 정합니다 — 실행 계획(EXPLAIN)이 바로 그 "길 찾기"의 결과입니다.

자세한 이야기(SEQUEL이 SQL이 된 사연, 오라클이 IBM보다 먼저 판 이야기)는 이야기로 보는 데이터 역사에 있습니다.

3장 · 업무용과 분석용이 갈라지다 — 웨어하우스와 ETL

1980년대에는 회사마다 관계형 DB로 주문 · 회계 · 재고 시스템을 만들었습니다. 그러자 새 문제가 생겼습니다.

  1. 분석 쿼리가 업무를 멈춘다 — 월말에 "지난 3년 매출을 지역별로"를 돌리면, 그 시간에 주문 입력이 느려집니다.
  2. 시스템마다 말이 다르다 — 영업 시스템의 고객번호와 회계 시스템의 고객번호가 다르고, "매출"의 정의도 다릅니다.
  3. 업무 DB는 지금만 안다 — 고객 주소가 바뀌면 덮어써서, "작년엔 어느 지역 고객이었나"를 모릅니다.

답은 분석 전용 DB를 따로 두자였습니다. 1988년 IBM의 배리 데블린과 폴 머피가 "비즈니스 데이터 웨어하우스" 구조를 논문으로 냈고, 1992년 빌 인먼이 책으로 이 생각을 퍼뜨렸습니다. 1993년에는 코드가 분석용 처리를 OLAP(Online Analytical Processing)이라 부르며, 업무용 처리 OLTP와 구분했습니다.

  업무 시스템들 (OLTP)                     분석용 (OLAP)
  ┌────────┐
  │ 주문 DB │──┐
  └────────┘  │    ┌───────────────────┐     ┌──────────────┐     ┌──────────┐
  ┌────────┐  ├──▶ │ ETL 서버           │ ──▶ │ 데이터 웨어하우스 │ ──▶ │ BI 보고서 │
  │ 회계 DB │──┤    │ E 추출 T 변환 L 적재 │     │ (이력 · 통일된 말) │     └──────────┘
  └────────┘  │    └───────────────────┘     └──────────────┘
  ┌────────┐  │      ↑ 변환은 여기서! 웨어하우스는 비싸고 작았으니까
  │ 재고 DB │──┘
  └────────┘          밤마다 배치

이 화살표를 맡는 상용 도구들이 1990년대에 쏟아졌습니다. Informatica(1993년 창업), Ab Initio, DataStage, 그리고 마이크로소프트 SQL Server의 DTS(1998) → SSIS(2005). 화면에서 상자를 끌어다 놓고 선으로 잇는 방식이 많았습니다. 웨어하우스 쪽에는 Teradata 같은 대형 병렬 처리(MPP) 장비가 있었고, 위에는 Business Objects · Cognos · MicroStrategy 같은 BI 도구가 올라갔습니다.

설계 방법을 두고는 인먼(전사 통합, 정규화 먼저)과 랄프 킴볼(1996, 업무 과정별 스타 스키마)이 갈렸습니다 — 이 논쟁은 데이터 역사 페이지와 필수 정리의 모델링 주간에서 자세히 다룹니다.

🧸 비유

업무 DB는 식당 주방, 웨어하우스는 본사 회계실입니다. 주방에서 장부 정리를 하면 요리가 늦어지니, 마감 후 영수증을 모아(E) 본사 양식으로 옮겨 적고(T) 회계실 서랍에 넣습니다(L). 서랍은 비싸고 좁아서, 옮겨 적는 일은 서랍 밖(ETL 서버)에서 끝내고 넣었습니다.

SQL 감각으로 옮기면

우리가 짜던 "임시 테이블 → DELETE → INSERT" 프로시저는 이 시절 ETL의 T와 L을 DB 안에서 SQL로 한 것입니다. 이 시대의 직업 이름이 ETL 개발자 · DW 개발자 · BI 개발자였습니다.

4장 · 인터넷이 데이터를 폭발시키다 — 구글 논문과 Hadoop

2000년대 초 구글은 웹 전체를 긁어 와 색인을 만들어야 했습니다. 데이터는 수백 테라바이트, 비싼 웨어하우스 장비 한 대로는 불가능한 크기였습니다. 구글의 답은 값싼 PC 수천 대를 묶는 것이었고, 그 방법을 논문 세 편으로 공개했습니다.

해논문한 줄 뜻지금 남아 있는 것
2003GFS (Google File System)큰 파일을 잘게 쪼개 여러 대에 나눠 저장, 복사본 3개로 고장 대비HDFS → S3 · GCS 같은 객체 저장소의 생각
2004MapReduce계산을 데이터가 있는 기계로 보내 각자 처리(Map), 키별로 모아 합침(Reduce)GROUP BY 의 분산판. Spark 의 셔플
2006Bigtable행 키로 빠르게 찾는 거대한 분산 표HBase, Cassandra 같은 NoSQL

야후에서 일하던 더그 커팅 등이 이 생각을 오픈소스로 만든 것이 Hadoop(2006)입니다. 이름은 커팅의 아들이 갖고 놀던 노란 코끼리 인형에서 왔습니다. 이제 누구나 서버를 사서 빅데이터를 처리할 수 있게 됐습니다.

  MapReduce = 분산 GROUP BY

  기계1: [서울,1][부산,1][서울,1]  ─Map─▶  서울:2  부산:1  ┐
  기계2: [부산,1][서울,1]          ─Map─▶  부산:1  서울:1  ├─셔플(키별로 모으기)─▶ 서울:3
  기계3: [대구,1]                  ─Map─▶  대구:1          ┘                    부산:2
                                                                             대구:1 ─Reduce

그런데 MapReduce는 자바 코드로 짜야 했습니다. 간단한 집계에도 수십 줄. 그래서 바로 "SQL로 쓰게 해 달라"는 요구가 나왔고, 2008년 페이스북이 Hive(SQL을 MapReduce로 바꿔 주는 도구)를 공개합니다. 야후는 Pig 라는 스크립트 언어를 냈습니다.

데이터 엔지니어에게는

여기서 "데이터 엔지니어"가 별도 직군으로 보이기 시작했습니다. 분석가가 SQL로 묻기 전에, 누군가 수백 대 클러스터를 운영하고 파이프라인 코드를 짜야 했기 때문입니다. 그리고 첫 번째 교훈이 나옵니다 — SQL을 버린 시스템은 결국 SQL을 다시 붙인다.

5장 · 더 빠르게, 끊임없이 — Spark 와 Kafka

Hadoop MapReduce는 단계마다 결과를 디스크에 썼다 읽었습니다. 같은 데이터를 여러 번 도는 작업(머신러닝, 반복 집계)은 너무 느렸습니다.

  • Spark — 2009년 UC 버클리 AMPLab 에서 마테이 자하리아가 시작. 중간 결과를 메모리에 두고, 할 일을 모았다가 한 번에 최적화해서 실행(지연 실행)합니다. 2014년 아파치 최상위 프로젝트가 됐고, 만든 사람들이 Databricks 를 세웠습니다. 나중엔 Spark SQL · DataFrame 이 주인공이 됩니다 — 또 SQL입니다.
  • Kafka — 링크드인이 2011년 공개. 클릭 · 주문 · 로그인 같은 사건을 끝없이 이어지는 로그로 저장하고, 여러 시스템이 각자 원하는 위치부터 읽게 합니다. 하루 한 번 배치 대신 "생기는 즉시" 처리하는 스트리밍의 기반이 됐습니다. 이어서 Storm, Flink, 구글 Dataflow(2015 논문, Apache Beam) 같은 스트림 처리 엔진이 나옵니다.
🧸 비유

배치가 밤에 한 번 오는 택배 트럭이라면 Kafka는 쉬지 않고 도는 컨베이어 벨트입니다. 물건(사건)이 벨트에 올라가면, 각 부서는 자기 속도로 벨트에서 집어 갑니다. 벨트 위 물건은 며칠 동안 남아 있어서, 늦게 온 부서도 처음부터 다시 볼 수 있습니다.

함정 "실시간이 더 좋다"는 착각이 흔합니다. 대부분의 보고서는 하루 한 번이면 충분하고, 스트리밍은 운영이 몇 배 어렵습니다. 누가 몇 분 안에 이 숫자를 보고 무엇을 결정하는가가 없으면 배치로 시작하세요.

6장 · 클라우드 웨어하우스와 ELT — 순서가 뒤집히다

2010년대에 들어 클라우드가 판을 바꿉니다.

  • BigQuery — 구글 내부 시스템 Dremel(2010 논문)을 서비스로 공개. 서버를 하나도 안 띄우고 SQL만 보내면 수천 대가 나눠서 답합니다. 읽은 바이트만큼 냅니다.
  • Redshift — AWS 가 2012년 발표. 웨어하우스를 몇 분 만에 빌려 씁니다.
  • Snowflake — 2012년 창업, 2014년 공개. 저장과 계산을 분리해서, 데이터는 한 곳에 두고 계산 자원(웨어하우스)만 필요한 만큼 켰다 껐다 합니다.

웨어하우스가 싸고 커지자 ETL의 순서가 뒤집혔습니다. 더는 밖에서 변환을 끝내고 넣을 이유가 없습니다. 일단 원본 그대로 넣고(EL), 변환은 웨어하우스 안에서 SQL로(T) — ELT입니다.

  1990년대  ETL:  원천 ──E──▶ [ETL 서버에서 T] ──L──▶ 작고 비싼 웨어하우스
  2010년대  ELT:  원천 ──E──L──▶ 크고 싼 클라우드 웨어하우스 ──▶ [안에서 SQL 로 T]
                                         ↑ 원본이 남아 있으니 언제든 다시 변환 가능

같은 시기, 파이프라인이 수백 개로 늘면서 "무엇을 언제, 어떤 순서로"를 크론으로 관리하는 게 한계에 부딪혔습니다. 2014년 에어비앤비의 맥심 보슈망이 Airflow를 만듭니다. 작업 순서를 파이썬 코드로 된 DAG로 적고, 실패 · 재시도 · 과거 날짜 다시 돌리기(백필)를 도구가 맡게 했습니다. 그는 2017년 글 「The Rise of the Data Engineer」에서, 이제 데이터 엔지니어는 끌어다 놓는 ETL 도구 대신 코드로 파이프라인을 짜는 소프트웨어 엔지니어에 가깝다고 정리했습니다.

파일 형식도 이때 정리됩니다. 열 단위로 저장해 필요한 컬럼만 읽는 Parquet(2013, 트위터 · 클라우데라)와 ORC 가 나왔고, 2013년 Docker, 2014년 Kubernetes 가 "어디서나 같은 환경으로 실행"을 가능하게 했습니다.

데이터 엔지니어에게는 지금 내가 쓰는 BigQuery + 스케줄러 + 버킷 구조가 바로 이 장면입니다. 두 번째 교훈 — 저장과 계산을 분리하면, 원본을 지키면서 계산은 마음껏 다시 할 수 있다. 그래서 "원본(raw)은 절대 덮어쓰지 않는다"는 규칙이 생겼습니다.

7장 · 모던 데이터 스택 — analytics engineer 의 등장

ELT가 표준이 되자 각 글자를 맡는 SaaS 가 조립식으로 붙었습니다. 이 조합을 흔히 모던 데이터 스택이라 부릅니다.

  E·L 수집          저장·계산              T 변환            보여 주기 · 의미
  Fivetran      ┐                      ┌─────────┐      Looker (LookML)
  Airbyte       ├──▶ BigQuery         │   dbt   │ ──▶  Metabase · Power BI
  직접 짠 수집    ┘    Snowflake  ◀──── │ (SELECT  │      Semantic Layer
                    Redshift          │ +테스트) │
                                      └─────────┘
              순서 · 일정 · 재시도 : Airflow · Dagster · Prefect

2016년 시작된 dbt는 변환을 "SELECT 파일 + ref + 테스트 + git"으로 바꿨습니다. 그러자 SQL을 잘하는 분석가가 엔지니어의 습관(버전 관리, 테스트, 코드 리뷰, CI)으로 데이터 모델을 직접 만들 수 있게 됐고, 2019년 무렵 dbt 커뮤니티를 중심으로 이 역할을 analytics engineer 라고 부르기 시작했습니다.

역할주로 하는 일주 무기
데이터 엔지니어수집(E·L), 플랫폼 · 인프라, 대용량 · 실시간, 파이프라인 운영Python, Spark, Kafka, Airflow, 클라우드
analytics engineer웨어하우스 안 변환(T), 마트 · 지표 정의, 데이터 품질 테스트SQL, dbt, git
데이터 분석가질문에 답하기, 보고서 · 대시보드, 의사결정 지원SQL, BI, 통계
SQL 감각으로 옮기면 프로시저로 마트를 만들던 일 = analytics engineer 의 일 그 자체입니다. 다른 점은 같은 일에 소프트웨어 습관을 입혔다는 것 하나입니다. 그래서 이 코스가 git · 테스트 · 환경 같은 "컴퓨터 기초"를 따로 다룹니다.

8장 · 레이크하우스 · 데이터 메시 · AI — 지금

데이터 레이크(2010년 무렵 나온 말)는 "형식 상관없이 일단 다 객체 저장소에 쏟아 두자"였습니다. 싸고 유연했지만 곧 "뭐가 어디 있는지 모르는 늪(data swamp)"이 됐습니다. 파일만 있고 테이블의 규칙(스키마, 트랜잭션, 이력)이 없었기 때문입니다.

그래서 테이블 포맷이 나왔습니다. 넷플릭스의 Iceberg(2017년 시작), 우버의 Hudi, Databricks 의 Delta Lake(2019 오픈소스). 객체 저장소의 Parquet 파일 위에 "이 파일들이 지금 이 테이블의 버전이다"라는 장부를 얹어, 레이크에서도 웨어하우스처럼 트랜잭션 · 스키마 변경 · 과거 시점 조회를 하게 합니다. 이 합친 모양을 Databricks 가 2020년 글(이듬해 논문)에서 레이크하우스라 부르며 널리 퍼뜨렸습니다.

조직 쪽에서는 2019년 자마크 데가니가 데이터 메시를 제안했습니다. 중앙 데이터팀 하나가 모든 데이터를 다 맡으면 병목이 되니, 각 업무 부서가 자기 데이터를 "제품"처럼 책임지고 공통 플랫폼과 규칙만 중앙이 맡자는 생각입니다.

그리고 2022년 이후의 LLM. 자연어로 질문하면 SQL을 만들어 주는 시대가 됐지만, 그럴수록 "매출이 뭔지", "활성 사용자가 뭔지"를 기계도 읽을 수 있게 정의해 둔 곳(Semantic Layer, 지표 정의, 문서, 테스트)이 중요해졌습니다. 정의가 흐리면 AI는 그럴듯하게 틀린 숫자를 빠르게 만듭니다.

데이터 엔지니어에게는 세 번째 교훈 — 자유(레이크)는 결국 규칙(테이블 포맷 · 계약 · 의미 정의)을 다시 부른다. 1990년대 웨어하우스가 풀던 "말을 통일하자"는 문제는 지금도 그대로입니다.

직업의 계보 — 이름은 바뀌어도 일은 이어진다

시기직업 이름그때의 핵심 문제지금 누가 이어받았나
1960~70년대천공 · 오퍼레이터, 배치 프로그래머밤사이 작업을 순서대로 실패 없이오케스트레이션 (Airflow)
1980년대~DBA (데이터베이스 관리자)DB 가 멈추지 않게, 빠르게, 안전하게데이터 플랫폼 엔지니어, 클라우드가 일부 대신
1990년대~ETL 개발자 · DW 개발자 · BI 개발자흩어진 시스템을 하나의 분석용 모델로analytics engineer, 데이터 모델러
2000년대 후반~빅데이터 엔지니어 (Hadoop)한 대로 안 되는 크기데이터 엔지니어 (Spark)
2010년대~데이터 엔지니어코드로 된 파이프라인, 클라우드, 실시간그대로 + 플랫폼 · 스트리밍 전문화
2019년 무렵~analytics engineer웨어하우스 안 변환을 소프트웨어처럼지표 · 의미 정의(Semantic Layer)까지 확장

130년이 반복해서 알려 주는 것

  1. SQL은 계속 돌아온다. Hadoop(→Hive), Spark(→Spark SQL), 스트리밍(→Flink SQL, ksqlDB). "무엇을 원하는지만 말하는" 선언형 언어를 사람들은 포기하지 않습니다. SQL 실력은 가장 오래가는 자산입니다.
  2. 배치 ↔ 실시간, 중앙 ↔ 분산, 자유 ↔ 규칙은 진자처럼 오간다. 새 유행이 오면 "이건 어느 쪽으로 흔들린 것인가"를 보세요.
  3. 저장과 계산을 분리하고, 원본을 지켜라. 다시 계산할 수 있으면 실수도 고칠 수 있습니다.
  4. 순서 · 재실행 · 멱등성은 영원한 숙제다. 천공카드 덱의 순서부터 Airflow 백필까지 같은 문제입니다.
  5. 결국 어려운 건 기술이 아니라 "말"이다. 고객 · 매출 · 활성의 정의를 맞추는 일은 1988년에도, AI 시대에도 가장 어렵고 가장 값집니다.
  6. 새 도구는 옛 문제의 새 답이다. 처음 보는 도구가 나오면 "이 전에는 무엇이 불편했길래?"를 먼저 물으면 절반은 이해한 것입니다.

퀴즈

1990년대 ETL 에서 변환(T)을 웨어하우스 밖 ETL 서버에서 한 가장 큰 이유는?

  1. SQL 이 아직 없어서
  2. 웨어하우스가 비싸고 작아서, 정리된 결과만 넣으려고
  3. 보안 규정 때문에
  4. BI 도구가 원본을 못 읽어서
SQL 은 1970년대부터 있었습니다. 당시 웨어하우스 장비는 비싸고 용량이 작아 원본을 다 넣고 그 안에서 계산할 여유가 없었습니다. 클라우드로 웨어하우스가 싸지자 순서가 ELT 로 뒤집혔습니다.

MapReduce 를 SQL 로 바꾸면 가장 가까운 것은?

  1. INSERT
  2. JOIN
  3. ORDER BY
  4. GROUP BY 집계 (여러 기계에서 나눠 세고, 키별로 모아 합침)
Map 은 각 기계가 자기 데이터에서 (키, 값)을 만들고, 셔플로 같은 키끼리 모은 뒤 Reduce 가 합칩니다. 분산된 GROUP BY 입니다. 이 "키별로 모으기"가 Spark 의 셔플로 이어집니다.

Hadoop 위에 Hive(2008), Spark 위에 Spark SQL 이 붙은 흐름이 보여 주는 것은?

  1. 사람들은 결국 선언형 언어(SQL)로 데이터를 묻기를 원한다
  2. 자바가 SQL 보다 빠르다
  3. 분산 시스템에서는 SQL 을 쓸 수 없다
  4. SQL 은 작은 데이터에만 쓴다
새 시스템이 SQL 없이 나와도 곧 SQL 층이 붙었습니다. "무엇을 원하는지만 말하고 방법은 시스템에 맡기는" 선언형 방식이 사람에게 가장 쓰기 쉽기 때문입니다.

Snowflake 가 강조한 "저장과 계산의 분리"로 얻는 것이 아닌 것은?

  1. 데이터는 한 곳에 두고 계산 자원만 필요할 때 늘렸다 줄이기
  2. 여러 팀이 같은 데이터를 각자 다른 계산 자원으로 읽기
  3. 쿼리를 짜지 않아도 지표 정의가 자동으로 통일됨
  4. 안 쓸 때 계산을 꺼서 비용 줄이기
저장 · 계산 분리는 비용 · 확장성 이야기입니다. "매출이 뭔가"를 통일하는 건 여전히 사람이 모델 · 지표 정의(dbt, Semantic Layer)로 해야 합니다.

Airflow 가 해결하려던 문제로 가장 알맞은 것은?

  1. SQL 을 더 빠르게 실행하기
  2. 수백 개 작업의 순서 · 일정 · 실패 재시도 · 과거 날짜 재실행을 코드로 관리하기
  3. 데이터를 열 단위로 압축 저장하기
  4. 웹 화면에서 대시보드 만들기
Airflow 는 직접 계산하지 않는 "지휘자"입니다. 크론으로는 의존 관계 · 재시도 · 백필을 관리하기 어려워서, 작업 흐름을 파이썬 DAG 로 적게 했습니다.

데이터 레이크가 "데이터 늪"이 되기 쉬웠던 이유는?

  1. 저장 비용이 너무 비싸서
  2. SQL 로는 아예 읽을 수 없어서
  3. 데이터를 실시간으로만 넣을 수 있어서
  4. 파일만 쌓이고 스키마 · 버전 · 주인 같은 "테이블의 규칙"이 없어서
레이크는 싸고 유연했지만 규칙이 없었습니다. Iceberg · Delta · Hudi 같은 테이블 포맷이 파일 위에 장부(스키마 · 트랜잭션 · 이력)를 얹어 이 문제를 풀고, 이것이 레이크하우스입니다.

LLM 시대에 오히려 더 중요해진 것은?

  1. SQL 문법 암기
  2. 더 큰 서버
  3. 지표 · 용어의 정의를 기계도 읽게 적어 두는 것 (Semantic Layer · 문서 · 테스트)
  4. 천공카드
AI 는 SQL 을 잘 만들지만 "우리 회사의 매출"이 무엇인지는 모릅니다. 정의가 흐리면 그럴듯하게 틀린 숫자를 빠르게 냅니다. 1988년 웨어하우스가 풀던 "말의 통일"이 다시 핵심입니다.
