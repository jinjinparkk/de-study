디버깅은 추리가 아니라 범위 좁히기

초보가 막히면 "왜 안 되지?"를 머릿속으로 오래 생각합니다. 숙련자는 생각보다 실험을 먼저 합니다. 디버깅은 거의 항상 같은 네 단계입니다.

  ① 재현한다          ② 범위를 반으로 줄인다     ③ 가설 하나만 바꿔 본다     ④ 고치고, 다시 재현해 본다
  ┌──────────┐       ┌──────────────┐         ┌──────────────┐         ┌──────────────┐
  │ 언제나 같은 │ ──▶  │ 앞 절반은 정상? │ ──▶     │ 버전만 바꾼다  │ ──▶     │ 같은 방법으로   │
  │ 방법으로 실패 │       │ 뒤 절반은?      │         │ 데이터만 바꾼다 │         │ 이제 성공하나?  │
  └──────────┘       └──────────────┘         └──────────────┘         └──────────────┘
       ▲                                                                       │
       └──────────────── 아니면 다시 ② 로 ─────────────────────────────────────┘
🧸 비유

집 전등이 안 켜질 때 전구 → 스위치 → 차단기 → 집 밖 전기 순서로 확인하는 것과 같습니다. 전구를 다른 방에 끼워 보면(재현 · 비교) 전구 문제인지 아닌지 한 번에 절반이 줄어듭니다. 동시에 전구와 스위치를 둘 다 바꾸면, 고쳐져도 무엇 덕분인지 모릅니다(가설은 하나씩).

SQL 감각으로 옮기면

긴 프로시저의 결과가 틀렸을 때, 우리는 이미 이렇게 합니다 — 임시 테이블을 하나씩 SELECT COUNT(*) 해 보며 어느 단계에서 숫자가 틀어졌는지 찾기. CTE 가 다섯 개라면 세 번째 CTE 까지만 떼어 돌려 보기. 이게 바로 "범위를 반으로 줄이기"(이분 탐색)입니다. 코드 디버깅도 똑같습니다.

에러 메시지는 아래에서부터 읽는다

파이썬 에러(트레이스백)는 무섭게 길지만, 읽는 순서만 알면 쉽습니다.

    {"order_id": 2, "amt": 20000},      # 컬럼 이름이 다른 행
]

def revenue(rows):
    total = 0
    for r in rows:
        total += r["amount"]
    return total

"어제는 됐는데" — 무엇이 바뀌었나 목록

코드를 안 바꿨는데 안 된다면, 코드 말고 다른 게 바뀐 것입니다. 실제로 자주 일어나는 순서대로 적으면 이렇습니다.

바뀐 것실제로 흔한 모습확인 방법
프로그램 · 패키지 버전브라우저가 자동 업데이트돼서 자동화용 드라이버와 버전이 안 맞음. pip install 하다 다른 패키지가 같이 올라감pip list, pip freeze 를 어제 것과 비교. 버전 고정(6장)
자격 증명 · 토큰저장해 둔 비밀번호가 지워짐, 토큰 만료, 비밀번호 변경로그인 단계만 따로 실행해 보기
데이터원천에서 새 컬럼 · 새 값 · 빈 파일 · 중복이 들어옴행 수 · 컬럼 목록 · 값 종류를 어제와 비교

데이터 버그 — 에러 없이 숫자만 틀릴 때

데이터 일의 버그는 대부분 에러 메시지가 없습니다. 쿼리는 잘 돌고, 숫자만 틀립니다. 그래서 "대조할 숫자"를 늘 갖고 있어야 합니다.

증상흔한 원인잡는 법
조인 후 매출이 늘어남팬아웃 — 한 주문에 결제가 2건이면 주문 금액이 2번 더해짐조인 전후 행 수 · 합계 비교. 조인 키의 유일성 테스트(unique)
조인 후 행이 사라짐INNER JOIN 인데 짝이 없는 행, 키 형식 차이('001' vs 1, 앞뒤 공백)LEFT JOIN 으로 바꿔 짝 없는 행을 세어 보기
합계 · 평균이 이상함NULL — COUNT(col) 은 NULL 을 빼고, NULL + 1 은 NULLCOUNT(*) vs COUNT(col) 비교, COALESCE
어제 숫자가 하루 밀림시간대 — 원천은 UTC, 보고는 한국 시간(KST = UTC+9)자정 근처 데이터를 골라 두 시간대로 날짜를 찍어 보기
지난주 숫자가 다시 바뀜늦게 도착한 데이터, 매체의 사후 보정"며칠 전까지 다시 계산할지"를 정해 두기(재처리 기간)
두 번 돌리면 두 배멱등하지 않은 적재 — 지우지 않고 INSERT 만같은 날짜로 두 번 돌려 결과가 같은지 확인 (dbt 5일차 멱등성)
🧸 비유

가계부 정리와 같습니다. 통장 잔고(원천 합계)와 가계부 합계(마트 합계)가 다르면, 어디가 틀렸는지 몰라도 틀렸다는 건 압니다. 그다음 월별 → 주별 → 일별로 쪼개 대조하면 틀린 날이 나옵니다. 데이터 테스트는 이 대조를 매일 자동으로 하는 것입니다.

관찰하는 습관 — print, 로그, 작은 데이터

  • 중간값을 찍어 본다. 파이썬은 print(type(x), x), SQL 은 CTE 하나만 떼어 SELECT ... LIMIT 10. 생각 말고 눈으로 확인합니다.
  • 로그를 남긴다. 몇 시에 무엇을 몇 건 처리했는지. 새벽에 돈 작업은 로그가 유일한 목격자입니다(6장).
  • 작게 줄인다. 1억 행에서 틀리면 문제 되는 10행을 뽑아 작은 예제로 만듭니다. 작게 재현되면 반은 푼 것입니다.
  • 한 번에 하나만 바꾼다. 바꾼 것과 결과를 메모장에 적습니다. 두 시간 뒤 "아까 그건 왜 됐지?"를 막아 줍니다.
  • 되돌릴 수 있게 한다. 고치기 전에 git 커밋, 원본 파일은 .bak 으로. 원본 데이터는 덮어쓰지 않습니다(7장 교훈).

답이 오는 질문 쓰기 — 사람에게도, AI 에게도

"안 돼요"라는 질문에는 "뭐가요?"라는 답밖에 못 옵니다. 좋은 질문에는 다섯 가지가 들어 있습니다.

1. 하려던 것:   BigQuery 테이블을 dbt 로 만들려고 dbt run 을 했습니다.
2. 환경:        Windows 11, Python 3.12, dbt-core 1.12, 가상환경 켬
3. 실행한 것:   dbt run --select stg_orders
4. 기대 vs 실제: 테이블이 생겨야 하는데, 아래 에러가 납니다. (에러 전문 붙임 — 키·비밀번호는 지움)
5. 이미 해 본 것: dbt debug 는 통과, 다른 모델은 됨, 이 모델만 실패
데이터 엔지니어에게는 이 틀을 쓰다 보면 질문을 다 쓰기도 전에 답을 찾는 일이 자주 생깁니다. "이미 해 본 것"을 적다가 안 해 본 것이 보이기 때문입니다. AI 에게 물을 때도 똑같이 쓰면 훨씬 정확한 답이 옵니다. 단, 회사 데이터 · 고객 정보 · 키는 절대 붙이지 마세요.

2. 조인 팬아웃을 내 눈으로 보기 (설치 없이 sqlite3)

import sqlite3                                  # 파이썬에 기본으로 들어 있는 작은 DB
c = sqlite3.connect(":memory:")                 # 메모리 안에 임시 DB 하나 만들기
c.executescript("""
create table orders(order_id int, amount int);
insert into orders values (1,10000),(2,20000),(3,30000);
create table payments(order_id int, method text);
insert into payments values (1,'card'),(2,'card'),(2,'point'),(3,'card');
""")
print(c.execute("select count(*), sum(amount) from orders").fetchone())
print(c.execute("""select count(*), sum(o.amount)
                   from orders o join payments p using(order_id)""").fetchone())

퀴즈

파이썬 트레이스백에서 "무슨 에러인지"는 어디에 있나요?

  1. 맨 위 Traceback (most recent call last) 줄
  2. 가운데 라이브러리 파일 줄
  3. 맨 아래 줄 (예: KeyError: 'amount')
  4. 트레이스백에는 에러 종류가 나오지 않는다
most recent call last — 가장 최근 호출(실제로 터진 곳)이 맨 아래입니다. 맨 아래 줄이 에러 종류와 메시지, 그 바로 위가 위치입니다.

버그를 고치려고 패키지 버전과 설정 파일을 동시에 바꿨더니 고쳐졌습니다. 무엇이 문제인가요?

  1. 무엇 덕분에 고쳐졌는지 몰라서, 다음에 같은 일이 생기면 또 헤맨다
  2. 아무 문제 없다, 고쳐졌으면 됐다
  3. 버전을 바꾸면 항상 더 나빠진다
  4. 설정 파일은 바꾸면 안 된다
가설은 하나씩 바꿔야 원인을 압니다. 원인을 모르면 재발을 막을 수도, 다른 사람에게 설명할 수도 없습니다.

주문 테이블(3건, 60,000원)을 결제 테이블과 조인했더니 4건, 80,000원이 됐습니다. 원인은?

  1. NULL 값
  2. 시간대 차이
  3. 인코딩 문제
  4. 한 주문에 결제가 여러 건이라 주문 행이 복제된 팬아웃
1:N 조인에서 N 쪽 행 수만큼 1 쪽이 복제됩니다. 결제를 주문 단위로 먼저 묶고 조인하거나, 그레인을 맞춰야 합니다. 에러가 없어서 대조 숫자로만 잡힙니다.

원천 시각이 UTC 인데 한국 날짜로 일별 집계할 때 시간대 변환을 빼먹으면?

  1. 쿼리가 에러로 멈춘다
  2. 매일 한국 시간 0시~9시 사이 데이터가 전날로 잘못 들어간다
  3. 아무 차이 없다
  4. 데이터가 두 배가 된다
KST 는 UTC+9 입니다. 한국 시간 새벽 0~9시는 UTC 로는 아직 전날이라, 변환 없이 날짜를 자르면 그 9시간이 전날 숫자에 들어갑니다. 에러는 나지 않습니다.

"코드는 그대로인데 오늘부터 안 된다"일 때 가장 먼저 의심할 것으로 알맞지 않은 것은?

  1. 프로그램 · 패키지가 자동 업데이트됐나
  2. 저장된 자격 증명이 만료 · 삭제됐나
  3. 어제 성공했으니 코드에 숨은 문법 오류가 생겼다
  4. 원천 데이터 모양이 바뀌었나
코드가 그대로라면 문법 오류가 새로 생길 수 없습니다. 바뀐 것은 코드 밖(버전 · 자격 증명 · 데이터 · 환경 · 네트워크 · 날짜)에 있습니다.

예외를 try 로 감싸고 아무것도 하지 않으면(조용히 넘기면) 생기는 일은?

  1. 실패해도 종료 코드 0 으로 끝나 스케줄러가 "성공"으로 알고, 아무도 모르게 데이터가 빈다
  2. 프로그램이 더 빨라진다
  3. 에러가 자동으로 고쳐진다
  4. 다음 실행 때 자동 재시도된다
조용한 실패가 가장 비쌉니다. 실패하면 로그를 남기고, 0 이 아닌 종료 코드로 끝내서 스케줄러 · Airflow 가 알게 해야 합니다.
