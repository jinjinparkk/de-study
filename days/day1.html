큰 그림 — 프로시저에서 dbt로

오늘은 dbt가 무엇을 대신해 주는지를 이해하고, 내 PC에서 첫 dbt 모델을 돌려 봅니다.

이론 약 70분 · 실습 약 60분 · 퀴즈 6문제

오늘 마치면 할 수 있는 것
  • ETL과 ELT의 차이, 그리고 dbt가 그중 어디(T)를 맡는지 설명하기
  • 내가 짜던 프로시저 한 개를 dbt 모델 여러 개로 바꾸면 무엇이 좋아지는지 말하기
  • dbt init → dbt debug → dbt run 까지 직접 실행하기
  • target/compiled 폴더를 열어 dbt가 실제로 보낸 SQL을 확인하기

왜 dbt인가

프로시저로 마트를 만들면 보통 이런 모양이 됩니다.

CREATE OR REPLACE PROCEDURE dm.sp_build_daily_sales(p_date DATE)
BEGIN
  -- 1) 정제
  CREATE TEMP TABLE tmp_orders AS
  SELECT order_id, customer_id, LOWER(TRIM(status)) AS status, order_date
  FROM raw.orders
  WHERE order_date = p_date;

  -- 2) 결제 합치기
  CREATE TEMP TABLE tmp_pay AS
  SELECT order_id, SUM(amount) AS amount
  FROM raw.payments GROUP BY order_id;

  -- 3) 마트 적재 (그날 것 지우고 다시 넣기)
  DELETE FROM dm.daily_sales WHERE order_date = p_date;
  INSERT INTO dm.daily_sales
  SELECT o.order_date, COUNT(*) AS orders, SUM(p.amount) AS revenue
  FROM tmp_orders o JOIN tmp_pay p USING (order_id)
  WHERE o.status = 'completed'
  GROUP BY o.order_date;
END;

잘 돌아갑니다. 그런데 이런 프로시저가 30개, 50개가 되면 아래 질문에 답하기 어려워집니다.

🧸 비유

프로시저는 요리사 한 명이 머릿속 레시피로 처음부터 끝까지 요리하는 것과 같습니다. 맛은 좋지만, 그 요리사가 없으면 아무도 순서를 모릅니다.

dbt는 레시피 카드를 단계별로 나눠 벽에 붙여 두는 것입니다. "양파 손질 카드", "소스 카드", "완성 카드"가 있고, 카드마다 "이 카드는 양파 손질 카드 다음에"라고 적혀 있습니다. 누가 와도 같은 순서로 같은 맛을 냅니다. 그리고 각 카드 옆에는 "간 확인" 같은 검사표(테스트)가 붙어 있습니다.

💡 한 줄 요약 dbt는 SQL을 새로 배우는 도구가 아니라, 내가 이미 쓰는 SELECT 문을 파일로 나누고, 순서·테스트·문서·이력을 자동으로 붙여 주는 도구입니다.

ETL에서 ELT로

예전에는 데이터를 웨어하우스에 넣기 전에 별도 서버에서 가공했습니다(ETL). 웨어하우스가 비싸고 느렸기 때문입니다. BigQuery·Snowflake처럼 계산이 싸고 빠른 웨어하우스가 나오면서, 일단 원본 그대로 넣고(Load) 웨어하우스 안에서 SQL로 가공(Transform)하는 방식이 표준이 됐습니다. 이게 ELT입니다.

ETL (예전)
┌────────┐  추출  ┌──────────────┐  가공된 것만  ┌────────────┐
│ 원천DB  │──────▶│ ETL 서버에서 가공 │────────────▶│ 웨어하우스    │
└────────┘       └──────────────┘              └────────────┘

ELT (지금)
┌────────┐  추출·적재(EL)  ┌──────────────────────────────────┐
│ 원천DB  │──────────────▶│ 웨어하우스                           │
│ API    │  Fivetran,     │  raw ──▶ staging ──▶ marts       │
│ 파일    │  Airbyte, 직접  │        └──── 이 부분이 dbt (T) ───┘ │
└────────┘  짠 수집 코드    └──────────────────────────────────┘
                                         ▲
                           Airflow가 "언제·어떤 순서로" 를 지휘

여기서 이번 7일 동안 배울 세 도구의 자리가 정해집니다.

도구맡는 일한 마디로
dbt웨어하우스 안에서 SQL로 가공(T)레시피 카드 묶음
Airflow수집·dbt·알림 같은 작업을 언제, 어떤 순서로 돌릴지 관리주방 매니저(타이머와 순서표)
Spark웨어하우스 밖에서 아주 큰 데이터를 여러 컴퓨터로 나눠 처리요리사 100명이 동시에 감자 깎기
헷갈리기 쉬운 점

dbt는 데이터를 옮기지 않습니다. dbt는 SQL을 만들어 웨어하우스에 "이거 실행해 줘"라고 보낼 뿐이고, 실제 계산은 BigQuery나 DuckDB가 합니다. 그래서 dbt 자체는 아주 가볍고, 성능은 웨어하우스에 달려 있습니다.

또 dbt에는 스케줄러가 없습니다(dbt Cloud 유료판 제외). "매일 아침 6시에 돌려" 는 Airflow 같은 도구가 맡습니다. 이게 5·6일차 내용입니다.

dbt가 일하는 방식

dbt의 핵심 동작은 딱 세 단계입니다.

  ① 내가 쓰는 것                ② dbt가 하는 일 (compile)          ③ 웨어하우스가 하는 일
┌──────────────────────┐   ┌───────────────────────────────┐   ┌────────────────────┐
│ models/fct_orders.sql │   │ {{ ref('stg_orders') }} 를       │   │ CREATE TABLE ...   │
│                      │──▶│ "main"."stg_orders" 로 바꾸고      │──▶│ 실제 계산·저장        │
│ select ...           │   │ CREATE TABLE AS 로 감싼 SQL 생성   │   │                    │
│ from {{ ref(...) }}  │   │ → target/compiled, target/run   │   │                    │
└──────────────────────┘   └───────────────────────────────┘   └────────────────────┘

내가 쓰는 건 SELECT 문 하나뿐입니다. CREATE TABLE, INSERT, DROP 같은 DDL·DML은 dbt가 대신 붙입니다. 이게 프로시저와 가장 크게 다른 점입니다.

프로시저: "어떻게 만들지"를 적는다
DROP TABLE IF EXISTS dm.fct_orders;
CREATE TABLE dm.fct_orders AS
SELECT o.order_id, p.amount
FROM stg.orders o
JOIN stg.payments p USING (order_id);
dbt: "무엇이 될지"만 적는다
select o.order_id, p.amount
from {{ ref('stg_orders') }} o
join {{ ref('stg_payments') }} p
  using (order_id)

오른쪽 파일 이름 fct_orders가 곧 테이블 이름이 됩니다. 테이블로 만들지 뷰로 만들지는 설정(materialization)으로 정합니다 — 2일차에 자세히 봅니다.

프로젝트 폴더 지도

shop/                         ← dbt 프로젝트 하나 = 폴더 하나
├── dbt_project.yml           ← 프로젝트 설정 (이름, 폴더별 기본 materialization)
├── models/                   ← ★ 여기에 SELECT 문 .sql 파일을 둔다 (하루의 90%를 여기서 보냄)
│   ├── staging/              ←   원본을 깨끗하게 (이름 바꾸기, 형 변환, TRIM)
│   └── marts/                ←   사람이 보는 최종 테이블
├── seeds/                    ← 작은 CSV를 테이블로 올릴 때 (코드표, 매핑표)
├── snapshots/                ← 변경 이력(SCD2) 보관 — 4일차
├── macros/                   ← 재사용 SQL 함수 (Jinja) — 4일차
├── tests/                    ← 직접 쓰는 테스트 SQL — 3일차
└── target/                   ← dbt가 만든 결과물 (compiled SQL, 로그). git에 안 올림

~/.dbt/profiles.yml           ← 접속 정보(어느 DB에, 어떤 계정으로). 프로젝트 밖에 둔다!
프로시저 감각으로 옮기면
  • models/의 SQL 파일 하나 = 프로시저 안의 CREATE TEMP TABLE ... AS SELECT 블록 하나
  • ref() = "앞 블록에서 만든 임시 테이블을 쓴다"는 표시. 다만 dbt는 이걸 보고 실행 순서까지 정합니다.
  • profiles.yml = 접속 정보. 비밀번호·키가 들어가니까 코드 저장소 밖에 둡니다.

왜 연습은 DuckDB로?

DuckDB는 파일 하나짜리 데이터베이스입니다(SQLite의 분석용 버전이라고 생각하면 됩니다). 설치가 pip 한 줄이고, 비용이 0원이고, CSV를 바로 읽을 수 있습니다. dbt 문법은 BigQuery와 거의 같기 때문에 여기서 익힌 건 그대로 회사·OKR 프로젝트(BigQuery)로 가져갈 수 있습니다. 다른 건 SQL 방언(날짜 함수 등) 정도입니다.

실습: 첫 dbt 프로젝트

작은 쇼핑몰 데이터(고객 15명, 주문 30건, 결제 32건)로 7일 내내 실습합니다. 오늘은 설치하고, 프로시저 하나를 dbt 모델로 옮겨 봅니다.

새 창을 열 때마다 하는 두 줄 (2단계 이후부터, 2~7일차 내내) 
cd $HOME\dbt-practice\shop
..\.venv\Scripts\Activate.ps1
  • 왜 cd? dbt는 지금 서 있는 폴더에서 dbt_project.yml을 찾습니다. 다른 폴더면 Not a dbt project 오류가 납니다. 또 read_csv('data/...') 같은 상대 경로와 shop.duckdb 파일 위치도 현재 폴더 기준이라, 엉뚱한 폴더에서 돌리면 빈 DB 파일이 새로 생겨서 "어제 만든 테이블이 사라진" 것처럼 보입니다.
  • 왜 Activate? dbt.exe는 .venv\Scripts 안에만 있습니다. 활성화는 그 창에만 적용되므로, 새 창을 열면 다시 해야 합니다. 안 하면 'dbt' 용어가 ... 인식되지 않습니다가 뜹니다.
  • 왜 ..? .venv는 shop이 아니라 한 단계 위 dbt-practice에 있기 때문입니다.
  • 두 줄의 순서는 바꿔도 됩니다. 프롬프트 앞에 (.venv)가 붙고 경로가 ...\shop>이면 준비 끝.
1. 작업 폴더와 가상환경 만들기

dbt는 파이썬 프로그램이라 pip로 설치합니다. 그냥 PC 전체 파이썬에 설치하면 다른 프로젝트(pandas 버전 고정 등)와 패키지 버전이 부딪히고, "어제는 됐는데 오늘은 안 돼"가 생깁니다. 그래서 이 연습 전용 파이썬 방(가상환경, venv)을 만들고 그 안에만 설치합니다. 프로시저로 치면 운영 스키마를 건드리지 않으려고 개인 작업용 스키마를 따로 만드는 것과 같습니다.

PowerShell을 열고 아래를 한 줄씩 실행합니다.

mkdir $HOME\dbt-practice
cd $HOME\dbt-practice
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
pip install dbt-duckdb
조각뜻
mkdir폴더 만들기 (make directory)
$HOME내 사용자 폴더 C:\Users\내이름. 어느 위치에서 쳐도 같은 곳을 가리킴
\dbt-practice그 아래 만들 폴더 이름
cd그 폴더로 들어가기 (change directory). 이후 명령은 전부 이 폴더 기준
python -m venv파이썬에 들어 있는 venv 기능을 실행 (-m = 모듈을 실행)
.venv만들 가상환경 폴더 이름. 앞의 점은 "숨김·설정용 폴더" 관례
.\현재 폴더 (dbt-practice)
.venv\Scripts\Activate.ps1가상환경 안의 활성화 스크립트. 실행하면 이 창에서 python·pip·dbt가 .venv 것을 가리킴. 프롬프트 앞에 (.venv)가 붙음
python -m pip install --upgrade pip설치 도구 pip 자체를 최신으로. 오래된 pip는 dbt 설치 중 오류를 내기 쉬움
pip install dbt-duckdbDuckDB 어댑터 설치. dbt Core 본체도 같이 딸려 옴

활성화는 그 창에서만 유효합니다. 창을 닫았다 열면 위 "새 창을 열 때마다 하는 두 줄"을 다시 하세요.

Activate.ps1 실행이 막힌다면

"이 시스템에서 스크립트를 실행할 수 없으므로" 오류가 나면 현재 창에서만 허용합니다: Set-ExecutionPolicy -Scope Process RemoteSigned 후 다시 실행. -Scope Process = 이 창이 닫힐 때까지만, RemoteSigned = 내 PC에서 만든 스크립트는 허용. PC 설정을 영구히 바꾸지 않는 가장 안전한 방법입니다.

확인: dbt --version 을 쳤을 때 Core와 duckdb 플러그인 버전이 나오면 성공입니다. (2026-11 기준 확인한 버전: Core 1.12.6, duckdb 1.11.1) --version은 "설치가 됐고 이 창에서 dbt가 보이는지"를 가장 싸게 확인하는 방법입니다.

"dbt v2 is available" 안내가 뜬다면

dbt Labs가 새 엔진(v2, Fusion 계열)을 내놓으면서 Core v1에 안내 문구를 띄웁니다. 무시하고 진행해도 됩니다. 이 코스는 pip로 설치하는 오픈소스 dbt Core(v1)를 기준으로 하고, 모델·ref·테스트·YAML 같은 핵심 문법은 v2에서도 그대로입니다. 차이는 엔진 속도와 일부 엄격해진 검사 정도입니다.

  • 저장소마다 가상환경을 하나씩 두고, 설치할 패키지와 버전을 requirements.txt(예: dbt-bigquery==1.x.y)에 고정해 git에 올립니다. 새로 온 사람은 pip install -r requirements.txt 한 줄로 팀과 같은 버전을 맞춥니다. 요즘은 uv·poetry 같은 도구로 같은 일을 하기도 합니다.
  • VS Code에서 파이썬 인터프리터로 .venv를 골라 두면 새 터미널을 열 때 자동으로 활성화해 줘서 Activate를 직접 칠 일이 거의 없습니다.
  • .venv 폴더 자체는 git에 올리지 않습니다(용량이 크고 PC마다 다름). 목록(requirements.txt)만 공유합니다.
2. dbt init 으로 프로젝트 만들기

dbt는 정해진 폴더 구조(dbt_project.yml, models/ …)와 접속 정보(profiles.yml)가 있어야 움직입니다. 이걸 손으로 만들면 이름 하나만 틀려도 Could not find profile named 'shop' 같은 오류가 납니다. dbt init은 이 뼈대를 한 번에 만들어 주는 명령입니다. 프로시저로 치면 "스키마 만들고 접속 계정 등록"까지를 해 주는 단계입니다.

dbt init shop
조각뜻
dbtdbt 프로그램 (.venv\Scripts\dbt.exe)
init새 프로젝트 만들기 하위 명령
shop프로젝트 이름 = 만들어질 폴더 이름 = profiles.yml 안의 프로필 이름

어떤 DB를 쓸지 물으면 [1] duckdb 처럼 번호가 나옵니다. 그 번호를 입력하고 Enter. 끝나면 두 가지가 생깁니다.

  • dbt-practice\shop\ 폴더 — 프로젝트 (모델·설정 파일)
  • C:\Users\내이름\.dbt\profiles.yml — 접속 정보 (프로젝트 밖)

profiles.yml 열어 보기 (PowerShell 기준. cmd 창이면 $HOME 대신 %USERPROFILE%)

type $HOME\.dbt\profiles.yml       # 내용만 보기
notepad $HOME\.dbt\profiles.yml    # 메모장으로 열어 고치기

dbt init이 만든 파일은 보통 path: dev.duckdb, threads: 1이고 prod 묶음도 같이 들어 있습니다. 이 코스는 DB 파일 이름을 shop.duckdb로 씁니다(뒤 실습·Airflow 연동이 이 이름 기준). dev 아래 두 줄만 아래처럼 바꾸고 저장하세요. prod 묶음은 둬도 됩니다(6일차에 씁니다). YAML은 띄어쓰기 칸 수가 문법이라 탭 대신 스페이스로, 윗줄과 같은 위치에 맞춥니다.

shop:
  target: dev
  outputs:
    dev:
      type: duckdb
      path: shop.duckdb   # dbt를 실행한 폴더에 이 파일이 생긴다
      threads: 4

맨 윗줄 shop은 프로필 이름이고, shop/dbt_project.yml 안의 profile: 'shop'과 이름이 같아야 연결됩니다. target: dev는 "아무 말 없으면 dev 묶음으로 접속"이라는 뜻이고, threads: 4는 서로 의존하지 않는 모델을 최대 4개까지 동시에 돌린다는 뜻입니다(1이면 하나씩 차례로).

  • profiles.yml에 dev와 prod 같은 target을 여러 개 둡니다. BigQuery라면 dev는 보통 개인 데이터셋(예: dbt_<이름>)을 가리켜서, 내가 무엇을 돌려도 운영 테이블이나 동료 작업을 덮어쓰지 않습니다.
  • 개발자 PC에서는 method: oauth로 gcloud auth application-default login한 내 구글 계정을 쓰고, 운영(스케줄러·CI)에서는 서비스 계정으로 접속합니다. 키 경로나 비밀번호는 파일에 직접 적지 않고 {{ env_var('...') }}로 환경 변수에서 읽습니다.
  • 운영 실행은 dbt run --target prod처럼 target을 바꿔서 돌립니다. 같은 SQL 코드가 접속 대상만 바뀌는 구조입니다. 6일차에 직접 해 봅니다.

5. 첫 모델: 프로시저의 1단계를 옮기기

"SELECT만 쓰면 dbt가 CREATE를 붙여 준다"를 직접 확인하는 단계입니다. 정제(TRIM·LOWER·형 변환)를 맨 앞 모델 한 곳에서만 해 두면, 뒤 모델들은 깨끗한 데이터만 받아 쓰고 정제 로직이 여기저기 복사되지 않습니다. 프로시저의 CREATE TEMP TABLE tmp_orders AS SELECT ...에서 SELECT 부분만 파일로 떼어 낸다고 보면 됩니다.

models/stg_orders.sql 파일을 새로 만들고 SELECT 문만 씁니다(메모장이면 notepad models\stg_orders.sql → "새 파일을 만드시겠습니까?"에 예). 오늘은 원본을 직접 읽고(read_csv), 내일 이 부분을 source()로 바꿉니다.

select
    order_id,
    customer_id,
    cast(order_date as date)  as order_date,
    lower(trim(status))       as status
from read_csv('data/raw_orders.csv')

끝에 세미콜론(;)은 붙이지 않습니다. dbt가 이 SELECT를 create view ... as ( ... ) 안에 끼워 넣기 때문에, 세미콜론이 있으면 문장이 중간에 끊겨 문법 오류가 납니다.

dbt run

(옵션) --select stg_orders그 모델 하나만. 모델이 많아지면 이렇게 골라 돌림. 줄여서 -s

  • 원본은 read_csv가 아니라 항상 {{ source('원천', '테이블') }}로 읽습니다. 원본 위치를 YAML 한 곳에 적어 두고, 리니지 그래프에도 원천이 표시되게 하려는 것입니다.

  • 편집은 메모장이 아니라 VS Code(+ dbt 확장 프로그램)에서 합니다. 문법 색, 자동 완성, 컴파일 결과 미리보기를 씁니다.
6. 직접 해보기: 결제 모델과 일별 매출 모델

모델 하나로는 dbt의 핵심인 모델끼리의 연결(ref())을 볼 수 없습니다. 프로시저 전체를 모델 3개로 쪼개 이어 붙이면, 순서를 적지 않아도 dbt가 알아서 순서를 정하는 것을 직접 확인할 수 있습니다. 이게 "프로시저 50개의 실행 순서를 사람이 관리하던 일"을 dbt가 대신하는 방식입니다.

5단계에서 프로시저의 "1) 정제" 블록을 stg_orders.sql로 옮겼습니다. 이번엔 같은 방식으로 나머지 두 블록을 옮겨서, 모델 3개가 서로 이어진 작은 파이프라인을 완성합니다.

  프로시저 블록                      →  만들 dbt 모델 파일
  ─────────────────────────────────────────────────────────────────────
  1) CREATE TEMP TABLE tmp_orders    →  models\stg_orders.sql    (5단계에서 완료 ✓)
  2) CREATE TEMP TABLE tmp_pay       →  models\stg_payments.sql  (6-1 지금 만들 것)
  3) DELETE + INSERT daily_sales     →  models\daily_sales.sql   (6-2 지금 만들 것)

  완성되면 이렇게 연결됩니다:
  raw_orders.csv   ──▶ stg_orders   ──┐
                                      ├──▶ daily_sales
  raw_payments.csv ──▶ stg_payments ──┘

6-1. stg_payments.sql 만들기

  1. models 폴더에 새 파일 stg_payments.sql을 만듭니다 (stg_orders.sql 옆). 메모장이면: notepad models\stg_payments.sql

  3. 결과 컬럼은 두 개: order_id, amount

왜 합치나요? 결제 파일은 "결제 1건 = 1행"이라, 5번·18번 주문처럼 카드 + 포인트로 나눠 낸 주문은 2행입니다. 주문과 그냥 조인하면 그 주문이 두 번 세어집니다. 그래서 먼저 주문당 1행으로 줄입니다.

  raw_payments.csv (원본)              stg_payments (만들 결과)

  ────────── ──────── ────── ──────     ────────  ──────
       5         5    card    49000  ┐
       6         5    point   10000  ┴─▶    5      59000
       ...                                ...

틀만 드리면 이렇습니다. ____ 칸을 채워 보세요.

select
    order_id,
    ____(amount) as amount
from read_csv('data/raw_payments.csv')

6-2. daily_sales.sql 만들기

  1. models 폴더에 새 파일 daily_sales.sql
  2. 프로시저 3) 블록의 INSERT 안의 SELECT 부분만 가져옵니다. DELETE와 INSERT INTO 줄은 버립니다 — 테이블을 지우고 다시 만드는 건 dbt가 합니다.
  3. 테이블 이름 자리에 tmp_orders, tmp_pay 대신 앞에서 만든 모델을 {{ ref('...') }}로 씁니다. 이게 이 단계의 핵심입니다.
  4. 조건: 상태가 completed인 주문만, 날짜별로 주문 수(orders)와 매출(revenue)
프로시저 3) 블록
DELETE FROM dm.daily_sales WHERE ...;   -- 버림
INSERT INTO dm.daily_sales               -- 버림
SELECT o.order_date, COUNT(*) AS orders,
       SUM(p.amount) AS revenue
FROM tmp_orders o JOIN tmp_pay p USING (order_id)
WHERE o.status = 'completed'
GROUP BY o.order_date;
dbt 모델 (빈칸 채우기)
select
    o.order_date,
    count(*)       as orders,
    sum(p.amount)  as revenue
from {{ ref('____') }} o
join {{ ref('____') }} p using (order_id)
where o.status = 'completed'
group by o.order_date

왜 그냥 from stg_orders라고 안 쓰고 ref()를 쓰나요? 테이블 이름을 직접 써도 이번엔 돌아갑니다. 하지만 그러면 dbt는 "daily_sales가 stg_orders를 필요로 한다"는 걸 모릅니다. ref()로 써야 ① 실행 순서를 dbt가 알아서 정하고 ② 리니지 그래프에 선이 그어지고 ③ dev/prod 환경에 맞는 실제 테이블 이름으로 바꿔 줍니다.

dbt run을 다시 하는 이유: 새 파일은 run을 해야 DB에 뷰로 생깁니다. --limit 20은 12행이 다 보이게 넉넉히 준 것입니다.

where o.status = 'completed'
group by o.order_date

dbt run 출력 순서를 보세요. 파일 이름은 알파벳순으로 daily_sales가 먼저지만, dbt는 ref()를 읽고 stg 두 개를 먼저, daily_sales를 마지막에 실행합니다. 순서를 적은 적이 없는데도요.

  • 다른 모델은 언제나 ref()로 참조하고, 테이블 이름을 직접 쓰지 않습니다. 직접 쓰면 dev에서 돌려도 운영 테이블을 읽어 버리는 사고가 납니다(ref()는 target에 맞는 데이터셋 이름으로 바꿔 줌).
  • 고친 모델과 그 앞뒤만 돌릴 때는 그래프 선택자를 씁니다: dbt run -s +daily_sales(앞쪽 모델까지), dbt run -s stg_orders+(뒤쪽 모델까지).
  • 결과 확인은 dbt show로 먼저 빠르게 보고, 꼼꼼히 볼 때는 BigQuery 콘솔에서 dev 데이터셋의 테이블을 직접 조회합니다. BigQuery에서는 dbt show도 실제 쿼리라 스캔 비용이 든다는 점을 기억해 둡니다.
7. dbt가 실제로 보낸 SQL 열어 보기

모델 파일에는 {{ ref() }} 같은 Jinja가 섞여 있어서, 오류가 나면 "DB가 실제로 받은 SQL"이 무엇인지 봐야 원인을 찾을 수 있습니다. 이걸 모르면 오류 메시지의 줄 번호가 내 파일과 안 맞아서 헤매게 됩니다. 프로시저에서 동적 SQL을 PRINT로 찍어 보던 것과 같은 용도입니다.

두 폴더를 비교합니다(탐색기나 notepad target\compiled\shop\models\daily_sales.sql로 열기).

  • target/compiled/shop/models/daily_sales.sql — {{ ref() }}가 실제 테이블 이름("shop"."main"."stg_orders")으로 바뀐 SELECT
  • target/run/shop/models/daily_sales.sql — 그 SELECT를 create view ... as로 감싼, DB에 실제로 보낸 SQL

에러가 나면 이 두 파일을 열어 보는 습관을 들이세요. "내 Jinja가 어떤 SQL로 바뀌었나"가 보입니다. 컴파일만 하고 싶으면 dbt compile, 결과 미리보기는 dbt show --select daily_sales 입니다.

dbt compile --select daily_sales
조각뜻
dbt compileJinja만 풀어서 target/compiled에 SQL을 쓰고, 테이블·뷰는 만들지 않음
--select daily_sales그 모델만 컴파일. 컴파일된 SELECT가 화면에도 출력됨
  • 모델이 이상할 때 가장 흔한 디버깅: dbt compile -s 모델 → 나온 SQL을 복사 → BigQuery 콘솔에 붙여서 부분부분 돌려 봄. 콘솔에 실행 전 "이 쿼리는 몇 GB를 처리합니다"가 표시돼 비용도 미리 볼 수 있습니다.
  • VS Code의 dbt 확장 프로그램은 저장할 때마다 컴파일된 SQL을 옆 창에 보여 줘서, 이 폴더를 직접 여는 일을 줄여 줍니다.
  • target/는 매번 다시 만들어지는 결과물이라 git에 올리지 않습니다(다음 단계).
8. 결과 확인하고 하루 마무리

모델이 SQL 파일이 됐다는 건 코드처럼 이력을 남길 수 있다는 뜻입니다. 오늘 상태를 git에 한 번 저장해 두면 내일 무언가 망가져도 "어제 되던 상태"와 비교하거나 되돌릴 수 있습니다. DB 안 프로시저는 이력이 잘 안 남던 문제를 여기서 해결합니다. dbt ls는 저장 전에 "dbt가 인식하는 모델이 내가 생각한 3개가 맞나"를 확인하는 용도입니다.

dbt show --select daily_sales --limit 20
dbt ls          # 프로젝트 안 모델 목록

dbt show는 6단계와 같은 명령으로 최종 결과를 한 번 더 확인하는 것입니다. dbt ls(list)는 아무것도 실행하지 않고 프로젝트 안 노드(모델 등)를 shop.daily_sales 같은 이름으로 나열합니다. example 모델이 보이면 3단계 삭제가 안 된 것입니다.

프로젝트 폴더를 git으로 관리하기 시작합니다. target/, logs/, *.duckdb는 올리지 않습니다(dbt init이 만든 .gitignore에 앞의 둘은 이미 있습니다).

Add-Content .gitignore "*.duckdb"
git init
git add .
git commit -m "1일차: 첫 dbt 모델"
조각뜻

git init현재 폴더(shop)를 git 저장소로 만듦. 숨김 폴더 .git이 생김. 프로젝트마다 처음 한 번만

git commit -m "..."목록에 올린 것을 하나의 이력으로 저장. -m 뒤는 무엇을 했는지 적는 메시지

  • main에 바로 커밋하지 않고 작업마다 브랜치(git switch -c feature/daily-sales)를 만들어 고친 뒤, GitHub에 올려 PR(풀 리퀘스트)로 동료 리뷰를 받고 합칩니다.

  • .gitignore에는 보통 target/, logs/, dbt_packages/, .venv/가 들어가고, 키 파일·profiles.yml 같은 비밀은 절대 올리지 않습니다.
자주 막히는 곳
  • dbt : 'dbt' 용어가 ... 인식되지 않습니다 → pip install dbt-duckdb가 아직 안 됐거나 실패했습니다. (.venv)가 붙은 창에서 다시 설치하세요.
  • Error: No such command 'C:\...\dbt.exe' → 설치는 정상인데 터미널이 명령을 이상하게 넘긴 경우입니다. 창을 닫고 Windows PowerShell을 새로 열어 Activate.ps1부터 다시 하면 대개 풀립니다. 그래도 안 되면 dbt 대신 python -m dbt.cli.main을 쓰세요.
  • Could not find profile named 'shop' → profiles.yml 맨 윗줄 이름과 dbt_project.yml의 profile: 값이 다릅니다.
  • IO Error: No files found that match the pattern "data/raw_orders.csv" → dbt run을 shop 폴더 안에서 실행했는지 확인하세요. 상대 경로 기준이 현재 폴더입니다.
  • IO Error: Could not set lock on file → DuckDB 파일은 한 번에 한 프로그램만 쓸 수 있습니다. DBeaver 같은 도구로 shop.duckdb를 열어 뒀다면 닫으세요.

💡 한 줄 요약 나는 SELECT만 쓰고, dbt가 CREATE·순서·테이블 이름을 채워서 웨어하우스에 보낸다. 실제 계산은 웨어하우스가 한다.
  • ELT의 T가 dbt, "언제·순서"는 Airflow, "웨어하우스로 감당 못 할 만큼 큰 처리"는 Spark
  • 모델 = SELECT 문이 담긴 .sql 파일 하나 = 테이블이나 뷰 하나
  • ref()가 의존 관계를 만들고, dbt는 그걸로 실행 순서를 정한다
  • 안 될 땐 dbt debug, 결과 SQL이 궁금하면 target/compiled

퀴즈

ELT에서 dbt가 맡는 부분은?

  1. E — 원천 시스템에서 데이터 추출
  2. L — 웨어하우스로 적재
  3. T — 웨어하우스 안에서 SQL로 가공
  4. 세 가지 모두
dbt는 이미 웨어하우스에 들어온 데이터를 SQL로 가공하는 T만 맡습니다. 추출·적재는 Fivetran·Airbyte·직접 짠 수집 코드 등이 하고, dbt는 데이터를 옮기지 않습니다.

dbt 모델 파일 안에 보통 쓰는 것은?

  1. CREATE TABLE ... AS SELECT 전체
  2. 결과가 될 SELECT 문 하나
  3. DELETE 후 INSERT
  4. 프로시저 정의 CREATE PROCEDURE
모델에는 SELECT만 씁니다. CREATE·INSERT·MERGE 같은 감싸는 문장은 materialization 설정에 따라 dbt가 만들어 붙입니다.

dbt run이 모델 실행 순서를 정하는 근거는?

  1. 파일 이름 알파벳 순서
  2. dbt_project.yml에 사람이 적은 순서
  3. 파일을 만든 날짜
  4. 모델 안의 ref()·source()로 만들어진 의존 관계
dbt는 모든 모델의 ref()를 읽어 DAG(방향이 있고 순환이 없는 그래프)를 만들고, 그 순서대로 실행합니다. 실습 6단계에서 daily_sales가 알파벳으론 먼저지만 마지막에 실행된 이유입니다.

DB 접속 정보(profiles.yml)를 보통 프로젝트 폴더 밖(~/.dbt/)에 두는 가장 큰 이유는?

  1. 비밀번호·키 같은 비밀이 git 저장소에 올라가지 않게 하려고
  2. dbt가 프로젝트 안의 yml을 못 읽어서
  3. 속도가 빨라서
  4. DuckDB만 그렇게 해야 해서
프로젝트 코드는 git으로 팀과 공유하고, 접속 정보는 사람·서버마다 다르고 비밀이기 때문에 분리합니다. 운영 환경에서는 환경 변수(env_var())로 넣는 경우가 많습니다.

"내 {{ ref() }}가 실제 어떤 테이블 이름으로 바뀌었는지" 보려면 어디를 열어야 하나요?

  1. models/ 폴더
  2. ~/.dbt/profiles.yml
  3. target/compiled/ 폴더
  4. dbt_project.yml
target/compiled에는 Jinja가 풀린 순수 SELECT가, target/run에는 DB에 실제로 보낸 CREATE 문까지 들어 있습니다.

다음 중 dbt Core가 혼자서는 하지 않는 일은?

  1. 모델 간 의존성에 따라 순서대로 SQL 실행
  2. 매일 아침 6시에 자동으로 실행
  3. 테스트 실행
  4. 문서 사이트 생성
dbt Core에는 스케줄러가 없습니다. 정해진 시간에 돌리는 건 Airflow·cron·dbt Cloud 같은 바깥 도구의 몫입니다. 5·6일차에서 Airflow로 이걸 붙입니다.
