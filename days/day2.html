모델·ref·source·계층 — 프로젝트에 뼈대 세우기

어제 만든 모델 3개를 원본(source) → staging → intermediate → marts 네 층으로 다시 짓습니다. dbt 프로젝트가 커져도 길을 잃지 않게 해 주는 규칙들을 배웁니다.

이론 약 90분 · 실습 약 80분 · 퀴즈 8문제

오늘 마치면 할 수 있는 것
  • source()와 ref()의 차이를 말하고, 원본 경로를 sources.yml 한 곳에 모으기
  • staging · intermediate · marts 각 층이 무엇을 하고 무엇을 하면 안 되는지 설명하기
  • stg_ · int_ · fct_ · dim_ 이름 규칙과 "한 행이 무엇인가(grain)"를 모델마다 말하기
  • view · table · ephemeral · incremental 의 차이를 알고, dbt_project.yml에서 폴더별로 정하기
  • --select, +모델, 모델+, path: 로 필요한 모델만 골라 실행하기

왜 층을 나누나

어제 만든 daily_sales는 잘 돌아갑니다. 그런데 내일 누가 "고객별 매출도 보고 싶어요"라고 하면 어떻게 될까요? 아마 daily_sales를 복사해서 customer_sales를 만들고, 그 안에 또 결제 합계 로직을 넣을 겁니다. 한 달 뒤에는 "결제 합계"가 다섯 군데에 다섯 가지 모양으로 흩어져 있게 됩니다. 프로시저 시절에 겪어 본 바로 그 상황입니다.

dbt 커뮤니티는 이 문제를 층(layer)으로 풉니다. 데이터가 흐르는 방향대로 역할이 다른 폴더를 두고, 각 층에는 정해진 일만 시킵니다.

  원본(source)          staging              intermediate           marts
 ─────────────      ─────────────────     ──────────────────     ──────────────────
  raw_customers ──▶  stg_customers ─────────────────────────────▶ dim_customers
                                                                     ▲
  raw_orders    ──▶  stg_orders    ─────────────────────────┬──▶ fct_orders
                                                            │       │
  raw_payments  ──▶  stg_payments  ──▶ int_order_payments ──┘       └──▶ (dim_customers 도 참조)

  "있는 그대로"       "깨끗하게"          "조립 부품"              "사람이 보는 완성품"
  손대지 않는다       1:1, 이름·형·정제    조인·집계 중간 단계       BI·분석가가 쓰는 테이블
층하는 일하면 안 되는 일보통 materialization
source

🧸 비유

식당 주방을 떠올려 보세요.

  • source = 납품받은 식재료 상자. 흙 묻은 채로 창고에 있습니다. 상자 자체는 건드리지 않습니다.
  • staging = 손질 담당. 양파는 양파대로 씻고 껍질 벗겨 통에 담습니다. 아직 다른 재료와 섞지 않습니다. 재료 하나당 손질 통 하나.
  • intermediate = 소스·육수 같은 반조리 재료. 여러 요리에 같이 쓰입니다. 손님 앞에 그대로 나가지는 않습니다.
  • marts = 접시에 담긴 완성 요리. 손님(분석가·대시보드)이 받는 건 이것뿐입니다.

양파 껍질 벗기는 법이 바뀌면 손질 통 하나만 고치면 되고, 그 양파를 쓰는 모든 요리에 저절로 반영됩니다.

프로시저 감각으로 옮기면
  • 프로시저 안의 CREATE TEMP TABLE tmp_orders AS SELECT ... LOWER(TRIM(status)) 블록 → staging 모델. 차이는 이 정제가 프로시저마다 복사되지 않고 한 곳에만 있다는 것.
  • tmp_pay처럼 "다음 단계에서 쓰려고 미리 합쳐 두는 임시 테이블" → intermediate 모델
  • 마지막 INSERT INTO dm.xxx의 대상 테이블 → marts 모델
  • BigQuery에서 데이터셋을 raw / stg / dm으로 나눠 쓰던 습관이 있다면, 그게 이미 층 나누기입니다. dbt는 그걸 폴더와 이름 규칙으로 강제해 줄 뿐입니다.
💡 한 줄 요약 staging은 원본 하나를 깨끗하게, intermediate는 조립, marts는 완성품. 정제 로직은 staging 한 곳에만 둔다.

source() — 원본에 이름표 붙이기

어제는 모델 안에 read_csv('data/raw_orders.csv')를 직접 썼습니다. 이렇게 원본 위치를 모델마다 하드코딩하면 세 가지 문제가 생깁니다.

  1. 원본 위치가 바뀌면(파일 → BigQuery 테이블, 데이터셋 이름 변경) 그 원본을 읽는 모든 모델을 찾아 고쳐야 합니다.
  2. dbt는 그 문자열이 "원본"이라는 걸 모릅니다. 그래서 리니지 그래프에 원본이 나타나지 않고, 원본에 테스트나 신선도 검사(3일차)를 붙일 수도 없습니다.
  3. 어떤 원본을 쓰고 있는지 목록이 어디에도 없습니다.

source()는 이 문제를 YAML에 원본 목록을 한 번 적고, 모델에서는 이름으로만 부르는 방식으로 풉니다.

1일차: 위치를 직접 적는다
select ...
from read_csv('data/raw_orders.csv')
2일차: 이름으로 부른다
select ...
from {{ source('shop_raw', 'raw_orders') }}

source('묶음 이름', '테이블 이름') 두 인자를 받습니다. 묶음(source)은 보통 "어디서 온 데이터인가" 단위입니다 — 쇼핑몰 DB, GA4, 광고 API 처럼요. 실제 위치는 sources.yml에 적습니다.

sources:
  - name: shop_raw                 # source('shop_raw', ...) 의 첫 번째 인자
    meta:
      external_location: "read_csv('data/{name}.csv', header = true)"
    tables:
      - name: raw_customers        # 두 번째 인자
      - name: raw_orders
      - name: raw_payments

external_location은 dbt-duckdb 전용 설정입니다. "이 source는 DB 안 테이블이 아니라 바깥 파일이다, 읽을 때는 이 표현식을 써라"는 뜻이고, {name} 자리에 테이블 이름이 들어갑니다. 그래서 source('shop_raw', 'raw_orders')는 컴파일하면 이렇게 바뀝니다(실제로 확인한 결과).

from read_csv('data/raw_orders.csv', header = true)
BigQuery에서는 이렇게 씁니다

회사·OKR 프로젝트(BigQuery)에서는 원본이 이미 테이블이므로 external_location 대신 프로젝트·데이터셋을 적습니다. 모델 코드는 한 글자도 바뀌지 않습니다 — 이게 source를 쓰는 이유입니다.

sources:
  - name: shop_raw
    database: my-gcp-project   # BigQuery 프로젝트
    schema: raw                # 데이터셋
    tables:
      - name: raw_orders       # → `my-gcp-project`.`raw`.`raw_orders`
source('묶음', '테이블')ref('모델')
가리키는 것dbt 바깥에서 만들어진 원본dbt 안에서 만든 모델
정의하는 곳sources.yml 같은 YAMLmodels/ 안의 .sql 파일 이름
dbt가 만드나?아니오, 읽기만예, dbt run 때 만든다
쓰는 곳원칙적으로 staging 모델에서만staging 이후 모든 층
🧸 비유

source()는 회사 주소록입니다. "김 대리에게 전화해"라고 말하면 되지, 매번 전화번호를 외워서 누르지 않습니다. 김 대리 번호가 바뀌면 주소록 한 줄만 고칩니다. sources.yml이 그 주소록입니다.

프로시저 감각으로 옮기면

프로시저 안의 FROM raw.orders를 FROM {{ source('shop_raw', 'raw_orders') }}로 바꾼다고 생각하면 됩니다. 원본 데이터셋 이름이 raw에서 raw_v2로 바뀌는 날, 프로시저 세계에서는 grep으로 전부 찾아 고치지만, dbt에서는 sources.yml의 schema: 한 줄만 고칩니다.

ref()와 DAG

모델끼리는 ref()로 연결합니다. dbt는 프로젝트의 모든 ref()와 source()를 읽어 DAG를 만듭니다.

DAG(Directed Acyclic Graph, 방향 있는 비순환 그래프)는 이름이 어렵지만 뜻은 간단합니다.

  • Directed(방향): 화살표에 방향이 있다. stg_orders → fct_orders는 "fct_orders가 stg_orders를 쓴다"는 뜻이고, 반대는 아니다.
  • Acyclic(순환 없음): 화살표를 따라가다 출발점으로 돌아오는 길이 없다. A가 B를 쓰고 B가 A를 쓰면 무엇을 먼저 만들지 정할 수 없기 때문.
  • Graph(그래프): 점(모델)과 선(의존 관계)의 모음.

DAG가 있으면 dbt는 두 가지를 스스로 정합니다.

  1. 실행 순서: 화살표가 들어오는 쪽을 먼저. stg_* → int_* → fct_orders → dim_customers
  2. 동시 실행: 서로 의존하지 않는 모델은 같이 돌립니다. profiles.yml의 threads: 4가 "최대 4개 동시"라는 뜻입니다. 오늘 실습 로그에서 stg 세 개가 같은 초에 START 되는 걸 보게 됩니다.
오늘 완성할 shop 프로젝트의 DAG

 [source]                 [staging]              [intermediate]          [marts]

 shop_raw.raw_customers ─▶ stg_customers ───────────────────────────────▶ dim_customers
                                                                              ▲
 shop_raw.raw_orders ────▶ stg_orders ─────────────────────────┐              │
                                                               ├─▶ fct_orders ┘
 shop_raw.raw_payments ──▶ stg_payments ──▶ int_order_payments ┘

 실행 순서:  ① stg 3개 동시  →  ② fct_orders (int 는 ephemeral 이라 안에 녹아 들어감)  →  ③ dim_customers

순환을 만들면 dbt는 아예 실행하지 않고 멈춥니다. 실제로 stg_orders에 ref('fct_orders')를 넣어 보면 이렇게 나옵니다.

Compilation Error
  Found a cycle: model.shop.stg_orders --> model.shop.fct_orders
주석 안의 ref도 진짜 ref입니다

위 순환 에러는 -- {{ ref('fct_orders') }}처럼 SQL 주석 안에 적었을 때도 똑같이 납니다. Jinja({{ }})는 SQL보다 먼저 처리되기 때문에, SQL 입장에서 주석이어도 Jinja는 그 안을 읽고 의존 관계를 만듭니다. 잠시 막아 두고 싶다면 Jinja 주석 {# ... #}을 쓰세요.

🧸 비유

DAG는 요리 순서도입니다. "소스를 만들려면 양파 손질이 먼저", "파스타를 담으려면 소스가 먼저". 순서도가 있으면 주방장이 없어도 보조 요리사 넷(threads 4)이 각자 할 수 있는 일부터 동시에 시작합니다. 그런데 "소스를 만들려면 파스타가 먼저, 파스타를 만들려면 소스가 먼저"라고 적혀 있으면 아무도 시작할 수 없습니다 — 그게 순환입니다.

프로시저 감각으로 옮기면

프로시저 세계에서는 "A 프로시저 끝나면 B, B 끝나면 C"를 스케줄러(또는 마스터 프로시저)에 사람이 적었습니다. 새 테이블이 생길 때마다 그 순서표도 손으로 고쳐야 했죠. dbt에서는 SQL 안의 ref()가 곧 순서표입니다. 순서표와 코드가 따로 놀 수가 없습니다.

이름 규칙과 grain

dbt에서 모델 파일 이름은 곧 테이블 이름입니다. 그래서 이름만 보고도 "어느 층인지, 한 행이 무엇인지" 알 수 있게 접두어를 붙입니다. dbt Labs가 권장하고 대부분 팀이 따르는 규칙입니다.

접두어층뜻오늘 만들 것한 행(grain)
stg_staging원본 하나를 깨끗하게 한 것stg_customers, stg_orders, stg_payments원본과 같음 (고객 1명 / 주문 1건 / 결제 1건)
int_intermediate조립 중간 단계. 이름에 동사·목적을 담는다int_order_payments주문 1건 (결제를 주문 단위로 합침)
fct_marts사실(fact): 일어난 일·사건. 행이 계속 쌓인다. 숫자(금액·건수)가 많다fct_orders주문 1건
dim_marts차원(dimension): 사람·상품·매장 같은 대상. 사실을 "누가/무엇을" 로 잘라 보는 기준dim_customers고객 1명

grain(그레인) — 모델마다 꼭 한 줄로 말할 수 있어야 하는 것

grain은 "이 테이블의 한 행이 무엇을 뜻하는가"입니다. 오늘 리팩터링에서 가장 중요한 결정이 여기서 나옵니다.

어제 stg_payments는 group by order_id로 주문 단위로 합친 모델이었습니다. 그런데 원본 raw_payments의 한 행은 결제 1건이고, 주문 5번과 18번은 카드 + 포인트 10,000원으로 나눠 낸 분할 결제입니다. staging은 원본과 grain이 같아야 하므로, 오늘 stg_payments는 결제 1건 = 1행으로 되돌리고, 합치는 일은 int_order_payments로 옮깁니다.

raw_payments (결제 1건 = 1행, 32행)          int_order_payments (주문 1건 = 1행, 30행)
┌────────────┬──────────┬────────┬───────┐     ┌──────────┬──────────────┬───────────────┐
│ payment_id │ order_id │ method │ amount│     │ order_id │ total_amount │ payment_count │
├────────────┼──────────┼────────┼───────┤     ├──────────┼──────────────┼───────────────┤
│     5      │    5     │ card   │ 49000 │ ──▶ │    5     │    59000     │       2       │
│     6      │    5     │ point  │ 10000 │     │    ...   │     ...      │      ...      │
└────────────┴──────────┴────────┴───────┘     └──────────┴──────────────┴───────────────┘

왜 이게 중요할까요? 나중에 누군가 "결제수단별 매출"을 보고 싶어 하면, 어제의 stg_payments에서는 이미 결제수단 정보가 합쳐져 사라졌습니다. staging에서 정보를 버리면 그 아래 층은 영영 되살릴 수 없습니다. 4일차에 결제수단 pivot 매크로를 만들 때 바로 이 stg_payments를 씁니다.

이름 규칙 조금 더
  • dbt Labs 가이드는 staging에 stg_<원본묶음>__<테이블>(밑줄 두 개)을 권합니다. 예: stg_shop__orders. 원본 묶음이 여러 개인 큰 프로젝트에서 유용합니다. 이번 실습은 묶음이 하나라 stg_orders로 짧게 씁니다.
  • 컬럼 이름도 규칙을 정해 두면 좋습니다. 기본 키·외래 키는 <대상>_id, 시각은 _at(updated_at), 날짜는 _date, 참·거짓은 is_/has_, 금액은 단위를 정해 두기(여기선 원).
  • staging에서 원본의 애매한 이름을 고칩니다. 오늘 name → customer_name, method → payment_method로 바꿉니다. 여러 테이블을 조인했을 때 name이 어느 테이블의 이름인지 헷갈리지 않게요.
프로시저 감각으로 옮기면

BigQuery 마트를 만들 때 "이 테이블 PK가 뭐지?"를 늘 확인하셨을 겁니다. grain은 그 질문을 모델마다 미리 문서로 답해 두는 것입니다. 조인 후 행 수가 갑자기 늘었다면(팬아웃) 거의 항상 grain이 다른 두 테이블을 그냥 붙였기 때문입니다. 3일차에 unique 테스트로 이걸 자동으로 잡습니다.

💡 한 줄 요약 모델 이름은 층(접두어) + 대상, 그리고 모델마다 “한 행 = ○○ 1개”를 말할 수 있어야 한다. staging은 원본과 grain이 같다.

materialization — 결과를 어떤 모양으로 남길까

모델에는 SELECT만 씁니다. 그 SELECT를 DB에 무엇으로 만들지(뷰? 테이블? 아무것도 안 남기기?)를 정하는 설정이 materialization입니다. SELECT는 그대로 두고 설정 한 줄만 바꾸면 dbt가 감싸는 SQL을 바꿔 줍니다.

종류dbt가 DB에 보내는 것장점단점어울리는 곳
view (기본값)create view ... as select ...저장 공간 0, 만드는 데 1초. 항상 최신읽을 때마다 SELECT를 다시 계산 → 무거운 로직이면 느림staging
table임시 테이블로 create table as 후 이름 바꿔치기읽기 빠름. BI가 바로 붙기 좋음매번 전체를 다시 만듦. 원본이 바뀌어도 다시 돌리기 전엔 옛날 값marts
ephemeral아무것도 안 만든다. 이 모델을 ref()한 쪽 SQL에 with __dbt__cte__이름 as (...)로 끼워 넣음DB에 쓸데없는 객체가 안 생김DB에서 직접 조회 불가. 여러 곳에서 쓰면 그만큼 반복 계산. 디버깅이 조금 불편가벼운 intermediate
incremental처음엔 table, 다음부터는 새로 생긴·바뀐 행만 merge/insert큰 테이블을 빨리 갱신설계가 까다로움(어떤 행이 "새것"인가). 가끔 --full-refresh 필요큰 fct — 4일차

ephemeral이 실제로 어떻게 되는지는 오늘 실습에서 직접 봅니다. int_order_payments를 ephemeral로 두면, fct_orders의 컴파일 결과 맨 위에 이런 CTE가 붙습니다(실제 결과).

with __dbt__cte__int_order_payments as (
select
    order_id,
    sum(amount)  as total_amount,
    count(*)     as payment_count
from "shop"."main"."stg_payments"
group by order_id
) select
    o.order_id,
    ...
from "shop"."main"."stg_orders" o
left join __dbt__cte__int_order_payments p
    on o.order_id = p.order_id
🧸 비유
  • view = 레시피 카드만 붙여 둔 것. 누가 달라고 할 때마다 그 자리에서 만듭니다. 늘 신선하지만 손님이 기다립니다.
  • table = 미리 만들어 냉장고에 넣어 둔 요리. 바로 꺼내 주지만, 아침에 만든 거라 점심 재료 변화는 반영 안 됩니다.
  • ephemeral = 따로 그릇에 담지 않고 요리하면서 바로 냄비에 넣는 밑준비. 냉장고(DB)에는 남지 않습니다.
  • incremental = 어제 만든 큰 솥 요리에 오늘 들어온 재료만 더 넣어 끓이기.
프로시저 감각으로 옮기면
  • view → CREATE OR REPLACE VIEW
  • table → CREATE OR REPLACE TABLE ... AS SELECT (dbt는 안전하게 임시 이름으로 먼저 만들고 바꿔치기)
  • ephemeral → 프로시저 안의 WITH 절. 혹은 세션이 끝나면 사라지는 TEMP TABLE에 가깝지만, 실제로는 테이블조차 만들지 않음
  • incremental → DELETE + INSERT 또는 MERGE로 그날 것만 갈아 끼우던 프로시저. 1일차 맨 위 sp_build_daily_sales가 바로 이 패턴입니다.

어디에 설정하나 — 세 군데, 가까운 쪽이 이긴다

materialization 같은 설정은 세 곳에 쓸 수 있고, 모델에 가까울수록 우선합니다.

  약함 ◀──────────────────────────────────────────────────────▶ 강함

  ① dbt_project.yml          ② 모델 YAML (schema.yml)        ③ 모델 파일 맨 위
  폴더 단위 기본값             config: 블록                     {{ config(materialized='table') }}
  models:
    shop:
      marts:
        +materialized: table

실무에서는 ①로 폴더마다 기본값을 정하고, 예외만 ③으로 덮어씁니다. 실제로 dim_customers.sql 맨 위에 {{ config(materialized='view') }}를 넣으면 marts 폴더 기본값(table)을 무시하고 view가 됩니다.

models:
  shop:                     # 프로젝트 이름 (name: 'shop')
    staging:                # models/staging/ 폴더
      +materialized: view
    intermediate:           # models/intermediate/ 폴더
      +materialized: ephemeral
    marts:                  # models/marts/ 폴더
      +materialized: table
왜 앞에 + 를 붙이나

dbt_project.yml의 models: 아래에서는 "폴더 이름"과 "설정 이름"이 같은 들여쓰기에 섞여 나옵니다. 만약 폴더 이름이 우연히 materialized라면 dbt가 헷갈리겠죠. +는 "이건 폴더가 아니라 설정이고, 이 아래 모든 모델에 적용해"라는 표시입니다. 설정 앞에는 항상 +를 붙이는 습관을 들이세요.

"unused configuration paths" 경고

1일차 dbt run 때 이런 경고를 보셨을 겁니다: Configuration paths exist in your dbt_project.yml file which do not apply to any resources. - models.shop.example. example 폴더를 지웠는데 설정은 남아 있어서입니다. 오늘 models: 블록을 바꾸면 사라집니다. 폴더 이름을 잘못 적었을 때도 같은 경고가 나오므로, 이 경고는 무시하지 말고 꼭 읽으세요.

💡 한 줄 요약 SELECT는 그대로, 만드는 방식만 설정으로 바꾼다. staging=view, intermediate=ephemeral, marts=table을 dbt_project.yml에 폴더별로 적는다.

선택자 기초 — 필요한 것만 돌리기

모델이 수백 개가 되면 매번 전부 돌릴 수 없습니다. "방금 고친 모델과 그 아래만", "이 마트를 만드는 데 필요한 것만" 같은 선택이 필요합니다. dbt run, dbt ls, dbt test, dbt build 모두 --select(줄여서 -s)를 받습니다.

쓰는 법뜻shop에서 실제로 고른 것 (dbt ls 결과)
-s fct_orders그 모델 하나fct_orders
-s +fct_orders그 모델 + 위쪽(부모·조상) 전부fct_orders, int_order_payments, stg_orders, stg_payments, source 2개
-s stg_orders+그 모델 + 아래쪽(자식·자손) 전부stg_orders, fct_orders, dim_customers
-s 1+dim_customers위쪽으로 한 단계만dim_customers, fct_orders, stg_customers
-s path:models/staging폴더 안 전부stg 3개 + 그 폴더 sources.yml의 source 3개
-s config.materialized:table설정값으로 고르기fct_orders, dim_customers
-s stg_orders stg_payments띄어쓰기 = 합집합(또는)둘 다
-s "+fct_orders,path:models/staging"쉼표 = 교집합(그리고)fct_orders 조상 중 staging 폴더에 있는 것
--exclude dim_customers빼기나머지 전부
🧸 비유

가계도를 떠올리면 쉽습니다. +나는 "나와 부모·조부모…", 나+는 "나와 자식·손자…". +가 어느 쪽에 붙었는지가 방향입니다. 기호가 이름 앞이면 위(과거, 재료 쪽), 뒤면 아래(미래, 완성품 쪽).

프로시저 감각으로 옮기면

"stg_orders 정제 규칙을 고쳤으니 이걸 쓰는 마트를 다 다시 돌려야 하는데, 뭐가 이걸 쓰지?" — 프로시저 세계에서는 코드 검색으로 찾던 질문입니다. dbt에서는 dbt run -s stg_orders+ 한 줄이 답입니다. 반대로 "이 마트 숫자가 이상한데 재료부터 다시 만들어 보자"는 dbt run -s +fct_orders.

실행 전에 dbt ls 로 먼저 확인

선택자가 헷갈리면 dbt run 대신 dbt ls -s ...를 먼저 쳐 보세요. 아무것도 실행하지 않고 "무엇이 골라지는지"만 보여 줍니다. 6일차에 Airflow에서 계층별로 나눠 돌릴 때, 그리고 CI에서 바뀐 모델만 돌리는 state:modified+를 배울 때 이 문법을 그대로 씁니다.

실습: shop 프로젝트를 층으로 다시 짓기

어제의 $HOME\dbt-practice\shop에서 이어갑니다. 끝나면 모델 6개(stg 3 · int 1 · fct 1 · dim 1)와 source 3개가 있는 프로젝트가 됩니다.

오늘 끝난 뒤 폴더 모양

shop/
├── dbt_project.yml          ← models: 아래 폴더별 materialization
├── data/                    ← raw_*.csv 3개 (어제 그대로)
└── models/
    ├── staging/
    │   ├── sources.yml      ← 원본 주소록
    │   ├── stg_customers.sql
    │   ├── stg_orders.sql
    │   └── stg_payments.sql ← grain: 결제 1건 (어제와 달라짐!)
    ├── intermediate/
    │   └── int_order_payments.sql
    └── marts/
        ├── fct_orders.sql
        └── dim_customers.sql
                             ← daily_sales.sql 은 지운다
1. 출발점 확인
cd $HOME\dbt-practice
.\.venv\Scripts\Activate.ps1
cd shop
dbt run

어제처럼 PASS=3이 나오면 출발 준비 완료입니다. 혹시 어제 커밋을 안 했다면 지금 해 두세요 — 오늘 파일을 많이 옮기기 때문에 돌아갈 지점이 있어야 합니다.

2. 층별 폴더 만들고 파일 옮기기
mkdir models\staging, models\intermediate, models\marts
Move-Item models\stg_orders.sql   models\staging\
Move-Item models\stg_payments.sql models\staging\
Remove-Item models\daily_sales.sql
Get-ChildItem -Recurse models

daily_sales는 왜 지울까요? "완료 주문의 날짜별 매출"은 오늘 만들 fct_orders에서 group by 한 번이면 나옵니다(8단계에서 확인). 집계 결과를 미리 마트로 만들어 두는 건 실제로 자주 쓰는 사람이 생겼을 때 하면 됩니다.

3. sources.yml 만들기

models/staging/sources.yml을 새로 만듭니다. 설정 파일이라 그대로 보여드립니다.

sources:
  - name: shop_raw
    meta:
      external_location: "read_csv('data/{name}.csv', header = true)"
    tables:
      - name: raw_customers
      - name: raw_orders
      - name: raw_payments

YAML은 들여쓰기(공백 2칸)가 문법입니다. 탭 문자를 쓰면 에러가 납니다. 확인: dbt ls --resource-type source 를 치면 source:shop.shop_raw.raw_customers 등 3줄이 나와야 합니다.

4. 직접 해보기: staging 3개를 source()로

세 모델을 만들거나 고칩니다. 규칙: 원본 하나당 모델 하나, 조인·집계·필터 없음, grain은 원본과 같게.

  • stg_orders.sql — read_csv(...)를 source()로 바꾸고, updated_at을 timestamp로 추가 (3일차 신선도 검사에 씁니다)
  • stg_payments.sql — group by를 없애고 결제 1건 = 1행으로. payment_id, order_id, method→payment_method, amount
  • stg_customers.sql (새로) — customer_id, name→customer_name, email, city, membership, updated_at(timestamp)
힌트 1

from {{ source('shop_raw', 'raw_orders') }} 처럼 첫 인자는 sources.yml의 name, 둘째 인자는 tables: 아래 name입니다.

힌트 2

이름 바꾸기는 method as payment_method, 형 변환은 cast(updated_at as timestamp) as updated_at. 어제 있던 sum(amount)와 group by는 5단계의 int_order_payments로 이사 갑니다.

정답 보기 
select
    order_id,
    customer_id,
    cast(order_date as date)      as order_date,
    lower(trim(status))           as status,
    cast(updated_at as timestamp) as updated_at
from {{ source('shop_raw', 'raw_orders') }}
select
    payment_id,
    order_id,
    method  as payment_method,
    amount
from {{ source('shop_raw', 'raw_payments') }}
select
    customer_id,
    name                          as customer_name,
    email,
    city,
    membership,
    cast(updated_at as timestamp) as updated_at
from {{ source('shop_raw', 'raw_customers') }}
5. 직접 해보기: int_order_payments

models/intermediate/int_order_payments.sql을 만듭니다. stg_payments를 주문 단위로 합쳐 order_id, total_amount(결제 금액 합계), payment_count(결제 건수)를 내는 모델입니다. 합계 컬럼 이름을 amount 그대로 두지 않고 total_amount로 바꾸는 건, "결제 1건 금액"과 "주문의 합계"를 이름만 보고 구분하기 위해서입니다. grain: 주문 1건 = 1행.

힌트 1

이제 원본이 아니라 모델을 읽으므로 source()가 아니라 ref()입니다.

힌트 2

결제 건수는 count(*). 분할 결제인 주문 5, 18번은 2가 나와야 합니다.

정답 보기 
select
    order_id,
    sum(amount)  as total_amount,
    count(*)     as payment_count
from {{ ref('stg_payments') }}
group by order_id
6. 직접 해보기: fct_orders 와 dim_customers
  • models/marts/fct_orders.sql — 주문 1건 = 1행. stg_orders에 int_order_payments를 붙여 order_id, customer_id, order_date, status, total_amount, updated_at. 결제가 없는 주문이 생겨도 주문은 빠지지 않게(그때 금액은 0). updated_at은 4일차 incremental에서 "바뀐 주문"을 고르는 기준으로 씁니다.
  • models/marts/dim_customers.sql — 고객 1명 = 1행. stg_customers의 customer_id, customer_name, city, membership에 주문 요약 first_order_date, last_order_date, order_count, lifetime_value(completed 주문 금액 합)를 붙입니다. 주문이 없는 고객도 남겨야 합니다.
힌트 1

"빠지지 않게" = left join. 비어 있는 숫자는 coalesce(값, 0).

힌트 2

dim_customers는 fct_orders를 ref()해서 고객별로 먼저 집계(CTE)한 뒤 stg_customers에 left join 하면 깔끔합니다. completed만 더할 때는 sum(case when status = 'completed' then total_amount else 0 end).

정답 보기 
select
    o.order_id,
    o.customer_id,
    o.order_date,
    o.status,
    coalesce(p.total_amount, 0) as total_amount,
    o.updated_at
from {{ ref('stg_orders') }} o
left join {{ ref('int_order_payments') }} p
    on o.order_id = p.order_id
with orders as (
    select
        customer_id,
        min(order_date)                                   as first_order_date,
        max(order_date)                                   as last_order_date,
        count(*)                                          as order_count,
        sum(case when status = 'completed' then total_amount else 0 end) as lifetime_value
    from {{ ref('fct_orders') }}
    group by customer_id
)

select
    c.customer_id,
    c.customer_name,
    c.city,
    c.membership,
    o.first_order_date,
    o.last_order_date,
    coalesce(o.order_count, 0)    as order_count,
    coalesce(o.lifetime_value, 0) as lifetime_value
from {{ ref('stg_customers') }} c
left join orders o
    on c.customer_id = o.customer_id

dbt_project.yml 맨 아래의 models: 블록(예제용 example:이 들어 있는 부분)을 통째로 아래로 바꿉니다.

models:

9. 남아 있는 옛 뷰 치우기

DB 안에 무엇이 있는지 봅니다.

dbt show --inline "select table_name, table_type from information_schema.tables order by 1" --limit 20
| table_name    | table_type |
| daily_sales   | VIEW       |   ← 파일은 지웠는데 아직 있다!
| dim_customers | BASE TABLE |
| fct_orders    | BASE TABLE |
| stg_customers | VIEW       |
| stg_orders    | VIEW       |
| stg_payments  | VIEW       |

dbt는 모델 파일을 지워도 DB 객체를 지우지 않습니다. dbt가 아는 건 "지금 있는 파일"뿐이라서, 예전에 만든 것을 누가 쓰고 있는지 알 수 없기 때문입니다. 직접 지웁니다(dbt-duckdb와 함께 설치된 duckdb 파이썬 패키지 사용).

# duckdb 파일에 접속해서(= DBeaver에서 연결 열기) DROP VIEW 한 줄 실행

정리

💡 한 줄 요약 원본은 source()로 이름 붙이고, 모델은 ref()로 잇고, 층마다 할 일과 materialization을 정해 두면, 프로젝트가 커져도 순서·영향 범위를 dbt가 알아서 계산한다.
  • source = dbt 밖에서 온 원본(읽기만), ref = dbt가 만든 모델. source는 staging에서만 쓴다
  • staging: 원본 1:1, 정제만 / intermediate: 조립 / marts: fct(사건)·dim(대상)
  • 모델마다 grain(한 행 = 무엇)을 말할 수 있어야 한다. staging에서 정보를 버리지 않는다
  • view·table·ephemeral·incremental — 폴더 기본값은 dbt_project.yml의 +materialized, 예외는 파일 안 config()
  • +모델은 위(재료)쪽, 모델+는 아래(완성품)쪽. 헷갈리면 dbt ls로 먼저 확인
  • dbt는 지운 모델의 DB 객체를 치우지 않는다

퀴즈

source()와 ref()에 대한 설명으로 옳은 것은?

  1. 둘은 같은 기능이고 이름만 다르다
  2. source()는 dbt 밖에서 만들어진 원본을, ref()는 dbt가 만든 모델을 가리킨다
  3. source()를 쓰면 dbt가 원본 테이블을 새로 만든다
  4. ref()는 YAML에, source()는 SQL 파일 이름으로 정의된다
source는 수집 도구 등이 넣어 둔 원본을 YAML에 등록해 이름으로 부르는 것이고, dbt는 읽기만 합니다. ref는 models/ 안의 다른 모델 파일을 가리키며 dbt가 직접 만듭니다. 4번은 정의 위치를 거꾸로 적었습니다.

staging 모델에서 하기에 알맞지 않은 일은?

  1. method 컬럼 이름을 payment_method로 바꾸기
  2. updated_at을 timestamp로 형 변환하기
  3. lower(trim(status))로 값 정리하기
  4. where status = 'completed'로 완료 주문만 남기기
staging은 원본과 grain이 같아야 하고, 이름·형·값 정리만 합니다. "완료 주문만"은 비즈니스 규칙이라 marts(또는 분석 쿼리)에서 합니다. staging에서 걸러 버리면 반품·배송 중 주문을 봐야 하는 다른 마트가 그 행을 되살릴 수 없습니다.

int_order_payments를 ephemeral로 설정하고 dbt run을 하면?

  1. DB에 아무 객체도 생기지 않고, 이를 ref()한 fct_orders의 SQL 안에 CTE로 들어간다
  2. 세션이 끝나면 사라지는 임시 테이블이 DB에 생긴다
  3. view가 만들어진다
  4. 에러가 난다 — intermediate는 table이어야 한다
ephemeral은 아무것도 만들지 않습니다. 실습에서 모델은 6개인데 실행은 5개였고, fct_orders 컴파일 결과 맨 위에 with __dbt__cte__int_order_payments as (...)가 붙었습니다. 임시 테이블조차 없다는 점이 프로시저의 TEMP TABLE과 다릅니다.

stg_orders의 정제 규칙을 고쳤습니다. 이 변경의 영향을 받는 모델만 다시 만들려면?

  1. dbt run -s +stg_orders
  2. dbt run -s path:models/staging
  3. dbt run -s stg_orders+
  4. dbt run --exclude stg_orders
+가 이름 뒤에 붙으면 아래쪽(자손)입니다. stg_orders+ = stg_orders, fct_orders, dim_customers. 1번은 위쪽(재료 쪽)이라 stg_orders와 그 source만 고르고, 2번은 staging 모델만 돌려 marts가 옛 값으로 남습니다.

dbt_project.yml에서 marts: +materialized: table로 정했는데, dim_customers.sql 맨 위에 {{ config(materialized='view') }}가 있다면?

  1. 충돌이라 에러가 난다
  2. dbt_project.yml이 이겨서 table이 된다
  3. 모델 파일 안 설정이 이겨서 view가 된다
  4. table과 view가 둘 다 만들어진다
설정은 모델에 가까울수록 우선합니다: dbt_project.yml(폴더 기본값) < 모델 YAML config: < 파일 안 config(). 실제로 넣어 보면 dbt ls -s config.materialized:view에 dim_customers가 나옵니다.

"이 테이블의 한 행이 무엇을 뜻하는가"를 가리키는 말은?

  1. grain
  2. materialization
  3. lineage
  4. source
grain입니다. stg_payments는 결제 1건, int_order_payments와 fct_orders는 주문 1건, dim_customers는 고객 1명. grain이 다른 테이블을 그냥 조인하면 행이 불어나는(팬아웃) 사고가 납니다. lineage는 모델 간 연결(계보), materialization은 만드는 방식입니다.

모델 파일 daily_sales.sql을 지우고 dbt run을 했습니다. DB 안의 daily_sales 뷰는?

  1. dbt가 자동으로 지운다
  2. dbt가 빈 뷰로 바꾼다
  3. dbt run이 에러를 낸다
  4. 그대로 남아 있다 — 직접 지워야 한다
dbt는 현재 있는 파일만 알고, 예전에 만든 객체를 누가 쓰는지 모르기 때문에 지우지 않습니다. 실습 9단계에서 information_schema.tables에 daily_sales가 남아 있는 걸 확인하고 직접 DROP 했습니다.

dbt_project.yml의 models: 아래 설정 이름 앞에 +를 붙이는 이유는?

  1. 설정을 더 강하게(우선순위 높게) 만들기 위해
  2. 폴더 이름과 설정 이름을 구분해, 그 아래 모든 모델에 적용되는 설정임을 표시하려고
  3. YAML 문법상 반드시 필요해서
  4. table materialization에만 붙인다
models: 아래에는 폴더 이름과 설정 이름이 같은 들여쓰기에 섞입니다. +는 "이건 폴더가 아니라 설정"이라는 표시입니다. 우선순위를 바꾸지는 않으며(1번), YAML 문법이 아니라 dbt의 약속입니다(3번).
