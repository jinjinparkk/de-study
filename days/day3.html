dbt 테스트는 무엇인가

프로시저로 마트를 만들 때도 검증은 했습니다. 보통 이런 식이죠.

-- PK 중복 없나?
SELECT order_id, COUNT(*) FROM dm.fct_orders GROUP BY 1 HAVING COUNT(*) > 1;
-- 상태값 이상한 거 없나?
SELECT DISTINCT status FROM dm.fct_orders;
-- 원본 결제 총액이랑 맞나?
SELECT (SELECT SUM(amount) FROM raw.payments), (SELECT SUM(total_amount) FROM dm.fct_orders);

문제는 이 쿼리들이 누군가의 메모장에 있고, 생각날 때만 돌린다는 점입니다. dbt 테스트는 이 검증 쿼리를 프로젝트 안에 넣고, 모델을 만들 때마다 자동으로 돌립니다.

dbt 테스트의 규칙은 딱 하나입니다.

💡 한 줄 요약 dbt 테스트 = "문제가 되는 행"을 찾는 SELECT. 결과가 0행이면 통과, 1행이라도 나오면 실패(또는 경고).

예를 들어 YAML에 unique 한 줄을 적으면, dbt는 이런 SQL을 만들어 돌립니다(실제 컴파일 결과).

select
    order_id as unique_field,
    count(*) as n_records
from "shop"."main"."stg_payments"
where order_id is not null
group by order_id
having count(*) > 1

위 프로시저 시절의 첫 번째 쿼리와 똑같습니다. 다른 점은 내가 이 SQL을 쓰지 않아도 된다는 것, 그리고 매번 돌아간다는 것뿐입니다.

🧸 비유

공장 출고 검사대를 떠올려 보세요. 검사원은 "괜찮은 제품"을 세지 않습니다. 불량품만 골라냅니다. 골라낸 불량품 바구니가 비어 있으면 출고 OK. dbt 테스트도 "불량 행"만 골라내는 SELECT이고, 바구니가 비면(0행) 통과입니다.

singular (단일)tests/ 폴더에 .sql 파일로 직접 쓴다이 프로젝트에만 있는 업무 규칙("포인트 단독 결제 금지" 등)
unit test (참고)YAML에 가짜 입력·기대 결과를 적는다 (1.8+)복잡한 SQL 로직을 실제 데이터 없이 검증. 이번 과정에선 개념만
프로시저 감각으로 옮기면

프로시저 끝에 IF (SELECT COUNT(*) FROM ... 중복 ...) > 0 THEN RAISE ...를 넣어 본 적이 있다면, 그게 바로 dbt 테스트입니다. dbt는 그 검사를 모델과 분리해서 선언하고, 결과를 모아서 "28개 중 27개 통과, 1개 경고"처럼 보여 줍니다.

기본 테스트 4종

dbt에 처음부터 들어 있는 generic 테스트는 네 개입니다. 이 네 개만 잘 걸어도 사고의 대부분을 막습니다.

테스트검사하는 것실패 = 이런 행이 있다shop에서 걸 곳
unique값이 겹치지 않는가같은 값이 2번 이상 나오는 값모든 모델의 기본 키(grain 검사)
not_null비어 있지 않은가NULL인 행기본 키, 꼭 있어야 하는 외래 키
accepted_values정해진 값 목록 안에 있는가목록 밖의 값status, payment_method, membership
relationships다른 테이블에 짝이 있는가 (참조 무결성)부모 테이블에 없는 값stg_orders.customer_id → stg_customers

YAML에는 이렇게 적습니다. 모델 SQL 파일과 같은 폴더의 schema.yml에 둡니다(파일 이름은 자유, .yml이면 dbt가 다 읽습니다).

models:
  - name: stg_orders                 # 모델 이름 (= 파일 이름)
    columns:
      - name: order_id
        data_tests:                  # 이 컬럼에 거는 테스트 목록
          - unique                   # 인자 없는 테스트는 이름만
          - not_null
      - name: status
        data_tests:
          - accepted_values:
              arguments:             # 인자 있는 테스트는 arguments: 아래에
                values: ['placed', 'shipped', 'completed', 'returned']
      - name: customer_id
        data_tests:
          - relationships:
              arguments:
                to: ref('stg_customers')   # 부모 모델
                field: customer_id         # 부모 쪽 컬럼
버전 차이: tests → data_tests, 그리고 arguments

인터넷 예제는 대부분 옛 문법입니다. 셋 다 지금도 돌아가지만, 새로 쓸 때는 오른쪽처럼 씁니다.

옛 문법 (~1.7 / ~1.9)
tests:
  - accepted_values:
      values: ['placed', 'shipped']
지금 (1.10+)
data_tests:
  - accepted_values:
      arguments:
        values: ['placed', 'shipped']
  • tests: → data_tests: (1.8): unit test가 생기면서 이름을 구분했습니다.
  • 인자를 arguments: 아래로 (1.10): 테스트 인자와 config:(severity 등)가 같은 높이에 섞이던 걸 정리했습니다. 옛 방식으로 쓰면 dbt 1.12에서 실제로 이런 경고가 나옵니다:
    [WARNING][MissingArgumentsPropertyInGenericTestDeprecation]: ... Arguments to generic tests should be nested under the `arguments` property.

무엇에 테스트를 걸까 — 최소 규칙

  1. 모든 모델의 기본 키에 unique + not_null. 이게 곧 "grain이 내가 생각한 그대로인가"를 검사하는 것입니다. 2일차에 배운 grain이 여기서 테스트로 바뀝니다.
  2. 코드값 컬럼에 accepted_values. 새 상태값이 생기면(예: cancelled) 마트의 case when이 조용히 틀립니다. 테스트가 먼저 알려 줍니다.
  3. 외래 키에 relationships. 고객 마스터에 없는 고객의 주문이 있으면 조인에서 조용히 빠집니다.
  4. 원본(source)에도 건다. 원본이 지저분하다는 걸 기록해 두고, 그게 staging에서 정리되는지 확인합니다.
🧸 비유

unique는 출석부 번호가 겹치지 않는지, not_null은 이름 칸이 비지 않았는지, accepted_values는 학년 칸에 1~6만 적혔는지, relationships는 "담임 선생님" 칸에 적힌 이름이 실제 교사 명단에 있는지 보는 것입니다.

singular 테스트 — 업무 규칙을 SQL로

generic 4종으로는 "결제 원본 총액과 주문 마트 총액이 같아야 한다" 같은 이 회사만의 규칙을 표현할 수 없습니다. 그럴 때는 tests/ 폴더에 SQL 파일을 직접 씁니다. 규칙은 똑같습니다: 규칙을 어긴 행을 SELECT 하면 됩니다.

-- 포인트는 다른 결제수단과 함께만 쓸 수 있다(포인트 단독 결제 금지).
-- 포인트 결제가 있는데 그 주문의 결제 건수가 1건뿐인 주문을 찾는다.
select
    p.order_id,
    op.payment_count
from {{ ref('stg_payments') }} p
join {{ ref('int_order_payments') }} op
    on p.order_id = op.order_id
where p.payment_method = 'point'
  and op.payment_count = 1

shop 데이터에서 포인트를 쓴 주문은 5번과 18번이고, 둘 다 카드와 함께 낸 분할 결제(payment_count = 2)입니다. 그래서 이 SELECT는 0행 → 통과합니다. 내일 누군가 포인트로만 결제한 주문을 넣으면 그 주문이 결과에 나오면서 실패합니다. ephemeral인 int_order_payments도 테스트 안에서 ref()할 수 있습니다 — 테스트 SQL에 CTE로 끼워 넣어 돌리기 때문입니다.

singular 테스트 쓰는 요령
  • 파일 이름은 assert_무엇이_참이어야_하는가.sql처럼 지켜져야 할 규칙을 이름으로. 실패 메시지에 이 이름이 그대로 나옵니다.
  • 맨 위 주석에 "왜 이 규칙이 있는지"를 적어 두면 6개월 뒤의 내가 고마워합니다.
  • 모델처럼 ref()·source()를 씁니다. 그래서 DAG에 들어가고, 참조한 모델이 다 만들어진 뒤에 돕니다.
  • 같은 검사를 여러 모델에 쓰고 싶어지면, 그때 직접 generic 테스트(매크로)로 만듭니다 — 4일차 매크로를 배우고 나면 쉽습니다.
프로시저 감각으로 옮기면

월말 결산 때 돌리던 "대사(對査) 쿼리" — 원천 시스템 합계와 마트 합계를 맞춰 보는 쿼리 — 가 singular 테스트의 대표 예입니다. 결산 때만이 아니라 매일 마트를 만들 때마다 돌아간다는 게 다릅니다.

실패의 강도 조절 — severity · warn_if · error_if · store_failures

모든 실패가 "당장 멈춰!"일 필요는 없습니다. 원본에 대문자 COMPLETED가 섞여 있는 건 알고 있고, staging에서 고치고 있는 문제입니다. 이런 건 경고(WARN)로만 남기고 싶습니다.

설정기본값뜻
severityerrorwarn으로 바꾸면 실패해도 경고만. 아래 모델 실행을 막지 않음
error_if"!=0"실패 행 수가 이 조건이면 ERROR
warn_if"!=0"ERROR가 아니고 이 조건이면 WARN
store_failuresfalsetrue(또는 실행 때 --store-failures)면 실패한 행을 DB 테이블로 저장
실패 행 수 n 이 나오면 dbt 는 이렇게 판정한다

   severity: error (기본)                        severity: warn
   ┌────────────────────────┐                   ┌────────────────────────┐
   │ n 이 error_if 에 맞나?  │── 예 ──▶ ERROR     │ n 이 warn_if 에 맞나?   │── 예 ──▶ WARN
   └───────────┬────────────┘                   └───────────┬────────────┘
               │ 아니오                                      │ 아니오
   ┌───────────▼────────────┐                               ▼
   │ n 이 warn_if 에 맞나?   │── 예 ──▶ WARN                  PASS
   └───────────┬────────────┘
               │ 아니오
               ▼
             PASS

   예) warn_if: ">0", error_if: ">5"  →  0행 PASS, 1~5행 WARN, 6행 이상 ERROR

설정은 테스트 아래 config:에 적습니다. arguments:와 같은 높이입니다.

          - name: status
            data_tests:
              - accepted_values:
                  arguments:
                    values: ['placed', 'shipped', 'completed', 'returned']
                  config:
                    warn_if: ">0"     # 1행이라도 있으면 경고
                    error_if: ">5"    # 6행 이상이면 멈춤

--store-failures를 붙여 실행하면 실패한 행이 main_dbt_test__audit 스키마에 테스트 이름과 같은 테이블로 저장되고, 로그에 조회 쿼리까지 찍어 줍니다(실제 출력).

FAIL 2 unique_stg_payments_order_id ................ [FAIL 2 in 0.14s]
  See test failures:
  select * from "shop"."main_dbt_test__audit"."unique_stg_payments_order_id"
🧸 비유

자동차 계기판과 같습니다. 엔진오일이 조금 부족하면 노란 경고등(WARN), 엔진 과열이면 빨간 경고등과 함께 차를 세웁니다(ERROR). warn_if/error_if는 "몇 도부터 노랑, 몇 도부터 빨강"을 정하는 눈금입니다. store_failures는 블랙박스 — 무엇이 문제였는지 나중에 돌려 볼 수 있습니다.

프로시저 감각으로 옮기면

프로시저에서 이상 데이터를 err_log 테이블에 INSERT 해 두고 진행하던 패턴이 severity: warn + store_failures이고, RAISE로 멈추던 패턴이 severity: error입니다.

source freshness — 원본이 제때 들어왔나

테스트는 "데이터 내용이 맞는가"를 봅니다. 그런데 운영에서 더 자주 터지는 사고는 "수집이 멈춰서 어제 데이터가 안 들어왔는데, 마트는 아무 일 없다는 듯 만들어졌다"입니다. 숫자는 깨끗한데 하루치가 통째로 없는 거죠. 이걸 잡는 게 source freshness입니다.

      - name: raw_orders
        config:
          loaded_at_field: updated_at          # "언제 들어온 행인가"를 알려 주는 컬럼
          freshness:
            warn_after: {count: 1, period: day}    # 가장 최근 행이 1일보다 오래되면 WARN
            error_after: {count: 3, period: day}   # 3일보다 오래되면 ERROR

dbt source freshness를 치면 dbt는 select max(updated_at) from 원본을 돌려 지금 시각과의 차이를 잽니다. 오늘(2026-11-04) 실제로 돌린 결과입니다.

1 of 1 START freshness of shop_raw.raw_orders ............ [RUN]
1 of 1 ERROR STALE freshness of shop_raw.raw_orders ...... [ERROR STALE in 0.03s]
[ERROR]: in source raw_orders (models\staging\sources.yml)
  Status: error

실습 데이터의 마지막 주문 시각은 2026-10-19 10:13이라 약 15.9일 지났습니다. 3일을 넘었으니 ERROR가 맞습니다. 이건 고장이 아니라 freshness가 정확히 제 일을 한 것입니다 — "10월 19일 이후로 주문이 한 건도 안 들어왔어요"라고 알려 준 거니까요.

freshness 는 "데이터"가 아니라 "파이프라인"을 검사합니다
  • 같은 CSV라도 10월 20일에 돌렸으면 PASS, 오늘 돌리면 ERROR입니다. 데이터는 그대로인데 시간이 흘렀기 때문입니다. 그래서 freshness는 dbt test·dbt build에 들어 있지 않고 별도 명령입니다.
  • 기준은 수집 주기에 맞춥니다. 매일 새벽에 들어오는 원본이면 warn 1일·error 2일 정도. 주 1회 들어오는 원본에 1일 기준을 걸면 매일 빨간불이고, 사람들은 곧 경고를 무시하게 됩니다.
  • 시각 비교는 UTC 기준입니다. updated_at이 한국 시각(KST)으로 저장돼 있으면 9시간 차이가 납니다. 일 단위 기준에서는 대개 문제없지만 시간 단위 기준이면 신경 써야 합니다.
  • raw_customers처럼 바뀔 때만 updated_at이 갱신되는 마스터 테이블에는 freshness를 걸지 않는 게 보통입니다. 고객 정보가 한 달 안 바뀌는 건 정상이니까요.
🧸 비유

우유 유통기한 확인과 같습니다. 우유 맛(내용)이 멀쩡한지는 테스트가 보고, freshness는 날짜만 봅니다. 그리고 같은 우유라도 오늘은 괜찮고 2주 뒤엔 상한 우유가 됩니다 — 우유가 변한 게 아니라 달력이 넘어갔기 때문이죠.

프로시저 감각으로 옮기면

배치 시작 전에 SELECT MAX(load_dt) FROM raw.orders를 확인하고 어제 날짜가 아니면 중단하던 "선행 체크"가 freshness입니다. 6일차에 Airflow DAG의 첫 태스크로 dbt source freshness를 넣으면, 원본이 늦게 온 날은 마트를 만들기 전에 멈추게 할 수 있습니다. ERROR일 때 종료 코드가 1(실패)이라서 Airflow가 그대로 알아챕니다. WARN일 때는 0입니다.

버전 차이: config 아래로

dbt 1.10부터 freshness와 loaded_at_field를 config: 아래에 쓰는 게 표준입니다. 예전처럼 테이블 바로 아래(config: 없이)에 써도 1.12에서 경고 없이 돌아가지만, 새로 쓸 때는 config: 안에 두세요. 또 source 전체(묶음)에 걸고 테이블별로 freshness: null로 끌 수도 있습니다.

  • 왼쪽에서 오른쪽으로 흐릅니다. 왼쪽 끝이 source, 오른쪽 끝이 marts.
  • 모델 하나를 클릭하고 그 페이지에서 그래프를 열면 그 모델의 위·아래만 보여 줍니다. 아래쪽 --select 칸에 어제 배운 선택자(+fct_orders, stg_orders+)를 그대로 넣을 수 있습니다.

  • 테스트는 그래프에 따로 그리지 않지만, 각 모델 페이지에 어떤 테스트가 걸려 있는지 나옵니다.

model contract — 마트의 모양을 약속하기

테스트는 테이블을 만든 뒤에 내용을 검사합니다. 그런데 fct_orders를 Looker Studio 대시보드나 다른 팀이 쓰고 있다면, 누군가 컬럼 이름을 바꾸거나 타입이 슬쩍 바뀌는 순간 그쪽이 깨집니다. model contract는 "이 모델은 이 이름·이 타입의 컬럼을 이 개수만큼 내놓는다"를 YAML로 약속하고, 약속과 다르면 테이블을 만들기 전에 멈춥니다.

models:
  - name: fct_orders
    config:
      contract:
        enforced: true            # 약속을 강제한다
    columns:
      - name: order_id
        data_type: bigint         # contract 가 켜지면 모든 컬럼에 data_type 필수
        constraints:              # DB 제약 조건 (DB가 지원하는 만큼 실제로 걸림)
          - type: not_null
          - type: primary_key
      - name: customer_id
        data_type: bigint
      ...
      - name: total_amount
        data_type: bigint
      - name: updated_at
        data_type: timestamp

오늘 실습에서 실제로 걸려 넘어질 곳이 있습니다. DuckDB에서 sum(bigint)의 결과는 HUGEINT(128비트 정수)입니다. 그래서 contract에 bigint라고 약속하면 이렇게 멈춥니다(실제 출력).

Compilation Error in model fct_orders (models\marts\fct_orders.sql)
  This model has an enforced contract that failed.
  Please ensure the name, data_type, and number of columns in your contract match ...

  | column_name  | definition_type | contract_type | mismatch_reason    |
  | ------------ | --------------- | ------------- | ------------------ |
  | total_amount | HUGEINT         | BIGINT        | data type mismatch |

contract 없이 지냈다면 "total_amount가 어느 날 다른 타입이 됐다"는 걸 대시보드가 깨지고 나서야 알았을 겁니다. 해결은 SQL에서 타입을 명시적으로 맞추는 것입니다. 합계를 만드는 곳, 즉 int_order_payments의 sum(amount)를 cast(sum(amount) as bigint)로 바꿉니다. 타입은 문제가 생기는 지점(집계)에서 바로잡아야, 이 모델을 쓰는 다른 모델도 같은 타입을 받습니다.

테스트contract
언제 검사테이블을 만든 뒤테이블을 만들기 전
무엇을데이터 내용(중복, NULL, 값 범위)테이블 모양(컬럼 이름·타입·개수)
실패하면테이블은 이미 바뀌어 있다 (아래 모델만 멈춤)기존 테이블은 그대로, 새 테이블을 안 만든다
어디에모든 모델다른 팀·BI가 기대는 marts 위주
constraints 는 DB마다 다르게 지켜집니다

dbt는 constraints를 create table 문에 넣어 줄 뿐이고, 실제로 지키는 건 DB입니다. DuckDB는 not_null·primary_key를 진짜로 검사합니다(실습에서 target/run의 order_id bigint not null primary key를 확인합니다). BigQuery는 not_null만 강제하고, primary/foreign key는 "정보용"으로만 기록합니다. 그래서 BigQuery에서는 PK 중복을 여전히 unique 테스트로 잡아야 합니다. contract와 테스트는 서로를 대신하지 않습니다.

🧸 비유

콘센트 규격과 같습니다. 플러그 모양(컬럼 이름·타입)이 규격과 다르면 아예 꽂히지 않게 막는 게 contract이고, 꽂힌 뒤 전압이 정상인지 재는 게 테스트입니다.

프로시저 감각으로 옮기면

마트 테이블을 CREATE TABLE dm.fct_orders (order_id INT64 NOT NULL, ...)처럼 DDL을 먼저 고정해 두고 INSERT만 하던 방식이 contract에 가깝습니다. DDL과 다른 SELECT를 넣으면 INSERT가 실패했죠. dbt의 기본(CREATE TABLE AS SELECT)은 SELECT 결과대로 모양이 정해지는데, contract를 켜면 그 옛날의 "DDL 먼저" 안전장치를 되찾는 셈입니다.

dbt build — run과 test를 DAG 순서로 엮기

dbt run 후 dbt test를 하면 될 것 같지만, 큰 차이가 있습니다.

dbt run → dbt test                          dbt build
─────────────────────────────────           ─────────────────────────────────────────
① 모든 모델을 먼저 다 만든다                  모델 하나 만들고 → 바로 그 모델 테스트
   stg_orders  (status 가 깨져 있음)           stg_orders 생성 → 테스트 FAIL
   fct_orders  (깨진 값으로 만들어짐)            └▶ fct_orders      SKIP (안 만듦)
   dim_customers (깨진 값으로 만들어짐)          └▶ dim_customers   SKIP (안 만듦)
② 그 다음에 테스트 → FAIL 발견
   → 하지만 대시보드는 이미 틀린 숫자를 보고 있다   → 대시보드는 어제의 맞는 숫자를 그대로 본다
  • dbt build는 모델(run)·테스트(test)·seed·snapshot을 DAG 순서대로 한 번에 돕니다.
  • 모델이 만들어지면 그 모델의 테스트를 곧바로 돌리고, ERROR가 나면 그 아래 모델을 전부 SKIP합니다. WARN은 막지 않습니다.
  • source에 건 테스트는 그 source를 읽는 staging보다 먼저 돕니다.
  • source freshness는 들어 있지 않습니다(따로 dbt source freshness).

run → test는 케이크를 끝까지 다 만들어 진열한 다음에 "아까 우유가 상했었네"를 발견하는 것. build는 단계마다 맛을 보고, 크림 단계에서 이상하면 그 위 장식과 포장은 하지 않는 것입니다. 진열대에는 어제 만든 멀쩡한 케이크가 그대로 있습니다.

프로시저 감각으로 옮기면

YAML 들여쓰기 주의
  • 들여쓰기는 스페이스만, 2칸씩. Tab 키를 누르면 Parsing Error ... Syntax error near line N이 납니다.
  • 높이가 곧 소속입니다. - name: stg_orders(2칸) 아래 columns:(4칸), 그 아래 - name: order_id(6칸), 그 아래 data_tests:(8칸), 테스트 이름(10칸).
  • arguments:는 - accepted_values:보다 한 단계 안쪽, values:는 다시 한 단계 안쪽입니다. 틀에서 칸 수를 바꾸지 말고 빈칸만 채우세요.

왜 이렇게 하나요? 프로시저 시절 손으로 돌리던 "PK 중복 없나? NULL 없나?" 검증 쿼리를, dbt가 이 YAML을 읽어 자동으로 만들어 돌려 줍니다. 한 번 적어 두면 매일 같은 검사를 빠짐없이 합니다.

힌트 1

맨 위는 models:, 그 아래 - name: 모델이름, 그 아래 columns:, 각 컬럼 아래 data_tests: 목록입니다. 이론의 예시를 그대로 따라가면 됩니다.

힌트 2

인자가 있는 accepted_values와 relationships는 arguments: 아래에 values: / to:·field:를 넣습니다. to:의 값은 ref('stg_customers')처럼 따옴표 없이 씁니다. values:는 ['placed', 'shipped', ...]처럼 작은따옴표 목록입니다.

정답 보기 
models:
  - name: stg_orders
    columns:
      - name: order_id
        data_tests:
          - unique
          - not_null
      - name: status
        data_tests:
          - accepted_values:

정리

💡 한 줄 요약 테스트는 "문제 행을 찾는 SELECT"(0행 = 통과), freshness는 "원본이 제때 왔나", contract는 "모양을 약속", 문서는 "코드 옆에 적는 설명". 그리고 dbt build가 이걸 DAG 순서로 엮어, 실패하면 아래를 지킨다.
  • 기본 4종: unique·not_null(grain), accepted_values(코드값), relationships(짝). 1.10+는 data_tests: + arguments:
  • 업무 규칙은 tests/에 singular 테스트. 이름은 지켜야 할 규칙으로
  • severity·warn_if·error_if로 강도 조절, --store-failures로 실패 행 보관(main_dbt_test__audit)
  • 테스트가 실패하면 먼저 "데이터가 틀렸나, 내 가정(grain)이 틀렸나?"
  • freshness는 데이터가 아니라 파이프라인 검사. 기준은 수집 주기에 맞춘다. ERROR면 종료 코드 1
  • contract는 만들기 전에 모양 검사, 테스트는 만든 뒤 내용 검사. 서로 대신하지 않는다

dbt 테스트가 "통과"로 판정되는 조건은?

  1. 테스트 SQL이 1행 이상을 돌려줄 때
  2. 테스트 SQL이 true를 돌려줄 때
  3. 테스트 SQL이 0행을 돌려줄 때
  4. 테스트 SQL이 에러 없이 컴파일될 때
dbt 테스트는 "규칙을 어긴 행"을 찾는 SELECT입니다. 0행이면 어긴 행이 없으니 통과, 1행이라도 나오면 실패(또는 경고)입니다. singular 테스트를 쓸 때도 "통과하는 행"이 아니라 "실패하는 행"을 SELECT 해야 합니다.

stg_payments.order_id에 건 unique 테스트가 FAIL 2로 나왔습니다. 가장 알맞은 대응은?

  1. stg_payments의 grain이 결제 1건임을 확인하고, unique는 payment_id에 건다
  2. severity: warn으로 바꿔 경고만 나오게 한다
  3. stg_payments에서 group by order_id로 합쳐 테스트를 통과시킨다
  4. 원본 CSV에서 중복 행을 지운다
실패 행(주문 5, 18)은 정상적인 분할 결제였습니다. 틀린 건 데이터가 아니라 "order_id가 기본 키"라는 가정이었죠. 2번은 틀린 가정을 덮어 두는 것이고, 3번은 staging에서 정보를 버리는 것(2일차에 되돌린 실수), 4번은 정상 데이터를 지우는 것입니다.

dbt 1.10+ 기준으로 올바른 accepted_values 작성법은?

  1. tests: [accepted_values: [placed, shipped]]
  2. data_tests: 아래 - accepted_values: 바로 밑에 values: [...]
  3. config: 아래에 values: [...]
  4. data_tests: 아래 - accepted_values: 밑에 arguments:, 그 아래 values: [...]
1.10부터 generic 테스트의 인자는 arguments: 아래에 둡니다. 2번(옛 방식)도 돌아가지만 dbt 1.12에서 MissingArgumentsPropertyInGenericTestDeprecation 경고가 나옵니다. config:는 severity 같은 설정 자리이지 인자 자리가 아닙니다.

테스트 설정이 warn_if: ">0", error_if: ">5"(severity는 기본값)이고, 실패 행이 2개 나왔다면?

  1. PASS
  2. WARN
  3. ERROR
  4. SKIP
먼저 error_if(>5)를 봅니다: 2는 해당하지 않음. 다음 warn_if(>0): 해당 → WARN. 실습의 원본 status 테스트가 정확히 이 경우였습니다(Got 2 results, configured to warn if >0). 6행 이상이면 ERROR가 됩니다.

10월 데이터로 오늘(11월 4일) dbt source freshness를 돌렸더니 ERROR STALE이 나왔습니다. 올바른 해석은?

  1. CSV 파일이 깨졌다
  2. 가장 최근 updated_at이 기준(3일)보다 오래됐다 — 원본이 새로 들어오지 않았다는 신호다
  3. loaded_at_field 문법이 틀렸다
  4. 테스트 중 하나가 실패했다
freshness는 max(updated_at)과 지금 시각의 차이를 잽니다. 마지막 주문이 10월 19일이니 약 16일 — 3일 기준을 넘어 ERROR입니다. 데이터 내용과는 무관하며, 같은 데이터라도 10월 20일에 돌렸다면 PASS였습니다. freshness는 테스트(dbt test)와 별개 명령입니다.

model contract에 대한 설명으로 옳지 않은 것은?

  1. 컬럼 이름·타입·개수가 약속과 다르면 테이블을 만들기 전에 멈춘다
  2. enforced: true면 모든 컬럼에 data_type을 적어야 한다
  3. DuckDB에서 sum(bigint) 결과가 HUGEINT라서 bigint 약속과 어긋날 수 있다
  4. contract를 켜면 BigQuery에서도 primary key 중복이 DB에서 막히므로 unique 테스트가 필요 없다
BigQuery는 not_null만 강제하고 primary/foreign key는 정보용으로만 기록합니다. 그래서 PK 중복은 여전히 unique 테스트로 잡아야 합니다. contract(모양)와 테스트(내용)는 서로를 대신하지 않습니다. 1~3번은 실습에서 직접 확인한 내용입니다.

stg_orders의 accepted_values 테스트가 실패한 날, dbt build를 돌리면 fct_orders는?

  1. SKIP 된다 — 어제 만든 테이블이 그대로 남는다
  2. 잘못된 값으로 새로 만들어진다
  3. 삭제된다
  4. 만들어지지만 테스트는 건너뛴다
dbt build는 모델을 만들고 곧바로 그 모델의 테스트를 돌리며, ERROR가 나면 아래 모델을 전부 SKIP합니다. 실습 6단계에서 SKIP relation main.fct_orders를 확인했습니다. dbt run 후 dbt test였다면 2번처럼 잘못된 값으로 먼저 만들어졌을 겁니다.

fct_orders.sql에서 잘못 넣은 where 줄을 지운 뒤 dbt test만 돌렸더니 singular 테스트가 여전히 실패합니다. 왜일까요?

  1. singular 테스트는 캐시를 쓰기 때문에
  2. 테스트 파일도 같이 고쳐야 해서
  3. fct_orders는 table이라, 다시 만들기 전까지 DB에는 고치기 전 결과가 남아 있어서
  4. --store-failures를 붙이지 않아서
테스트는 SQL 파일이 아니라 지금 DB에 있는 테이블을 검사합니다. 파일을 고쳐도 fct_orders 테이블은 다시 만들기 전까지 반품이 빠진 상태입니다. dbt build --select fct_orders+로 다시 만들고 검사해야 합니다.
