Jinja 기초 — SQL을 찍어 내는 틀

지금까지 쓴 {{ ref('stg_orders') }}가 바로 Jinja입니다. Jinja는 Python 세계의 템플릿 언어로, "글자를 만들어 내는 틀"입니다. dbt는 모델 파일을 Jinja로 먼저 풀어서 순수 SQL 글자를 만든 다음, 그 SQL을 DB에 보냅니다.

🧸 비유

Jinja는 메일 머지(편지 병합)와 같습니다. "안녕하세요 {{이름}} 님" 이라는 틀 하나로 고객 100명에게 100통의 편지를 찍어 내죠. 편지를 받는 사람(DB)은 틀을 본 적이 없고, 완성된 편지(SQL)만 받습니다.

세 가지 표시

표시이름하는 일예
{{ ... }}표현식(expression)값을 계산해서 그 자리에 글자로 찍는다{{ ref('stg_orders') }}, {{ var('run_date') }}
{% ... %}문장(statement)찍지는 않고 흐름을 제어한다 (변수, 반복, 조건, 매크로 정의){% set x = 1 %}, {% for %}, {% if %}
{# ... #}주석컴파일 결과에 남지 않는 메모{# TODO: 결제 취소 반영 #}

SQL 주석 -- ... 은 Jinja가 신경 쓰지 않는 그냥 글자라서 컴파일 결과에 그대로 남습니다. 그래서 -- {{ ref('x') }} 처럼 SQL 주석 안에 Jinja를 넣어도 Jinja는 실행되고, 의존성도 생깁니다. 코드를 "꺼 두고" 싶으면 {# #}를 써야 합니다.

set — 변수

{% set min_amount = 10000 %}
{% set methods = ['card', 'bank_transfer', 'kakaopay', 'point'] %}

select * from {{ ref('stg_payments') }}
where amount >= {{ min_amount }}

숫자, 문자열, 리스트([...]), 딕셔너리({'a': 1})를 담을 수 있습니다. 여러 줄 SQL 덩어리를 담을 땐 블록 형태를 씁니다.

{% set q %}
select distinct payment_method from {{ ref('stg_payments') }}
{% endset %}

for — 반복

select
    order_id,
    {% for m in methods %}
    sum(case when payment_method = '{{ m }}' then amount else 0 end) as {{ m }}_amount{% if not loop.last %},{% endif %}
    {% endfor %}
from {{ ref('stg_payments') }}
group by order_id

반복 안에서는 loop라는 특별한 변수가 생깁니다.

loop 변수뜻주로 쓰는 곳
loop.last마지막 차례면 참마지막 컬럼 뒤에 쉼표를 안 붙이기 ({% if not loop.last %},{% endif %})
loop.first첫 차례면 참where 뒤 첫 조건에만 and 빼기
loop.index1부터 세는 순번별칭 붙이기 t{{ loop.index }}
쉼표 사고

SELECT 컬럼 목록을 반복으로 만들 때 가장 흔한 오류는 마지막 컬럼 뒤 쉼표입니다(... as point_amount, from ... → 문법 오류). loop.last로 막거나, 반복 앞에 고정 컬럼을 두고 반복 안에서는 앞에 쉼표를 붙이는 방법(, sum(...))도 씁니다.

if — 조건

select *
from {{ ref('fct_orders') }}
{% if target.name == 'dev' %}
where order_date >= current_date - interval 30 day   -- 개발 때는 최근 30일만
{% endif %}

target.name은 profiles.yml에서 고른 target 이름(dev, prod)입니다. 개발할 땐 데이터를 줄여서 빨리 돌리는 패턴으로 자주 씁니다. ==, !=, and, or, not, in을 쓸 수 있습니다.

공백 제어 — {%- 와 -%}

Jinja 문장 {% %}은 글자를 찍지 않지만, 그 줄 자체(줄바꿈·공백)는 남습니다. 그래서 반복을 쓰면 컴파일된 SQL에 빈 줄이 숭숭 생깁니다. 괄호 안쪽에 -를 붙이면 그쪽 방향의 공백·줄바꿈을 지웁니다.

공백 제어 없음 → 빈 줄이 생긴다
select
    order_id,


    sum(...) as card_amount,


    sum(...) as point_amount


from ...
{%- for %}, {%- endfor %} → 깔끔
select
    order_id,
    sum(...) as card_amount,
    sum(...) as point_amount
from ...

{%-는 왼쪽(앞) 공백을, -%}는 오른쪽(뒤) 공백을 지웁니다. 너무 많이 지우면 단어가 붙어 버리니(order_idsum(...)), 결과를 target/compiled에서 보면서 맞춥니다. SQL 결과는 똑같으니 보기 좋게 하는 용도일 뿐입니다.

프로시저 감각으로 옮기면
  • DECLARE/SET → {% set %}. 다만 DB 변수가 아니라 SQL을 만들기 전에 글자로 바뀌는 값입니다.
  • FORMAT() + EXECUTE IMMEDIATE로 만들던 동적 SQL → Jinja for. 문자열을 이어 붙일 필요도, 실행할 필요도 없습니다. Jinja가 만든 글자가 곧 SQL입니다.
  • IF ... THEN ... END IF → {% if %}...{% endif %}. 다만 Jinja의 if는 DB 데이터를 보고 분기하지 않습니다(그러려면 아래 run_query). target, 변수, 설정을 보고 분기합니다.
💡 한 줄 요약 {{ }}는 찍는다, {% %}는 흐름을 정한다, {# #}는 지워진다. Jinja는 SQL을 실행하지 않고 SQL 글자를 만든다.

컴파일은 어떻게 일어나나

dbt run을 치면 dbt는 크게 두 번 파일을 읽습니다. 이 순서를 알면 "왜 여기서는 쿼리 결과를 못 쓰지?" 같은 의문이 풀립니다.

① 파싱(parse)  ─ 모든 파일을 훑는다. DB에는 아직 안 물어본다
   │  ref()·source()·config() 를 모아 DAG(의존 그래프)와 manifest.json 을 만든다
   │  이때 execute = False  →  run_query() 는 빈 결과(None)
   ▼
② 실행(execute) ─ DAG 순서대로 모델 하나씩
   │  a) 컴파일: Jinja를 풀어 순수 SELECT 를 만든다   → target/compiled/...
   │  b) 감싸기: materialization 이 CREATE/MERGE 등을 붙인다 → target/run/...
   │  c) DB에 보낸다
   │  이때 execute = True  →  run_query() 가 실제로 DB에 쿼리한다
   ▼
   run_results.json (모델별 성공/실패, 걸린 시간)
명령①파싱②-a 컴파일②-b,c 실행
dbt parse✓
dbt compile✓✓ (target/compiled)
dbt run / dbt build✓✓✓ (target/run)
dbt show✓✓SELECT만 실행해서 미리보기 (테이블은 안 만듦)

run_query 와 execute

가끔은 DB 데이터를 보고 SQL을 만들어야 합니다. 예: "결제 수단 목록을 하드코딩하지 말고 DB에서 읽어 와서 pivot". 이럴 때 run_query()를 씁니다. 다만 파싱 단계에서는 DB에 묻지 않으니, execute가 참일 때만 결과를 꺼내야 합니다.

{% set q %}
select distinct payment_method from {{ ref('stg_payments') }} order by 1
{% endset %}
{% set res = run_query(q) %}

{% if execute %}
  {% set methods = res.columns[0].values() %}   {# 첫 번째 컬럼의 값들 → 리스트 #}
{% else %}
  {% set methods = [] %}                         {# 파싱 때는 빈 리스트로 #}
{% endif %}

if execute를 빼먹으면 파싱 단계에서 'None' has no attribute 'columns' 같은 오류가 납니다. 그리고 run_query는 모델을 돌릴 때마다 쿼리를 한 번 더 보내니, 남용하지 말고 "목록이 자주 바뀌어서 하드코딩이 위험할 때"만 씁니다.

실제로 확인한 결과

위 코드로 만든 pivot은 결제 수단이 order by 1 순서(bank_transfer, card, kakaopay, point)로 나옵니다. 하드코딩한 리스트 순서와 다르죠 — 컬럼 순서가 DB 데이터에 따라 달라질 수 있다는 뜻이고, contract가 걸린 모델에서는 이게 문제가 될 수 있습니다.

매크로 — 재사용하는 SQL 조각

매크로는 Jinja로 만든 함수입니다. macros/ 폴더의 .sql 파일에 정의하면, 프로젝트 어느 모델에서든 부를 수 있습니다. 사실 ref(), source(), is_incremental()도 dbt가 미리 만들어 둔 매크로입니다.

{% macro clean_text(col) -%}
    nullif(lower(trim({{ col }})), '')
{%- endmacro %}
select {{ clean_text('status') }} as status   -- → nullif(lower(trim(status)), '') as status
from {{ source('shop_raw', 'raw_orders') }}
부분뜻
{% macro 이름(인자) %} ... {% endmacro %}정의. 인자 기본값도 가능: (col, default='')
{{ 이름('status') }}호출. 안에서 만든 글자가 그 자리에 찍힘
'status' (따옴표)컬럼 이름을 글자로 넘긴다. 따옴표가 없으면 Jinja 변수 status를 찾다가 빈 값이 됨
{% do return(값) %}글자가 아니라 리스트·딕셔너리 같은 값을 돌려줄 때
🧸 비유

매크로는 도장입니다. "정제 도장"을 하나 파 두면, 문서(모델) 어디에든 꾹 찍으면 같은 문구가 들어갑니다. 문구를 고치고 싶으면 도장만 다시 파면 모든 문서가 다음번 찍을 때 바뀝니다.

프로시저 감각으로 옮기면 — UDF와 다른 점
  • UDF(CREATE FUNCTION)는 DB 안에 저장되어 쿼리 실행 중에 행마다 불립니다.
  • 매크로는 SQL을 만들 때 펼쳐지고 사라집니다. 컴파일된 SQL에는 매크로 이름이 없고 nullif(lower(trim(status)), '')만 남습니다. DB에는 아무것도 생기지 않습니다.
  • 그래서 매크로는 컬럼 목록, 조인 조건, WHERE 조건 같은 SQL 구조까지 찍어 낼 수 있습니다. UDF는 값 계산만 할 수 있죠.

generate_schema_name — dbt가 스키마 이름을 정하는 매크로

dbt가 내부적으로 쓰는 매크로 중 실무에서 자주 덮어쓰는 것이 generate_schema_name입니다. 모델에 +schema: marts를 주면 어디에 만들어질까요?

설정기본 동작(직접 확인)매크로를 덮어쓰면(흔한 방식)
schema 설정 없음main (target의 schema)main
+schema: martsmain_marts (target 스키마 + _ + 설정값)marts

기본이 "이어 붙이기"인 이유는, 여러 사람이 각자 target 스키마(dbt_eunjin, dbt_minji)에서 개발할 때 dbt_eunjin_marts처럼 서로 안 부딪치게 하려는 것입니다. 운영(prod)에서만 marts 그대로 쓰고 싶다면 macros/generate_schema_name.sql을 만들어 덮어씁니다.

{% macro generate_schema_name(custom_schema_name, node) -%}
    {%- if custom_schema_name is none -%}
        {{ target.schema }}
    {%- elif target.name == 'prod' -%}
        {{ custom_schema_name | trim }}
    {%- else -%}
        {{ target.schema }}_{{ custom_schema_name | trim }}
    {%- endif -%}
{%- endmacro %}

오늘 실습에서는 스키마를 나누지 않습니다(전부 main). "이런 매크로가 있고, 같은 이름으로 만들면 dbt 기본 동작을 바꿀 수 있다"만 기억하세요. 6일차 dev/prod 이야기에서 다시 나옵니다.

incremental — MERGE 프로시저를 모델로

지금까지 fct_orders는 table이었습니다. 매번 전체를 지우고 처음부터 다시 만듭니다. 주문 40건이면 상관없지만, 하루 수백만 건이 3년 쌓인 테이블이라면 매일 전체를 다시 만드는 건 돈과 시간 낭비입니다. 프로시저에서는 그래서 MERGE나 DELETE+INSERT로 "바뀐 것만" 넣었죠. dbt에서는 그게 incremental materialization입니다.

🧸 비유

table은 매일 가계부를 새 공책에 처음부터 다시 쓰는 것, incremental은 어제까지 쓴 공책에 오늘 생긴 일만 이어 쓰고, 고칠 줄은 고치는 것입니다. 이어 쓰기가 빠르지만, "어디부터가 새로 생긴 일인지"를 잘못 판단하면 빠뜨린 줄이 영영 안 들어갑니다. 그래서 가끔은 새 공책에 다시 쓰는 날(--full-refresh)이 필요합니다.

가장 중요한 결정: "새로 바뀐 것"을 무엇으로 판단하나

incremental 모델이 틀리는 이유의 대부분은 전략이 아니라 필터 컬럼입니다.

필터잡는 것놓치는 것
order_date > max(order_date)새 주문예전 주문의 상태 변경(반품, 배송 완료)
order_date >= max(order_date) - 3일새 주문 + 최근 3일 주문의 변경3일보다 오래된 주문의 변경
updated_at >= max(updated_at) - 3일언제 주문이든 최근에 바뀐 행원천이 updated_at을 안 고치고 값을 바꾼 경우, 3일보다 늦게 도착한 데이터

뒤에 붙인 "- 3일"을 lookback window(되돌아보기 구간)라고 합니다. 데이터가 늦게 도착하는 경우(어제 바뀐 행이 오늘 새벽에야 원천에 들어옴)를 대비해 최댓값보다 조금 앞에서부터 다시 읽는 것입니다. 이미 있는 행을 다시 읽어도 unique_key로 MERGE 하니까 중복이 생기지 않습니다 — 그래서 lookback은 unique_key와 짝입니다.

오늘 실습의 함정 미리보기

다음 날 데이터에서 주문 3번(10월 2일 주문)이 10월 21일에 returned로 바뀝니다. order_date 기준 필터는 3일 lookback을 줘도 10월 16일 이후 주문만 보니까 3번을 영영 못 봅니다. 그리고 한 번 놓친 행은, 나중에 필터를 고쳐도 기준점(max)이 이미 지나가 버려서 다시 잡히지 않습니다. 이걸 고치는 방법이 --full-refresh입니다.

on_schema_change — 컬럼이 바뀌면

incremental 테이블은 계속 살아 있으니, 모델 SELECT에 컬럼을 추가하면 기존 테이블과 모양이 달라집니다.

값동작
ignore (기본)새 컬럼을 무시. 테이블에 안 생김 (조용히 빠지니 위험)
fail모양이 다르면 실패시킴
append_new_columns새 컬럼을 테이블에 추가. 기존 행은 NULL. 없어진 컬럼은 그대로 둠
sync_all_columns추가·삭제 모두 맞춤 (타입 변경 포함)
contract와 같이 쓸 때 (직접 확인)

fct_orders처럼 contract가 걸린 incremental 모델에서 on_schema_change='ignore'(기본값)이면 dbt가 실행을 거부합니다: Models materialized as incremental with contracts enabled must set on_schema_change to 'append_new_columns' or 'fail'. 그래서 오늘 예제는 append_new_columns를 적었습니다.

--full-refresh — 새 공책에 다시 쓰기

dbt run -s fct_orders --full-refresh

is_incremental()을 강제로 거짓으로 만들어 테이블을 처음부터 다시 만듭니다. 이럴 때 씁니다.

  • 필터 로직이 틀렸던 걸 발견했을 때 (오늘 실습)
  • 컬럼 계산식을 바꿔서 과거 행까지 다시 계산해야 할 때
  • on_schema_change로 해결 안 되는 구조 변경

아주 큰 테이블은 실수로 full refresh 되면 비용이 크니, config(full_refresh=false)로 막아 두기도 합니다.

snapshot — SCD2 이력 테이블

원천 고객 테이블은 현재 상태만 가지고 있습니다. 2번 고객이 basic → gold로 바뀌면 basic이었던 기록은 사라지죠. "10월 15일 당시 이 고객의 등급은?" 에 답하려면 변경 이력을 따로 쌓아야 합니다. 이걸 SCD Type 2(Slowly Changing Dimension)라고 하고, dbt에서는 snapshot이 맡습니다.

🧸 비유

snapshot은 키 재는 문틀입니다. 아이 키가 클 때마다 문틀에 선을 긋고 날짜를 적어 두면, 지금 키(현재 행)와 예전 키(과거 행)를 다 볼 수 있습니다. 문틀은 지우지 않고 계속 쌓는 기록이라서, 한번 잘못 그으면 되돌리기 어렵습니다.

버전 차이

dbt 1.8 이하에서는 snapshots/customers_snapshot.sql 파일 안에 {% snapshot customers_snapshot %} {{ config(...) }} select * from ... {% endsnapshot %} 블록으로 썼습니다. 지금도 동작하지만 1.9부터는 위의 YAML 방식이 권장입니다. relation:에는 source(...)나 ref(...)를 적고, 원천을 조금 걸러야 하면 ephemeral 모델을 하나 만들어 ref()합니다. hard_deletes와 dbt_valid_to_current도 1.9에서 생긴 설정입니다(예전엔 invalidate_hard_deletes: true).

INSERT INTO dm.customers_hist ...

왜 이 단계부터? 오늘 뒤에 나오는 매크로·incremental·snapshot은 전부 Jinja 위에서 돌아갑니다. Jinja가 "SQL 글자를 어떻게 찍어 내는지" 눈으로 한 번 보지 않으면, 뒤에서 오류가 났을 때 Jinja 문제인지 SQL 문제인지 구분이 안 됩니다. 그래서 DB를 건드리지 않는 안전한 곳(analyses)에서 먼저 찍어 보고 결과 글자만 확인합니다.

건너뛰면? 2단계 매크로에서 쉼표 하나 때문에 syntax error at or near "from"이 나도 어디를 봐야 할지 모릅니다. 정답은 늘 target\compiled 안에 있다는 습관을 여기서 들입니다.

프로시저로 치면: 수단이 늘 때마다 CASE 줄을 복사하거나, 문자열을 이어 붙여 동적 SQL을 만들고 EXECUTE IMMEDIATE 전에 SELECT @sql(또는 PRINT)로 찍어 보던 일입니다. dbt에서는 그 "찍어 보기"가 dbt compile이고, 결과가 파일로 남습니다.

목표: 결제 수단 4개마다 sum(case when ...) 컬럼을 손으로 4번 쓰는 대신, Jinja for로 한 번만 쓰고 4번 찍어 내기. DB에는 아무것도 만들지 않고, dbt가 만들어 낸 SQL 글자만 확인합니다.

2. 결제 수단 pivot 매크로 만들기

왜? 1단계의 반복은 jinja_play.sql 한 파일 안에만 있습니다. "수단별 합계 컬럼 만들기"를 다른 모델에서도 쓰려면 복사해야 하고, 규칙이 바뀌면 복사본을 전부 찾아 고쳐야 하죠. 한곳(macros\)에 두면 한 번 고치면 모든 모델에 반영됩니다.

건너뛰면? 3·4단계, 그리고 실무 코드 대부분이 매크로 호출입니다. 매크로를 직접 만들어 보지 않으면 dbt_utils.xxx()도 "마법 함수"로만 보입니다.

프로시저로 치면: 공통 로직을 UDF나 공통 프로시저로 빼 두던 것. 다른 점은, 매크로는 DB에 저장되지 않고 컴파일할 때 SQL 글자로 펼쳐진다는 것입니다. 그래서 값 계산뿐 아니라 컬럼 목록 같은 SQL 구조까지 찍어 낼 수 있습니다.

5. fct_orders 를 incremental 로 바꾸기 (일부러 함정 버전)

왜? 지금 fct_orders는 돌릴 때마다 30행 전부를 지우고 다시 만듭니다. 실무의 주문·이벤트 테이블은 수억 행이라, 매일 전체를 다시 만들면 시간도 웨어하우스 비용(BigQuery는 읽은 바이트만큼 과금)도 감당이 안 됩니다. 그래서 "바뀐 것만 넣는" incremental로 바꿉니다.

왜 일부러 틀린 필터? 많은 사람이 처음에 "주문 날짜 기준 최근 N일"로 씁니다. 그게 무엇을 놓치는지 8단계에서 직접 보면, 9단계의 올바른 기준(updated_at)이 왜 필요한지 몸으로 알게 됩니다.

프로시저로 치면: MERGE INTO dm.fct_orders T USING (SELECT ... WHERE order_date >= 기준일) S ON T.order_id = S.order_id WHEN MATCHED THEN UPDATE ... WHEN NOT MATCHED THEN INSERT ... 에서 unique_key = ON 절, is_incremental() 블록 = USING 안의 WHERE, {{ this }} = 대상 테이블 T입니다. MERGE 문 자체는 dbt가 써 줍니다. (날짜 단위로 DELETE 후 INSERT 하던 프로시저라면 delete+insert 전략에 해당합니다.)

목표: fct_orders를 "매번 통째로 다시 만들기(table)"에서 "바뀐 것만 MERGE(incremental)"로 바꿉니다. 오늘은 일부러 많은 사람이 처음 쓰는 order_date 기준 + 3일 lookback 필터로 만들고, 8단계에서 무엇을 놓치는지 봅니다.

  지금(3일차)  fct_orders = table        매번 DROP + CREATE (30행 전부 다시)
  바꾸면       fct_orders = incremental
               ├ 첫 실행 / --full-refresh  →  전체를 새로 만듦
               └ 그다음 실행부터            →  필터에 걸린 행만 골라서
                                               order_id 가 있으면 UPDATE, 없으면 INSERT (MERGE)

고칠 파일은 models\marts\fct_orders.sql 하나입니다(notepad models\marts\fct_orders.sql). 3일차에 쓴 SELECT는 한 글자도 건드리지 않고, 위와 아래에 블록을 하나씩 덧붙입니다. contract가 걸린 models\marts\schema.yml도 그대로 둡니다.

두 번째 실행 후 target\run\shop\models\marts\fct_orders.sql을 열어 보세요. MERGE INTO "shop"."main"."fct_orders" ... ON (DBT_INTERNAL_SOURCE.order_id = DBT_INTERNAL_DEST.order_id) WHEN MATCHED THEN UPDATE BY NAME WHEN NOT MATCHED THEN INSERT BY NAME — 내가 쓰던 MERGE 프로시저와 같은 문장입니다. 첫 실행(full refresh) 때는 이 파일에 create table ... fct_orders__dbt_tmp와 contract의 컬럼 정의(order_id bigint not null primary key …)가 들어 있었습니다.

두 가지를 더 보세요.

  • ephemeral이 끼워 넣어진 모습 — target\compiled\shop\models\marts\fct_orders.sql 맨 위에 with __dbt__cte__int_order_payments as (...)가 있고, 조인은 left join __dbt__cte__int_order_payments p로 바뀌어 있습니다. 증분 필터(where o.order_date ...)는 주문 쪽에만 걸리고 결제 CTE는 매번 전체를 다시 계산합니다. 지금은 작아서 괜찮지만, 결제가 아주 커지면 CTE 안에도 같은 범위 조건을 넣거나 intermediate를 테이블로 바꾸는 걸 고민하게 됩니다.
  • primary key 제약 — DuckDB는 PK를 실제로 검사합니다. MERGE는 같은 order_id를 UPDATE하므로 PK와 부딪치지 않고, incremental_strategy='delete+insert'로 바꿔도 먼저 지우고 넣기 때문에 문제없이 돌았습니다(둘 다 직접 확인). 반대로 unique_key 없이 append 하면 같은 주문이 두 번 들어가려다 PK 위반으로 실패합니다 — 제약이 실수를 막아 주는 셈입니다.

  • 언제 incremental로 바꾸나: 처음엔 table로 두고, 빌드 시간·비용이 문제 될 때 바꾸는 게 일반적입니다. incremental은 로직이 복잡해지고 틀릴 여지가 생기니 "작은 테이블까지 전부 incremental"은 피합니다.

    materialized='incremental',

6. 고객 snapshot 만들고 첫 실행 (데이터 바꾸기 전에!)

왜? 원천 고객 테이블은 현재 상태만 갖고 있어서, 등급이 바뀌는 순간 예전 등급은 사라집니다. "10월 15일 당시 gold 고객의 매출" 같은 질문에 답하려면 바뀌기 전 상태를 미리 찍어 둬야 합니다. 그래서 데이터를 바꾸기(7단계) 전에 지금 상태를 첫 버전으로 남깁니다.

프로시저로 치면: 고객 이력 테이블(SCD2)을 직접 관리하던 프로시저 — "updated_at이 바뀐 고객은 현재 행의 end_date를 채워 닫고, 새 버전을 end_date = NULL로 INSERT" — 를 이 yml 몇 줄이 대신합니다. 이론의 snapshot 절에 나온 UPDATE + INSERT 문을 dbt가 만들어 줍니다.

  • 일정에 맞춰 모델보다 먼저 돌립니다. 보통 스케줄러(Airflow 등)에서 dbt snapshot → dbt run(또는 dbt build가 DAG 순서대로 처리) 순서로 매일 같은 시각에 돌립니다. snapshot은 돌린 시점의 상태만 남기니, 주기(하루 1번? 1시간마다?)가 곧 이력의 해상도입니다.

  • timestamp vs check: 원천에 믿을 만한 수정 시각이 있으면 timestamp. 없거나 원천이 수정 시각을 제대로 안 고치면 check + 꼭 필요한 컬럼만 check_cols로(전부 all로 하면 느리고, 의미 없는 컬럼 변경도 쌓입니다).

  • snapshot 테이블은 되살릴 수 없으니 별도 스키마(schema: snapshots)에 두고, 실수로 지우지 않게 권한·백업을 따로 챙기는 팀이 많습니다.
7. "다음 날" 데이터로 바꿔 끼우기

왜? incremental과 snapshot은 "어제와 오늘 데이터가 다를 때"만 차이가 보입니다. 데이터가 그대로면 둘 다 아무 일도 안 일어나서 제대로 동작하는지 알 수 없습니다. 그래서 하루가 지나 원천에서 새 파일이 도착한 상황을 흉내 냅니다.

왜 백업부터? 9단계(다시 재생해 보기)와 5·7일차에 3일차 원본이 다시 필요합니다. 덮어쓰기 전에 원본을 따로 두지 않으면 되돌릴 방법이 없습니다. 운영 테이블을 건드리기 전에 백업 테이블을 떠 두던 습관과 같습니다.

왜 직접 고치지 않고 통째로 바꾸나? 메모장으로 줄을 덧붙이면 줄바꿈 문자가 섞여 DuckDB가 CSV 형식을 잘못 추측할 수 있습니다. 검증된 파일을 통째로 바꿔 끼우면 결과가 이 페이지의 숫자와 정확히 맞습니다.

목표: dbt가 읽는 data\ 폴더의 CSV 3개를 "다음 날" 버전으로 바꿉니다. 하루가 지나 원천 시스템에서 새 파일이 도착한 상황을 흉내 내는 것입니다. 이 단계에서 모델·yml·shop.duckdb는 하나도 건드리지 않습니다.

바뀌는 파일 (덮어씀)지금 (3일차)바꾼 뒤 (다음 날)
data\raw_customers.csv15명 (줄 수 16)16명 (줄 수 17)
data\raw_orders.csv30건 (줄 수 31)40건 (줄 수 41)

줄 수 = 헤더 1줄 + 데이터 행. 끝나면 폴더가 이렇게 됩니다.

  C:\Users\<내이름>\dbt-practice\shop\
  ├── data\          ← dbt가 읽는 곳 (sources.yml: data/{name}.csv). 여기 3개가 "다음 날" 버전으로 바뀜
  ├── data_day3\     ← ① 백업: 3일차 원본 3개 (되돌릴 때 씀, 7일차에도 씀)
  └── data_next\     ← ② 내려받은 "다음 날" 파일 3개 (9단계에서 다시 씀)

dbt는 data\raw_*.csv 세 파일만 정확한 경로로 읽으므로 data_day3\, data_next\는 무시합니다. data\ 밖에 두는 건 헷갈리지 않게 하려는 것입니다.

PowerShell(shop 폴더, venv 켠 상태)에서 아래를 위에서부터 한 덩어리씩 붙여 넣으세요.

Get-ChildItem data_next            # 3개 보이면 OK
# ③ 바꿔 끼우기: data_next\ 의 3개로 data\ 의 3개를 덮어씀

# ④ 확인: 줄 수 (17 / 41 / 43 이면 성공)

Copy-Item 원본 대상\파일 복사(cp, copy와 같음).
data\*.csv*는 "아무 글자나". data 폴더의 CSV 전부 = 3개.

$base = "…"변수 만들기. PowerShell 변수는 $로 시작합니다. 긴 주소를 한 번만 쓰려고.

-s / -L-s 진행 표시를 숨김(silent), -L 주소가 다른 곳으로 넘어가면 따라감(redirect).

되돌리기와 주의
  • 3일차 원본으로 되돌리기: Copy-Item data_day3\*.csv data\ -Force — 다시 다음 날로: Copy-Item data_next\*.csv data\ -Force. 9단계에서 이 두 줄을 씁니다.
  • ①은 한 번만. ③ 다음에 ①을 또 치면 백업이 "다음 날" 파일로 덮여 원본이 사라집니다. 그랬다면 원본을 다시 받으면 됩니다: 위 ②에서 주소 끝의 /next를 뺀 $base = "https://jinjinparkk.github.io/de-study/practice/data"로 바꾸고, -o "data_day3\$f"로 받습니다.
  • mkdir에서 "이미 있습니다" 오류가 나면 폴더가 이미 있다는 뜻이라 무시해도 됩니다.
  • ④에서 숫자가 1이나 이상한 값이면 내려받기가 실패한 것입니다(회사 프록시 등). 아래 링크를 브라우저로 열어 다른 이름으로 저장해 data_next\에 넣고 ③부터 다시 합니다.

직접 받으려면: next/raw_customers.csv · next/raw_orders.csv · next/raw_payments.csv

8. 다시 돌리고 관찰하기 — 주문 3번은 어떻게 됐나?

왜? 이게 "하루가 지난 뒤의 정기 실행"입니다. 증분 모델이 무엇을 반영하고 무엇을 놓치는지, snapshot이 이력을 어떻게 쌓는지 예상 → 실행 → 비교로 확인합니다. 결과를 보기 전에 예상을 먼저 해 보세요. 예상이 틀린 곳이 오늘 배울 곳입니다.

건너뛰면? 증분 모델의 버그는 오류 메시지 없이 조용히 숫자를 틀리게 만듭니다. "OK가 떴으니 맞겠지"가 얼마나 위험한지를 여기서 직접 봅니다(8-2의 테스트도 통과합니다).

프로시저로 치면: MERGE 프로시저가 정상 종료됐는데 대사(원천과 마트 비교) 결과가 안 맞는 상황을 찾아내는 일입니다.

목표: 파일은 고치지 않고 명령만 돌립니다. 5단계의 incremental(order_date 필터)과 6단계의 snapshot이 "다음 날" 데이터를 어떻게 받아들이는지 봅니다. 핵심 질문은 하나: 10-02에 주문했다가 10-21에 반품된 3번 주문이 마트에 반영될까?

8-1. incremental 다시 돌리기

5단계와 같은 dbt run이지만 이번엔 원천이 바뀌었으니 필터·MERGE가 실제로 일을 합니다. 3번(오래된 주문의 변경), 28·30번(최근 주문의 변경), 31번(신규)을 골라 보는 이유는 세 경우가 각각 다르게 처리되기 때문입니다.

dbt run -s fct_orders
dbt show --inline "select order_id, order_date, status, updated_at from {{ ref('fct_orders') }} where order_id in (3, 28, 30, 31) order by 1"
dbt show --inline "select count(*) as n from {{ ref('fct_orders') }}"

결과를 보기 전에 예상해 보세요. 필터는 order_date >= 10-19 - 3일 = 10-16입니다.

실제 결과 보기 
| order_id | order_date | status    |          updated_at |
| -------- | ---------- | --------- | ------------------- |
|        3 | 2026-10-02 | completed | 2026-10-02 10:35:00 |   ← 안 바뀜!
|       28 | 2026-10-18 | completed | 2026-10-21 10:00:00 |   ← returned → completed 반영
|       30 | 2026-10-19 | completed | 2026-10-21 10:00:00 |   ← shipped → completed 반영

테스트가 이런 "조용한 오류"를 잡아 주는지 확인하려고 돌립니다. dbt test는 프로젝트의 모든 테스트(generic + tests\의 singular)를 실행만 하고 모델은 안 만듭니다.

  • "테스트 통과 = 맞다"가 아니라서, 증분 마트에는 원천과의 대사 테스트를 따로 두는 팀이 많습니다. 예: 원천과 마트의 건수·합계 비교, 원천과 마트의 상태가 다른 키가 있으면 실패하는 singular 테스트, dbt_utils의 equal_rowcount·recency 테스트.
  • 증분 모델을 처음 배포할 때는 며칠 동안 full refresh 결과와 증분 결과를 나란히 비교해 보고 넘어가기도 합니다(audit_helper 활용).
  • snapshot 결과는 "현재 행이 키마다 정확히 1개인가"(dbt_valid_to is null인 행의 customer_id가 unique)를 테스트로 걸어 두면 꼬였을 때 바로 알 수 있습니다.
9. 함정 고치기: updated_at 필터 + --full-refresh

왜? 8단계에서 마트가 원천과 달라졌습니다(3번이 아직 completed → 매출이 부풀려짐). 증분 버그를 고칠 때는 두 가지를 해야 합니다: ① 앞으로 안 놓치게 필터를 고치기, ② 이미 놓친 과거 행을 바로잡기. 많은 사람이 ①만 하고 끝내서 틀린 숫자가 계속 남습니다. 9-2에서 그걸 직접 봅니다.

건너뛰면? 실무에서 가장 흔한 incremental 사고("예전 주문 상태가 안 바뀐다")의 원인과 처리 순서를 모른 채 운영하게 됩니다.

프로시저로 치면: 증분 적재의 기준을 업무 날짜에서 워터마크(마지막으로 가져온 변경 시각)로 바꾸고, 로직 수정 후 전체 재적재를 한 번 돌리는 것.

목표: 증분 필터의 기준을 "주문한 날(order_date)"에서 "마지막으로 바뀐 시각(updated_at)"으로 바꿔서, 3번 주문처럼 오래전 주문이 나중에 바뀐 경우도 잡히게 합니다. 그리고 이미 놓친 행은 어떻게 바로잡는지 봅니다.

9-1. 필터 고치기

  1. notepad models\marts\fct_orders.sql
  2. 맨 아래 {% if is_incremental() %} 블록 안에서 order_date 두 군데를 updated_at으로 바꿉니다(o.order_date → o.updated_at, max(order_date) → max(updated_at)). config와 SELECT는 그대로, 3일 lookback도 그대로.
{% if is_incremental() %}
where o.____ >= (
    select max(____) - interval {{ var('lookback_days', 3) }} day
    from {{ this }}
)
{% endif %}

왜 updated_at인가요? 주문 날짜는 한 번 정해지면 안 바뀌지만, 상태는 며칠·몇 주 뒤에 바뀔 수 있습니다. "언제 생겼나"가 아니라 "언제 바뀌었나"로 걸러야 바뀐 행을 놓치지 않습니다.

9-2. 증분 실행 → 3번이 고쳐졌나?

필터만 고치면 충분한지 확인하려고, 먼저 full refresh 없이 평소처럼 증분으로 돌려 봅니다.

dbt run -s fct_orders
dbt show --inline "select order_id, status, updated_at from {{ ref('fct_orders') }} where order_id = 3"

3번이 returned가 됐나요? 예상해 본 뒤 힌트를 여세요.

힌트 1

where o.updated_at >= (select max(updated_at) - interval {{ var('lookback_days', 3) }} day from {{ this }})

힌트 2 — 왜 안 고쳐지지?

지금 마트의 max(updated_at)은 8단계에서 들어간 40번 주문의 10-24 19:55입니다. 3일을 빼도 10-21 19:55. 주문 3번의 updated_at은 10-21 11:30이라 여전히 필터 밖입니다. 한 번 놓친 행은 기준점이 지나가 버려서 증분 실행으로는 다시 못 잡습니다(실제로 확인해 보면 3번은 계속 completed).

정답 보기 
{% if is_incremental() %}
-- 증분 실행일 때만: 이미 들어 있는 행 중 가장 늦게 바뀐 시각의 N일 전 이후에 바뀐 주문
where o.updated_at >= (
    select max(updated_at) - interval {{ var('lookback_days', 3) }} day
    from {{ this }}
)
{% endif %}

로직을 고친 뒤에는 과거 행을 바로잡기 위해 full refresh가 필요합니다. 프로시저로 치면 "로직 수정 후 전체 재적재"입니다.

dbt run -s fct_orders --full-refresh
dbt show --inline "select order_id, status from {{ ref('fct_orders') }} where order_id = 3"

이제 3번이 returned로 나옵니다(실제 확인).

9-3. 고친 로직이라면 처음부터 잡았을까? (다시 재생해 보기)

full refresh는 "결과"를 고쳤을 뿐, 고친 필터가 정기 증분 실행에서 3번을 잡는지는 아직 증명하지 못했습니다. 어제 → 오늘을 다시 재생해 증분만으로 맞는지 확인합니다. 고친 로직을 운영에 올리기 전에 하는 검증과 같습니다.

3일차 데이터로 되돌려 마트를 새로 만든 다음, 다음 날 데이터로 바꿔 증분으로만 돌립니다. 7단계에서 만든 두 폴더를 그대로 씁니다. 이 과정에서는 dbt snapshot(과 dbt build)을 돌리지 마세요 — 고객 이력이 꼬입니다.

Copy-Item data_day3\*.csv data\ -Force

  • 증분 버그 처리 순서: ① 필터(워터마크) 수정 → ② 리뷰·CI 통과 → ③ 운영에서 해당 모델만 dbt run -s 모델 --full-refresh (하위 모델도 영향이 있으면 -s 모델+) → ④ 대사 쿼리로 확인. 너무 큰 테이블이라 전체 재빌드가 부담되면 --vars로 lookback을 크게 줘서 영향 기간만 다시 돌리거나, microbatch라면 --event-time-start/--event-time-end로 그 기간만 backfill 합니다.
  • 워터마크 컬럼은 원천 담당자에게 "값이 바뀔 때마다 갱신되는지"를 꼭 확인합니다. 갱신을 안 하는 원천이면 적재 시각(_loaded_at)을 쓰거나, 정기 full refresh로 보완합니다.
  • 증분 기준을 {{ this }}의 max()로 잡으면 실행마다 대상 테이블을 한 번 더 읽습니다. BigQuery에서는 파티션 컬럼으로 거르거나, 고정 기간(current_date - 3)으로 잡아 비용을 줄이기도 합니다.

  • {{ }} 찍기, {% %} 흐름, {# #} 주석. -로 공백 제어. 결과는 언제나 target/compiled에서 확인
  • 파싱 때는 DB에 묻지 않는다 → run_query는 if execute 안에서
  • 매크로는 DB에 저장되지 않고 SQL에 펼쳐진다. 패키지(dbt deps)로 남의 매크로도 쓴다
  • incremental: 첫 실행은 전체, 그다음은 필터+MERGE. 로직을 고치면 --full-refresh

다음 중 컴파일된 SQL(target/compiled)에 남지 않는 것은?

  1. -- 정제 단계
  2. {# 정제 단계 #}
  3. {{ ref('stg_orders') }} 가 바뀐 테이블 이름
  4. {% for %} 반복이 만들어 낸 컬럼들
{# #}는 Jinja 주석이라 컴파일하면 사라집니다. --는 Jinja 입장에선 그냥 글자라서 그대로 남고(그 안의 Jinja도 실행됩니다), ③④는 Jinja가 찍어 낸 결과 그 자체입니다.

{% for m in methods %} sum(...) as {{ m }}_amount, {% endfor %} from ... 를 실행했더니 문법 오류가 났습니다. 가장 알맞은 해결은?

  1. {%- -%}로 공백을 모두 지운다
  2. {{ }}를 {% %}로 바꾼다
  3. 반복을 매크로로 옮긴다
  4. 쉼표를 {% if not loop.last %},{% endif %}로 바꾼다
마지막 컬럼 뒤에 쉼표가 남아 ..._amount, from이 된 것이 원인입니다. 공백 제어(①)는 보기만 바꿀 뿐 쉼표는 그대로이고, 매크로로 옮겨도(③) 같은 문제가 따라갑니다. ②는 값을 찍지 못하게 만들어 더 망가집니다.

run_query() 결과를 쓸 때 {% if execute %}로 감싸야 하는 이유는?

  1. dbt가 처음 파일을 훑는 파싱 단계에서는 DB에 쿼리하지 않아 결과가 비어 있기 때문
  2. run_query는 prod target에서만 동작하기 때문
  3. 쿼리 결과를 캐시해서 비용을 줄이기 위해
  4. execute가 없으면 쿼리가 두 번 실행되기 때문
dbt는 실행 전에 모든 파일을 파싱해 DAG를 만드는데, 이때 execute는 거짓이고 run_query는 None을 돌려줍니다. 실제 실행 단계에서만 결과가 있습니다. target 종류(②)나 캐시(③)와는 관계없습니다.

incremental 모델에서 is_incremental()이 거짓이 되는 경우가 아닌 것은?

  1. 대상 테이블이 아직 DB에 없을 때
  2. --full-refresh로 실행했을 때
  3. 원천에 새 행이 하나도 없을 때
  4. 같은 이름의 객체가 테이블이 아니라 뷰일 때
is_incremental()은 "대상이 이미 테이블로 있고, full refresh가 아니고, 모델이 incremental인가"만 봅니다. 원천 데이터가 있는지 없는지는 보지 않습니다. 새 행이 없으면 필터 결과가 0행일 뿐, 증분 실행은 그대로 일어납니다.

실습에서 order_date >= max(order_date) - 3일 필터로 다음 날 데이터를 돌렸을 때 일어난 일은?

  1. 주문 31~40번이 들어가지 않았다
  2. 주문 26~30번이 중복으로 두 줄씩 생겼다
  3. 주문 28·30번의 상태 변경은 반영됐지만 주문 3번의 반품은 반영되지 않았다
  4. 모든 변경이 반영됐다
필터가 10-16 이후 주문(25~40번, 16건)만 읽었습니다. 26~30번은 그 안이라 MERGE로 UPDATE, 31~40번은 INSERT. 하지만 3번은 10-02 주문이라 필터 밖이었습니다. unique_key가 있으니 중복(②)은 생기지 않습니다.

증분 필터를 updated_at으로 고친 뒤 dbt run을 했는데도 주문 3번이 여전히 completed였습니다. 이유와 해결로 맞는 것은?

  1. 기준점 max(updated_at)이 이미 3번의 수정 시각보다 뒤로 지나가서 → --full-refresh
  2. unique_key가 없어서 → unique_key 추가
  3. merge 전략은 UPDATE를 못 해서 → delete+insert로 변경
  4. snapshot을 먼저 돌려야 해서 → dbt snapshot
마트에는 이미 10-24 19:55까지의 행이 있어, 3일 lookback을 줘도 10-21 19:55 이후만 읽습니다. 3번은 10-21 11:30에 바뀌었으니 계속 필터 밖이죠. 한 번 놓친 행은 full refresh로만 바로잡힙니다. merge는 UPDATE를 하고(③ 틀림), snapshot은 fct_orders와 무관합니다(④).

snapshot의 strategy: check를 고르는 가장 알맞은 상황은?

  1. 원천에 믿을 만한 updated_at 컬럼이 있을 때
  2. 이력을 빨리 쌓고 싶을 때
  3. 원천에서 지워진 행을 닫고 싶을 때
  4. 원천에 수정 시각 컬럼이 없어서, 정해 둔 컬럼 값이 달라졌는지로 판단해야 할 때
check는 check_cols의 값을 비교해 변경을 찾습니다. 수정 시각이 있으면 timestamp가 더 빠르고 정확합니다(①②). 삭제 처리(③)는 전략과 별개인 hard_deletes 설정입니다.

실습 8단계 뒤 customers_snapshot에서 2번 고객의 행은 어떻게 되어 있었나요?

  1. gold 한 줄만 있다 (basic은 덮어써짐)
  2. basic(dbt_valid_to = 10-21 08:00) 한 줄 + gold(dbt_valid_to NULL) 한 줄
  3. basic 한 줄만 있다 (snapshot은 신규만 넣음)
  4. basic·gold 두 줄 모두 dbt_valid_to가 NULL
SCD2는 덮어쓰지 않고, 옛 버전을 닫고(dbt_valid_to에 새 버전 시작 시각) 새 버전을 현재(NULL)로 추가합니다. 그래서 전체가 15행 → 18행(2·5번 +1씩, 16번 신규)이 되었고 현재 행은 16개입니다. 현재 행이 두 개(④)라면 unique_key가 깨진 것입니다.
