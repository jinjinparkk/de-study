Airflow 핵심 개념 — "언제, 어떤 순서로, 몇 번이든 같게"

🧸 비유

cron은 알람 시계입니다. "6시에 울려라"만 압니다. 앞사람이 일을 끝냈는지, 어제 실패했는지는 모릅니다.

Airflow는 주방 매니저입니다. 순서표(DAG)를 들고 "재료 손질이 끝났으니 이제 볶기 시작", "볶기가 실패했네, 5분 뒤 다시", "지난주 화요일 메뉴를 다시 만들어 달래? 화요일 재료로 다시 해" 를 지휘합니다. 매니저는 직접 요리하지 않습니다. 요리는 요리사(BigQuery, dbt, Spark…)가 합니다.

프로시저 감각으로 옮기면
  • 예약 쿼리의 "매일 06:00" = Airflow의 schedule
  • 프로시저 인자 p_date = Airflow가 실행마다 넣어 주는 logical date ({{ ds }})
  • "적재 끝나면 CALL" 을 사람이 시간 간격으로 맞추던 것 = 태스크 의존성 (적재 >> 프로시저)
  • 실패 시 수동 재실행·날짜 바꿔 재실행 = retries · 백필
Airflow가 하지 않는 일

Airflow는 데이터를 직접 옮기거나 계산하는 곳이 아닙니다. 수 GB 데이터를 Airflow 태스크 안에서 pandas로 돌리는 건 가능은 하지만 나쁜 습관입니다. 무거운 일은 BigQuery·dbt·Spark에 시키고, Airflow는 "시켜라, 기다려라, 결과 확인해라"만 합니다. (아래 XCom 절에서 다시 나옵니다.)

💡 한 줄 요약 오케스트레이터는 시간이 아니라 "앞 작업의 성공"으로 순서를 잇고, 실패·재시도·과거 날짜 재처리·기록을 대신 챙겨 주는 지휘자입니다.

DAG · Task · Operator · TaskFlow

DAG = 작업 순서도 한 장

DAG(Directed Acyclic Graph, 방향이 있고 되돌아오는 길이 없는 그래프)는 2일차 dbt 리니지와 같은 개념입니다. 화살표는 "앞이 끝나야 뒤가 시작"을 뜻하고, 돌고 도는 고리는 허용하지 않습니다. Airflow에서 DAG 하나는 보통 파이썬 파일 하나에 정의하고, 그 안에 이름(dag_id)·스케줄·시작일 같은 설정과 태스크들의 순서를 적습니다.

┌────────────┐     ┌─────────────┐     ┌─────────┐     ┌────────────┐
│ show_dates │────▶│ extract_day │────▶│  check  │────▶│ list_files │
└────────────┘     └─────────────┘     └─────────┘     └────────────┘

 (@task 함수)        (@task 함수)          (@task 함수)      (BashOperator)

Task와 Operator

  • Task = 순서도의 칸 하나. "이 일을 해라"의 단위이고, 성공·실패·재시도도 태스크 단위로 기록됩니다.
  • Operator = 칸의 종류(틀). "셸 명령을 돌리는 칸"(BashOperator), "파이썬 함수를 돌리는 칸"(PythonOperator), "BigQuery 쿼리를 보내는 칸"(BigQueryInsertJobOperator), "무언가를 기다리는 칸"(Sensor) 등이 있습니다. Operator에 설정값을 채우면 Task가 됩니다.
종류예언제
액션 OperatorBashOperator, PythonOperator, BigQueryInsertJobOperator무언가를 실행
SensorFileSensor, S3KeySensor, ExternalTaskSensor조건이 맞을 때까지 기다림 (파일 도착 등)
TaskFlow @task파이썬 함수에 @task를 붙임파이썬 로직을 짧게. 내부적으로는 PythonOperator

Operator는 provider 패키지로 나뉘어 있습니다. Bash·Python 같은 기본 Operator는 Airflow 3부터 apache-airflow-providers-standard에 들어 있어서 import 경로가 airflow.providers.standard.operators.bash입니다. BigQuery는 apache-airflow-providers-google.

TaskFlow API — 함수에 @task만 붙이기

Airflow 3에서 DAG을 쓰는 표준 방식입니다. from airflow.sdk import dag, task 두 개면 됩니다.

from airflow.sdk import dag, task      # Airflow 3 의 DAG 작성용 공개 도구 모음

@dag(schedule=None)                    # 아래 함수 = DAG 하나
def my_pipeline():
    @task                              # 아래 함수 = 태스크 하나
    def extract():
        return [1, 2, 3]               # return 값은 다음 태스크로 전달된다 (XCom)

    @task
    def load(rows):                    # 앞 태스크 결과를 인자로 받는다
        print(len(rows))

    load(extract())                    # 함수 호출 모양 = 순서 연결 (extract → load)

my_pipeline()                          # 파일 맨 아래에서 한 번 불러야 등록된다

의존성 표시: >>

a >> b              # a 다음 b
a >> [b, c] >> d    # a 다음 b·c 동시에, 둘 다 끝나면 d
b << a              # 같은 뜻 (반대 방향 화살표)
load(transform(extract()))   # TaskFlow: 값을 넘기면 자동으로 순서가 생긴다
  a >> [b, c] >> d   를 그리면

        ┌───▶ b ───┐
  a ────┤          ├───▶ d      d 는 기본적으로 b, c 가 "모두 성공"해야 시작
        └───▶ c ───┘            (trigger_rule="all_success" 가 기본값)
가장 흔한 오해: DAG 파일은 "실행"되는 코드가 아니라 "순서도를 그리는" 코드

DAG 파일의 맨 위(태스크 함수 바깥)에 적은 코드는 Airflow가 파일을 읽을 때마다(기본 수십 초~몇 분 간격) 실행됩니다. 여기에 DB 조회나 API 호출을 넣으면 하루에 수천 번 불립니다. 실제 일은 태스크 함수 안에서만 하세요.

또 extract()를 "부르는" 순간 데이터가 읽히는 게 아닙니다. 순서도에 칸이 하나 생길 뿐이고, 실제 실행은 나중에 워커가 합니다.

🧸 비유

DAG 파일은 공연 큐시트입니다. 큐시트를 인쇄한다고 조명이 켜지지는 않죠. 큐시트(DAG)에는 "1번 조명 → 2번 음악 → 3번 막 내림" 순서와 "매일 저녁 7시 공연"(schedule)이 적혀 있고, 공연 날마다 스태프(워커)가 큐시트대로 실제로 움직입니다. 공연 한 번이 DagRun, 그 공연에서 "2번 음악" 한 번 튼 것이 TaskInstance입니다.

프로시저 감각으로 옮기면
  • DAG = 여러 프로시저를 순서대로 부르는 마스터 프로시저 (단, 순서를 화살표로 선언)
  • Task = 마스터 프로시저 안의 CALL sp_xxx() 한 줄. 다만 줄마다 성공/실패 기록이 따로 남고, 실패한 줄만 다시 돌릴 수 있다
  • Operator = "CALL 하는 대상의 종류" (BigQuery 쿼리냐, 셸 스크립트냐, 파이썬이냐)

DagRun과 TaskInstance, 그리고 상태

DAG가 "설계도"라면, 실행할 때마다 생기는 기록이 둘 있습니다.

  • DagRun = DAG의 실행 1회. "2026-10-03 날짜분 실행" 같은 단위. run_id로 구분(scheduled__…, manual__…, backfill__…).
  • TaskInstance = 그 DagRun 안에서 태스크 1개의 실행. 상태·시도 횟수·로그가 여기 붙습니다.
TaskInstance 상태 흐름 (자주 보는 것만)

   │         스케줄러가       실행기가     워커가     │
   │         "돌릴 차례"      대기열에     실행 중    ├──▶ failed ──(retries 남음)──▶ up_for_retry ──▶ scheduled …
   │                                            │
   │                                            ├──▶ skipped        (일부러 건너뜀)
   │                                            └──▶ deferred       (triggerer 에게 기다림을 맡김)
   └──▶ upstream_failed   (앞 태스크가 실패해서 시작도 못 함)

프로시저 감각으로 옮기면

프로시저 실행 이력을 남기려고 etl_log(job_name, run_date, status, started_at, ended_at, error_msg) 테이블을 직접 만들어 본 적이 있다면, 그게 바로 Airflow 메타DB의 dag_run · task_instance 테이블입니다. Airflow는 이걸 기본으로 갖고 있고, 화면까지 붙여 줍니다.

Airflow를 처음 배우는 사람 거의 모두가 여기서 막힙니다. "10월 4일 0시에 돌았는데 왜 날짜가 10월 3일이지?" 천천히 갑니다.

출발점: 배치는 "지나간 구간"을 처리한다

일 배치는 보통 어제 하루치 데이터를 오늘 새벽에 처리합니다. 10월 3일 데이터는 10월 3일 23:59:59가 지나야 다 모이니까, 빨라도 10월 4일 0시 이후에야 처리할 수 있습니다. 그러면 이 실행을 부를 이름이 두 개 생깁니다.

  • "10월 4일 0시에 돈 실행" — 실제 실행 시각 (Airflow 용어로 run_after)
  • "10월 3일 데이터를 처리한 실행" — 데이터 기준 날짜 (logical date)

프로시저로 치면 CALL sp_build_daily_sales('2026-10-03')을 10월 4일 새벽에 부르는 것과 같습니다. 인자 p_date는 10-03이고, 부른 시각은 10-04입니다. Airflow의 logical date는 이 p_date 쪽입니다. 이름이 "실행 날짜"(옛 이름 execution_date)처럼 들려서 헷갈렸던 거라, Airflow 2.2부터 "논리적 날짜(logical date)"로 이름을 바꿨습니다.

"구간이 있는" 스케줄: CronDataIntervalTimetable

오늘 실습 DAG는 schedule=CronDataIntervalTimetable("0 0 * * *", timezone="UTC")를 씁니다. "매일 00:00마다, 직전 하루 구간을 처리한다"는 뜻입니다.

실제 시간 ──▶
            10-03 00:00               10-04 00:00               10-05 00:00
 ────────────────┼─────────────────────────┼─────────────────────────┼──────────
                 │◀──── 데이터 구간 A ─────▶│◀──── 데이터 구간 B ─────▶│
                 │   (10-03 하루치 주문)     │   (10-04 하루치 주문)     │
                                           ▲                         ▲
                                     실행 A 시작                 실행 B 시작
                                     (구간 A 가 끝난 직후)          (구간 B 가 끝난 직후)

 실행 A:  run_after           = 10-04 00:00     ← 실제로 도는 시각
          data_interval_start = 10-03 00:00     ← 구간 시작
          data_interval_end   = 10-04 00:00     ← 구간 끝 (이 시각은 포함 안 함)
          logical_date        = 10-03 00:00     ← = 구간 시작
          ds                  = "2026-10-03"    ← logical_date 의 날짜 부분 (문자열)

즉 이 스케줄에서는 ds = 처리할 데이터의 날짜가 되어 프로시저의 p_date와 딱 맞습니다. 그래서 DAG 안에서 WHERE order_date = '{{ ds }}'처럼 쓰면 됩니다.

스케줄러가 다음 실행을 어떻게 계산하는지, Airflow 3.3.2의 시간표 객체에 직접 물어본 결과입니다(10-03부터 시작한다고 가정).

CronDataInterval UTC    | run_after 2026-10-04 00:00:00+00:00 | logical 2026-10-03 00:00:00+00:00 | interval 2026-10-03 00:00:00+00:00 ~ 2026-10-04 00:00:00+00:00
CronTrigger(@daily) UTC | run_after 2026-10-03 00:00:00+00:00 | logical 2026-10-03 00:00:00+00:00 | interval 2026-10-03 00:00:00+00:00 ~ 2026-10-03 00:00:00+00:00

Airflow 3에서 바뀐 함정: schedule="@daily"는 구간이 없다

두 번째 줄을 보세요. Airflow 3에서는 "@daily"나 "0 0 * * *" 같은 cron 문자열을 그냥 쓰면 CronTriggerTimetable이 됩니다(설정 [scheduler] create_cron_data_intervals의 기본값이 False로 바뀜 — 실측 확인). 이 시간표는 "그 시각에 방아쇠를 당긴다"만 알고 구간 개념이 없습니다.

10-04 00:00에 도는 실행CronDataIntervalTimetable (Airflow 2의 @daily와 같음)schedule="@daily" (Airflow 3 기본 = CronTriggerTimetable)
logical_date10-03 00:0010-04 00:00
data_interval10-03 00:00 ~ 10-04 00:0010-04 00:00 ~ 10-04 00:00 (길이 0)
{{ ds }}2026-10-03 (= 처리할 날짜)2026-10-04 (= 오늘. 어제 데이터를 원하면 {{ macros.ds_add(ds, -1) }})

둘 다 맞는 방식입니다. 다만 인터넷 예제(대부분 Airflow 2)를 그대로 옮기면 하루가 밀립니다. 그래서 이 과정에서는 "구간"을 분명히 하려고 CronDataIntervalTimetable을 명시합니다. 실습 직접 비교 결과(같은 날짜 2026-10-04로 airflow dags test):

logical_date        = 2026-10-04 00:00:00+00:00
data_interval_start = 2026-10-04 00:00:00+00:00
data_interval_end   = 2026-10-04 00:00:00+00:00
ds                  = 2026-10-04

두 번째 함정: ds는 UTC 날짜다

ds는 logical_date를 UTC로 날짜만 잘라 만든 문자열입니다(Airflow 3.3.2 소스: ds = logical_date.strftime("%Y-%m-%d"), logical_date는 UTC). 그래서 스케줄을 서울 00:00으로 잡으면, 서울 10-03 00:00 = UTC 10-02 15:00 이라서 ds가 하루 전 날짜로 찍힙니다. 실제로 서울 시간대 시간표로 바꿔 돌려 본 결과:

logical_date        = 2026-10-02 15:00:00+00:00
ds                  = 2026-10-02          ← 서울 기준으로는 10-03 인데!

그래서 실습 DAG는 시간대를 UTC로 둡니다(한국 시간 매일 09:00 실행). 서울 날짜가 꼭 필요하면 data_interval_start.in_timezone("Asia/Seoul")로 바꿔서 쓰면 됩니다.

세 번째 함정: 손으로 돌린 실행

Trigger 버튼이나 airflow dags test DAG 2026-10-04로 돌리면 입력한 시각이 그대로 logical_date가 되고, 구간은 "그 시각에 끝나는 직전 구간"으로 추정됩니다. 그래서 구간 시간표에서도 수동 실행은 ds와 구간 시작이 하루 어긋납니다(실측):

logical_date        = 2026-10-04 00:00:00+00:00
data_interval_start = 2026-10-03 00:00:00+00:00
data_interval_end   = 2026-10-04 00:00:00+00:00
ds                  = 2026-10-04

실습 DAG는 ds 하나만 기준으로 씁니다. 그러면 "스케줄 실행·백필 = 그 구간의 날짜", "수동 실행 = 내가 입력한 날짜"가 되어 사람이 예측하기 쉽습니다. 한 DAG 안에서 ds와 data_interval_*를 섞어 쓰지 마세요.

🧸 비유

회사 월간 마감을 생각해 보세요. "9월 마감"은 10월 2일에 합니다. 마감 서류에 적는 이름은 "9월분"(logical date)이고, 실제로 작업한 날은 10월 2일(run_after)입니다. 누구도 "10월 2일 마감"이라고 부르지 않죠. Airflow도 실행을 "몇 월분인지"로 부릅니다.

프로시저 감각으로 옮기면 
-- 예약 쿼리 (매일 06:00):
CALL dm.sp_build_daily_sales(DATE_SUB(CURRENT_DATE(), INTERVAL 1 DAY));
--                           └ 이 "어제 날짜 계산"을 Airflow 가 대신 해서 {{ ds }} 로 준다

차이점: 예약 쿼리는 "오늘 기준 어제"를 매번 계산하니, 사흘 전 날짜분을 다시 돌리려면 SQL을 고쳐야 합니다. Airflow는 실행마다 logical date가 고정돼 있어서, 10-03 실행을 한 달 뒤에 다시 돌려도 ds는 여전히 "2026-10-03"입니다. 이게 백필과 재실행을 가능하게 하는 핵심입니다.

절대 하지 말 것: 태스크 안에서 "오늘 날짜" 쓰기

datetime.now(), CURRENT_DATE()로 처리 날짜를 정하면, 같은 실행을 나중에 다시 돌렸을 때 다른 날짜를 처리합니다. 백필도 전부 "오늘"을 처리해 버립니다. 처리 날짜는 언제나 {{ ds }}(또는 data_interval)에서 가져오세요.

💡 한 줄 요약 logical date는 "몇 일분을 처리하는 실행인가"이고, 실제로 도는 시각이 아닙니다. 구간 시간표에서는 ds = 구간 시작 날짜, Airflow 3의 "@daily"에서는 ds = 도는 날. 그리고 ds는 UTC 날짜입니다.

catchup과 백필

catchup: 켜는 순간 "밀린 숙제"를 할까?

start_date=2026-10-01인 DAG를 오늘(11-04)에 처음 켜면, 10-01부터 11-03까지 33개 구간이 "아직 안 돈" 상태입니다.

  • catchup=True → 33개를 전부 자동으로 만들어 돌립니다.
  • catchup=False (Airflow 3 기본값, 실측 확인) → 가장 최근 구간 하나(11-03분)만 돌고, 그 뒤로 정상 스케줄.

catchup을 실수로 켜 두면 DAG를 켜는 순간 몇 백 개 실행이 쏟아질 수 있어서, 보통 False로 두고 필요할 때 백필을 명시적으로 합니다.

백필: 지정한 과거 구간을 다시 돌리기

Airflow 3의 백필은 airflow backfill create로 "이 범위를 돌려 달라"는 요청을 등록하면, 스케줄러가 일반 실행처럼 처리합니다(화면에서도 진행 상황이 보임). 먼저 --dry-run으로 어떤 날짜가 만들어질지 확인하는 습관을 들이세요. 아래는 실습 DAG로 실제로 본 결과입니다.

Runs to be attempted:
+---------------------------+-----------------+------------------+
| logical_date              | partition_key   | partition_date   |
+===========================+=================+==================+
| 2026-10-01 00:00:00+00:00 |                 |                  |
| 2026-10-02 00:00:00+00:00 |                 |                  |
| 2026-10-04 00:00:00+00:00 |                 |                  |
| 2026-10-05 00:00:00+00:00 |                 |                  |
+---------------------------+-----------------+------------------+

10-03이 빠졌습니다. 그 날짜로 이미 실행 기록이 있었기 때문입니다. 기본값 --reprocess-behavior none은 "이미 있는 날짜는 건너뛰기"입니다. 같은 명령에 --reprocess-behavior completed를 붙이자 10-01~10-05 다섯 개가 모두 나왔습니다.

옵션뜻

--reprocess-behavior none|failed|completed기록이 이미 있는 날짜를: 건너뜀(기본) / 실패한 것만 다시 / 성공한 것까지 다시

백필은 실행 기록만 만들고, 실제 실행은 스케줄러가 합니다. 스케줄러는 꺼진(paused) DAG의 태스크를 대기열에 넣지 않습니다(3.3.2 스케줄러 코드에서 확인). 화면에서 DAG 토글을 켠 뒤 백필하세요.

프로시저 감각으로 옮기면 
-- 백필 = 이걸 날짜 범위로 돌려 주는 것
FOR d IN ('2026-10-01' .. '2026-10-05') LOOP
  CALL dm.sp_build_daily_sales(d);
END LOOP;

단, 프로시저가 몇 번 돌려도 같은 결과여야 이 루프를 안심하고 돌릴 수 있습니다. 그게 다음 절입니다.

멱등성: 몇 번 돌려도 같은 결과

멱등(idempotent)은 "같은 입력으로 1번 돌리든 10번 돌리든 결과가 같다"는 뜻입니다. Airflow는 재시도·Clear·백필로 같은 날짜를 여러 번 돌리는 게 일상이라, 모든 태스크가 멱등이어야 합니다.

멱등이 아님: 돌릴 때마다 쌓인다
INSERT INTO dm.daily_sales
SELECT order_date, COUNT(*), SUM(amount)
FROM ... WHERE order_date = '{{ ds }}'
GROUP BY order_date;
-- 재시도 1번 = 같은 날짜 행이 2줄
멱등: 그 날짜 칸을 통째로 바꾼다
DELETE FROM dm.daily_sales
WHERE order_date = '{{ ds }}';
INSERT INTO dm.daily_sales
SELECT ... WHERE order_date = '{{ ds }}' ...;
-- 몇 번 돌려도 그 날짜는 1줄

프로시저에서 이미 쓰던 DELETE + INSERT (날짜 기준) 패턴이 정확히 멱등 패턴입니다. 다른 모양도 있습니다.

  • 파티션 덮어쓰기: BigQuery WRITE_TRUNCATE 로 table$20261003 파티션 교체, 파일이면 dt=2026-10-03/ 폴더를 통째로 교체 (오늘 실습)
  • MERGE(키 기준 upsert): 4일차 dbt incremental의 unique_key
  • 임시 파일에 쓰고 마지막에 이름 바꾸기: 중간에 죽어도 반쪽 파일이 남지 않게 (오늘 실습 DAG의 os.replace)
멱등을 깨는 흔한 원인
  • 처리 날짜를 now()로 정함 (위 절)
  • INSERT만 하고 지우지 않음, 파일에 append
  • "마지막으로 처리한 ID 이후" 같은 상태를 태스크 바깥(변수 등)에 저장하고 갱신
  • 입력 원천 자체가 바뀜 (API가 과거 데이터를 다시 주지 않음) → 원본을 날짜별로 보관(raw 적재)하는 이유
🧸 비유

엘리베이터 버튼은 멱등입니다. 3층 버튼을 다섯 번 눌러도 3층에 한 번 섭니다. 반면 자판기 버튼은 멱등이 아니죠 — 다섯 번 누르면 다섯 개가 나옵니다(돈이 있다면). 배치 태스크는 엘리베이터 버튼처럼 만들어야 합니다.

💡 한 줄 요약 "그 날짜(ds) 칸만 통째로 지우고 다시 채운다" — 프로시저의 DELETE + INSERT가 Airflow 멱등성의 기본형입니다.

템플릿과 컨텍스트: {{ ds }}는 어디서 오나

Airflow는 실행 직전에 각 태스크에 컨텍스트(그 실행의 정보 묶음)를 만들어 줍니다. 이걸 꺼내 쓰는 방법이 두 가지입니다.

① 템플릿 (Jinja) — 문자열 안에 {{ }}

dbt에서 쓰던 그 Jinja입니다. Operator의 템플릿 가능한 인자(예: BashOperator의 bash_command, SQL Operator의 sql)에 쓰면 실행 직전에 값으로 바뀝니다.

BashOperator(
    task_id="list_files",
    bash_command="ls -l {{ params.out_root }}/dt={{ ds }}",   # 실행 직전 → ls -l /opt/airflow/output/orders/dt=2026-10-03
)

템플릿이 모든 인자에서 되는 건 아닙니다. 각 Operator 문서의 template_fields에 있는 인자만 바뀝니다. 태스크 화면의 Rendered Template(렌더링 결과) 탭에서 실제로 무엇으로 바뀌었는지 볼 수 있습니다 — dbt의 target/compiled와 같은 역할입니다.

    ctx = get_current_context()      # 전체 컨텍스트가 필요하면 (from airflow.sdk import get_current_context)

XCom: 태스크끼리 쪽지 주고받기

태스크는 서로 다른 프로세스(운영에선 다른 서버)에서 돕니다. 파이썬 변수를 공유할 수 없죠. 그래서 작은 값을 메타DB에 적어 두고 다음 태스크가 읽어 가는 장치가 XCom(cross-communication)입니다. TaskFlow에서 return 하면 자동으로 XCom에 저장되고, 그 값을 다음 @task의 인자로 넘기면 자동으로 꺼내 옵니다.

extract_day ──return "/opt/airflow/output/orders/dt=2026-10-03/orders.csv"──▶ ┌──────────┐
                                                                            │ 메타DB    │
check(path) ◀──────────────── 같은 값을 꺼내 인자로 ───────────────────────────── │ xcom 테이블│
                                                                            └──────────┘
XCom에 큰 데이터를 넣지 마세요
  • XCom은 메타DB의 한 칸입니다. 수만 행 데이터프레임을 넣으면 DB가 커지고 느려지고, 크기 제한에 걸려 실패합니다.
  • 넣는 것: 파일 경로, 테이블 이름, 행 수, 배치 ID 같은 쪽지. 데이터 자체는 저장소(GCS·S3·웨어하우스 테이블)에 두고 그 위치만 넘깁니다.
  • 오늘 DAG도 데이터는 파일로 쓰고, XCom에는 경로 문자열만 넘깁니다.
프로시저 감각으로 옮기면

XCom = 프로시저 간에 OUT 파라미터로 스칼라 값(행 수, 상태 코드)을 넘기는 것. 결과 집합을 넘길 땐 OUT 파라미터가 아니라 임시 테이블에 넣고 이름을 넘겼죠. 똑같습니다.

params와 재시도 기초

params: 실행 인자

@dag(params={"min_amount": 0})처럼 기본값을 두면, 화면에서 Trigger할 때 값을 바꿔 넣을 수 있고 태스크에서는 {{ params.min_amount }}나 ctx["params"]["min_amount"]로 읽습니다. 프로시저의 기본값 있는 인자와 같습니다. 단, 스케줄 실행은 항상 기본값으로 돕니다.

재시도

from datetime import timedelta            # 시간 길이 (SQL 의 INTERVAL)

@dag(..., default_args={                  # 이 DAG 의 모든 태스크 기본값
    "retries": 2,                         # 실패하면 2번 더 (총 3번 시도)
    "retry_delay": timedelta(minutes=5),  # 시도 사이 5분 쉬기
})

재시도는 "일시적 실패"(네트워크, 잠깐의 잠금)를 흡수하는 장치입니다. SQL 오타 같은 영구적 실패는 몇 번 재시도해도 같으니, 재시도 횟수를 너무 크게 두지 마세요. 그리고 재시도는 같은 태스크를 다시 돌리는 것이라 멱등이 아니면 데이터가 꼬입니다. 알림·타임아웃 같은 운영 설정은 6일차에 자세히 봅니다.

2. 작업 폴더와 설정 파일 준비

컨테이너는 언제든 버리고 새로 만드는 물건입니다. 그 안에 DAG 파일이나 결과를 두면 컨테이너를 지울 때 같이 사라집니다. 그래서 오래 남겨야 할 것(DAG 코드·입력·결과·로그)은 내 PC 폴더에 두고, 컨테이너와 공유 폴더처럼 연결(volume mount)합니다. 내가 메모장으로 DAG를 고치면 컨테이너 안 Airflow가 바로 그 파일을 봅니다.

"어떤 이미지로, 어떤 포트로, 어떤 폴더를 연결해서" 띄울지는 docker-compose.yml 한 파일에 적어 둡니다. 서버 설정을 사람 기억이 아니라 문서(코드)로 남기는 것이라, 내일 다시 띄워도·다른 PC에서 띄워도 똑같이 뜹니다. 이 단계를 건너뛰면 3단계에서 no configuration file provided, 7단계에서 FileNotFoundError가 납니다.

목표: dbt 프로젝트와 섞이지 않는 새 폴더 C:\Users\<내이름>\airflow-practice를 만들고, 그 안에 설정 파일 1개 + 폴더 4개 + 입력 CSV 1개를 둡니다. 폴더 4개는 3단계에서 컨테이너 안 경로와 연결(mount)됩니다 — 한쪽에서 파일을 바꾸면 다른 쪽에서도 바로 보입니다.

  내 PC (Windows)                                  컨테이너 안 (Linux)

# 5일차: Airflow 3 를 컨테이너 하나(standalone)로 띄우는 설정
# 실행:  docker compose up -d      →  http://localhost:8083
# 끄기:  docker compose stop       (기록 유지)   /   docker compose down  (컨테이너 삭제 → 실행 기록도 사라짐)
name: de-airflow

services:
  airflow:
    image: apache/airflow:3.3.2
    command: standalone            # 스케줄러·dag-processor·api-server·triggerer 를 한 컨테이너에서 같이 띄우는 연습용 모드
    ports:
      - "8083:8080"                # 내 PC 8083 → 컨테이너 8080 (8000·8001·8081 은 이미 사용 중)
    environment:
      AIRFLOW__CORE__LOAD_EXAMPLES: "False"                 # 예제 DAG 수십 개를 안 보이게
      AIRFLOW__CORE__SIMPLE_AUTH_MANAGER_ALL_ADMINS: "True" # 로그인 없이 모두 관리자 (내 PC 연습용에서만!)
      AIRFLOW__DAG_PROCESSOR__REFRESH_INTERVAL: "30"        # 새 DAG 파일을 30초마다 찾기 (기본 300초)
    volumes:
      - ./dags:/opt/airflow/dags          # 내가 쓰는 DAG 파일
      - ./data:/opt/airflow/data:ro       # 읽기 전용 입력 (raw_orders.csv 를 여기에 복사)
      - ./output:/opt/airflow/output      # DAG 가 쓰는 결과 파일
      - ./logs:/opt/airflow/logs          # 태스크 로그를 내 PC 에서도 열어 볼 수 있게

5. 직접 해보기: 첫 TaskFlow DAG (태스크 3개)

DAG는 스케줄러에 등록해 두는 "프로시저 실행 순서표"이고, 태스크는 그 안의 프로시저 블록 하나입니다. 진짜 일을 하는 DAG를 쓰기 전에, 일은 거의 안 하는 가장 작은 DAG로 "파일 저장 → Airflow가 읽음 → 목록에 등록"이라는 길이 뚫려 있는지부터 확인합니다. 이 길이 막힌 상태에서 복잡한 DAG를 쓰면, 안 보일 때 원인이 코드인지 폴더 연결인지 구분이 안 됩니다. 1일차에 SELECT 1로 접속부터 확인한 것과 같은 이유입니다.

목표: 태스크 3개가 차례로 도는 가장 작은 DAG를 직접 써서, Airflow 목록에 나타나게 합니다. 프로시저로 치면 "블록 3개짜리 프로시저를 만들고 등록하기"입니다.

    dag_id="hello_taskflow",                     # 화면에 보이는 이름. 파일 이름과 달라도 되지만 맞추는 게 편하다
    schedule=None,                               # 자동 실행 없음. 버튼(Trigger)으로만 돌린다
    start_date=pendulum.datetime(2026, 10, 1, tz="Asia/Seoul"),  # 이 DAG 가 "유효해지는" 날짜
    catchup=False,                               # 지난 날짜를 몰아서 채우지 않기
    tags=["day5"],                               # 화면에서 거르기용 꼬리표
)
def hello_taskflow():                            # 이 함수 몸통은 "순서도를 그리는 코드". 데이터 처리는 안에서 안 한다

    @task                                        # 이 함수 = 태스크 하나 (프로시저 안의 블록 하나)
    def extract() -> list[dict]:
        rows = [                                 # 원래는 API·DB 에서 읽어 오는 부분. 오늘은 고정값
            {"order_id": 1, "amount": 39000},
            {"order_id": 2, "amount": 59000},
            {"order_id": 3, "amount": 19000},
        ]
        print(f"extract: {len(rows)}건 읽음")    # print 는 태스크 로그에 그대로 찍힌다
        return rows                              # return 값은 XCom 에 저장된다 (아주 작은 값만!)

    @task
    def transform(rows: list[dict]) -> int:      # 앞 태스크의 return 값을 인자로 받는다
        total = sum(r["amount"] for r in rows)   # SELECT SUM(amount) FROM rows
        print(f"transform: 합계 {total}원")
        return total

    @task
    def load(total: int) -> None:
        print(f"load: 오늘 매출 {total:,}원 을 적재했다고 칩시다")

    load(transform(extract()))                   # 함수에 함수를 넘기면 순서가 생긴다: extract >> transform >> load


hello_taskflow()                                 # 맨 아래에서 한 번 불러 줘야 Airflow 가 DAG 로 등록한다

7. 직접 해보기: 날짜별 파일을 멱등하게 쓰는 DAG

실무 배치의 90%는 "날짜 하나를 받아 → 그 날짜 데이터만 처리하고 → 그 날짜 칸만 갈아 끼우는" 모양입니다. 프로시저의 p_date 인자 + DELETE/INSERT 패턴을 Airflow식으로 옮기는 단계입니다. 5단계 DAG는 날짜를 안 써서 재시도·백필을 해도 의미가 없었지만, 이 DAG는 날짜를 받으므로 8·9·10단계(재실행·스케줄·백필)를 전부 이 DAG로 해 볼 수 있습니다.

처리 날짜를 now()가 아니라 Airflow가 넣어 주는 ds로 받지 않으면, 10월 3일분을 한 달 뒤에 다시 돌려도 "오늘"을 처리해 버려 백필이 불가능해집니다.

목표: 실행마다 Airflow가 넣어 주는 날짜(ds)로 그날 주문만 골라 날짜별 폴더에 파일로 씁니다. 같은 날짜로 다시 돌려도 결과가 같아야 합니다(멱등). 프로시저로 치면 p_date 인자를 받아 DELETE … WHERE dt = p_date; INSERT … WHERE order_date = p_date; 하는 것과 같습니다.

  data\raw_orders.csv  (30건, 10-01 ~ 10-19)
        │
        │  ds = 2026-10-03 인 실행  →  WHERE order_date = '2026-10-03'
        ▼
  output\orders\dt=2026-10-03\orders.csv   (1건)
  output\orders\dt=2026-10-04\orders.csv   (2건)
  ...                                         날짜마다 폴더 하나. 다시 돌리면 그 폴더 파일만 통째로 교체

  태스크 순서:  show_dates ──▶ extract_day ──▶ check ──▶ list_files
               날짜 출력       파일 쓰기       건수 세기    ls -l (BashOperator)

7-1. 파일 만들기

  1. notepad dags\daily_orders_partition.py → 예
  2. 아래 빈칸 틀을 붙여 넣고 ____ 7곳을 채운 뒤 저장
import csv
import os
import pendulum
from airflow.sdk import dag, task, get_current_context, CronDataIntervalTimetable
from airflow.providers.standard.operators.bash import BashOperator

SRC = "/opt/airflow/data/raw_orders.csv"         # 컨테이너 안 경로 (2단계 그림의 오른쪽)
OUT_ROOT = "/opt/airflow/output/orders"


@dag(
    dag_id="daily_orders_partition",
    schedule=CronDataIntervalTimetable("____", timezone="UTC"),   # ① 매일 00:00 (cron 5칸)
    start_date=pendulum.datetime(2026, 10, 1, tz="UTC"),
    catchup=False,
    max_active_runs=3,
    params={"min_amount": 0},
    tags=["day5"],
)
def daily_orders_partition():

    @task
    def show_dates(ds=None, data_interval_start=None, data_interval_end=None, logical_date=None):
        print(f"logical_date        = {logical_date}")
        print(f"data_interval_start = {data_interval_start}")
        print(f"data_interval_end   = {data_interval_end}")
        print(f"ds                  = {ds}")

    @task
    def extract_day(____=None) -> str:             # ② Airflow 가 날짜 문자열을 채워 줄 인자 이름
        out_dir = f"{OUT_ROOT}/dt={ds}"
        os.makedirs(out_dir, exist_ok=True)
        tmp = f"{out_dir}/orders.csv.tmp"
        final = f"{out_dir}/orders.csv"

        with open(SRC, newline="", encoding="utf-8") as f:
            rows = [r for r in csv.DictReader(f)
                    if r["____"] == ds]              # ③ WHERE ____ = ds

        with open(____, "w", newline="", encoding="utf-8") as f:   # ④ 어느 파일에 먼저 쓰나?
            w = csv.DictWriter(f, fieldnames=["order_id", "customer_id", "order_date", "status"],
                               extrasaction="ignore")
            w.writeheader()
            w.writerows(rows)
        os.replace(____, ____)                       # ⑤ 임시 파일 → 진짜 이름 (통째로 교체)

        print(f"{ds}: {len(rows)}건 → {final}")
        return final

    @task
    def check(path: str) -> int:
        ctx = get_current_context()
        min_amount = ctx["params"]["min_amount"]
        with open(path, encoding="utf-8") as f:
            n = sum(1 for _ in f) - 1
        print(f"검사: {path} 에 {n}건 (params.min_amount={min_amount})")
        return n

    list_files = BashOperator(
        task_id="list_files",
        bash_command="ls -l {{ params.out_root }}/dt={{ ds }}",
        params={"out_root": OUT_ROOT},
    )

    path = extract_day()
    show_dates() >> ____                          # ⑥ show_dates 다음에 extract_day
    check(path) >> ____                           # ⑦ check 다음에 list_files


daily_orders_partition()

코드 조각뜻 (SQL·프로시저로 빗대면)

path = extract_day()태스크 칸을 변수에 받아 두기. 이 시점엔 실행되지 않음
a >> b"a가 끝나야 b 시작". BashOperator는 @task가 아니라 값을 주고받지 않으므로 >>로 순서를 직접 붙입니다
힌트 1 — 날짜 받기·스케줄

① cron은 "분 시 일 월 요일" 5칸, 매일 0시 0분은 0 0 * * *. ② 이론 절 "템플릿과 컨텍스트"에서 본 날짜 키 이름(두 글자). ③ raw_orders.csv의 날짜 컬럼 이름(헤더: order_id,customer_id,order_date,status,updated_at).

# 5일차: logical date 별로 파일을 "덮어써서" 멱등하게 만드는 DAG
# 프로시저로 치면:  DELETE FROM t WHERE dt = p_date;  INSERT INTO t SELECT ... WHERE order_date = p_date;
# p_date 를 사람이 넣는 대신 Airflow 가 실행마다 {{ ds }} 로 넣어 준다.

import csv                                       # CSV 읽기·쓰기 (표준 라이브러리, 설치 필요 없음)
import os                                        # 폴더 만들기·파일 이름 바꾸기
import pendulum
from airflow.sdk import dag, task, get_current_context, CronDataIntervalTimetable  # CronDataIntervalTimetable = "구간"이 있는 스케줄 (본문 참고)
from airflow.providers.standard.operators.bash import BashOperator   # 셸 명령을 돌리는 전통적인 Operator

SRC = "/opt/airflow/data/raw_orders.csv"         # 입력: 컨테이너 안 경로 (내 PC 의 practice/airflow/data)
OUT_ROOT = "/opt/airflow/output/orders"          # 출력: dt=YYYY-MM-DD 폴더를 날짜마다 하나씩


@dag(
    dag_id="daily_orders_partition",
    # 매일 00:00(UTC, 한국 09:00)에 "어제 하루" 구간을 처리한다. ds = 구간 시작 날짜 = 처리할 데이터의 날짜
    # 시간대를 UTC 로 둔 이유: ds 는 UTC 기준으로 계산된다. 서울 00:00 으로 잡으면 ds 가 하루 전 날짜로 찍힌다 (본문 참고)
    schedule=CronDataIntervalTimetable("0 0 * * *", timezone="UTC"),
    start_date=pendulum.datetime(2026, 10, 1, tz="UTC"),
    catchup=False,                               # 켜면 10-01 부터 오늘까지 전부 자동 실행된다 (백필로 따로 해 볼 것)
    max_active_runs=3,                           # 백필 때 동시에 도는 날짜 수 상한
    params={"min_amount": 0},                    # 수동 실행 때 화면에서 바꿀 수 있는 값 (SQL 의 프로시저 인자 기본값)
    tags=["day5"],
)
def daily_orders_partition():

    @task
    def show_dates(ds=None, data_interval_start=None, data_interval_end=None, logical_date=None):
        # 인자 이름을 컨텍스트 키와 똑같이 적으면 Airflow 가 값을 채워 준다
        print(f"logical_date        = {logical_date}")
        print(f"data_interval_start = {data_interval_start}")
        print(f"data_interval_end   = {data_interval_end}")
        print(f"ds                  = {ds}")

    @task
    def extract_day(ds=None) -> str:
        out_dir = f"{OUT_ROOT}/dt={ds}"          # 파티션 폴더: ... /dt=2026-10-03
        os.makedirs(out_dir, exist_ok=True)      # 있으면 그냥 두고, 없으면 만든다 (CREATE SCHEMA IF NOT EXISTS)
        tmp = f"{out_dir}/orders.csv.tmp"        # 먼저 임시 파일에 쓰고
        final = f"{out_dir}/orders.csv"          # 다 쓰면 진짜 이름으로 바꾼다 (중간에 죽어도 반쪽 파일이 안 남게)

        with open(SRC, newline="", encoding="utf-8") as f:   # FROM raw_orders
            rows = [r for r in csv.DictReader(f)             # 한 줄씩 dict 로 읽어서
                    if r["order_date"] == ds]                # WHERE order_date = ds

        with open(tmp, "w", newline="", encoding="utf-8") as f:
            w = csv.DictWriter(f, fieldnames=["order_id", "customer_id", "order_date", "status"],
                               extrasaction="ignore")        # SELECT 할 컬럼만 (updated_at 은 버림)
            w.writeheader()
            w.writerows(rows)
        os.replace(tmp, final)                   # 같은 날짜 파일이 있으면 통째로 교체 = DELETE + INSERT

        print(f"{ds}: {len(rows)}건 → {final}")
        return final                             # XCom 에는 "파일 경로"만 넘긴다 (데이터 자체는 X)

    @task
    def check(path: str) -> int:
        ctx = get_current_context()              # 컨텍스트 전체가 필요할 때 꺼내는 방법
        min_amount = ctx["params"]["min_amount"] # params 읽기 (지금은 출력만)
        with open(path, encoding="utf-8") as f:
            n = sum(1 for _ in f) - 1            # 헤더 한 줄 빼고 줄 수 = COUNT(*)
        print(f"검사: {path} 에 {n}건 (params.min_amount={min_amount})")
        return n

    # 전통적인 Operator 방식 태스크. bash_command 안의 {{ ds }} 는 실행 직전에 날짜로 바뀐다 (템플릿)
    list_files = BashOperator(
        task_id="list_files",
        bash_command="ls -l {{ params.out_root }}/dt={{ ds }}",
        params={"out_root": OUT_ROOT},
    )

    path = extract_day()                         # 태스크를 "부르면" 실행되는 게 아니라 순서도에 칸이 하나 생긴다
    show_dates() >> path                         # show_dates 가 끝나야 extract_day 시작
    check(path) >> list_files                    # extract_day → check → list_files


daily_orders_partition()

10. 백필: 10월 1~5일 다시 만들기

"지난주 원천 데이터가 잘못 들어왔으니 그 기간을 다시 만들어 달라"는 요청은 실무에서 아주 흔합니다. 프로시저 시절엔 날짜를 바꿔 가며 손으로 여러 번 CALL 했죠. 백필은 이 반복을 Airflow에 맡기는 것이고, 7·8단계에서 멱등하게 만들어 둔 덕분에 안심하고 돌릴 수 있습니다.

먼저 --dry-run을 치는 이유: 날짜 범위를 한 글자만 틀려도(예: 2025년) 수백 개 실행이 한꺼번에 만들어지고, 웨어하우스였다면 그만큼 비용이 나갑니다. "무엇이 만들어질지"를 먼저 보는 건 DELETE 전에 같은 WHERE로 SELECT COUNT(*)부터 해 보는 습관과 같습니다.

  • DAG(순서도) → DagRun(1회 실행) → TaskInstance(태스크 1회 실행)
  • dag-processor 읽기 / scheduler 정하기 / executor·worker 실행 / api-server 화면·중계 / 메타DB 기억 / triggerer 기다리기

  • catchup은 자동 밀린 숙제, 백필은 명시적 재처리(airflow backfill create, 먼저 --dry-run)
  • XCom에는 쪽지(경로·건수)만

원천 적재(cron 05:00)와 마트 프로시저(예약 쿼리 06:00)를 시간 간격으로만 맞춰 둔 구조의 가장 큰 약점은?

  1. SQL을 두 번 써야 한다
  2. 적재가 늦게 끝나면 프로시저가 반쪽 데이터로 돈다 — 순서가 "성공"이 아니라 "시각"으로만 이어져 있다
  3. BigQuery 비용이 두 배가 된다
  4. cron은 하루 한 번만 돌릴 수 있다
시간 간격은 "앞 작업이 끝났다"를 보장하지 않습니다. 오케스트레이터는 "앞 태스크가 success면 시작"이라는 의존성으로 이 문제를 없앱니다. 비용·SQL 중복은 이 구조의 본질적인 문제가 아니고, cron은 하루 여러 번도 돌릴 수 있습니다.

DAG 파일의 태스크 함수 바깥 맨 위에 rows = requests.get(API).json()를 적었습니다. 어떤 일이 생기나요?

  1. DAG가 실행될 때 한 번만 호출된다
  2. 첫 번째 태스크가 시작될 때 호출된다
  3. Airflow가 오류를 내고 막아 준다
  4. dag-processor가 파일을 읽을 때마다(수십 초~몇 분 간격) 계속 호출된다
DAG 파일은 "순서도를 그리는 코드"라서 파싱할 때마다 맨 위 코드가 실행됩니다. 실행할 때 한 번이 아니라 읽을 때마다입니다. 실제 작업은 태스크 함수 안에서만 해야 합니다.

CronDataIntervalTimetable("0 0 * * *", timezone="UTC") DAG가 2026-10-04 00:00 UTC에 스케줄로 돌았습니다. 이 실행의 {{ ds }}는?

  1. 2026-10-03
  2. 2026-10-04
  3. 2026-10-05
  4. 실행할 때마다 달라진다
구간 시간표는 직전 구간 [10-03 00:00, 10-04 00:00)을 처리하고, logical_date = 구간 시작 = 10-03 00:00입니다. ds는 그 날짜 부분이라 2026-10-03. 실행 시각(10-04)과 다르다는 게 핵심입니다. 같은 실행을 나중에 다시 돌려도 ds는 그대로라서 ④도 틀립니다.

Airflow 3에서 schedule="@daily"로만 적은 DAG가 2026-10-04 00:00에 돌았습니다. 어제(10-03) 데이터를 처리하려면?

  1. {{ ds }}를 그대로 쓰면 10-03이 나온다
  2. datetime.now() - 1일로 계산한다
  3. {{ macros.ds_add(ds, -1) }}처럼 하루를 빼거나, 구간 시간표(CronDataIntervalTimetable)로 바꾼다
  4. catchup=True로 바꾼다
Airflow 3에서 cron 문자열은 기본적으로 CronTriggerTimetable이 되어 logical_date = 실행 시각, ds = 10-04입니다(실측). 그래서 하루를 빼거나 구간 시간표를 명시해야 합니다. now()는 재실행·백필 때 엉뚱한 날짜가 되니 금지이고, catchup은 날짜 의미와 상관없습니다.

airflow backfill create ... --from-date 2026-10-01 --to-date 2026-10-05 --dry-run 결과에 10-03만 빠져 있습니다. 가장 그럴듯한 이유는?

  1. 10-03에 원본 주문이 없어서
  2. 10-03 logical date로 이미 실행 기록이 있고, 기본값 --reprocess-behavior none이 이를 건너뛰어서
  3. --to-date가 포함되지 않는 범위라서
  4. DAG가 꺼져 있어서
실측에서 그대로 본 상황입니다. 기록이 있는 날짜는 기본적으로 건너뛰고, --reprocess-behavior completed를 주면 포함됩니다. Airflow는 원본 데이터 유무를 모르며, to-date는 포함 범위이고, paused 여부는 목록 생성과 무관합니다(실제 실행에는 영향).

다음 중 멱등한 태스크는?

  1. INSERT INTO t SELECT ... WHERE dt = '{{ ds }}'
  2. 오늘 날짜(now()) 폴더에 결과 파일을 덮어쓰기
  3. 결과를 orders.csv에 append 모드로 이어 쓰기
  4. dt={{ ds }}/ 폴더의 파일을 임시 파일로 쓴 뒤 통째로 교체하기
④는 그 날짜 칸만 통째로 바꾸므로 몇 번 돌려도 같습니다(DELETE+INSERT와 같은 효과). ①③은 돌릴 때마다 쌓이고, ②는 덮어쓰기는 하지만 날짜를 now()로 정해서 재실행·백필 때 다른 날짜를 건드립니다.

XCom 사용으로 가장 알맞은 것은?

  2. DB 비밀번호를 태스크 간에 넘긴다
  3. 방금 쓴 파일 경로와 행 수를 넘긴다

XCom은 메타DB에 저장되는 작은 쪽지입니다. 데이터는 저장소에 두고 위치·건수만 넘깁니다. 큰 데이터는 DB를 무겁게 하고 실패를 부르며, 비밀번호는 Connection·Secret으로 관리합니다.

  1. api-server
  2. dag-processor
  3. triggerer
  4. scheduler
Airflow 3의 api-server는 UI·REST API와 함께 태스크용 실행 API를 제공하고, 워커는 메타DB에 직접 붙지 않고 이 API를 거칩니다. dag-processor는 DAG 파일 파싱, triggerer는 긴 대기, scheduler는 실행 시점 결정과 대기열 담당입니다.
