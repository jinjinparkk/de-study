Airflow로 dbt 돌리기 — 운영 패턴까지

어제 만든 Airflow에 1~4일차의 shop dbt 프로젝트를 올립니다. "dbt build 한 줄"에서 시작해 계층별 태스크, 재시도·알림, 동시 실행 제어, 그리고 "데이터가 들어오면 dbt가 돈다"(Asset)까지 운영에서 실제로 쓰는 모양을 만들어 봅니다.

운영 패턴 ①: 실패에 대비하는 설정

새벽 배치는 반드시 언젠가 실패합니다. 운영에서 중요한 건 "실패하지 않기"가 아니라 일시적 실패는 알아서 넘기고, 진짜 실패는 빨리 사람에게 알리는 것입니다.

설정뜻보통 값
retries실패 후 추가로 시도할 횟수1~3
retry_delay시도 사이 쉬는 시간1~10분
retry_exponential_backoff · max_retry_delay쉬는 시간을 2배씩 늘림 · 최대 대기 상한API 호출처럼 상대가 잠깐 막힐 때
execution_timeout태스크 하나가 이 시간을 넘기면 강제로 실패 처리평소 걸리는 시간의 2~3배
dagrun_timeout (DAG 설정)DagRun 전체가 이 시간을 넘기면 실패다음 실행 전까지
on_failure_callback재시도까지 다 실패했을 때 부를 함수 (슬랙·메일 알림)모든 운영 DAG
on_retry_callback · on_success_callback재시도할 때 · 성공했을 때 부를 함수필요할 때만

이 값들은 태스크마다 줄 수도 있지만, 보통 default_args로 DAG 안 모든 태스크에 한 번에 줍니다.

from datetime import timedelta                   # 시간 길이 (SQL 의 INTERVAL)

def notify_failure(context):                     # 실패 알림 함수. 실제로는 슬랙·메일로 보낸다
    ti = context["ti"]                           # ti = 실패한 태스크 인스턴스
    print(f"[알림] {ti.dag_id}.{ti.task_id} 실패 (run_id={ti.run_id}, 시도 {ti.try_number}회)")

@dag(
    ...,
    default_args={                               # 모든 태스크에 공통으로 들어가는 기본값
        "retries": 2,                            # 실패하면 2번 더 시도
        "retry_delay": timedelta(seconds=30),    # 시도 사이 30초 쉬기
        "execution_timeout": timedelta(minutes=20),  # 20분 넘으면 강제 실패
        "on_failure_callback": notify_failure,   # 재시도까지 다 실패했을 때 부를 함수
    },
)

SLA는 Airflow 3에서 없어졌습니다 → Deadline Alerts

Airflow 2의 sla=·sla_miss_callback은 3.0에서 삭제됐습니다(3.3.2 소스의 안내 문구: "The SLA feature is removed in Airflow 3.0, to be replaced with DeadlineAlerts in 3.1"). "07:00까지 안 끝나면 알려줘" 같은 요구는 이렇게 대신합니다.

  • Deadline Alerts (3.1+): DAG에 deadline=DeadlineAlert(...)를 걸면 기준 시각 + 간격 안에 안 끝날 때 콜백이 불림. 아래 모양이 3.3.2에서 파싱되는 것까지만 확인했고, 실제로 알림이 오는지는 검증하지 못했습니다.
  • execution_timeout·dagrun_timeout + on_failure_callback: "넘으면 실패시키고 알림"
  • 별도 감시 DAG: "마트 테이블의 오늘 파티션이 있나?"를 검사하는 태스크를 07:00에 돌리기 (가장 단순하고 확실)
from datetime import timedelta
from airflow.sdk import dag, DeadlineAlert, DeadlineReference, SyncCallback

def late_alert(**kwargs):                        # 늦었을 때 부를 함수 (모듈 최상단에 있어야 함)
    print("[알림] 30분 안에 안 끝남", kwargs)

@dag(
    ...,
    deadline=DeadlineAlert(
        reference=DeadlineReference.DAGRUN_QUEUED_AT,   # 기준: 실행이 대기열에 들어간 시각
        interval=timedelta(minutes=30),                 # + 30분
        callback=SyncCallback("my_dag_file.late_alert"),  # "모듈이름.함수이름" 문자열
    ),
)
🧸 비유

택배 기사님을 생각해 보세요. 초인종에 대답이 없으면 잠깐 뒤 한 번 더 눌러 봅니다(retry). 세 번 눌러도 없으면 문자를 남깁니다(on_failure_callback). 한 집 앞에서 한 시간을 서 있지는 않습니다(execution_timeout). 처음 대답이 없을 때마다 본사에 전화하면 본사가 마비되겠죠 — 그래서 알림은 마지막에 한 번입니다.

프로시저 감각으로 옮기면

프로시저 안의 BEGIN ... EXCEPTION WHEN ERROR THEN 블록에서 "재시도 루프 + 에러 로그 테이블 INSERT + 메일 발송"을 직접 짜던 것을, 설정 몇 줄로 바꾸는 것입니다. 차이는 재시도 단위가 태스크라는 점 — 프로시저 전체가 아니라 실패한 단계만 다시 돕니다.

운영 패턴 ②: 동시에 몇 개까지? (pool, max_active_runs)

Airflow는 기본적으로 할 수 있는 만큼 동시에 돌립니다. 그런데 "이 DB는 동시에 한 명만 써야 한다", "이 API는 동시 3개까지" 같은 제약이 있죠. 이걸 표현하는 손잡이가 여러 개 있습니다.

손잡이범위예
max_active_runs (DAG)이 DAG의 DagRun이 동시에 몇 개백필 때 날짜 3개씩만
max_active_tasks (DAG)이 DAG 안에서 동시에 도는 태스크 수한 번에 하나씩
pool (태스크에 pool="이름")여러 DAG에 걸쳐 같은 자원을 쓰는 태스크들의 총 동시 실행 수duckdb 풀 슬롯 1개 → DuckDB에 쓰는 태스크는 어느 DAG든 한 번에 하나
depends_on_past (태스크)어제 같은 태스크가 성공해야 오늘 시작누적 계산
  pool "duckdb" (슬롯 1개)
  ┌──────────────┐
  │ ■ 사용 중      │◀── dbt_shop_layers.staging.build   (running)
  └──────────────┘
          ▲  대기

pool은 미리 만들어 둬야 합니다

태스크에 pool="duckdb"를 적어도 풀이 자동으로 생기지 않습니다. 실습 4단계에서 airflow pools set duckdb 1 "..."로 만듭니다. 그리고 airflow dags test는 스케줄러를 거치지 않아서 풀을 무시하고 그냥 실행합니다(풀 없이 돌려 보니 성공 — 실측). 풀 동작은 스케줄로 돌거나 Trigger로 돌 때만 적용됩니다.

운영 패턴 ③: Task Group — 화면을 접었다 폈다

태스크가 수십 개가 되면 화면이 복잡해집니다. @task_group으로 묶으면 그래프에서 하나의 상자로 접히고, 태스크 이름 앞에 그룹 이름이 붙습니다(staging.build, marts.build — 실측). 실행 순서나 재시도에는 영향이 없는 보기용 묶음입니다. (Airflow 2의 SubDAG는 3에서 삭제됐고, Task Group이 그 자리를 대신합니다.)

from airflow.sdk import dag, task_group

@task_group(group_id="staging")       # 이 함수 안에서 만든 태스크는 staging.xxx 이름이 된다
def staging():
    dbt_step("build", "build --select path:models/staging")

staging() >> snapshot >> marts()     # 그룹끼리도 >> 로 잇는다
💡 한 줄 요약 retries는 일시적 실패를, 알림 콜백은 진짜 실패를, timeout은 멈춘 작업을, pool은 공유 자원 충돌을 맡습니다. Task Group은 보기용입니다.

dbt 자체가 이미 DAG(리니지) 순서대로 돌기 때문에, ① 하나로 시작해서 필요해지면 나누는 것이 보통 순서입니다. 오늘은 ①과 ②를 직접 만들고, ③은 개념과 선택 실습으로 봅니다.

프로시저 감각으로 옮기면
  • ① = 마스터 프로시저 CALL sp_build_all() 한 줄을 스케줄러에 걸기
  • ② = CALL sp_staging() → CALL sp_snapshot() → CALL sp_marts() 세 줄로 나눠 걸기. 마트에서 실패하면 staging은 다시 안 돌림
  • ③ = 테이블 하나하나를 각각 스케줄러 작업으로 등록 (프로시저 세계에선 관리가 불가능했던 수준을 자동 생성)

이미지 만들기: 왜 dbt를 별도 가상환경에 넣나

Airflow 공식 이미지에는 dbt가 없습니다. 넣는 방법은 두 가지입니다.

  • Airflow와 같은 파이썬에 pip install dbt-duckdb → Airflow와 dbt가 같이 쓰는 라이브러리(jinja2, protobuf, pydantic 등)의 버전 요구가 부딪히기 쉽습니다. 하나를 올리면 다른 쪽이 깨지는 일이 생깁니다.
  • dbt 전용 가상환경(/opt/dbt_venv)을 따로 만들기 → 서로의 라이브러리를 건드리지 않습니다. Airflow는 그냥 /opt/dbt_venv/bin/dbt라는 명령어를 실행할 뿐입니다. 오늘 쓰는 방식이고, Cosmos 문서도 이 방식을 권합니다.
# 6일차: Airflow 공식 이미지 + dbt-duckdb (별도 가상환경)
FROM apache/airflow:3.3.2

# dbt 는 Airflow 와 쓰는 라이브러리(jinja2, protobuf 등) 버전이 겹쳐서 같은 파이썬에 넣으면 충돌하기 쉽다.
# → /opt/dbt_venv 라는 "dbt 전용 방"을 따로 만들어 설치한다.
# 버전은 내 PC 와 맞춘다 (pip show dbt-core dbt-duckdb duckdb 로 확인). DuckDB 는 버전이 다르면 파일을 못 읽을 수 있다.
USER root
RUN python -m venv /opt/dbt_venv \
 && /opt/dbt_venv/bin/pip install --no-cache-dir \
      "dbt-core==1.12.6" "dbt-duckdb==1.11.1" "duckdb==2.0.0" \
 && /opt/dbt_venv/bin/dbt --version
USER airflow
🧸 비유

한 부엌에서 한식 셰프와 양식 셰프가 양념통을 같이 쓰면, 한쪽이 소금을 다른 걸로 바꿨을 때 다른 쪽 요리가 망가집니다. 그래서 양식 셰프에게 자기 양념통 선반(별도 venv)을 따로 줍니다. 주방 매니저(Airflow)는 "양식 셰프님, 3번 요리 해 주세요"라고 부르기만 합니다.

버전은 내 PC와 맞추세요 (특히 DuckDB)

위 Dockerfile의 버전(dbt-core 1.12.6, dbt-duckdb 1.11.1, duckdb 2.0.0)은 이 페이지 작성일에 pip install dbt-duckdb로 받아지던 최신이자 작성자가 실제로 dbt build를 확인한 조합입니다. 내 PC에서 pip show dbt-core dbt-duckdb duckdb로 버전을 보고 다르면 Dockerfile 숫자를 내 것으로 바꾸세요. DuckDB는 새 버전이 만든 파일을 옛 버전이 못 여는 경우가 있습니다.

dev · prod target과 env_var()

같은 dbt 코드를 내가 개발할 때와 운영에서 돌릴 때 다른 곳에 쓰게 하는 장치가 target입니다. profiles.yml 하나에 여러 출력(outputs)을 두고, 실행할 때 --target으로 고릅니다.

# 컨테이너 안에서 dbt 가 쓰는 접속 정보 (DBT_PROFILES_DIR=/opt/airflow/dbt)
shop:
  target: dev
  outputs:
    dev:                       # 내 PC 에서 쓰던 것과 같은 파일. 컨테이너에서는 쓰지 않는다
      type: duckdb
      path: shop.duckdb
      threads: 4
    prod:                      # Airflow 가 쓰는 "운영" 파일. 경로는 환경 변수로 받는다
      type: duckdb
      path: "{{ env_var('DBT_DUCKDB_PATH', 'shop_prod.duckdb') }}"
      threads: 1
  • {{ env_var('DBT_DUCKDB_PATH', 'shop_prod.duckdb') }} — 환경 변수 값을 읽고, 없으면 두 번째 값을 씁니다. 비밀번호·경로·프로젝트 ID처럼 환경마다 다른 값을 코드 밖에서 넣는 표준 방법입니다. (DBT_ENV_SECRET_으로 시작하는 이름은 dbt가 로그에서 가려 줍니다.)
  • Airflow는 항상 --target prod로 돌리고, 나는 PC에서 평소처럼 dbt build(기본 dev)로 개발합니다.
  • 모델 안에서도 {{ target.name }}으로 갈라 쓸 수 있습니다. 예: dev에서는 최근 3일치만 {% if target.name == 'dev' %} where order_date >= current_date - 3 {% endif %}

DuckDB 단일 쓰기 잠금 주의

DuckDB는 파일 하나짜리 DB라서 한 파일을 쓰기 모드로 여는 프로세스는 한 번에 하나입니다. 두 번째가 열려고 하면 1일차에 본 IO Error: Could not set lock on file이 납니다. Airflow를 붙이면 이 문제가 세 군데서 생깁니다.

  1. Airflow 안에서 dbt 태스크 두 개가 동시에 같은 파일에 씀 → max_active_runs=1 + pool duckdb(슬롯 1)로 한 번에 하나만
  2. dbt 안에서 스레드 여러 개 → 한 프로세스 안의 스레드는 괜찮지만, 안전하게 prod는 threads: 1
  3. 나(PC)와 Airflow(컨테이너)가 동시에 같은 파일 → 파일을 아예 나눕니다: 나는 shop.duckdb(dev), Airflow는 shop_prod.duckdb(prod)
3번을 "잠금"에 맡기지 않는 이유 (검증 안 된 부분이 있어 보수적으로)

Windows 폴더를 Docker 컨테이너에 연결(bind mount)하면, 리눅스 쪽 파일 잠금이 Windows 쪽 프로그램에 제대로 전달된다는 보장이 없습니다. 잠금이 안 걸리면 오류도 없이 두 쪽이 동시에 써서 파일이 깨질 수 있습니다. 작성자는 이 경계에서의 잠금 동작을 확인하지 못했기 때문에, "같은 파일을 양쪽에서 쓰지 않는다"를 규칙으로 둡니다. Airflow 결과를 DBeaver 등으로 볼 때는 DAG가 돌지 않을 때 shop_prod.duckdb를 읽기 전용으로 여세요.

BigQuery 같은 웨어하우스는 이런 제약이 없습니다. 이건 연습용 DuckDB의 특성입니다.

🧸 비유

DuckDB 파일은 한 사람만 쓸 수 있는 화이트보드입니다. 회의실 안(컨테이너)과 밖(PC)에서 같은 보드에 동시에 쓰려 하면 글씨가 겹칩니다. 그래서 보드를 두 개(dev, prod) 두고, 회의실 안에서는 "펜은 하나"(pool 슬롯 1) 규칙을 씁니다.

Asset: "데이터가 들어오면" 실행하기

지금까지 스케줄은 시각이었습니다. 그런데 dbt는 사실 "06:00"이 아니라 "원천 데이터가 새로 들어왔을 때" 돌아야 맞습니다. Airflow 3의 Asset(2.x의 Dataset)은 이걸 표현합니다.

  collect_shop_raw (수집 DAG)                         dbt_shop_layers (dbt DAG)
  ┌──────────────────────────────┐                   schedule=[SHOP_RAW]
  │ move_landing_files            │   성공하면          ┌─────────┐  ┌────────┐  ┌───────┐
  │  outlets=[SHOP_RAW] ──────────┼──▶ Asset 이벤트 ──▶│ staging │─▶│snapshot│─▶│ marts │
  └──────────────────────────────┘   "shop_raw 갱신"   └─────────┘  └────────┘  └───────┘
         skipped / failed 면 → 이벤트 없음 → dbt 안 돎
  • 생산자: 태스크에 outlets=[SHOP_RAW]. 이 태스크가 성공하면 "SHOP_RAW가 갱신됐다"는 이벤트가 메타DB에 기록됩니다.
  • 소비자: DAG에 schedule=[SHOP_RAW]. 이벤트가 생기면 스케줄러가 실행을 만듭니다.
  • Asset의 URI(file:///opt/airflow/shop/data)는 이름표일 뿐입니다. Airflow가 그 파일을 들여다보거나 감시하지 않습니다. "갱신됐다"는 판단은 오직 생산자 태스크의 성공으로 합니다.
  • 여러 Asset 조합: schedule=(a & b) 둘 다 갱신되면, (a | b) 하나라도. 시간과 섞으려면 AssetOrTimeSchedule.
# 6일차: 여러 DAG 가 같이 쓰는 Asset 정의 (dags 폴더 안의 보통 파이썬 파일 = 공용 모듈)
from airflow.sdk import Asset

# "shop 의 원본 CSV 가 새로 갱신됐다" 를 뜻하는 이름표. Airflow 는 이 URI 의 파일을 직접 들여다보지 않는다.
SHOP_RAW = Asset(name="shop_raw", uri="file:///opt/airflow/shop/data")

작성자가 확인한 동작(Airflow 3.3.2, dags test + 메타DB 조회):

① landing 이 비어 있을 때 수집 DAG 실행
   Skipping task.  reason='landing 에 새 파일이 없습니다'   → asset_event 0건 (이벤트 안 생김)
② landing 에 raw_orders.csv 를 넣고 실행
   옮긴 파일: ['raw_orders.csv']                         → asset_event 1건
   asset_dag_run_queue: []                               ← 소비자 DAG 가 꺼져(paused) 있어서 대기열에 안 들어감
③ dbt_shop_layers 를 켜고(unpause) 다시 넣고 실행
   옮긴 파일: ['raw_customers.csv', 'raw_payments.csv']   → asset_event 2건
   asset_dag_run_queue: [('dbt_shop_layers', '2026-11-04 07:03:04')]   ← 실행 대기열에 등록됨

③ 다음 단계(스케줄러가 대기열을 보고 dbt_shop_layers 실행을 만드는 것)는 스케줄러를 띄울 수 없어 직접 보지 못했습니다. 실습 9단계에서 화면으로 확인해 보세요.

소비자 DAG는 켜져 있어야 이벤트를 받습니다

위 ②처럼, 꺼진(paused) 소비자 DAG는 이벤트가 생겨도 대기열에 쌓이지 않았습니다. 나중에 켜도 그 이벤트로 돌지 않습니다. 소비자 DAG를 먼저 켜 두고 생산자를 돌리세요.

프로시저 감각으로 옮기면

프로시저 세계에서 "적재가 끝나면 마트를 돌린다"를 하려면 적재 쪽 마지막 줄에 INSERT INTO etl_flag(job, done_at)를 남기고, 마트 쪽이 5분마다 그 플래그 테이블을 폴링했습니다. Asset은 그 플래그 테이블 + 폴링을 Airflow가 기본으로 해 주는 것입니다.

💡 한 줄 요약 생산자 태스크가 성공하면 Asset 이벤트, 이벤트가 생기면 소비자 DAG 실행. Airflow는 데이터 자체를 보지 않고 "성공했다는 사실"만 봅니다.

Cosmos: dbt 모델을 Airflow 태스크로 펼치기

astronomer-cosmos는 dbt 프로젝트를 읽어 모델·스냅샷·테스트마다 Airflow 태스크를 자동으로 만들어 주는 패키지입니다. dbt 리니지가 그대로 Airflow 그래프가 됩니다.

# 6일차(선택): astronomer-cosmos 로 dbt 모델 하나하나를 Airflow 태스크로 펼치기
# 준비: Dockerfile 의 Airflow 쪽 파이썬에  pip install astronomer-cosmos  추가 → 이 파일을 dags/ 로 복사
import pendulum
from airflow.sdk import dag
from cosmos import DbtTaskGroup, ProjectConfig, ProfileConfig, ExecutionConfig, RenderConfig
from cosmos.constants import LoadMode

DBT = "/opt/dbt_venv/bin/dbt"
SHOP = "/opt/airflow/shop"

profile_config = ProfileConfig(
    profile_name="shop",                                   # profiles.yml 맨 윗줄 이름
    target_name="prod",                                    # 어느 target 으로 돌릴지
    profiles_yml_filepath="/opt/airflow/dbt/profiles.yml", # 이미 있는 profiles.yml 을 그대로 쓴다
)


@dag(
    dag_id="dbt_shop_cosmos",
    schedule=None,
    start_date=pendulum.datetime(2026, 10, 1, tz="UTC"),
    catchup=False,
    max_active_runs=1,
    max_active_tasks=1,          # DuckDB 는 동시에 한 프로세스만 쓸 수 있으니 태스크도 한 번에 하나씩
    tags=["day6", "dbt", "cosmos"],
)
def dbt_shop_cosmos():
    DbtTaskGroup(
        group_id="shop",
        project_config=ProjectConfig(SHOP),                # dbt 프로젝트 폴더
        profile_config=profile_config,
        execution_config=ExecutionConfig(dbt_executable_path=DBT),  # 별도 venv 의 dbt 를 쓰게
        render_config=RenderConfig(load_method=LoadMode.DBT_LS),    # 파싱 때 dbt ls 로 모델 목록을 읽는다
    )


dbt_shop_cosmos()

Cosmos 검증 범위와 주의
  • 확인함: Airflow 3.3.2 + cosmos 1.16.0에서 DAG 파싱 성공, 위 태스크 목록 생성.
  • 확인 못 함: 태스크 실제 실행. 작성자의 검증 환경(Windows)에서 cosmos가 쓰는 프로세스 기능이 지원되지 않아 실행 단계에서 멈췄습니다. 리눅스 컨테이너에서는 다를 것으로 예상하지만 직접 보지 않았습니다.
  • LoadMode.DBT_LS는 DAG 파일을 읽을 때마다 dbt ls를 실행합니다(맨 위 코드가 파싱마다 도는 것과 같은 문제). 운영에서는 CI에서 만든 manifest.json을 읽는 LoadMode.DBT_MANIFEST를 많이 씁니다.
  • 이미지에 astronomer-cosmos를 Airflow 쪽 파이썬에 설치해야 합니다(dbt venv가 아님). 기본 실습 이미지에는 없습니다.

dbt 선택자, state:modified, slim CI

2일차의 --select를 운영 관점에서 다시 봅니다. 오늘 계층별 DAG는 경로 선택자를 씁니다.

선택자뜻
path:models/staging그 폴더 아래 모델(과 그 모델들의 테스트)
tag:dailyconfig에 tags: ['daily']를 단 것
fct_orders+ / +fct_orders그 모델과 하류 전부 / 상류 전부
source:shop_raw+그 source를 쓰는 모든 하류
state:modified+기준 시점과 비교해 바뀐 모델과 그 하류
result:error+지난 실행에서 실패한 것과 하류 (dbt retry와 비슷)

state:modified와 slim CI

dbt는 실행할 때마다 target/manifest.json(프로젝트의 모든 모델·SQL·설정을 담은 목록)을 만듭니다. 운영에서 마지막으로 쓴 manifest를 보관해 두고, 새 코드의 manifest와 비교하면 "무엇이 바뀌었는지" 알 수 있습니다.

  PR 올림 (fct_orders.sql 한 줄 수정)
        │
        ▼
  CI 서버: dbt build --select state:modified+ --defer --state prod_artifacts/
        │        │                         │            └ 운영 manifest.json 이 있는 폴더
        │        │                         └ 안 바뀐 상류 모델은 다시 만들지 않고 "운영 테이블"을 참조
        │        └ 바뀐 것(fct_orders) + 그 하류만
        ▼
  CI 전용 스키마에 fct_orders 와 하류만 빌드·테스트 → 통과하면 머지 → 운영 Airflow 가 다음 실행에 반영

모델이 500개여도 CI에서는 바뀐 5개와 하류만 돌기 때문에 "slim"(가벼운) CI라고 부릅니다. Airflow와의 관계는 이렇습니다: 운영 Airflow의 dbt 태스크가 끝날 때마다 manifest.json을 버킷 등에 올려 두면, CI가 그걸 --state로 씁니다. (오늘 실습에서는 개념만 봅니다. 해 보고 싶다면 PC에서 dbt build 후 target 폴더를 prod_artifacts로 복사하고, 모델 하나를 고친 뒤 dbt ls --select state:modified+ --state prod_artifacts를 쳐 보세요.)

프로시저 감각으로 옮기면

프로시저를 하나 고치면 "이걸 쓰는 하위 프로시저가 뭐였지?"를 찾아서 손으로 다시 돌려 확인했죠. state:modified+는 그 "바뀐 것 + 영향받는 것만 골라 돌리기"를 리니지로 자동 계산합니다. --defer는 "안 바뀐 앞단은 운영 테이블을 그대로 빌려 쓰기"입니다.

1. Docker Desktop 켜고 엔진·메모리 확인하기

5일차와 같은 이유(엔진이 꺼져 있으면 모든 docker 명령이 실패)에 더해, 오늘은 이미지를 직접 만들고(설치 작업) 그 안에서 dbt까지 돌려 메모리를 더 씁니다. 빌드 도중 메모리가 모자라 죽으면 원인 찾기가 번거로우니, 시작 전에 엔진 상태와 떠 있는 컨테이너를 정리해 둡니다.

목표: 오늘은 이미지를 직접 빌드(dbt 설치)하고 그 안에서 dbt까지 돌려서 5일차보다 무겁습니다. 시작 전에 엔진이 켜져 있고 쓸데없는 컨테이너가 없는지 봅니다.

  1. 시작 메뉴에서 Docker Desktop 실행 → 1분 기다리기
  2. PowerShell에서 확인: 
    docker info --format "{{.ServerVersion}}"
docker ps

    (5일차 1단계와 같음: docker info = 엔진이 살아 있나, docker ps = 지금 도는 컨테이너 목록)

    첫 줄이 28.3.2처럼 숫자면 엔진 OK. failed to connect to the docker API at npipe:…이면 엔진이 아직 꺼져 있습니다(5일차 1단계). 둘째 줄에 5일차 de-airflow-airflow-1이 떠 있어도 괜찮습니다(2단계에서 멈춤). 그 밖에 안 쓰는 컨테이너가 있으면 그 컨테이너를 띄운 폴더에서 docker compose stop으로 내려 두세요.
메모리가 부족한 PC라면

이미지 빌드(pip 설치)와 dbt 실행이 겹치면 메모리를 꽤 씁니다(정확한 양은 작성자가 재 보지 못함). 브라우저 탭·DBeaver 등을 닫고 시작하고, 끝나면 11단계대로 반드시 docker compose … down 하세요. 빌드 중에 Killed나 exit code: 137이 나오면 메모리 부족입니다 — 다른 프로그램을 닫고 같은 명령을 다시 치면 이미 받은 부분은 재사용됩니다.

  • 팀에서는 Airflow 이미지를 개발자 PC에서 각자 빌드하기보다, CI(GitHub Actions, Cloud Build 등)가 빌드해서 이미지 저장소(Artifact Registry, ECR 등)에 올리고 개발자·운영 환경은 그걸 받아 씁니다. 그래야 "내 PC에서 빌드한 것과 운영 이미지가 다르다"가 안 생깁니다.
  • 이미지 태그는 latest 대신 버전이나 git 커밋 해시로 붙여, 문제가 생기면 이전 태그로 되돌립니다(롤백).
2. 파일 받기와 SHOP_DIR 설정

오늘 목표는 "Airflow가 1~4일차에 만든 바로 그 dbt 프로젝트를 돌리게" 하는 것입니다. 프로젝트를 컨테이너 안으로 복사하면 내 PC에서 고친 모델이 반영되지 않으니, 5일차 dags처럼 공유 폴더(volume mount)로 연결합니다.

그런데 shop 폴더 위치는 사람마다 다릅니다(C:/Users/내이름/…). 이 값을 compose 파일에 박아 두면 다른 PC에서 못 쓰므로, 사람마다 다른 값만 .env 파일로 뺍니다. 프로시저로 치면 서버 이름을 코드에 적지 않고 설정 테이블에서 읽는 것과 같습니다. 또 어제 compose 파일은 그대로 두고 "오늘 추가분"만 docker-compose.dbt.yml에 적어 겹쳐 씁니다 — 무엇이 바뀌었는지 한눈에 보이게.

목표: 어제 폴더(C:\Users\<내이름>\airflow-practice)에 오늘 파일 5개와 .env 한 줄을 더해서, 컨테이너가 1~4일차 dbt 프로젝트(shop)를 볼 수 있게 연결합니다.

  내 PC (Windows)                                       컨테이너 안 (Linux)
  C:\Users\<내이름>\airflow-practice\
  ├─ docker-compose.yml       5일차 그대로
  ├─ docker-compose.dbt.yml   오늘: 위 설정에 "덧씌울" 차이
  ├─ Dockerfile               오늘: dbt 가 들어간 이미지 레시피
  ├─ .env                     오늘: SHOP_DIR=… 한 줄 (아래 shop 폴더 위치)
  ├─ dags\         ◀──────▶  /opt/airflow/dags     + shop_assets.py, collect_shop_raw.py
  ├─ dbt\profiles.yml ─────▶  /opt/airflow/dbt      컨테이너용 접속 정보 (읽기 전용)
  ├─ landing\      ◀──────▶  /opt/airflow/landing  "새 파일 도착" 자리 (8단계)
  └─ data\ output\ logs\     (5일차 그대로)

  C:\Users\<내이름>\dbt-practice\shop\  ◀──────▶  /opt/airflow/shop   1~4일차 dbt 프로젝트 그대로
       (models\, snapshots\, data\, dbt_project.yml …)        ← DAG 의 cwd, 여기에 shop_prod.duckdb 생김
  1. shop 프로젝트 위치 확인 — 1일차에 만든 폴더가 이 자리에 있어야 합니다. 
    Test-Path $HOME\dbt-practice\shop\dbt_project.yml

    Test-Path = 그 경로에 파일이 있으면 True, 없으면 False (IF EXISTS). shop 폴더의 "표식" 파일인 dbt_project.yml로 확인합니다.

    True면 OK. False면 shop 폴더가 다른 곳에 있는 것이니, 4번의 .env 경로를 그 위치로 바꿔 적으세요.
  2. 어제 컨테이너 멈추고 폴더 만들기 
    cd $HOME\airflow-practice
docker compose stop
mkdir dbt, landing -ErrorAction SilentlyContinue
    조각뜻
    docker compose stop(5일차 11단계) 어제 컨테이너를 멈춤. 오늘 3단계에서 같은 이름 컨테이너를 새 이미지로 바꿔 띄우기 전 정리
    mkdir dbt, landing오늘 연결할 폴더 2개 (dbt = 컨테이너용 접속 정보, landing = "새 파일 도착" 자리)
    -ErrorAction SilentlyContinue이미 있어서 나는 오류는 조용히 넘어가기 (IF NOT EXISTS와 비슷한 효과)
  3. 오늘 파일 5개 받기 — foreach는 SQL의 커서 루프처럼 목록을 하나씩 돌며 같은 명령을 실행합니다. 받는 위치(-o $f)가 사이트 경로와 같아서 dags/…는 dags 폴더에, dbt/…는 dbt 폴더에 들어갑니다. 
    $base = "https://jinjinparkk.github.io/de-study/practice/airflow"
foreach ($f in "Dockerfile","docker-compose.dbt.yml","dbt/profiles.yml","dags/shop_assets.py","dags/collect_shop_raw.py") {
  curl.exe -fsSL "$base/$f" -o $f
}
  4. .env 만들기 — compose가 자동으로 읽는 설정 파일입니다. 경로의 \를 /로 바꿔 한 줄로 씁니다. 
    "SHOP_DIR=$($HOME -replace '\\','/')/dbt-practice/shop" | Out-File .env -Encoding ascii
Get-Content .env
    조각뜻
    "SHOP_DIR=…".env에 쓸 한 줄. 이름=값 모양
    $( … )문자열 안에서 괄호 속 식을 먼저 계산해 끼워 넣기
    $HOME -replace '\\','/'C:\Users\…의 \를 /로 바꾸기 (REPLACE(home, '\', '/')). 첫 칸은 정규식이라 \를 두 번 써야 "글자 \ 하나"
    | Out-File .env그 줄을 .env 파일로 저장 (있으면 덮어씀)
    -Encoding ascii글자 인코딩을 단순하게. PowerShell 5.1 기본(UTF-16)으로 쓰면 compose가 못 읽을 수 있음
    기대 결과: SHOP_DIR=C:/Users/내이름/dbt-practice/shop 한 줄.
  5. dbt 버전 맞추기 — 컨테이너 안 dbt·DuckDB 버전은 Dockerfile에 적혀 있습니다(dbt-core==1.12.6, dbt-duckdb==1.11.1, duckdb==2.0.0). 내 PC 버전을 봅니다. 
    & $HOME\dbt-practice\.venv\Scripts\pip.exe show dbt-core dbt-duckdb duckdb | Select-String "^(Name|Version)"
    조각뜻
    & 경로\pip.exe& = "이 경로의 프로그램을 실행". 1일차 가상환경의 pip를 활성화 없이 바로 부름
    show dbt-core dbt-duckdb duckdb설치된 패키지 정보 보기
    | Select-String "^(Name|Version)"그중 Name·Version으로 시작하는 줄만 (WHERE line LIKE 'Name%' OR line LIKE 'Version%')

    버전을 맞추는 이유: 내 PC의 dbt와 컨테이너의 dbt가 같은 프로젝트·같은 DuckDB 파일 형식을 다루기 때문입니다. 운영과 개발 버전이 다르면 "내 PC에선 되는데 운영에선 깨짐"이 생깁니다.

    다르면 메모장으로 Dockerfile을 열어(notepad Dockerfile) 세 숫자를 내 PC 버전으로 고칩니다. 특히 duckdb가 다르면 파일을 못 읽을 수 있습니다.
  6. 확인 — 두 compose 파일이 합쳐진 결과를 미리 봅니다(컨테이너는 안 띄움). 
    Get-ChildItem dags, dbt, landing
docker compose -f docker-compose.yml -f docker-compose.dbt.yml config | Select-String "source:|target:"
    조각뜻
    -f A -f B설정 파일을 직접 지정. 여러 개면 순서대로 겹침(B가 A 위에)
    config컨테이너는 안 띄우고, 겹친 최종 설정과 .env 값이 채워진 결과만 출력. 띄우기 전 미리보기 (dbt의 compile과 비슷)
    | Select-String "source:|target:"폴더 연결 줄(source = 내 PC, target = 컨테이너)만 골라 보기
    dags에 5일차 파일 2개 + shop_assets.py, collect_shop_raw.py, dbt에 profiles.yml이 있고, config 출력에 source: 줄로 내 dbt-practice의 shop 경로가, 바로 아래 target: /opt/airflow/shop이 보이면 연결 준비 끝입니다(오류 없이 출력되는 것 자체가 .env를 읽었다는 뜻).

직접 받기: Dockerfile · docker-compose.dbt.yml · dbt/profiles.yml · dags/shop_assets.py · dags/collect_shop_raw.py

# 6일차: 5일차 설정 위에 "dbt 가 들어간 이미지 + shop 프로젝트"를 덧씌우는 파일
# 실행:  docker compose -f docker-compose.yml -f docker-compose.dbt.yml up -d --build
# 준비:  같은 폴더의 .env 파일에  SHOP_DIR=C:/Users/내이름/dbt-practice/shop  한 줄
services:
  airflow:
    image: de-airflow-dbt:3.3.2    # 아래 Dockerfile 로 직접 만든 이미지 이름
    build: .
    environment:
      DBT_PROFILES_DIR: /opt/airflow/dbt          # profiles.yml 을 찾을 폴더
      DBT_TARGET_PATH: /opt/airflow/dbt_target    # target/ 을 shop 폴더 밖에 쓰게 (내 PC 의 target/ 과 안 섞이게)
      DBT_LOG_PATH: /opt/airflow/logs/dbt         # dbt.log 위치
      DBT_DUCKDB_PATH: /opt/airflow/shop/shop_prod.duckdb  # prod target 이 쓸 DuckDB 파일 (내 PC 의 shop.duckdb 와 다른 파일)
      DBT_USE_COLORS: "false"                     # 로그에 색깔용 제어 문자가 안 섞이게
      DBT_SEND_ANONYMOUS_USAGE_STATS: "false"     # 사용 통계 끄기 (읽기 전용 dbt 폴더에 .user.yml 을 쓰려 하지 않게)
    volumes:
      - ${SHOP_DIR:?SHOP_DIR 를 .env 에 적어 주세요}:/opt/airflow/shop
      - ./dbt:/opt/airflow/dbt:ro
      - ./landing:/opt/airflow/landing    # 수집 DAG 가 "새로 도착한 파일"을 찾는 곳
왜 compose 파일을 두 개로 나눴나

-f A -f B로 주면 B의 내용이 A 위에 합쳐집니다(같은 키는 덮어쓰고, 목록은 이어 붙임). 어제 설정은 그대로 두고 "dbt용 차이"만 B에 모아 두면, 무엇이 추가됐는지 한눈에 보입니다. SQL로 치면 기본 뷰 위에 컬럼 몇 개를 더한 뷰를 하나 더 얹는 것과 비슷합니다.

이 파일의 새 키 (image·environment·volumes의 기본 뜻은 5일차 2단계)

키뜻과 이유
image: de-airflow-dbt:3.3.2이번엔 받아 올 이미지가 아니라 내가 만들 이미지의 이름. 어제 apache/airflow:3.3.2를 덮어씀
build: ."이 폴더(.)의 Dockerfile로 이미지를 만들어라"
DBT_PROFILES_DIRdbt가 profiles.yml을 찾을 폴더. 기본(~/.dbt) 대신 연결한 dbt 폴더를 보게
DBT_TARGET_PATH / DBT_LOG_PATHdbt가 만드는 target/·로그를 shop 폴더 밖에 쓰게. 내 PC에서 돌린 결과와 섞이지 않음
DBT_DUCKDB_PATHprod target이 쓸 DuckDB 파일. profiles.yml이 env_var()로 읽음 → 코드 수정 없이 환경마다 다른 파일
${SHOP_DIR:?메시지}:/opt/airflow/shop.env의 SHOP_DIR 값으로 바꿔 끼움. 값이 없으면 ? 뒤 메시지를 내고 멈춤 (조용히 엉뚱한 폴더를 연결하지 않게)
./dbt:/opt/airflow/dbt:ro접속 정보는 읽기 전용으로 연결
  • dbt 프로젝트는 보통 별도 git 저장소(또는 Airflow와 같은 저장소의 하위 폴더)에 둡니다. 운영에 올릴 때는 ① 이미지 안에 dbt 프로젝트를 복사해 굽거나(COPY), ② 관리형 Airflow의 버킷(예: Composer의 dags·data 폴더)에 CI가 동기화합니다. 오늘처럼 개인 PC 폴더를 연결하는 건 로컬 개발에서만입니다.
  • .env처럼 사람·환경마다 다른 값이 든 파일은 git에 올리지 않습니다(.gitignore). 대신 예시 파일(.env.example)만 올려 "무엇을 채워야 하는지" 알려 줍니다.
  • profiles.yml은 저장소에 올려도 되게 만들고, 비밀번호·키 경로 같은 값은 전부 {{ env_var('…') }}로 빼서 운영에선 비밀 저장소가 환경 변수로 넣어 줍니다.
3. 이미지 빌드하고 다시 띄우기

공식 Airflow 이미지에는 dbt가 없습니다. 태스크는 컨테이너 안에서 돌기 때문에, 내 PC에 dbt가 있어도 컨테이너 안에 없으면 dbt: command not found가 납니다. 그래서 공식 이미지 위에 dbt를 얹은 새 이미지를 만듭니다. Dockerfile은 "서버 설치 절차서"를 코드로 적은 것이라, 몇 번을 다시 만들어도 같은 서버가 나옵니다.

dbt를 Airflow와 같은 파이썬에 바로 설치하지 않고 전용 가상환경(/opt/dbt_venv)에 넣는 이유는 이론 절대로, 두 프로그램이 쓰는 라이브러리 버전이 부딪히기 때문입니다. 1일차에 venv를 만든 이유와 같습니다.

목표: Dockerfile대로 "Airflow + dbt" 이미지를 만들고, 그 이미지로 컨테이너를 새로 띄웁니다.

Dockerfile을 한 줄씩 (전체는 이론 절 "이미지 만들기"와 같음)

줄뜻과 이유
FROM apache/airflow:3.3.2"이 이미지에서 출발". 공식 이미지를 통째로 바탕으로 깔고 그 위에 덧붙임 (기본 뷰 위에 뷰 얹기). 버전을 박아야 Airflow가 몰래 바뀌지 않음
USER root이후 명령을 관리자 권한으로. /opt에 폴더를 만들려면 필요
RUN …이미지를 만드는 동안 셸 명령 실행. 결과가 이미지에 저장됨 (설치 스크립트 한 줄)
python -m venv /opt/dbt_venvdbt 전용 가상환경 만들기 (1일차 python -m venv .venv와 같음)
&& / \&& = 앞 명령이 성공하면 다음 명령. \ = 줄 바꿈 이어 쓰기. 하나라도 실패하면 빌드가 멈춤
/opt/dbt_venv/bin/pip install --no-cache-dir "dbt-core==1.12.6" …가상환경 안의 pip로 버전을 고정(==)해 설치. --no-cache-dir = 설치 파일 캐시를 안 남겨 이미지 크기 줄이기
/opt/dbt_venv/bin/dbt --version설치가 정말 됐는지 빌드 중에 바로 확인. 실패하면 이미지가 안 만들어짐 (스모크 테스트)
USER airflow다시 일반 사용자로. 공식 이미지는 airflow 사용자로 돌아야 함 (보안·권한)
  apache/airflow:3.3.2  ──(Dockerfile: dbt 전용 venv 에 dbt-duckdb 설치)──▶  de-airflow-dbt:3.3.2
                                                                               └─ 컨테이너 de-airflow-airflow-1 (새로 만듦)
  1. 빌드 + 기동 (처음엔 pip 설치 때문에 몇 분): 
    cd $HOME\airflow-practice
docker compose -f docker-compose.yml -f docker-compose.dbt.yml up -d --build
    조각뜻
    -f … -f …(2단계) 두 설정을 겹쳐서
    up -d(5일차 3단계) 만들고 뒤에서 켜기
    --build켜기 전에 build:에 적힌 Dockerfile로 이미지를 (다시) 만들기. Dockerfile을 고친 뒤에는 꼭 붙여야 반영됨
    빌드 로그 끝부분에 Dockerfile의 dbt --version 줄이 찍은 Core: … installed: 1.12.6, duckdb: 1.11.1 비슷한 줄이 보입니다.

4. pool 만들고 dbt 연결 확인

DuckDB는 파일 하나에 한 번에 한 프로세스만 쓸 수 있는 DB입니다(이론 절). dbt 태스크 두 개가 동시에 같은 파일을 쓰려 하면 Could not set lock으로 실패합니다. pool은 "이 이름표를 단 태스크는 동시에 N개까지만"을 거는 입장권 묶음이고, 1장짜리로 만들면 줄을 세워 하나씩 돌게 됩니다. 프로시저로 치면 같은 테이블을 건드리는 잡에 세마포어·잠금을 거는 것과 같습니다.

dbt debug를 먼저 치는 이유는 1일차와 같습니다. DAG에서 dbt가 실패하면 원인이 SQL인지 경로·프로필인지 헷갈리니, 컨테이너 안에서 프로필·경로가 맞는지만 먼저 따로 확인합니다.

목표: DuckDB에 쓰는 태스크가 한 번에 하나만 돌게 할 슬롯 1개짜리 pool을 만들고, 컨테이너 안 dbt가 shop 프로젝트를 제대로 찾는지 봅니다.

  1. pool 만들기 (화면이라면 Admin → Pools → 추가, 메뉴 이름 미검증): 
    docker compose exec airflow airflow pools set duckdb 1 "DuckDB single writer"
docker compose exec airflow airflow pools list
    조각뜻
    pools setpool 만들기(있으면 고치기)
    duckdbpool 이름. 태스크에서 pool="duckdb"로 가리킴
    1슬롯 수 = 동시에 돌 수 있는 태스크 수
    "DuckDB single writer"설명 (화면에 보이는 메모)
    pools listpool 목록 확인
    표에 default_pool(128)과 duckdb(1) 두 줄이 보이면 OK.
  2. dbt 연결 확인 — -w는 "이 폴더에서 실행"(= BashOperator의 cwd)입니다.

    마지막에 All checks passed!면 컨테이너 안 dbt가 shop 프로젝트와 prod 프로필을 찾은 것입니다.

    docker compose exec -w /opt/airflow/shop airflow /opt/dbt_venv/bin/dbt deps

pool은 메타DB(컨테이너 안 SQLite)에 저장되므로, 컨테이너를 다시 만들면(down, up --build) 1번 명령을 다시 쳐야 합니다.

  • pool은 DuckDB 같은 단일 파일 DB보다 외부 한도를 지키는 용도로 더 많이 씁니다: 원천 API 호출 한도, 웨어하우스 동시 쿼리 수, 운영 DB 부하. BigQuery 자체는 동시 쓰기가 되지만 슬롯·비용을 아끼려고 pool로 동시 실행을 묶기도 합니다.
  • pool·Variables 같은 설정을 화면에서 손으로 만들면 컨테이너·환경을 새로 만들 때마다 빠뜨리기 쉽습니다. 팀에서는 airflow pools import pools.json 같은 명령을 배포 스크립트에 넣거나 Terraform으로 관리해 코드로 남깁니다.
  • dbt debug는 배포 파이프라인이나 DAG 맨 앞에 넣어 접속 문제를 모델 실패와 구분하는 데도 씁니다.

6. 직접 해보기: 계층별 태스크 + 재시도·알림·pool + Asset 스케줄

5단계의 한 덩어리는 marts 모델 하나만 실패해도 staging부터 전부 다시 돌려야 하고, 화면에선 "dbt_build 실패" 한 칸만 보여 어느 계층이 문제인지 로그를 뒤져야 압니다. 계층별로 나누면 실패한 프로시저 블록만 다시 돌리고, 화면만 봐도 어디서 막혔는지 보입니다.

여기에 운영 설정 세 가지를 붙입니다. retries = 실패 시 재실행 잡 설정(일시적 오류는 사람 없이 흡수), execution_timeout = 멈춘 채 몇 시간씩 자리를 잡는 것 방지, on_failure_callback = 재시도까지 다 실패하면 사람에게 알림. 마지막으로 시각 대신 Asset(= "원천 테이블 적재가 끝나면 다음 실행")으로 스케줄을 걸어, 5일차 첫 표의 "적재가 늦게 끝나면 반쪽 데이터로 도는" 문제를 없앱니다.

  │  path:models/  │                     │  path:models/intermediate │

def notify_failure(context):                     # 실패 알림 함수. 실제로는 슬랙·메일로 보낸다
    ti = context["ti"]                           # ti = 실패한 태스크 인스턴스
    print(f"[알림] {ti.dag_id}.{ti.task_id} 실패 (run_id={ti.run_id}, 시도 {ti.try_number}회)")


def dbt_step(task_id: str, args: str) -> BashOperator:
    # 같은 모양의 BashOperator 를 여러 번 만드는 도우미 (SQL 로 치면 매크로)
    return BashOperator(
        task_id=task_id,
        cwd=SHOP,
        bash_command=f"{DBT} {args} --target prod",
        pool="duckdb",                           # 슬롯 1개짜리 풀: DuckDB 에 쓰는 태스크는 한 번에 하나만
    )

    dag_id="dbt_shop_layers",

        "on_failure_callback": notify_failure,   # 재시도까지 다 실패했을 때 부를 함수
    },
    tags=["day6", "dbt"],

7. 일부러 실패시켜 재시도·알림·upstream_failed 보기

운영의 대부분은 "잘 돌 때"가 아니라 "실패했을 때 무엇을 하느냐"입니다. 6단계에서 적은 재시도·알림 설정은 실제로 실패해 보기 전엔 맞게 적었는지 알 수 없습니다. 새벽 장애 때 처음 보는 것보다, 지금 일부러 실패시켜 색깔 변화 → 알림 → 고치고 Clear(실패 지점부터 재실행)까지 한 바퀴 돌려 보는 게 훨씬 쌉니다. 프로시저로 치면 TRY…CATCH와 재실행 잡을 만들고 일부러 에러를 던져 보는 테스트입니다.

dags test가 아니라 화면 Trigger로 돌리는 이유: 재시도 대기·pool은 스케줄러가 처리하는 동작이라 스케줄러를 거쳐야 보입니다.

목표: 6단계 설정이 실패 때 실제로 어떻게 움직이는지 봅니다. 프로시저의 TRY … CATCH + 재실행 잡을 Airflow가 대신 해 주는 장면입니다.

  1. 내 프로젝트의 $HOME\dbt-practice\shop\models\staging\stg_orders.sql을 메모장으로 열어 첫 줄 select를 selec로 바꿔 저장합니다(SQL 문법 오류).
  2. 화면에서 dbt_shop_layers 토글을 켜고 Trigger (버튼 이름 미검증). dags test가 아니라 화면으로 돌려야 pool·재시도가 실제로 적용됩니다.
  3. 태스크 칸 색을 지켜봅니다(약 1~2분):
    • staging.build가 up_for_retry(노란색 계열)로 바뀌고 30초 뒤 다시 도는지 — 이걸 두 번
    • 세 번째 시도까지 실패하면 failed(빨간색), 로그 끝에 [알림] dbt_shop_layers.staging.build 실패 … 시도 3회
    • snapshot과 marts.build는 한 번도 안 돌고 upstream_failed(주황색 계열)
  4. 고치고 이어서 돌리기: selec를 select로 되돌려 저장 → 실패한 실행에서 staging.build 칸을 누르고 Clear(하류 포함 옵션을 켠 채로, 메뉴 이름 미검증) → 세 칸이 차례로 초록색이 되면 끝.

새 실행을 만들지 않고 같은 실행 안에서 실패한 부분부터 이어 가는 게 Airflow 운영의 기본 동작입니다.

왜 알림이 "시도 3회"인가

retries=2는 "추가로 2번"이라 총 3번 시도합니다. 위 이론 절 실측(retries=1)에서는 "시도 2회"였습니다.

  • 장애 대응 순서(런북)를 팀 문서로 정해 둡니다: 알림 확인 → 로그로 원인 분류(데이터 문제 / 코드 문제 / 인프라·권한 문제) → 고치기 → 실패한 태스크부터 Clear → 하류 결과 확인 → 공지.
  • 새 실행을 만들지 않고 Clear로 이어 가는 이유는 같은 logical date로 다시 돌아야 해서입니다. 새로 Trigger하면 날짜가 달라져 엉뚱한 날을 처리할 수 있습니다(5일차).
  • 재시도로 결국 성공한 실패도 기록을 봅니다. 매일 한 번씩 재시도로 넘어가는 태스크는 언젠가 진짜로 터지는 경고 신호입니다.

# 6일차: "수집" DAG. landing 폴더에 새 CSV 가 있으면 shop/data 로 옮기고 Asset 을 갱신한다
import glob                                      # 파일 이름 패턴으로 찾기 (LIKE '%.csv')
import os
import shutil                                    # 파일 복사
import pendulum
from airflow.sdk import dag, task
from airflow.sdk.exceptions import AirflowSkipException   # "이번엔 건너뛰기" 신호
from shop_assets import SHOP_RAW                 # 같은 dags 폴더의 shop_assets.py 에서 가져오기

LANDING = "/opt/airflow/landing"                 # 내 PC 의 practice/airflow/landing
SHOP_DATA = "/opt/airflow/shop/data"             # 내 PC 의 dbt-practice/shop/data


@dag(
    dag_id="collect_shop_raw",
    schedule=None,                               # 연습이라 수동 실행. 실제로는 매시간 등
    start_date=pendulum.datetime(2026, 10, 1, tz="Asia/Seoul"),
    catchup=False,
    tags=["day6"],
)
def collect_shop_raw():

    @task(outlets=[SHOP_RAW])                    # 이 태스크가 "성공"하면 SHOP_RAW 가 갱신됐다고 기록된다
    def move_landing_files() -> list[str]:
        files = sorted(glob.glob(f"{LANDING}/raw_*.csv"))
        if not files:                            # 새 파일이 없으면 건너뛰기(skipped) → Asset 갱신도 없음
            raise AirflowSkipException("landing 에 새 파일이 없습니다")
        moved = []
        for src in files:                        # FOR 문: 파일마다
            dst = os.path.join(SHOP_DATA, os.path.basename(src))
            shutil.copyfile(src, dst)            # shop/data 의 같은 이름 파일을 덮어쓴다
            os.remove(src)                       # 옮긴 파일은 landing 에서 지운다 (다음 실행 때 또 옮기지 않게)
            moved.append(os.path.basename(src))
        print(f"옮긴 파일: {moved}")
        return moved

    move_landing_files()

10. (선택) Cosmos 맛보기

6단계는 계층 3칸으로 나눴지만, 실패 단위는 여전히 "staging 전체"입니다. Cosmos는 dbt 프로젝트를 읽어 모델 하나 = 태스크 하나로 펼쳐 줘서, 실패한 모델만 다시 돌리고 dbt 리니지를 Airflow 화면에서 그대로 볼 수 있습니다. 대신 모델이 수백 개면 태스크도 수백 개가 되고 DAG 파싱이 무거워지므로, "언제 쓸 만한지"를 감으로 익히려고 맛만 봅니다.

on_failure_callback은 태스크가 최종적으로 failed가 될 때 불립니다. 앞의 두 번 실패는 up_for_retry 상태라 불리지 않습니다(실측: retries=1에서 두 번째 실패 뒤 한 번). 재시도마다 알림이 필요하면 on_retry_callback을 따로 겁니다.

Airflow 3에서 "07:00까지 마트가 안 만들어지면 알려줘"를 구현할 때 쓸 수 없는 것은?

  1. 태스크의 sla=timedelta(hours=1)와 DAG의 sla_miss_callback
  2. DAG의 deadline=DeadlineAlert(...)
  3. execution_timeout·dagrun_timeout + on_failure_callback
  4. 07:00에 마트 파티션 존재를 검사하는 별도 DAG
SLA 기능은 Airflow 3.0에서 삭제됐습니다. 3.1부터 Deadline Alerts가 그 자리를 대신하고, timeout+실패 콜백이나 별도 검사 DAG도 흔히 씁니다.

dbt를 Airflow 이미지 안의 별도 가상환경(/opt/dbt_venv)에 설치하는 가장 큰 이유는?

  3. DuckDB 잠금 문제를 없애려고
  4. Airflow와 dbt가 함께 쓰는 라이브러리의 버전 요구가 부딪히지 않게 하려고

BashOperator로 dbt build를 돌렸더니 No such file: data/raw_orders.csv가 납니다. 가장 먼저 의심할 것은?

  1. pool을 만들지 않았다
  2. BashOperator의 cwd가 dbt 프로젝트 폴더가 아니다
  3. retries가 0이다
  4. Asset 이름이 틀렸다
sources.yml의 read_csv('data/{name}.csv')는 현재 폴더 기준 상대 경로입니다. dbt를 프로젝트 폴더 밖에서 실행하면 파일을 못 찾습니다. pool이 없으면 실행 자체가 대기하고, retries·Asset은 이 오류와 상관없습니다.

수집 DAG의 태스크(outlets=[SHOP_RAW])가 "새 파일 없음"으로 skipped 되었습니다. schedule=[SHOP_RAW]인 dbt DAG는?

  1. 바로 실행된다 — 수집 DAG가 끝났으니까
  2. Airflow가 Asset URI의 폴더를 확인해 파일이 바뀌었으면 실행한다
  3. 실행되지 않는다 — 생산자 태스크가 성공하지 않아 Asset 이벤트가 생기지 않는다
  4. 오류로 실패한다
Asset 이벤트는 outlets를 가진 태스크가 성공할 때만 생깁니다(실측: skip 때 이벤트 0건). Airflow는 URI가 가리키는 파일을 보지 않습니다. 이벤트가 없으니 소비자도 돌지 않고, 실패도 아닙니다.

Airflow 컨테이너(prod)와 내 PC(dev)가 shop의 DuckDB를 다루는 방식으로 가장 안전한 것은?

  1. 파일을 나눈다 — Airflow는 shop_prod.duckdb(prod target), 나는 shop.duckdb(dev)
  2. 같은 shop.duckdb를 쓰고, 잠금이 알아서 막아 주길 기대한다
  3. 둘 다 threads: 1로 두면 같은 파일을 동시에 써도 된다
  4. Airflow 태스크 retries를 크게 둬서 잠금 오류를 넘긴다
DuckDB는 한 파일에 쓰기 프로세스 하나만 허용하고, Windows 폴더를 컨테이너에 연결한 경계에서는 잠금이 제대로 전달된다는 보장이 없습니다. 그래서 target으로 파일을 나누는 게 안전합니다. threads는 한 프로세스 안의 설정이라 두 프로세스 문제를 못 막고, 재시도는 근본 해결이 아닙니다.

dbt build --select state:modified+ --defer --state prod_artifacts/에서 --defer의 역할은?

  2. 테스트를 건너뛴다
  3. 바뀐 모델의 상류까지 전부 다시 만든다
  4. 이번에 만들지 않는(안 바뀐) 상류 모델은 운영 환경의 테이블을 참조하게 한다
slim CI에서는 바뀐 것과 하류만 빌드합니다. 그러면 안 바뀐 상류 테이블이 CI 스키마에 없으니, --defer가 ref()를 운영 manifest 기준의 운영 테이블로 돌려 줍니다. 상류를 다시 만들지 않는 게 핵심이라 ③은 반대입니다.
