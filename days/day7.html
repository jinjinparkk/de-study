왜 분산 처리인가 — 그리고 언제 필요 없는가

컴퓨터 한 대의 메모리·디스크·CPU로 감당이 안 되는 데이터가 있습니다. 하루 로그가 2TB라면, 아무리 좋은 서버 한 대라도 읽는 데만 몇 시간이 걸립니다. 이걸 100대가 20GB씩 나눠 동시에 읽으면 몇 분이면 끝납니다. 이게 분산 처리의 전부입니다. Spark는 "나눠서 동시에 계산하고 결과를 다시 모으는 일"을 대신 해 주는 엔진입니다.

🧸 비유

감자 1만 개를 깎아야 합니다. 요리사 한 명이면 하루가 걸립니다. 요리사 100명에게 100개씩 나눠 주면 금방 끝나지만, 대신 나눠 주고, 다 깎았는지 확인하고, 깎은 감자를 한곳에 모으는 사람(주방장)이 필요하고, 감자를 옮기는 데 시간도 듭니다. 감자가 30개뿐이라면? 혼자 깎는 게 훨씬 빠릅니다. 나눠 주는 시간이 더 걸리니까요.

여기서 솔직하게 말씀드리면, 마케팅·분석 업무의 대부분은 Spark가 필요 없습니다. BigQuery·Snowflake는 이미 내부적으로 수천 대에 나눠 계산하는 분산 엔진입니다. 내가 SQL만 쓰면 분산은 웨어하우스가 알아서 합니다. 그래서 "데이터가 크다 → Spark"가 아니라 "웨어하우스 안으로 넣기 어렵거나, SQL로 표현하기 어렵거나, 웨어하우스 비용이 감당 안 될 때 → Spark"입니다.

Spark SQL (익숙한 쪽)
select order_date,
       count(*)    as orders,
       sum(amount) as revenue
from fct_orders
where status = 'completed'
group by order_date
DataFrame API (같은 뜻)
(fct_orders
  .where(F.col("status") == "completed")  # WHERE
  .groupBy("order_date")                  # GROUP BY
  .agg(F.count("*").alias("orders"),      # count(*)
       F.sum("amount").alias("revenue"))) # sum(amount)
🧸 비유

RDD는 재료를 손으로 하나하나 집어 옮기는 것, DataFrame은 "양파 30개 썰어 주세요"라고 주문서를 쓰는 것, Spark SQL은 같은 주문서를 다른 양식(SQL)으로 쓰는 것입니다. 주문서가 있으면 주방장(Catalyst)이 "양파를 먼저 거르고 썰면 덜 썰어도 되겠네" 하고 순서를 고쳐 줍니다. 손으로 옮기면 그런 최적화가 없습니다.

지연 실행 — 변환과 액션

Spark에서 select, where, join, groupBy를 쓰면 아무 계산도 일어나지 않습니다. 계획만 쌓입니다. show(), count(), write 같은 액션을 만나야 그 계획 전체를 한 번에 최적화해서 실행합니다.

종류예결과
변환 (Transformation)select, where, withColumn, join, groupBy().agg(), orderBy, repartition새 DataFrame(=계획)을 돌려줌. 즉시 끝남
액션 (Action)show, count, collect, toPandas, write.parquet, take실제 실행(Job) 시작. 시간이 걸림
🧸 비유

온라인 장보기와 같습니다. 장바구니에 담는 동안(변환)은 아무것도 배송되지 않습니다. 결제 버튼(액션)을 눌러야 창고가 움직이는데, 그때 창고는 장바구니 전체를 보고 "같은 창고 물건끼리 한 번에 싸자"고 묶어서 보냅니다. 하나 담을 때마다 배송했다면 훨씬 비쌌겠죠.

프로시저 감각으로 옮기면
  • 변환 = 뷰(VIEW) 정의. CREATE VIEW는 바로 끝나고, 실제 계산은 그 뷰를 SELECT 할 때 일어나죠. Spark DataFrame도 뷰 정의가 차곡차곡 쌓인 것과 같습니다.
  • 액션 = 그 뷰를 실제로 SELECT 하거나 INSERT 하는 순간. dbt의 ephemeral 모델이 CTE로 합쳐져 한 번에 실행되는 것과도 닮았습니다.
  • 그래서 같은 DataFrame에 액션을 두 번 하면 처음부터 두 번 계산합니다(뷰를 두 번 조회하듯). 이걸 막는 게 뒤에 나올 캐시입니다.

          셔플이 필요한 곳에서 끊는다                  ▼
┌──────────── Stage 0 ────────────┐   셔플   ┌──── Stage 1 ────┐

파티션 · narrow와 wide · 셔플

파티션은 DataFrame을 나눈 조각입니다. 익스큐터는 파티션 하나에 Task 하나를 붙여 처리합니다. 그래서 파티션 수가 곧 동시에 할 수 있는 일의 최대치입니다. 파티션이 2개인데 코어가 100개면 98개는 놉니다. 반대로 1KB짜리 파티션이 10만 개면 일보다 관리 비용이 더 큽니다.

narrow 변환wide 변환
뜻내 파티션 안의 데이터만 보면 되는 연산다른 파티션의 데이터도 봐야 하는 연산
예select, where, withColumn, lower/trim, coalescegroupBy, join(브로드캐스트 아닌 경우), distinct, orderBy, repartition
비용싸다. 앞뒤 연산이 한 Stage로 묶임비싸다. 셔플이 일어나고 Stage가 나뉨

셔플은 "같은 키를 가진 행을 같은 파티션으로 모으려고" 데이터를 디스크에 쓰고 네트워크로 다른 익스큐터에 보내는 작업입니다. group by order_date를 하려면 10-05 주문이 여러 파티션에 흩어져 있으면 안 되니까, 10-05 행을 한 파티션으로 모아야 하죠. Spark 성능 문제의 대부분은 셔플을 얼마나, 어떻게 하느냐로 귀결됩니다.

반 아이들이 아무렇게나 앉아 있습니다(파티션). "자기 이름표 쓰기"는 각자 자리에서 하면 됩니다(narrow). 그런데 "생일 달별로 모여 앉기"를 하려면 반 전체가 일어나서 자리를 옮겨야 합니다(셔플, wide). 자리 이동이 끝나야 다음 일을 시작할 수 있죠(Stage 경계).

셔플 뒤 파티션 수는 기본 200입니다. 30행짜리 데이터에도 200개로 나누려 하니 연습할 땐 과합니다. 실습 코드는 8로 줄였습니다. Spark 3.2부터는 AQE(Adaptive Query Execution)가 기본으로 켜져 있어, 실행 중에 실제 크기를 보고 작은 파티션을 합치거나 조인 방식을 바꿉니다. explain() 맨 위의 AdaptiveSparkPlan이 그 표시입니다.

조인 전략 · 스큐 · 캐시

두 표를 조인하려면 같은 키의 행이 같은 곳에 있어야 합니다. Spark가 이걸 맞추는 대표적인 방법은 두 가지입니다.

① Broadcast Hash Join  (한쪽이 작을 때 — 기본 기준 10MB 이하)
   작은 표 stg_payments ──복사──▶ 익스큐터 1, 2, 3 모두에게
   큰 표 orders 는 제자리에서 그냥 붙임  → 큰 표 셔플 없음 ✓ 빠름

② Sort-Merge Join  (양쪽 다 클 때)

스큐(skew) — 한 명만 야근하는 문제

셔플은 키 값으로 행을 나눕니다. 그런데 customer_id = NULL이나 "비회원" 같은 값 하나에 행의 40%가 몰려 있다면? 그 키를 맡은 파티션 하나만 거대해지고, 나머지 199개 Task는 1초 만에 끝나 그 하나를 기다립니다. Spark UI의 Stage 상세에서 Task 시간의 최댓값이 중앙값보다 훨씬 크면 스큐입니다.

  • 대책 ①: 몰린 키(NULL 등)를 먼저 걸러 따로 처리
  • 대책 ②: AQE의 skew join 처리(spark.sql.adaptive.skewJoin.enabled, 기본 켜짐)가 큰 파티션을 쪼개 줌
  • 대책 ③: 작은 쪽이면 브로드캐스트로 셔플 자체를 없앰
  • 대책 ④: 키에 랜덤 꼬리표(salt)를 붙여 강제로 흩뿌린 뒤 두 번 집계
프로시저 감각으로 옮기면

BigQuery에서도 같은 일이 있었습니다. 특정 키에 몰린 JOIN이 "Resources exceeded"로 죽거나, 실행 상세의 한 단계만 유난히 오래 걸리던 경험이 있다면 그게 스큐입니다. 웨어하우스는 대부분 알아서 처리해 주지만, Spark에서는 내가 보고 손을 대야 합니다.

캐시 — 여러 번 쓸 DataFrame은 잡아 두기

작은 파일 문제

Spark는 파티션(메모리 조각)마다 폴더마다 파일을 하나씩 씁니다. 메모리 파티션이 200개, 날짜 폴더가 365개면 최대 73,000개 파일이 생길 수 있습니다. 파일 하나에 몇 KB씩이면, 나중에 읽을 때 파일 목록을 가져오고 여닫는 시간이 데이터 읽는 시간보다 길어집니다.

  • 쓰기 전에 .repartition("order_date") → 같은 날짜가 한 파티션에 모여 폴더마다 파일 1개 (실습 코드가 이 방식)
  • 전체가 작으면 .coalesce(n)으로 파일 수 줄이기
  • 너무 잘게 나누지 않기: 하루 몇 MB짜리 데이터를 시간 단위 폴더로 나누지 않기. 파일 하나 수백 MB~1GB가 적당한 크기
  • Delta·Iceberg는 OPTIMIZE/compaction으로 작은 파일을 주기적으로 합침
이름이 같아서 헷갈리는 "파티션"

Spark 파티션은 메모리 속 데이터 조각(병렬 처리 단위), 파일 파티션(partitionBy)은 디스크 폴더 나누기, BigQuery 파티션은 테이블 저장 단위입니다. 셋 다 "나눈다"는 뜻은 같지만 다른 물건입니다. repartition은 앞의 것, partitionBy는 두 번째 것을 바꿉니다.

3. 직접 해보기: DataFrame API로 stg → fct_orders → daily_sales

dbt 모델 세 개를 DataFrame 변수 세 개로 옮겨 보세요.

  • stg_orders: order_id, customer_id, order_date, lower(trim(status)) as status
  • stg_payments: 주문별 sum(amount) as amount
  • fct_orders: 두 개를 order_id로 left join
  • daily_sales_df: completed만, 날짜별 orders, revenue, 날짜순 정렬 → .show()
힌트 1

SQL 절 하나가 메서드 하나입니다. SELECT → .select(), WHERE → .where(), GROUP BY ... 집계 → .groupBy(...).agg(...), JOIN USING → .join(b, on="키", how="left"), ORDER BY → .orderBy(). 명령어 모음에 대응표가 있습니다.

힌트 2

함수는 F.에 있습니다: F.lower(F.trim("status")), F.sum("amount"), F.count("*"). 컬럼 이름 붙이기(AS)는 .alias("이름"). 조건은 F.col("status") == "completed" (등호 두 개).

정답 보기 
stg_orders = orders_raw.select(               # select
    "order_id", "customer_id", "order_date",
    F.lower(F.trim("status")).alias("status"),  # lower(trim(status)) as status
)
stg_payments = (payments_raw
    .groupBy("order_id")                       # group by order_id
    .agg(F.sum("amount").alias("amount")))     # sum(amount) as amount

fct_orders = stg_orders.join(stg_payments, on="order_id", how="left")  # left join using (order_id)

daily_sales_df = (fct_orders
    .where(F.col("status") == "completed")     # where status = 'completed'
    .groupBy("order_date")                     # group by order_date
    .agg(F.count("*").alias("orders"),         # count(*) as orders
         F.sum("amount").alias("revenue"))     # sum(amount) as revenue
    .orderBy("order_date"))                    # order by order_date

daily_sales_df.show()                          # 액션: 여기서 계산

4. 같은 것을 Spark SQL로 + 두 결과 비교

DataFrame을 임시 뷰로 등록하면 SQL로 질의할 수 있습니다. dbt 모델 SQL을 거의 그대로 붙여 넣으면 됩니다.

orders_raw.createOrReplaceTempView("raw_orders")      # CREATE TEMP VIEW raw_orders AS ...
payments_raw.createOrReplaceTempView("raw_payments")

daily_sales_sql = spark.sql("""
    with stg_orders as (
        select order_id, customer_id, order_date, lower(trim(status)) as status
        from raw_orders
    ),
    stg_payments as (
        select order_id, sum(amount) as amount from raw_payments group by order_id
    )
    select o.order_date, count(*) as orders, sum(p.amount) as revenue
    from stg_orders o
    left join stg_payments p using (order_id)
    where o.status = 'completed'
    group by o.order_date
    order by o.order_date
""")                                                  # spark.sql() 도 변환. 아직 실행 안 됨

# A EXCEPT ALL B, B EXCEPT ALL A 가 둘 다 0행이면 두 결과는 같다
diff = (daily_sales_df.exceptAll(daily_sales_sql).count()
        + daily_sales_sql.exceptAll(daily_sales_df).count())
print("차이 행 수:", diff)

차이 행 수: 0이 나오면 두 방식의 결과가 완전히 같습니다. 이제 둘의 실행 계획을 비교해 보세요.

daily_sales_df.explain()
daily_sales_sql.explain()

실제로 돌려 보면 두 출력은 내부 번호(plan_id)만 다르고 연산자와 순서가 한 줄도 다르지 않습니다. Catalyst가 두 코드를 같은 계획으로 바꾼 것입니다.

5. 직접 해보기: explain() 에서 셔플과 조인 찾기

위 explain 읽는 법의 표를 옆에 두고 daily_sales_df.explain() 출력에서 아래 세 가지를 찾아 적어 보세요.

  1. 셔플(Exchange)은 몇 번, 어떤 컬럼 기준으로 일어나나요?
  2. 조인 방식은 무엇이고, 왜 그게 골라졌을까요?
  3. status = 'completed' 조건(Filter)은 조인보다 위에 있나요, 아래에 있나요? 코드에 쓴 순서와 같나요?
힌트 1

Exchange로 시작하는 줄만 세어 보세요. BroadcastExchange는 셔플이 아니라 "작은 표 복사"입니다.

정답 보기
  1. 세 번: hashpartitioning(order_id, 8)(결제 합계용), hashpartitioning(order_date, 8)(일별 집계용), rangepartitioning(order_date ASC, 8)(정렬용). 각각이 Stage 경계입니다.
  2. BroadcastHashJoin. 결제 합계 쪽이 수 KB라 기준(10MB)보다 훨씬 작아서 복사해 붙이는 게 싸다고 판단했습니다. 그래서 orders 쪽은 조인 때문에 셔플되지 않았습니다.
  3. 조인 아래, orders FileScan 바로 위에 있습니다. 코드에선 join 뒤에 where를 썼지만, 옵티마이저가 "orders 컬럼만 쓰는 조건이니 조인 전에 거르면 조인할 행이 줄어든다"고 판단해 앞으로 옮겼습니다(predicate pushdown). 다만 lower(trim()) 같은 함수가 낀 조건이라 CSV 읽기 자체로는 못 내려가서 PushedFilters: []이고 DataFilters에만 적혀 있습니다. 반면 payments 쪽은 PushedFilters: [IsNotNull(order_id)]가 읽기 단계로 내려갔습니다.

이어서 브로드캐스트를 끄고 조인 방식이 바뀌는 걸 확인합니다.

spark.conf.set("spark.sql.autoBroadcastJoinThreshold", "-1")   # 브로드캐스트 끄기
stg_orders.join(stg_payments, "order_id", "left").explain()      # SortMergeJoin 이 보여야 함

💡 한 줄 요약 Spark는 변환을 계획으로 쌓았다가 액션 때 한 번에, 데이터를 파티션으로 나눠 익스큐터들이 동시에 계산하는 엔진이고, 비용의 대부분은 셔플에서 나온다.
  • Spark가 필요한 곳: 웨어하우스 밖의 큰 원본 파일·로그·JSON, 스트리밍, ML 피처, 레이크하우스. 테이블에 있는 데이터의 SQL 가공은 대부분 웨어하우스+dbt로 충분
  • 드라이버는 계획·지시, 익스큐터는 계산, 클러스터 매니저는 자원 배정. local 모드는 한 대에서 전부
  • DataFrame과 Spark SQL은 같은 옵티마이저 → 같은 실행 계획. RDD는 거의 쓸 일 없음
  • narrow는 셔플 없음, wide(groupBy·join·orderBy)는 셔플 → Stage 경계
  • 작은 표 조인은 Broadcast, 큰 표끼리는 Sort-Merge. 한 키에 몰리면 스큐
  • explain은 아래에서 위로: FileScan → Filter → Exchange(셔플) → HashAggregate → Join
  • 분석 저장은 parquet, partitionBy로 날짜 폴더, 쓰기 전 repartition으로 작은 파일 줄이기

퀴즈

다음 중 Spark를 도입할 이유가 가장 약한 경우는?

  1. GCS에 매일 500GB씩 쌓이는 원본 JSON 로그를 정제해 parquet로 만들기
  2. Kafka로 들어오는 클릭 이벤트를 몇 분 단위로 집계하기
  3. 이미 BigQuery 테이블에 있는 매체 리포트를 일별 마트로 집계하기
  4. 수억 행의 사용자 행동 데이터로 ML 학습용 피처 만들기
이미 웨어하우스에 있는 정형 데이터를 SQL로 집계하는 일은 BigQuery가 내부적으로 분산 처리해 줍니다. 여기에 Spark를 끼우면 데이터를 꺼냈다 다시 넣는 일과 클러스터 관리만 늘어납니다. dbt 모델이 맞습니다. 나머지 셋(웨어하우스 밖 대용량 원본, 스트리밍, ML 피처)은 Spark가 잘하는 영역입니다.

아래 코드에서 실제로 계산(Job)이 시작되는 줄은?

a = spark.read.parquet("events")           # (1)
b = a.where(F.col("country") == "KR")      # (2)
c = b.groupBy("day").count()               # (3)
c.show()                                   # (4)
  1. (1)부터 줄마다 하나씩
  2. (4)에서 (1)~(3)을 합친 계획이 한 번에
  3. (3)의 groupBy에서
  4. (2)의 where에서
read, where, groupBy().count()는 모두 변환이라 계획만 쌓입니다. show()가 액션이라 이때 전체 계획을 최적화해(예: country 조건을 파일 읽기로 내려보내기) 한 번에 실행합니다. 참고로 read는 스키마 확인 때문에 파일 메타데이터를 살짝 보기도 하지만, 데이터 전체를 계산하지는 않습니다.

다음 중 셔플을 일으키지 않는 연산은?

  1. df.groupBy("customer_id").agg(F.sum("amount"))
  2. df.orderBy("order_date")
  3. df.repartition(16)
  4. df.where(F.col("status") == "completed").select("order_id")
where와 select는 각 파티션 안에서 끝나는 narrow 변환이라 셔플이 없습니다. groupBy(같은 키 모으기), orderBy(전체 정렬), repartition(재분배)은 모두 다른 파티션의 데이터가 필요한 wide 연산이라 explain에 Exchange가 생깁니다.

10억 행 주문 표와 300행짜리 매체 코드표를 조인합니다. Spark가 보통 고르는 조인 방식과 그 이유는?

  1. Broadcast Hash Join — 작은 코드표를 모든 익스큐터에 복사하면 큰 주문 표를 셔플하지 않아도 되므로
  2. Sort-Merge Join — 큰 표가 있으면 항상 정렬 후 조인해야 하므로
  3. Broadcast Hash Join — 큰 주문 표를 모든 익스큐터에 복사하므로
  4. Cartesian Join — 키가 다르면 모든 조합을 만들어야 하므로
브로드캐스트되는 쪽은 작은 표입니다(기본 10MB 이하). 300행 코드표를 복사해 두면 10억 행은 제자리에서 붙기만 하니 셔플이 사라집니다. 3번처럼 큰 표를 복사하면 메모리가 터집니다. Sort-Merge는 양쪽이 다 클 때의 방식입니다.

Spark UI의 한 Stage에서 Task 199개는 2초, 1개는 25분 걸렸습니다. 가장 먼저 의심할 것은?

  1. 익스큐터 수가 너무 많다
  2. parquet 대신 CSV를 써서 그렇다
  3. 특정 키에 데이터가 몰린 스큐(skew)
  4. 캐시를 너무 많이 했다
셔플은 키 값으로 행을 나누기 때문에, NULL·"비회원" 같은 한 값에 행이 몰리면 그 파티션 하나만 거대해집니다. 다른 Task는 금방 끝나고 그 하나를 기다리는 모양이 전형적인 스큐입니다. 몰린 키를 따로 처리하거나, AQE skew join, 브로드캐스트, salt로 대응합니다.

explain() 출력에서 셔플이 일어나는 지점을 알려 주는 연산자는?

  1. FileScan
  2. Exchange hashpartitioning(...)
  3. Project
  4. BroadcastExchange
Exchange hashpartitioning(키, n)(정렬이면 rangepartitioning)이 셔플이고 Stage 경계입니다. FileScan은 파일 읽기, Project는 SELECT 컬럼 고르기입니다. BroadcastExchange는 작은 표를 복사해 보내는 것이라 이름은 비슷해도 큰 표를 섞는 셔플과는 다릅니다.

df.write.partitionBy("order_date").parquet("out")로 썼더니 날짜 폴더 365개마다 작은 파일이 200개씩 생겼습니다. 가장 알맞은 대처는?

  1. parquet 대신 CSV로 쓴다
  2. spark.sql.shuffle.partitions를 2000으로 올린다
  3. partitionBy를 order_date, hour 두 단계로 더 잘게 나눈다
  4. 쓰기 직전에 .repartition("order_date")로 같은 날짜를 한 조각에 모은다
파일 수 ≈ 메모리 파티션 수 × 폴더 수입니다. 쓰기 전에 repartition("order_date")를 하면 같은 날짜 행이 한 메모리 파티션에 모여 폴더마다 파일이 하나가 됩니다. 셔플 파티션을 늘리거나 폴더를 더 잘게 나누면 파일이 오히려 늘어나고, CSV는 형식만 나빠질 뿐 파일 수 문제와 관계없습니다.

"Airflow → Spark → dbt" 구성에서 각 도구의 역할을 바르게 짝지은 것은?

  1. Airflow: 언제·순서·재시도 / Spark: 원본 파일을 정제된 parquet로 / dbt: parquet를 source로 받아 마트·테스트
  2. Airflow: 원본 파일 정제 / Spark: 스케줄 / dbt: 대시보드
  3. Airflow: SQL 모델 관리 / Spark: 테스트 / dbt: 클러스터 자원 배정
  4. 세 도구 모두 같은 일을 하므로 하나만 쓰면 된다
Airflow는 계산을 직접 하지 않고 지휘만 합니다(5·6일차). Spark는 웨어하우스 밖의 큰 원본을 손질해 parquet로 쓰고, dbt는 그 결과를 source로 받아 SQL 모델·테스트·문서를 붙입니다. 오늘 실습 8·9단계가 이 연결의 축소판입니다.
