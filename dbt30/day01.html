오늘은 dbt를 "SQL 실행 도구"가 아니라 SQL 컴파일러 + DAG 실행기 + 메타데이터 생산자로 이해하고, 30일 동안 쓸 Ad Performance Validator 프로젝트의 뼈대를 직접 설계합니다.

2. 핵심 개념

dbt가 실제로 하는 일

dbt는 데이터를 옮기지도, 계산하지도 않습니다. 계산은 전부 BigQuery가 합니다. dbt가 하는 일은 세 가지입니다.

역할하는 일결과물
컴파일러Jinja가 섞인 .sql을 웨어하우스가 읽을 수 있는 순수 SQL로 바꾼다. ref()·source()는 실제 테이블 이름으로 풀린다target/compiled/
DAG 실행기ref() 관계로 의존 그래프를 만들고, 순서·병렬(threads)을 정해 DDL/DML로 감싸서 보낸다target/run/, BigQuery 테이블·뷰
메타데이터 생산자모든 노드·설정·의존·실행 결과를 JSON으로 남긴다. CI의 변경 감지, 문서, 리니지, Semantic Layer가 이걸 읽는다manifest.json, run_results.json 등
🧸 비유

dbt는 건축 설계 사무소입니다. 벽돌을 직접 쌓지 않습니다(그건 시공사 = BigQuery). 사무소는 ① 도면(SQL 파일)을 시공사가 읽을 수 있는 시공도로 바꾸고(compile), ② "기초 → 골조 → 내장" 공정표를 짜서 시공사에 순서대로 지시하고(DAG 실행), ③ 어떤 자재로 무엇을 지었는지 준공 기록을 남깁니다(artifacts). 리모델링할 때 "이 벽을 헐면 어디가 무너지나"를 알 수 있는 건 준공 기록 덕분입니다.

project · profile · target · adapter

  [저장소 안 · 팀이 공유]  dbt project
  ┌────────────────────────────────────┐
  │ dbt_project.yml                     │
  │   name: ad_performance_validator    │
  │   profile: ad_performance_validator │──┐ 이름으로 연결
  │   models: (계층별 config)              │  │
  │ models/ seeds/ tests/ macros/ ...   │  │
  └────────────────────────────────────┘  │
                                          ▼
  [저장소 밖 · 사람·환경마다 다름]  ~/.dbt/profiles.yml
  ┌────────────────────────────────────┐
  │ ad_performance_validator:           │
  │   target: dev        ← 기본 환경       │
  │   outputs:                          │
  │     dev:  dataset dbt30_dev         │
  │     prod: dataset dbt30_prod        │
  └──────────────────┬─────────────────┘
                     │ type: bigquery
                     ▼
  adapter (dbt-bigquery) : SQL 방언 · DDL · 인증 차이를 흡수
  • project: 무엇을 만들지. 모델·테스트·설정. git으로 관리합니다.
  • profile: 어디에 어떤 권한으로 연결할지. 인증 정보가 있으니 저장소 밖($HOME\.dbt\profiles.yml, 폴더가 없으면 mkdir $HOME\.dbt)에 둡니다.
  • target: 한 profile 안의 환경(dev·ci·prod). 같은 코드를 --target prod로 다른 곳에 짓습니다.
  • adapter: 웨어하우스별 번역기. create or replace table, merge, 파티션 문법 같은 차이를 흡수합니다.

실행 생명주기와 artifacts

  dbt build / run
     │
     ├─ ① parse    : 모든 .sql/.yml 읽기 → 노드 그래프       ─▶ manifest.json, partial_parse.msgpack
     │               (DB 접속 없음. 문법·ref 오류는 여기서)
     ├─ ② compile  : Jinja 렌더링, ref/source → 실제 이름    ─▶ target/compiled/**.sql
     │               (introspective 쿼리 run_query 는 여기서 DB 접속)
     └─ ③ execute  : materialization 이 DDL/DML 로 감싸 실행 ─▶ target/run/**.sql, run_results.json
                     (threads 만큼 병렬, 실패하면 하위 노드 skip)

  다른 명령이 남기는 것:  docs generate → catalog.json   source freshness → sources.json
                        parse(semantic model 이 있을 때) → semantic_manifest.json, MetricFlow 가 이걸 읽음
프로시저 감각으로 옮기면

프로시저는 "실행 계획 + 실행"이 한 덩어리입니다. 실행하기 전에는 무엇이 무엇에 의존하는지 DB도 사람도 정확히 모릅니다. dbt는 실행 전에 의존 그래프를 파일로 확정합니다(manifest). 그래서 "이 컬럼을 바꾸면 영향 받는 모델"을 돌려 보지 않고도 계산할 수 있고, CI에서 state:modified+로 바뀐 것과 그 하위만 빌드할 수 있습니다(Day 24).

💡 한 줄 요약 dbt의 진짜 산출물은 테이블이 아니라 manifest입니다. 테이블은 BigQuery가 만들고, dbt는 "무엇이 무엇으로부터, 어떤 규칙으로 만들어지는지"를 기계가 읽을 수 있게 남깁니다.

3. 아키텍처 설명 — 이 프로젝트의 dbt 경계

오늘 정할 것은 dbt가 어디부터 어디까지 책임지는가와 그 안을 어떻게 나누는가입니다.

  dbt 밖 (수집)                dbt 안 (변환·검증·정의)                          dbt 밖 (소비)
  ┌────────────┐   source() ┌──────────────────────────────────────────┐   ┌─────────────┐
  │ generator  │──▶ raw ───▶│ staging        intermediate      marts    │──▶│ Cube        │
  │ bq load    │   데이터셋   │ 매체·원천별     통합·매핑·귀속    fact/dim  │   │ Metabase    │
  └────────────┘   (dbt가    │ 1:1 정제        (재사용 로직)     (그레인   │   │ LLM Chatbot │
                    안 만듦)  │                                  고정)    │   └─────────────┘
                             │ seeds: 채널 분류·캠페인 매핑 (Reference)      │      exposures 로
                             │ snapshots: 캠페인·예산 변경 이력              │      소비자 선언
                             │ tests: 계층마다 다른 목적                     │
                             └──────────────────────────────────────────┘

  BigQuery 데이터셋 (dev 예시)
    raw_ads, raw_ga4        ← 적재 스크립트가 만든다. dbt는 읽기만
    dbt30_dev_staging       ← dbt가 만든다 (이름 규칙은 실습 5에서 직접 확인)
    dbt30_dev_intermediate
    dbt30_dev_marts

설계할 때 걸리는 결정은 대부분 아래 다섯 가지입니다. 오늘 실습에서 전부 직접 답을 정합니다.

  1. 프로젝트 단위: 한 저장소·한 dbt 프로젝트로 갈지, 도메인별로 쪼갤지(dbt Mesh)
  2. 계층: staging / intermediate / marts 를 어떤 기준으로 나누고, 폴더를 원천별로 볼지 도메인별로 볼지
  3. 계층별 기본 materialization: 폴더 단위로 기본값을 주고 예외만 파일에서 바꿀지
  4. 환경과 데이터셋 이름: dev·prod를 데이터셋으로 나눌지 프로젝트로 나눌지, 사람마다 dev 데이터셋을 둘지
  5. 비용 안전장치: BigQuery는 스캔량 과금 — 실수 한 번이 비용으로 이어짐

4. 실무 사례

사례 1 · "staging 하나 고쳤더니 대시보드 세 개가 깨졌다"

매체 리포트의 cost 단위를 원 → 마이크로로 바꾼 커밋이 들어갔는데, 어떤 mart와 대시보드가 이 컬럼을 쓰는지 아무도 몰랐습니다. 원인은 mart 몇 개가 staging을 거치지 않고 raw를 직접 읽고 있었고, 대시보드는 dbt에 선언돼 있지 않았던 것.

설계 교훈: raw를 읽는 곳은 staging뿐이어야 그래프가 끊기지 않습니다. 소비자(대시보드·챗봇)는 exposures로 선언해야 영향 범위에 잡힙니다. 오늘 폴더 구조와 규칙을 정할 때 이 경계를 먼저 박아 둡니다.

사례 2 · 데이터셋 이름이 analytics_analytics

prod target의 dataset을 analytics로 두고 mart 폴더에 +schema: analytics를 줬더니 analytics_analytics가 생겼습니다. dbt 기본 규칙은 <target dataset>_<custom schema>이기 때문입니다. 개발자 각자의 dev가 서로 덮어쓰지 않게 하려는 의도된 동작인데, 모르고 쓰면 이름이 엉망이 됩니다. 이 동작을 바꾸는 매크로(generate_schema_name)는 Day 18에서 직접 씁니다. 오늘은 기본 동작을 눈으로 확인합니다.

사례 3 · dev에서 GA4 원천 풀스캔

날짜 조건 없이 이벤트 테이블을 조인한 모델을 dev에서 몇 번 돌렸더니 한 달 무료 쿼리 한도를 며칠 만에 다 썼습니다. BigQuery profile의 maximum_bytes_billed를 걸어 두면 한도를 넘는 쿼리는 실행 전에 실패합니다. 안전장치는 "나중에"가 아니라 프로젝트 첫날 겁니다.

5. 코드 예제

아래 예시는 다른 도메인(커머스 주문)입니다. 그대로 복사하지 말고, 형태만 보고 실습에서 Ad Performance Validator에 맞게 직접 설계하세요.

shop_analytics:            # dbt_project.yml 의 profile: 값과 같아야 한다
  target: dev               # --target 을 안 주면 쓰는 환경
  outputs:
    dev:
      type: bigquery
      method: oauth         # gcloud auth application-default login 으로 받은 인증 사용
      project: my-gcp-project
      dataset: shop_dev     # 이 target 의 기본 데이터셋
      location: US          # 원천 데이터셋과 같은 위치여야 조인 가능
      threads: 4
      priority: interactive
      job_execution_timeout_seconds: 300
      job_retries: 1
      maximum_bytes_billed: 1000000000   # 1GB 넘게 스캔하는 쿼리는 실행 거부
    prod:
      type: bigquery
      method: oauth
      project: my-gcp-project
      dataset: shop_prod
      location: US
      threads: 8
      maximum_bytes_billed: 10000000000
name: shop_analytics
version: "1.0.0"
config-version: 2
profile: shop_analytics

model-paths: ["models"]
seed-paths: ["seeds"]
test-paths: ["tests"]
macro-paths: ["macros"]
snapshot-paths: ["snapshots"]
analysis-paths: ["analyses"]
clean-targets: ["target", "dbt_packages"]

models:
  shop_analytics:           # 프로젝트 이름 아래, 폴더 경로대로 들여쓴다
    +persist_docs:
      relation: true        # description 을 BigQuery 테이블 설명에도 남김
      columns: true
    staging:
      +materialized: view
      +schema: staging
    marts:
      +materialized: table
      +schema: marts
      +labels:
        layer: marts        # 테이블·뷰에 붙는 라벨(저장소 분류). 쿼리 비용을 계층별로 보려면 query-comment 의 job-label
버전 차이 (1.10+) +로 시작하는 키는 config입니다. dbt 1.10부터는 dbt가 모르는 임의의 키를 config에 바로 쓰면 경고가 나고, 사용자 정의 값은 +meta: 아래에 둬야 합니다. 예전 블로그 글의 +owner: ... 같은 표기는 +meta: {owner: ...}로 바꿔 읽으세요. 
import json                                  # JSON 읽는 도구 꺼내기 (SQL 의 함수 라이브러리 같은 것)
m = json.load(open("target/manifest.json", encoding="utf-8"))   # 파일 → 딕셔너리(키-값 표) 하나로 읽기
for uid, node in m["nodes"].items():         # FOR 각 행 IN nodes 표 ... (uid = 기본키, node = 행)
    if node["resource_type"] == "model":     # WHERE resource_type = 'model'
        print(uid, node["config"]["materialized"], node["depends_on"]["nodes"])   # SELECT 세 컬럼

1. 가상환경과 dbt 설치

단순 설치 단계라 명령을 그대로 보여 드립니다. 버전을 고정하는 이유도 생각해 보세요.

python -m venv .venv
.\.venv\Scripts\Activate.ps1

확인: dbt --version 출력에 core 1.12.x 와 bigquery 플러그인 1.12.x 가 보이면 됩니다. 버전을 requirements.txt로 저장해 두세요(pip freeze 전체보다 직접 쓴 두 줄이 낫습니다 — 이유는 리뷰 때 묻습니다).

2. BigQuery 인증과 profiles.yml 작성

gcloud auth application-default login으로 인증한 뒤, $HOME\.dbt\profiles.yml에 dev와 prod 두 target을 직접 작성하세요. 조건:

  • profile 이름은 프로젝트 이름과 같게 (ad_performance_validator)
  • dev는 개인용 데이터셋, prod는 별도 데이터셋
  • 두 target 모두 스캔 한도를 걸되, 한도 값을 왜 그렇게 정했는지 설명할 수 있게
  • location은 원천 데이터를 둘 위치와 맞추기
힌트 1

예제의 키를 그대로 쓰되 값은 전부 내 환경 기준으로 정합니다. project는 gcloud config get-value project로 확인합니다.

힌트 2

dev 한도는 "가장 큰 원천 테이블의 하루치를 몇 번 스캔해도 괜찮은가"로 잡아 보세요. 한도가 너무 작으면 정상 빌드가 막히고, 너무 크면 안전장치가 아닙니다. prod 한도를 dev보다 크게 둘지도 직접 판단합니다.

8. 퀴즈

dbt parse만 실행했을 때 일어나지 않는 일은?

  1. 모든 모델·YAML을 읽어 노드 그래프를 만든다
  2. BigQuery에 접속해 모델 SQL을 dry run 한다
  3. target/manifest.json을 쓴다
  4. 존재하지 않는 모델을 ref()하면 에러를 낸다

parse는 DB에 접속하지 않습니다. 파일을 읽고 그래프와 manifest를 만드는 단계라, 없는 ref 같은 구조적 오류는 여기서 잡히지만 SQL 문법·권한·테이블 존재 여부는 compile(일부)·execute 단계에서야 드러납니다.

prod target의 dataset이 apv, marts 폴더에 +schema: marts를 줬습니다. 기본 generate_schema_name일 때 mart 모델이 만들어지는 데이터셋은?

  1. marts
  2. apv
  3. marts_apv
  4. apv_marts

기본 규칙은 <target dataset>_<custom schema>입니다. custom schema만 쓰고 싶다면(①) generate_schema_name 매크로를 재정의해야 하고, 그때 dev 실행이 prod 데이터셋을 덮어쓰지 않도록 target별로 분기해야 합니다(Day 18).

저장소에 커밋하면 안 되는 것은?

  1. BigQuery 인증 정보가 들어 있는 profiles.yml
  2. 계층별 materialization이 적힌 dbt_project.yml
  3. 설계 결정을 적은 ARCHITECTURE.md
  4. dbt 버전을 고정한 requirements.txt

profile은 사람·환경마다 다른 연결 정보이고 인증 키가 들어갈 수 있어 저장소 밖에 둡니다. CI처럼 공유가 필요한 경우엔 값 대신 env_var()로 비밀을 주입하는 profile을 따로 둡니다(Day 24~25). 나머지 셋은 팀이 같은 결과를 재현하는 데 필요하므로 커밋 대상입니다.

CI에서 "바뀐 모델과 그 하위만 빌드"하려면 무엇이 반드시 필요한가요?

  1. prod의 catalog.json
  2. prod의 run_results.json
  3. 비교 기준이 되는 prod의 manifest.json
  4. BigQuery INFORMATION_SCHEMA 조회 권한

state:modified+는 현재 코드로 만든 manifest를 기준 manifest와 비교해 바뀐 노드를 찾습니다. 그래서 prod 배포 때 만든 manifest를 보관해 두는 게 CI 설계의 출발점입니다. catalog는 문서용 컬럼 정보, run_results는 실행 결과라 변경 감지 기준이 아닙니다.

intermediate 계층 기본값을 ephemeral로 정했을 때 생기는 단점으로 가장 맞는 것은?

  1. BigQuery 저장 비용이 늘어난다
  2. 중간 결과가 테이블·뷰로 남지 않아, 하위 모델이 틀렸을 때 중간 단계를 직접 조회해 확인하기 어렵다
  3. ref()로 참조할 수 없게 된다
  4. 테스트를 붙이면 자동으로 view로 바뀐다

ephemeral은 하위 모델 SQL에 CTE로 끼워 넣어지므로 저장 비용은 없고(①은 반대), ref도 정상 동작합니다(③ 틀림). 대신 BigQuery에 객체가 없어 디버깅·직접 조회가 어렵고, ephemeral 모델에 붙인 테스트도 제약이 있습니다. 그래서 "재사용이 많고 디버깅이 잦은" intermediate는 view나 table로 두는 팀이 많습니다 — 오늘 결정할 때 이 대가를 적어 두세요.
