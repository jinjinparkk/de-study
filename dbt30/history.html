dbt 30일 · 쉬어 가는 페이지

이야기로 보는 데이터 역사 — SQL에서 dbt까지

dbt의 문법은 대부분 누군가 예전에 겪은 문제의 답입니다. "왜 이렇게 생겼지?"가 궁금할 때 읽는 페이지입니다. 외울 것은 없고, 각 장 끝의 "그래서 dbt에서는"만 기억하면 됩니다.

읽기 약 20분 · 퀴즈 5문제 · 함께 보면 좋은 페이지: 모델링 관점 (킴볼 · 인먼 이론 상세)

이 페이지의 성격 공부하다 나온 이야기를 모아 제 말로 정리한 것입니다. 연도와 인물은 널리 알려진 사실 위주로 적었지만, 인용하거나 발표에 쓸 때는 원문을 한 번 확인하세요. 특히 최근 일(2025년 이후 회사 합병 등)은 이후 상황이 바뀌었을 수 있습니다.

1970 · 코드 — "무엇을 원하는지만 말하라"

에드거 F. 코드(Edgar F. Codd)는 IBM 연구원이던 1970년, 논문 「대규모 공유 데이터뱅크를 위한 관계형 데이터 모델」을 냈습니다.

  • 그 전: 데이터를 꺼내려면 "이 레코드에서 포인터를 따라 저 레코드로 가라"는 경로를 프로그래머가 직접 짰습니다. 저장 구조가 바뀌면 프로그램도 다 고쳐야 했습니다.
  • 코드의 생각: 데이터를 표(관계, relation)로 두고 집합론으로 다룬다. 사용자는 무엇을 원하는지만 말하고, 어떻게 찾을지는 시스템이 정한다.
  • 이 공로로 1981년 튜링상을 받았습니다. 정규화(1NF · 2NF · 3NF)도 코드에게서 나왔습니다.
💡 그래서 dbt에서는 dbt 모델에는 SELECT만 씁니다. CREATE TABLE, 실행 순서, 증분 처리 방식은 dbt가 정합니다. "무엇만 말하면 어떻게는 시스템이"라는 코드의 생각이 한 층 더 올라간 것입니다.

1974 · SEQUEL → SQL

코드의 이론은 수학 기호라 일반인이 쓰기 어려웠습니다. 같은 IBM의 도널드 체임벌린(Donald Chamberlin)과 레이먼드 보이스(Raymond Boyce)가 이를 영어 문장처럼 쓰는 언어로 만들었습니다.

  • 이름은 SEQUEL(Structured English Query Language). 영국 항공기 회사가 이미 상표로 쓰고 있어서 SQL로 줄였습니다. 지금도 "에스큐엘"과 "시퀄" 두 발음이 다 쓰이는 이유입니다.
  • 보이스는 SEQUEL을 발표한 1974년, 20대의 나이로 세상을 떠났습니다. 정규화의 BCNF(보이스-코드 정규형)에 이름이 남아 있습니다.
  • IBM은 연구용 시스템(System R)을 만들었지만, 첫 상용 제품은 1979년 오라클(당시 Relational Software)이 먼저 냈습니다. IBM이 공개한 논문을 보고 만들었습니다.
  • 1986년 ANSI 표준이 됐고, 50년 가까이 지난 지금도 BigQuery · DuckDB · Snowflake 모두 SQL을 씁니다.
💡 그래서 dbt에서는 dbt는 SQL을 대신하는 새 언어를 만들지 않았습니다. SQL은 그대로 두고 주변을 채웠습니다. 그래서 DuckDB에서 짠 모델을 BigQuery로 옮길 때도, 다른 건 DB마다 다른 몇 군데(UNNEST, 날짜 함수 등)뿐이고 매크로로 감출 수 있습니다.

1990년대 · 인먼 vs 킴볼 — 웨어하우스를 어떻게 쌓을까

회사마다 데이터베이스가 늘자 "분석용 데이터를 한곳에 모으자"는 데이터 웨어하우스가 등장했고, 쌓는 방식을 두고 두 사람이 맞붙었습니다.

빌 인먼 (Bill Inmon)랄프 킴볼 (Ralph Kimball)
별명데이터 웨어하우스의 아버지차원 모델링의 아버지
대표 책『Building the Data Warehouse』 (1992)『The Data Warehouse Toolkit』 (1996)
방향위에서 아래로: 회사 전체 웨어하우스를 먼저, 부서 마트는 거기서 뽑음아래에서 위로: 업무 하나씩 바로 쓰는 마트를 만들고 이어 붙임
모양정규화(3NF), 중복 없이 잘게 쪼갬스타 스키마, 가운데 사실(fct) · 둘레에 차원(dim)
장점하나의 진실, 변화에 튼튼함결과가 빨리 나옴, 분석가가 이해하기 쉬움
단점오래 걸리고 비쌈, 쓰려면 조인이 많음마트끼리 기준이 어긋나면 숫자가 따로 놂
  • 인먼: "부서마다 마트를 따로 만들면 매출이 부서마다 다르다. 회사 기준부터 세워라."
  • 킴볼: "그거 만들다 2년 간다. 업무별로 바로 쓰게 만들되 공통 차원(conformed dimension)을 같이 쓰면 안 어긋난다." → 업무 × 차원 표인 버스 매트릭스
  • 킴볼이 가장 강조한 것: 그레인(한 행이 무엇인가)을 먼저 정하라. 설계 4단계 = 업무 과정 → 그레인 → 차원 → 사실
  • 2000년대에는 댄 린스테트의 Data Vault(Hub · Link · Satellite)가 "원천이 바뀌어도 이력은 덮어쓰지 않는다"는 세 번째 길을 냈습니다.
🧸 비유

인먼은 도시 계획부터 세우고 건물을 짓는 사람, 킴볼은 필요한 건물부터 짓되 도로 규격(공통 차원)만 맞추는 사람입니다. 계획 없이 지으면 도로가 안 이어지고, 계획만 하면 아무도 입주를 못 합니다.

💡 그래서 dbt에서는 지금은 둘 중 하나를 고르지 않고 계층별로 섞습니다. staging(원천 정리) → intermediate(통합된 하나의 기준, 인먼 느낌) → marts(스타 스키마, 킴볼). BI와 Semantic Layer 앞단은 거의 다 킴볼식이고, Cube의 measures · dimensions가 그대로 fct · dim입니다. 이론 상세는 모델링 관점에.

2006 ~ 2010년대 · 빅데이터에서 다시 SQL로

  • Hadoop(2006): 데이터가 한 대에 안 들어가자 여러 대에 나눠 처리하는 방식이 퍼졌습니다. 처음엔 Java로 MapReduce 코드를 직접 짰고, 곧 그 위에 다시 SQL(Hive)을 얹었습니다. 결국 사람들은 SQL로 돌아왔습니다.
  • 클라우드 웨어하우스: BigQuery(구글, 2010년 공개), Redshift(아마존, 2012년 발표), Snowflake(2012년 창업) — 저장 공간이 싸지고 계산을 필요한 만큼 빌려 쓰게 됐습니다.
  • 이 변화가 ETL → ELT를 만들었습니다.
    • ETL: 웨어하우스가 비싸서, 넣기 전에 변환(T)해서 필요한 것만 넣었습니다.
    • ELT: 일단 원천을 그대로 다 넣고(EL), 웨어하우스 안에서 SQL로 변환(T)합니다.
  • EL을 자동화한 회사가 Fivetran(2012), 지표 정의를 코드로 관리한 BI가 Looker(2012, LookML)입니다.
💡 그래서 dbt에서는 dbt는 ELT의 T만 맡습니다. 원천을 넣는 일(EL)은 하지 않습니다. 그래서 source()로 "이미 들어와 있는 원천"을 가리키는 것부터 시작합니다.

2016 · dbt — SQL에 개발자의 습관을

ELT로 웨어하우스 안에 SQL 변환이 쌓이자 새 문제가 생겼습니다. 수백 개의 SQL 파일을 어떤 순서로 돌리나, 누가 고쳤나, 숫자가 맞는지 어떻게 아나. 소프트웨어 개발자들은 이미 Git · 테스트 · 의존성 관리로 풀어 둔 문제였습니다.

트리스턴 핸디(Tristan Handy)가 이끈 컨설팅 회사 Fishtown Analytics가 2016년 dbt(data build tool)를 만들었고, 회사는 2020년 이름을 dbt Labs로 바꿨습니다. dbt는 SQL을 새로 만든 게 아니라 이미 있던 것들을 조합했습니다.

원래 있던 것dbt에서 쓰는 방식
SQL SELECT모델 하나 = SELECT 하나 (CREATE TABLE은 dbt가 씀)
Jinja (파이썬 템플릿){{ ref() }}, 매크로, target.type 분기
소프트웨어의 의존성 그래프 (make 등)ref()로 실행 순서 · 리니지 자동 생성
개발자의 테스트 · Git · CIdbt test, PR, GitHub Actions

ref는 무슨 뜻인가

ref = reference(참조), "다른 모델을 가리킨다"입니다. 실행할 때 두 가지 일을 합니다.

  1. 진짜 테이블 이름으로 바꿔 줌 — 개발에선 dev 스키마, 운영에선 prod 스키마. 같은 코드로 target만 바꾸면 됩니다.
  2. "이 모델은 저 모델 다음"이라고 기록 — 모든 ref를 모으면 의존성 그래프(DAG)가 되고, dbt가 순서를 스스로 정합니다. dbt docs의 리니지 그림이 이것입니다.
select * from dev.main.stg_google_ads__ad_group_daily        -- ❌ 순서 · 환경 · 리니지가 깨짐
select * from {{ ref('stg_google_ads__ad_group_daily') }}    -- ✅

source()는 dbt가 만들지 않은 원천, ref()는 dbt가 만든 모델. 그래서 staging만 source를 읽고, 나머지는 전부 ref로 읽습니다.

💡 그래서 dbt에서는 dbt의 핵심 아이디어는 "분석가도 소프트웨어 엔지니어처럼 일하자"입니다. 이 흐름에서 애널리틱스 엔지니어(AE)라는 직무 이름도 퍼졌습니다.

2020년대 · Semantic Layer와 합병

  • Semantic Layer: 테이블은 하나로 맞췄는데, BI 도구마다 ROAS를 다르게 계산하는 문제가 남았습니다. 지표 정의를 한곳에 두자는 흐름 — Looker의 LookML이 앞서 했고, dbt Labs는 2023년 Transform을 인수해 MetricFlow(dbt Semantic Layer)를 만들었습니다. Cube도 같은 자리의 오픈소스입니다.
  • dbt Fusion(2025): 새 실행 엔진. dbt Core(Apache 2.0)와 라이선스가 달라(ELv2) 앞으로 방향을 지켜볼 부분입니다.
  • Fivetran · dbt Labs 합병 발표(2025년 10월): EL을 하던 회사와 T를 하던 회사가 합칩니다. ELT 두 칸을 한 회사가 가져가는 그림입니다. 무료 오픈소스 dbt Core를 로컬에서 쓰는 데에는 바로 영향이 없습니다.
💡 그래서 내 프로젝트에서는 수집(EL) 자리는 생성기 · 적재 코드가, 변환(T)은 직접 짜는 dbt가 맡습니다. 원천을 실제 매체 API 응답 모양으로 맞춰 둔 이유가 여기 있습니다 — 나중에 EL을 Fivetran 같은 도구로 바꿔도 dbt 쪽은 그대로 둘 수 있습니다.

퀴즈

코드(Codd)의 관계형 모델이 그 전 방식과 가장 크게 달랐던 점은?

  1. 데이터를 파일 대신 테이프에 저장했다
  2. 사용자는 무엇을 원하는지만 말하고, 찾는 방법은 시스템이 정한다
  3. 모든 데이터를 하나의 큰 표에 넣었다
  4. 프로그래머가 레코드 사이 포인터를 직접 관리하게 했다

그 전에는 데이터를 찾는 경로를 프로그래머가 짰습니다(④가 옛 방식). 코드는 "무엇"과 "어떻게"를 분리했고, dbt의 "SELECT만 쓰면 나머지는 dbt가"도 같은 생각입니다.

SQL이 처음 SEQUEL에서 이름을 바꾼 이유는?

  1. 오라클이 먼저 SEQUEL이라는 제품을 냈다
  2. ANSI 표준에서 네 글자 이상을 금지했다
  3. 다른 회사가 이미 SEQUEL을 상표로 쓰고 있었다
  4. 구조화(Structured)라는 단어를 빼기로 했다

영국 항공기 회사의 상표 때문에 모음을 빼고 SQL로 줄였습니다. 그래서 지금도 "시퀄"이라고 읽는 사람이 많습니다.

킴볼이 "부서별 마트를 따로 만들면 숫자가 어긋난다"는 인먼의 비판에 내놓은 답은?

  1. 공통 차원(conformed dimension)을 모든 마트가 같이 쓴다
  2. 모든 표를 3NF로 정규화한다
  3. 마트를 하나만 만든다
  4. Data Vault의 Hub를 쓴다

날짜 · 캠페인 같은 차원을 마트마다 따로 만들지 않고 하나를 같이 쓰면, 마트끼리 같은 기준으로 비교할 수 있습니다. 이 프로젝트의 매체 vs GA4 비교가 바로 이 원리입니다.

ETL에서 ELT로 바뀐 가장 큰 이유는?

  1. SQL이 표준이 되어서
  2. Hadoop이 SQL을 지원하지 않아서
  3. dbt가 E와 L을 대신해 줘서
  4. 클라우드 웨어하우스로 저장 · 계산이 싸져서 원천을 그대로 넣을 수 있게 되어서

웨어하우스가 비쌀 때는 넣기 전에 줄여야 했습니다. 싸지자 일단 다 넣고 안에서 SQL로 변환하게 됐고, 그 T를 맡은 것이 dbt입니다. dbt는 E · L을 하지 않습니다(③).

모델 안에서 테이블 이름을 직접 쓰지 않고 ref()를 쓸 때 얻는 것이 아닌 것은?

  1. dbt가 실행 순서를 스스로 정한다
  2. 쿼리 실행 속도가 빨라진다
  3. dev / prod target에 따라 테이블 위치가 바뀐다
