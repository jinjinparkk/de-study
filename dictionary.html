프로시저 ↔ dbt 사전

"프로시저에서는 이렇게 했는데, dbt에서는 뭐라고 하지?" 가 떠오를 때 찾아보는 페이지입니다. 왼쪽이 BigQuery 프로시저, 오른쪽이 dbt입니다.

처음부터 읽기보다, 필요한 항목을 목차에서 골라 보세요. 자세한 설명은 각 일차 페이지에 있습니다.

한눈에 보는 대응표

프로시저에서 하던 것dbt에서는배우는 곳
CREATE TEMP TABLE 로 단계 나누기CTE, ephemeral 모델, intermediate 모델2일차
CREATE OR REPLACE TABLE ... ASmaterialized='table' (뷰는 'view')1·2일차
날짜 단위 DELETE 후 INSERTincremental delete+insert / insert_overwrite / microbatch4일차
MERGEincremental merge + unique_key4일차
이력 테이블(SCD2) 직접 관리snapshot4일차
파라미터 p_date, DECLAREvar(), env_var(), Jinja {% set %}4일차
IF·LOOP·EXECUTE IMMEDIATEJinja {% if %}·{% for %}, run_query()4일차
공통 SQL 조각·UDF매크로(macros/), 패키지(dbt_utils)4일차
ASSERT, 검증 쿼리, RAISE테스트(data_tests), severity, contract3일차
로그 테이블에 INSERTtarget/run_results.json 등 아티팩트, on-run-end 훅3·6일차
실행 전후 SQLpre_hook / post_hook이 페이지
스케줄 쿼리, cronAirflow (dbt Core에는 스케줄러 없음)5·6일차
GRANT SELECT ...grants 설정이 페이지
엑셀 정의서, COMMENTYAML description, dbt docs, persist_docs3일차
개발용·운영용 데이터셋 바꿔 치기target(dev/prod), generate_schema_name4·6일차
프로시저 호출 순서표ref() 가 만든 DAG + 선택자(+model)2일차
💡 한 줄 요약 프로시저는 "어떻게"(DDL·DML·순서)를 사람이 적고, dbt는 "무엇"(SELECT)만 적으면 나머지를 설정과 Jinja로 dbt가 채웁니다. 대부분의 프로시저 문법은 "설정 한 줄" 또는 "Jinja 한 줄"로 바뀝니다.

임시 테이블 → CTE·ephemeral·intermediate

프로시저 안의 CREATE TEMP TABLE은 "중간 결과에 이름 붙이기"입니다. dbt에는 그 이름을 붙이는 방법이 세 가지 있고, 얼마나 여러 곳에서 다시 쓰는지로 고릅니다.

프로시저
CREATE TEMP TABLE tmp_pay AS
SELECT order_id, SUM(amount) AS amount
FROM raw.payments
GROUP BY order_id;

SELECT o.order_id, p.amount
FROM raw.orders o
JOIN tmp_pay p USING (order_id);
dbt ① 한 모델 안에서만 쓰면: CTE
with pay as (
    select order_id, sum(amount) as amount
    from {{ ref('stg_payments') }}
    group by order_id
)
select o.order_id, p.amount
from {{ ref('stg_orders') }} o
join pay p using (order_id)
dbt ② 여러 모델이 쓰지만 테이블은 필요 없으면: ephemeral
{{ config(materialized='ephemeral') }}

select order_id, sum(amount) as total_amount
from {{ ref('stg_payments') }}
group by order_id

DB에 아무것도 만들지 않고, 이 모델을 ref() 하는 쪽 SQL에 CTE로 끼워 넣어집니다.

dbt ③ 여러 모델이 쓰고 확인도 하고 싶으면: intermediate 모델(view/table)
models:
  shop:
    intermediate:
      +materialized: view

DB에 뷰가 생기므로 DBeaver 같은 다른 도구에서도 바로 조회할 수 있습니다.

고르는 기준

한 곳에서만 쓰면 CTE → 두 곳 이상이면 별도 모델. 이 강의의 shop 프로젝트는 intermediate 폴더를 ephemeral로 둡니다. ephemeral도 dbt show로 결과를 볼 수 있고 테스트도 붙일 수 있지만(dbt가 CTE로 감싸서 실행), DB에 남는 객체가 없어서 dbt run을 해도 아무것도 안 생기고 다른 도구에서는 조회할 수 없습니다. 자주 들여다봐야 하면 view가 편합니다.

CREATE OR REPLACE → materialized table·view

프로시저
CREATE OR REPLACE TABLE dm.dim_customers AS
SELECT c.customer_id, c.customer_name,
       COUNT(o.order_id) AS order_count
FROM stg.customers c
LEFT JOIN stg.orders o USING (customer_id)
GROUP BY 1, 2;
dbt
{{ config(materialized='table') }}

select c.customer_id, c.customer_name,
       count(o.order_id) as order_count
from {{ ref('stg_customers') }} c
left join {{ ref('stg_orders') }} o using (customer_id)
group by 1, 2

테이블 이름(dim_customers)은 파일 이름에서, 데이터셋(스키마)은 profiles.yml의 schema(BigQuery는 dataset)에서 옵니다. 폴더 단위로 한꺼번에 정하려면 dbt_project.yml에 +materialized: table을 씁니다.

materializationdbt가 보내는 SQL(대략)언제
viewCREATE OR REPLACE VIEW ... AS SELECTstaging처럼 가볍고 늘 최신이어야 할 때
tableCREATE OR REPLACE TABLE ... AS SELECT (어댑터에 따라 임시 이름으로 만든 뒤 바꿔 치기)marts처럼 많이 조회될 때
incremental처음엔 CREATE TABLE AS, 그다음부터 MERGE/DELETE+INSERT/INSERT크고, 매번 다 다시 만들기 아까울 때
ephemeral없음 (CTE로 끼워 넣음)재사용용 중간 단계
materialized_viewCREATE MATERIALIZED VIEWDB가 지원할 때(BigQuery 지원, DuckDB 미지원)

날짜별 DELETE + INSERT → incremental

가장 흔한 프로시저 패턴입니다. "그날 것만 지우고 다시 넣는다". dbt에서는 incremental 모델 + 전략(incremental_strategy)으로 표현합니다.

프로시저
DELETE FROM dm.daily_sales
WHERE order_date = p_date;

INSERT INTO dm.daily_sales
SELECT order_date, COUNT(*) AS orders,
       SUM(amount) AS revenue
FROM stg.orders
WHERE order_date = p_date
GROUP BY order_date;
dbt (delete+insert)
{{ config(
    materialized='incremental',
    incremental_strategy='delete+insert',
    unique_key='order_date'
) }}

select order_date, count(*) as orders,
       sum(total_amount) as revenue
from {{ ref('fct_orders') }}
{% if is_incremental() %}
where order_date >= (select max(order_date) - interval 3 day
                     from {{ this }})
{% endif %}
group by order_date

unique_key에 적은 값(여기선 날짜)과 같은 행을 기존 테이블에서 지우고, 새 결과를 넣습니다. BigQuery에서는 파티션 통째로 갈아 끼우는 insert_overwrite가 더 싸고 빠른 경우가 많습니다.

{{ config(
    materialized='incremental',
    incremental_strategy='insert_overwrite',
    partition_by={'field': 'order_date', 'data_type': 'date'}
) }}
p_date는 어디로?

프로시저는 "오늘 처리할 날짜"를 밖에서 받습니다. dbt incremental은 보통 대상 테이블의 최댓값({{ this }})을 보고 스스로 범위를 정합니다. 밖에서 날짜를 꼭 받아야 하면 var()를 쓰거나(아래 "파라미터" 항목), 1.9+의 microbatch 전략을 씁니다 — dbt run --event-time-start 2026-10-01 --event-time-end 2026-10-05 처럼 날짜 구간을 넘기면 하루씩 나눠 돌려 줍니다.

MERGE → incremental merge

프로시저
MERGE dm.fct_orders t
USING (
  SELECT * FROM stg.orders
  WHERE updated_at >= TIMESTAMP_SUB(
    CURRENT_TIMESTAMP(), INTERVAL 3 DAY)
) s
ON t.order_id = s.order_id
WHEN MATCHED THEN UPDATE SET
  status = s.status, updated_at = s.updated_at
WHEN NOT MATCHED THEN INSERT ROW;
dbt (merge)
{{ config(
    materialized='incremental',
    incremental_strategy='merge',
    unique_key='order_id'
) }}

select order_id, customer_id, order_date,
       status, updated_at
from {{ ref('stg_orders') }}
{% if is_incremental() %}
where updated_at > (select max(updated_at)
                    from {{ this }})
{% endif %}
MERGE의 부분dbt에서 어디에
MERGE dm.fct_orders t파일 이름 + materialized='incremental'
USING (...) s모델의 SELECT (is_incremental() 블록 포함)
ON t.order_id = s.order_idunique_key='order_id' (여러 컬럼이면 리스트)
WHEN MATCHED THEN UPDATE SET ...기본은 전체 컬럼. 일부만 바꾸려면 merge_update_columns=['status','updated_at']
WHEN NOT MATCHED THEN INSERT자동
처음 실행 때 테이블 만들기자동 (is_incremental()이 거짓 → 전체 SELECT로 CREATE TABLE AS)
테이블 통째로 다시 만들기dbt run --full-refresh -s fct_orders
조심

필터 컬럼을 무엇으로 잡느냐가 핵심입니다. order_date로 잡으면 "예전 주문의 상태가 오늘 바뀐 것"을 놓칩니다. 바뀐 시각(updated_at)으로 잡아야 합니다. 4일차 실습에서 직접 겪어 봅니다.

이력 테이블(SCD2) → snapshot

프로시저 (직접 관리하는 이력 테이블)
-- 1) 바뀐 고객의 현재 행 닫기
UPDATE dm.customers_hist h
SET valid_to = CURRENT_TIMESTAMP()
FROM stg.customers s
WHERE h.customer_id = s.customer_id
  AND h.valid_to IS NULL
  AND s.updated_at > h.updated_at;

-- 2) 새 버전(또는 신규 고객) 넣기
INSERT INTO dm.customers_hist
SELECT s.*, s.updated_at AS valid_from,
       NULL AS valid_to
FROM stg.customers s
LEFT JOIN dm.customers_hist h
  ON h.customer_id = s.customer_id
 AND h.valid_to IS NULL
WHERE h.customer_id IS NULL;
dbt (YAML snapshot, 1.9+)
snapshots:
  - name: customers_snapshot
    relation: source('shop_raw', 'raw_customers')
    config:
      unique_key: customer_id
      strategy: timestamp
      updated_at: updated_at
dbt snapshot

닫기(UPDATE)와 넣기(INSERT)를 dbt가 대신 만들어 보냅니다. DuckDB에서는 왼쪽과 똑같이 UPDATE 후 INSERT 두 문장으로, BigQuery·Snowflake에서는 MERGE 한 문장으로 보냅니다. 결과 테이블에 dbt_valid_from, dbt_valid_to, dbt_scd_id, dbt_updated_at 컬럼이 붙습니다.

이력 테이블에서 하던 것snapshot 설정
"수정일이 바뀌면 새 버전"strategy: timestamp + updated_at: 컬럼
수정일이 없어서 컬럼 값을 비교strategy: check + check_cols: [membership, city] (또는 all)
현재 행 표시 valid_to IS NULL기본 동작. 먼 미래 날짜로 두려면 dbt_valid_to_current: "'9999-12-31'"
원천에서 지워진 행 처리hard_deletes: ignore(기본) / invalidate(닫기) / new_record(삭제 표시 행 추가)
이력 테이블을 다른 데이터셋에schema: snapshots
버전 차이

1.8 이하에서는 snapshots/*.sql 안에 {% snapshot %} ... {% endsnapshot %} 블록으로 썼습니다. 지금도 동작하지만, 1.9부터는 위처럼 YAML로 쓰는 것이 권장 방식입니다. 인터넷 예제가 SQL 블록이면 오래된 글입니다.

DECLARE와 다른 점

Jinja 변수는 SQL이 만들어지기 전에 글자로 바뀝니다. {% set min_amount = 10000 %} 은 DB 변수가 아니라 "문장 안에 10000을 붙여 넣어라"입니다. 그래서 target/compiled를 열면 >= 10000 으로 보입니다.

IF·LOOP·동적 SQL → Jinja

프로시저 (동적 SQL로 피벗)
DECLARE cols STRING;
SET cols = (
  SELECT STRING_AGG(
    FORMAT("SUM(IF(method='%s', amount, 0)) AS %s_amount",
           method, method))
  FROM (SELECT DISTINCT method FROM raw.payments)
);
EXECUTE IMMEDIATE FORMAT("""
  SELECT order_id, %s
  FROM raw.payments GROUP BY order_id
""", cols);
dbt (Jinja for)
{% set methods = ['card', 'bank_transfer',
                  'kakaopay', 'point'] %}

select
    order_id,
    {%- for m in methods %}
    sum(case when payment_method = '{{ m }}'
             then amount else 0 end) as {{ m }}_amount
    {%- if not loop.last %},{% endif %}
    {%- endfor %}
from {{ ref('stg_payments') }}
group by order_id
프로시저Jinja
IF cond THEN ... ELSE ... END IF;{% if cond %} ... {% else %} ... {% endif %}
FOR x IN (SELECT ...) DO ... END FOR;{% for x in 리스트 %} ... {% endfor %}
목록을 DB에서 읽어 와서 반복run_query() 결과로 리스트 만들기 (또는 dbt_utils.get_column_values)
EXECUTE IMMEDIATE필요 없음 — Jinja가 만든 글자가 곧 SQL
환경별 분기 (IF @@dataset = 'dev'){% if target.name == 'dev' %}
{% set q %}select distinct payment_method from {{ ref('stg_payments') }} order by 1{% endset %}
{% set res = run_query(q) %}
{% if execute %}
  {% set methods = res.columns[0].values() %}
{% else %}
  {% set methods = [] %}
{% endif %}
execute 를 꼭 감싸는 이유

dbt는 실행 전에 모든 파일을 한 번 훑어서(파싱) DAG를 만드는데, 이때는 DB에 쿼리하지 않습니다. 그래서 run_query 결과는 실제 실행 단계(execute가 참)에서만 쓸 수 있습니다.

공통 SQL·UDF → 매크로·패키지

프로시저 / UDF
CREATE TEMP FUNCTION clean_text(s STRING) AS (
  NULLIF(LOWER(TRIM(s)), '')
);

SELECT clean_text(status) AS status
FROM raw.orders;
dbt 매크로
{% macro clean_text(col) -%}
    nullif(lower(trim({{ col }})), '')
{%- endmacro %}
select {{ clean_text('status') }} as status
from {{ source('shop_raw', 'raw_orders') }}

UDF는 DB 안에서 실행 시점에 불리고, 매크로는 SQL을 만들 때 글자로 펼쳐집니다. 그래서 매크로는 어떤 DB에서든 쓸 수 있고, 컴파일된 SQL에는 매크로 이름 대신 nullif(lower(trim(status)), '')가 그대로 들어 있습니다.

남이 만든 매크로 묶음은 패키지로 받습니다.

프로시저
SELECT TO_HEX(MD5(CONCAT(
  CAST(order_id AS STRING), '-',
  CAST(payment_id AS STRING)))) AS pay_key
FROM raw.payments;
dbt + dbt_utils
packages:
  - package: dbt-labs/dbt_utils
    version: [">=1.3.0", "<2.0.0"]
select {{ dbt_utils.generate_surrogate_key(
           ['order_id', 'payment_id']) }} as pay_key
from {{ ref('stg_payments') }}

스케줄 → Airflow

프로시저
-- BigQuery 예약 쿼리(매일 06:00)
CALL dm.sp_build_stg();
CALL dm.sp_build_fct_orders();
CALL dm.sp_build_daily_sales();
-- 순서는 사람이 적고, 하나 실패하면 수동 재실행
dbt + Airflow
from airflow.sdk import dag            # DAG = 예약 작업 하나
from airflow.providers.standard.operators.bash import BashOperator  # 셸 명령 실행 부품

@dag(schedule="0 6 * * *")             # 매일 06:00 (예약 쿼리의 일정)
def shop_dbt():
    BashOperator(                      # CALL 목록 대신 명령 하나
        task_id="dbt_build",
        bash_command="cd /opt/shop && dbt build",  # 순서는 dbt가 ref()로 정함
        retries=2,                     # 실패하면 두 번 더 시도
    )

shop_dbt()                             # DAG 등록

dbt Core에는 스케줄러가 없습니다. "언제"는 Airflow, "어떤 순서로"는 dbt가 맡습니다. 5·6일차에서 직접 만듭니다.

GRANT → grants 설정

프로시저
CREATE OR REPLACE TABLE dm.fct_orders AS ...;
GRANT `roles/bigquery.dataViewer`
  ON TABLE dm.fct_orders
  TO "group:analysts@company.com";
dbt
models:
  shop:
    marts:
      +grants:
        roles/bigquery.dataViewer:
          - "group:analysts@company.com"

테이블을 다시 만들 때마다 dbt가 권한을 다시 걸어 줍니다. 프로시저에서 CREATE OR REPLACE 후 권한이 날아가는 사고를 막아 줍니다. DuckDB는 권한 개념이 없어서 이 설정을 쓰지 않습니다(Postgres·Snowflake는 select: ['analyst'] 처럼 씁니다).

주석·정의서 → description·docs

프로시저
-- 주문 팩트: 주문 1건 = 1행
-- total_amount: 결제 합계(원), 분할결제 포함
ALTER TABLE dm.fct_orders
  ALTER COLUMN total_amount
  SET OPTIONS (description = '결제 합계(원)');
-- + 엑셀 테이블 정의서 따로 관리
dbt
models:
  - name: fct_orders
    description: 주문 팩트. 주문 1건 = 1행
    config:
      persist_docs: {relation: true, columns: true}
    columns:
      - name: total_amount
        description: 결제 합계(원), 분할결제 포함
dbt docs generate
dbt docs serve --port 8085

persist_docs를 켜면 설명이 DB의 테이블·컬럼 설명(BigQuery 콘솔에 보이는 그것)에도 들어갑니다. 정의서와 코드가 한 파일에 있어서 어긋나지 않습니다.

개발·운영 데이터셋 → target·generate_schema_name

프로시저
-- 개발할 땐 dev_dm 으로 복사해서 이름 바꿔 실행
CREATE OR REPLACE TABLE dev_dm.fct_orders AS ...;
-- 운영 반영할 땐 dm 으로 다시 고쳐서 실행
CREATE OR REPLACE TABLE dm.fct_orders AS ...;
dbt
shop:
  target: dev
  outputs:
    dev:
      type: bigquery
      dataset: dbt_eunjin     # 내 개발 공간
      # ...
    prod:
      type: bigquery
      dataset: dm             # 운영
      # ...
dbt run              # dev 로
dbt run --target prod  # 같은 코드, prod 로

코드는 그대로, 어디에 만들지만 target으로 바꿉니다. 모델에 schema='marts' 같은 설정을 주면 기본적으로 <target 스키마>_marts가 되는데, 이 규칙을 바꾸는 매크로가 generate_schema_name입니다(4일차).

💡 한 줄 요약 프로시저 한 개 = dbt에서는 모델 여러 개 + 설정 + 테스트 + 문서로 나뉘고, 순서와 스케줄은 ref()와 Airflow가 나눠 맡습니다.
