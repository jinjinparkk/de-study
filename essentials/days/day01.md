# Day 1. 데이터 모델링과 아키텍트의 역할

## 오늘의 한 줄

데이터 모델링은 업무 규칙을 데이터 구조로 못 박는 일입니다. 아키텍트는 그 구조가 운영계(OLTP)에서 DW·BI(OLAP)까지 같은 뜻으로 이어지도록 경계와 기준을 정하는 사람입니다.

## 왜 중요한가

한빛제약 영업기획팀 정 과장이 "3월 매출" 대시보드를 요청했고, 누군가 Power BI를 ERP 운영 DB의 주문 테이블에 바로 연결했다고 해 보겠습니다. 월말 마감 시간에 대시보드 조회와 ERP 주문 처리가 같은 DB 자원을 나눠 쓰고, 숫자는 회계팀 자료와 맞지 않습니다. 주문 금액을 셀지, 출고된 것만 셀지, 매출전표 기준으로 볼지 아무도 정하지 않았기 때문입니다. 기술이 모자라서 생긴 문제가 아닙니다. "무엇을 매출이라 부르는가"를 정하는 개념·논리 단계와 "운영계와 정보계를 나눌 것인가"라는 아키텍처 판단을 건너뛰어서 생긴 문제입니다.

## 핵심 개념

### 1. 개념·논리·물리 3단계는 서로 다른 질문에 답합니다

쉽게 말하면 개념 모델은 "무엇이 존재하는가", 논리 모델은 "어떤 규칙으로 연결되는가", 물리 모델은 "이 DB에서 어떻게 저장하고 빨리 꺼내는가"에 답합니다. 단계를 나누는 이유는 결정하는 사람과 바뀌는 속도가 다르기 때문입니다.

| 단계 | 답하는 질문 | 주로 결정하는 것 | 같이 앉는 사람 | 바뀌는 속도 |
|---|---|---|---|---|
| 개념 | 업무에 무엇이 있나, 범위는 어디까지인가 | 핵심 엔터티, 주요 관계, 범위 | 현업 리더, PM, 아키텍트 | 가장 느림 (사업 구조가 바뀔 때) |
| 논리 | 어떤 규칙으로 식별·연결되나 | 속성, 식별자, 카디널리티, 정규화 수준 | 현업 담당자, 모델러 | 중간 (업무 규칙이 바뀔 때) |
| 물리 | 특정 DBMS에서 어떻게 구현하나 | 데이터 타입, NULL, 제약조건, 인덱스, 파티션 | 모델러, DBA, 개발자 | 가장 빠름 (성능·용량 이슈마다) |

정확한 용어로는 개념 모델(Conceptual Data Model), 논리 모델(Logical Data Model), 물리 모델(Physical Data Model)입니다. 핵심은 논리 모델이 **DBMS와 무관해야 한다**는 점입니다. 이 과정에서도 그렇습니다. 계열사 ERP는 Oracle이지만 실습 환경은 PostgreSQL입니다. 같은 논리 모델이 Oracle에서는 `VARCHAR2`·`NUMBER`, PostgreSQL에서는 `VARCHAR`·`NUMERIC`으로 구현됩니다. 논리와 물리가 섞여 있었다면 이렇게 옮길 수 없습니다.

### 2. 단계를 건너뛰면 무엇이 깨지는가

개념 단계를 건너뛰면 범위 논쟁이 구축 중반에 터집니다. 정 과장은 "매출"이 회계 매출(전표)이라고 생각했는데 개발자는 주문 금액을 합산했다면, 그 차이는 테스트 단계에서야 드러납니다.

논리 단계를 건너뛰고 바로 DDL을 쓰면 업무 규칙이 테이블과 컬럼 사이에 묻힙니다. "거래처 담당 영업사원은 기간별로 바뀐다" 같은 규칙이 ERD에 남지 않고 개발자 머릿속에만 남습니다. 몇 년 뒤 DW를 만드는 사람은 그 규칙을 데이터에서 역으로 추적해야 합니다.

물리 단계를 대충 하면 기능은 돌아가지만 데이터가 쌓이면서 느려지고, NULL·중복이 막히지 않아 품질 문제가 생깁니다.

### 3. 데이터 아키텍트·모델러·엔지니어의 경계

회사마다 직함이 섞여 쓰이지만, 판단 기준은 "누가 무엇을 결정하고 책임지는가"입니다.

| 역할 | 결정하는 것 | 결정하지 않는 것 | 대표 산출물 |
|---|---|---|---|
| 데이터 아키텍트 | 데이터 흐름 전체 구조(운영계·ODS·DW·마트 레이어), 표준, 원천 범위, 모델링 원칙 | 개별 컬럼 길이, 개별 쿼리 튜닝 | 데이터 아키텍처 정의서, 표준 정의서, 설계 원칙 |
| 데이터 모델러 | 엔터티·속성·관계, 식별자, 정규화·반정규화 수준 | 어떤 ETL 도구를 쓸지 | ERD, 엔터티·테이블 정의서 |
| 데이터 엔지니어 | 적재 방식(전체·증분), 파이프라인, 스케줄, 오류 처리 | 업무 용어의 정의 | 매핑정의서, 배치 설계서, 파이프라인 코드 |
| DBA | 저장 구조, 인덱스·파티션 운영, 권한, 백업 | 엔터티를 어떻게 나눌지 | 물리 설계 검토, 운영 가이드 |

Analytics Engineer로 일할 때는 dbt 모델 하나가 "논리 + 물리 + 변환"을 한꺼번에 담고 있어서 이 경계를 의식할 일이 적습니다. 그룹 IT 회사에서는 다릅니다. ERP 운영팀이 운영계 DB 변경 승인권을 갖고 있고, 마스터 데이터는 그룹 경영지원실이 관리합니다. 그래서 "내가 정할 수 있는 것"과 "근거를 들어 요청해야 하는 것"을 나누는 일이 아키텍트 업무의 절반입니다.

### 4. 운영계(OLTP)와 정보계(OLAP)는 설계 목표가 반대입니다

운영계는 **한 건을 정확하고 빠르게 처리**하는 것이 목표입니다. 정보계는 **많은 건을 일관된 기준으로 합산**하는 것이 목표입니다. 같은 "주문" 데이터를 다루는데도 설계 원칙이 정반대로 갈리는 이유가 여기에 있습니다.

| 구분 | 운영계 OLTP (한빛제약 ERP) | 정보계 OLAP (그룹 DW·마트) |
|---|---|---|
| 대표 작업 | 주문 1건 등록, 상태 변경 | 지역별·거래처유형별 월 매출 합계 |
| 한 번에 다루는 행 | 몇 건 | 기간 전체의 대량 행 |
| 설계 원칙 | 정규화, 중복 최소화 | 차원 모델(스타 스키마), 조회 편의를 위한 의도적 중복 |
| 이력 | 필요한 것만 (현재 상태 중심) | 변경 이력을 남겨 과거 시점 재현 |
| 실패 비용 | 주문 누락, 이중 출고 | 잘못된 의사결정, 숫자 불신 |
| 주 사용자 | 영업·물류 실무자, 애플리케이션 | 경영진, 기획, 분석가, BI 도구 |

정확한 용어로 OLTP(Online Transaction Processing), OLAP(Online Analytical Processing)라고 부릅니다. Week 1은 운영계 모델링을, Week 3은 정보계 차원 모델링을 다룹니다. 운영계를 먼저 배우는 이유는 DW의 원천이 결국 운영계이기 때문입니다. 원천 구조를 못 읽으면 DW에서 grain(한 행의 의미)을 잘못 잡습니다.

### 5. 나의 자리: 그룹 DW PL

이 과정에서 "나"는 한빛정보기술 소속 데이터 아키텍트이자 그룹 DW 프로젝트 PL입니다. 1차 범위는 한빛제약 영업실적과 한빛로지스 출고·재고입니다. 요청자는 한빛제약 영업기획팀 정 과장(영업실적 대시보드)과 한빛로지스 물류운영팀 한 대리(출고·재고)입니다. 운영계 DB 변경은 한빛정보기술 ERP 운영팀이 승인하고, 그룹 공통 지표와 마스터의 오너는 그룹 경영지원실입니다.

PL에게 모델링 지식이 필요한 이유는 ERD를 직접 다 그리기 위해서가 아닙니다. 모델러와 엔지니어가 만든 설계가 **요구사항과 표준에 맞는지 판정**하고, 현업에게 "왜 이 구조여야 하는지"를 설명해야 하기 때문입니다.

## 예시

모든 SQL은 공통 스키마 `schema/00_base.sql`을 실행한 PostgreSQL에서 돌아갑니다. 운영계 테이블은 `erp` 스키마에 있습니다.

정 과장의 요구 문장 하나를 3단계로 내려 보겠습니다.

> "거래처유형(병원·약국·도매상)별, 지역별로 월 주문 금액을 보고 싶습니다. 취소된 주문은 빼 주세요."

**개념 단계**에서는 명사와 관계만 봅니다. 거래처, 주문, 주문상세, 품목, 사원이 보이고 "거래처가 주문을 한다", "주문은 여러 품목을 담는다"는 관계가 보입니다.

```text
[CUST] --- 한다 ---> [ORD] --- 담는다 ---> [ITEM]     거래처·주문·품목
                       |
                    [EMP] 가 받는다                   사원
```

**논리 단계**에서는 속성과 식별자, 규칙을 정합니다. 거래처는 거래처번호로 식별하고 거래처유형은 01 병원, 02 약국, 03 도매상 중 하나입니다. 주문은 주문상태를 가지며 90은 취소입니다. "월 주문 금액"은 주문상세 금액의 합이고, 기준 일자는 주문일자입니다. 이 정의가 정해져야 표준용어사전에 "주문금액"을 올릴 수 있습니다.

| 엔터티 | 식별자 | 주요 속성 |
|---|---|---|
| 거래처 | 거래처번호 (CUST_NO) | 거래처명 (CUST_NM), 거래처유형코드 (CUST_TP_CD), 지역코드 (RGN_CD) |
| 주문 | 주문번호 (ORD_NO) | 주문일자 (ORD_DT), 거래처번호 (CUST_NO), 사원번호 (EMP_NO), 주문상태코드 (ORD_STAT_CD) |
| 주문상세 | 주문번호 + 주문순번 (ORD_NO, ORD_SEQ) | 품목코드 (ITEM_CD), 주문수량 (ORD_QTY), 단가 (UPRC), 주문금액 (ORD_AMT) |

**물리 단계**에서는 DBMS에 맞는 타입, 제약조건, 감사 컬럼을 붙입니다. 계열사 ERP(Oracle)에서라면 거래처 테이블은 이렇게 정의됩니다.

```oracle
CREATE TABLE TB_CUST (
  CUST_NO     VARCHAR2(10)  NOT NULL,
  CUST_NM     VARCHAR2(100) NOT NULL,
  CUST_TP_CD  VARCHAR2(2)   NOT NULL,
  BIZ_REG_NO  VARCHAR2(12),
  RGN_CD      VARCHAR2(3)   NOT NULL,
  USE_YN      CHAR(1)       DEFAULT 'Y' NOT NULL,
  REG_DTM     DATE          DEFAULT SYSDATE NOT NULL,
  CONSTRAINT PK_TB_CUST PRIMARY KEY (CUST_NO),
  CONSTRAINT CK_TB_CUST_01 CHECK (CUST_TP_CD IN ('01', '02', '03')),
  CONSTRAINT CK_TB_CUST_02 CHECK (USE_YN IN ('Y', 'N'))
);
```

같은 논리 모델을 공통 스키마에서는 PostgreSQL 타입(`VARCHAR`, `TIMESTAMP`)으로 구현했습니다. 실제 구조는 아래처럼 카탈로그에서 확인할 수 있습니다.

```sql
-- 공통 스키마의 거래처 테이블 물리 구조 확인
SELECT column_name, data_type, character_maximum_length, is_nullable, column_default
  FROM information_schema.columns
 WHERE table_schema = 'erp' AND table_name = 'tb_cust'
 ORDER BY ordinal_position;
```

여기서 `CHAR(1)`로 여부를 표현할지, CHECK 제약을 둘지, 감사 컬럼을 무엇으로 할지는 모두 물리 단계의 결정입니다. 논리 모델에는 "사용여부: 예/아니오"만 있으면 됩니다. 공통 스키마에는 CHECK 제약이 빠져 있는데, 이처럼 "논리 규칙은 있는데 DB가 강제하지 않는" 곳을 찾아 테이블정의서에 적는 것도 물리 설계 검토의 일입니다.

운영계와 정보계의 SQL은 성격이 다릅니다. 운영계는 주문 한 건을 트랜잭션으로 저장합니다. 헤더와 상세가 함께 성공하거나 함께 실패해야 합니다(아래는 연습이므로 마지막에 되돌립니다).

```sql
-- 운영계(OLTP): 늘봄약국 주문 1건 등록
BEGIN;
INSERT INTO erp.tb_ord (ord_no, ord_dt, cust_no, emp_no, ord_stat_cd)
VALUES ('SO2026040003', DATE '2026-04-06', 'C000202', 'E1004', '10');
INSERT INTO erp.tb_ord_dtl (ord_no, ord_seq, item_cd, ord_qty, uprc, ord_amt)
VALUES ('SO2026040003', 1, 'P10002', 3, 12000, 36000);
ROLLBACK;  -- 실제 업무라면 COMMIT
```

정보계 질문은 많은 행을 읽어 합산합니다.

```sql
-- 정보계(OLAP) 성격의 질문: 2026년 3월 거래처유형별 주문금액(취소 제외)
SELECT c.cust_tp_cd,
       SUM(d.ord_amt) AS ord_amt
  FROM erp.tb_ord o
  JOIN erp.tb_ord_dtl d ON d.ord_no = o.ord_no
  JOIN erp.tb_cust c    ON c.cust_no = o.cust_no
 WHERE o.ord_dt >= DATE '2026-03-01'
   AND o.ord_dt <  DATE '2026-04-01'
   AND o.ord_stat_cd <> '90'
 GROUP BY c.cust_tp_cd
 ORDER BY c.cust_tp_cd;
```

결과는 01 병원 124,000원, 02 약국 82,000원, 03 도매상 2,160,000원입니다(전부 가상 데이터).

## Before / After

**Before: 대시보드가 운영 DB를 직접 조회하고, 팀마다 매출을 다르게 정의함**

영업기획팀, 물류운영팀, 경영지원실이 각자 SQL을 짜서 "3월 매출"을 구했습니다.

```sql
-- 같은 "3월 매출"을 세 가지 정의로 구하면
SELECT
  (SELECT SUM(d.ord_amt)
     FROM erp.tb_ord o JOIN erp.tb_ord_dtl d ON d.ord_no = o.ord_no
    WHERE o.ord_dt >= DATE '2026-03-01' AND o.ord_dt < DATE '2026-04-01'
      AND o.ord_stat_cd <> '90')                        AS ord_amt_excl_cancel,
  (SELECT SUM(sd.ship_qty * od.uprc)
     FROM erp.tb_ship s
     JOIN erp.tb_ship_dtl sd ON sd.ship_no = s.ship_no
     JOIN erp.tb_ord_dtl od  ON od.ord_no = sd.ord_no AND od.ord_seq = sd.ord_seq
    WHERE s.ship_dt >= DATE '2026-03-01' AND s.ship_dt < DATE '2026-04-01') AS ship_amt,
  (SELECT SUM(sd.cr_amt)
     FROM erp.tb_slip sl JOIN erp.tb_slip_dtl sd ON sd.slip_no = sl.slip_no
    WHERE sl.slip_dt >= DATE '2026-03-01' AND sl.slip_dt < DATE '2026-04-01'
      AND sd.acct_cd = '41100')                         AS slip_sales_amt;
```

| 누가 | 정의 | 3월 결과 (가상) |
|---|---|---|
| 영업기획팀 | 주문금액, 취소 제외 | 2,366,000원 |
| 물류운영팀 | 출고수량 × 주문단가 | 2,302,000원 |
| 경영지원실 | 매출전표의 제품매출(41100) 대변 | 82,000원 |

세 숫자 모두 SQL로는 틀리지 않았습니다. 틀린 것은 **"매출"이라는 한 단어에 정의가 셋이라는 점**입니다. 공통 샘플에는 매출전표가 한 건만 들어 있어서 차이가 극단적으로 보이지만, 실제로도 주문·출고·전표 시점이 다르면 월말 기준 숫자는 반드시 어긋납니다. 게다가 세 조회가 모두 ERP 운영 DB에서 돌아 주문 처리와 자원을 다툽니다.

**After: 레이어를 나누고, 용어를 먼저 정의함**

```text
[ERP DB] tb_ord, tb_ship, tb_slip          운영계
    |  매일 배치 적재(증분)
    v
[STG_ / ODS_] 원천 그대로 복제              스테이징
    |  정의된 규칙으로 변환
    v
[DW] 주문·출고·전표 팩트                    정보계
    |
    v
[DM_] 월별 거래처유형 매출 마트             BI 조회
```

- 표준용어사전에 "주문금액", "출고금액", "매출액(회계)"을 서로 다른 용어로 등록하고 산식을 적습니다. 한 단어로 세 가지를 뜻하게 두지 않습니다.
- Power BI는 마트만 조회합니다. 운영 DB에는 적재 배치만 접근합니다.
- 운영계 테이블 구조는 그대로 둡니다. 운영계를 대시보드에 맞추려고 고치지 않습니다.

## 시니어는 이렇게 판단한다

시니어는 "정답 구조"를 외우지 않고 상황 변수를 보고 고릅니다.

| 상황 | 이럴 땐 A | 저럴 땐 B |
|---|---|---|
| 현업이 "운영 DB에 바로 붙여 주세요" | 일회성 탐색이고 조회량이 작으면 읽기 전용 복제본이나 뷰로 임시 허용 | 매일 보는 지표, 여러 팀이 쓰는 지표라면 DW·마트로 분리 |
| 논리 모델을 생략하고 DDL부터 쓰자는 의견 | 한 애플리케이션만 쓰는 작은 테이블 몇 개라면 테이블정의서에 규칙을 적고 진행 | 계열사가 공유하는 마스터(거래처·품목)나 DW 원천이 되는 테이블이면 논리 모델 필수 |
| 모델러가 따로 없는 프로젝트 | 아키텍트가 논리 모델까지 직접 책임지고, 물리는 DBA 검토 | 모델러가 있으면 아키텍트는 원칙과 리뷰 기준만 내려보내고 개별 설계에 덜 개입 |
| 운영계에 집계 컬럼을 넣자는 요청 | 운영 화면 자체가 그 값을 실시간으로 써야 하면 운영계 반정규화 검토(Day 5) | 분석·보고용이면 운영계는 그대로 두고 DW에서 계산 |
| "매출" 정의가 팀마다 다름 | 용도가 정말 다르면 이름이 다른 용어 여러 개로 공존 | 같은 용도인데 조건만 다르면 오너(경영지원실)가 하나로 확정 |

판단할 때 던지는 질문은 네 가지입니다. 이 데이터를 누가 바꾸는가(소유권), 몇 명이 어떤 빈도로 읽는가(부하), 틀리면 누가 피해를 보는가(실패 비용), 1년 뒤 누가 이 구조를 이어받는가(유지보수).

## 흔한 실수 3가지

1. **물리 모델을 모델링의 전부로 여기는 실수.** DDL부터 쓰면 "거래처 담당은 기간별로 바뀐다" 같은 규칙이 어디에도 남지 않습니다. 테이블은 있는데 업무 규칙 문서가 없는 시스템이 됩니다.
2. **운영계와 정보계의 원칙을 섞는 실수.** 운영계에 보고용 집계 컬럼을 잔뜩 넣어 갱신 로직이 꼬이거나, 반대로 DW에 운영계 3NF를 그대로 복제해 BI가 테이블 열 개를 조인하게 만듭니다. 레이어마다 목표가 다르다는 점을 잊은 결과입니다.
3. **역할 경계를 문서로 남기지 않는 실수.** 아키텍트가 모든 컬럼을 직접 정하면 병목이 되고, 아무 원칙도 내려보내지 않으면 팀마다 다른 모델이 나옵니다. "아키텍트가 정하는 것"을 설계 원칙서로 써 두고 나머지는 리뷰로 통제해야 합니다.

## 셀프 체크 질문

**Q1. 논리 모델과 물리 모델을 굳이 나누는 이유를 한빛제약 예시로 설명해 보세요.**

:::answer 모범 답안 보기
논리 모델은 업무 규칙을, 물리 모델은 특정 DBMS에서 구현하는 방식을 담습니다. 바뀌는 이유와 속도가 다르기 때문에 나눕니다. "거래처유형은 병원·약국·도매상 중 하나"는 업무 규칙이라 논리 모델에 남습니다. 이것을 문자 2자리 + CHECK로 할지, 공통코드 테이블 FK로 할지는 물리 결정입니다. 실제로 이 과정에서도 ERP는 Oracle(`VARCHAR2`), 실습은 PostgreSQL(`VARCHAR`)로 물리 모델만 다르고 논리 모델은 같습니다. 둘이 섞여 있으면 DW를 다른 플랫폼으로 옮길 때 어디까지가 규칙이고 어디부터가 구현 편의인지 구분할 수 없습니다.
:::

**Q2. 정 과장이 "ERP 화면에 이미 데이터가 있는데 왜 DW를 따로 만드나요?"라고 묻습니다. 어떻게 답하겠습니까?**

:::answer 모범 답안 보기
세 가지로 답합니다. 첫째, 부하 분리입니다. 대시보드는 많은 행을 합산하는데 같은 DB에서 주문 처리가 돌고 있으니 서로 느려질 수 있습니다. 둘째, 정의 통일입니다. 지금은 팀마다 기준이 달라 같은 "3월 매출"이 주문 기준, 출고 기준, 전표 기준으로 세 가지 숫자가 나옵니다. DW에서 정의를 한 번 정하면 모두 같은 숫자를 봅니다. 셋째, 이력과 통합입니다. ERP는 현재 상태 중심이라 담당자가 바뀌면 과거 실적 귀속이 흔들리고, 한빛로지스 출고·재고는 다른 시스템에 있습니다. DW는 과거 시점을 재현하고 계열사 데이터를 한곳에서 연결합니다. "ERP를 못 믿어서"가 아니라 "목적이 다른 일을 같은 곳에서 하지 않기 위해서"라고 설명하는 것이 핵심입니다.
:::

**Q3. 데이터 아키텍트와 데이터 엔지니어의 차이를 "결정하는 것" 기준으로 말해 보세요.**

:::answer 모범 답안 보기
아키텍트는 데이터가 어떤 레이어를 거쳐 어떤 기준으로 흐를지, 어떤 표준과 원칙을 따를지를 결정합니다. 예를 들어 "1차 범위는 한빛제약 영업과 한빛로지스 출고, BI는 마트만 조회, 마스터는 경영지원실 기준 코드로 통합"이 아키텍트의 결정입니다. 엔지니어는 그 원칙 안에서 적재 방식(전체·증분), 스케줄, 오류 처리, 재처리 방법을 결정하고 구현합니다. 아키텍트의 실수는 프로젝트 전체 구조를 틀리게 만들고, 엔지니어의 실수는 특정 파이프라인을 틀리게 만듭니다. 그래서 아키텍트는 결정의 근거를 설계서와 ADR(Day 28)로 남겨야 합니다.
:::

## 오늘의 과제

**과제 1.** 정 과장이 "지역별로 3월 주문금액(취소 제외)과 3월 출고금액을 나란히 보고 싶다"고 합니다. 출고금액은 출고상세 수량 × 해당 주문상세의 단가, 기준일은 출고일자입니다. 공통 스키마에서 아래 모양의 결과를 내는 SQL을 작성하세요.

| rgn_cd | ord_amt | ship_amt |
|---|---|---|
| GGD | ? | ? |
| SEL | ? | ? |

힌트: 주문상세와 출고상세를 한 번에 조인한 뒤 합산하면 어떤 일이 생기는지 먼저 생각해 보세요. 한 주문상세가 여러 로트로 나뉘어 출고된 경우가 샘플에 있습니다.

:::answer 해설 보기
주문과 출고는 grain(한 행의 의미)이 다릅니다. 주문상세 1줄이 출고상세 여러 줄(로트 분할)로 나뉘므로, 둘을 먼저 조인하고 합산하면 주문금액이 출고 줄 수만큼 불어납니다. 그래서 각각 따로 집계한 뒤 지역으로 붙입니다. 이 "따로 집계 후 결합" 습관이 Week 3의 fan-out 방지와 같은 원리입니다.

```sql
WITH ord AS (
  SELECT c.rgn_cd, SUM(d.ord_amt) AS ord_amt
    FROM erp.tb_ord o
    JOIN erp.tb_ord_dtl d ON d.ord_no = o.ord_no
    JOIN erp.tb_cust c    ON c.cust_no = o.cust_no
   WHERE o.ord_dt >= DATE '2026-03-01' AND o.ord_dt < DATE '2026-04-01'
     AND o.ord_stat_cd <> '90'
   GROUP BY c.rgn_cd
), shp AS (
  SELECT c.rgn_cd, SUM(sd.ship_qty * od.uprc) AS ship_amt
    FROM erp.tb_ship s
    JOIN erp.tb_ship_dtl sd ON sd.ship_no = s.ship_no
    JOIN erp.tb_ord_dtl od  ON od.ord_no = sd.ord_no AND od.ord_seq = sd.ord_seq
    JOIN erp.tb_ord o       ON o.ord_no = s.ord_no
    JOIN erp.tb_cust c      ON c.cust_no = o.cust_no
   WHERE s.ship_dt >= DATE '2026-03-01' AND s.ship_dt < DATE '2026-04-01'
   GROUP BY c.rgn_cd
)
SELECT COALESCE(o.rgn_cd, s.rgn_cd) AS rgn_cd,
       COALESCE(o.ord_amt, 0)       AS ord_amt,
       COALESCE(s.ship_amt, 0)      AS ship_amt
  FROM ord o
  FULL OUTER JOIN shp s ON s.rgn_cd = o.rgn_cd
 ORDER BY 1;
```

결과는 GGD 2,160,000 / 2,160,000, SEL 206,000 / 142,000입니다. SEL의 차이 64,000원은 3월 20일 확정됐지만 아직 출고되지 않은 청솔내과의원 주문(SO2026030004)입니다. 이 차이를 현업에게 설명할 수 있어야 "주문금액"과 "출고금액"을 다른 용어로 등록하자는 제안에 힘이 실립니다.
:::

:::note Oracle 차이
`COALESCE`와 `FULL OUTER JOIN`은 Oracle에서도 그대로 동작합니다. Oracle에서는 흔히 `NVL`을 쓰지만 두 인자만 받습니다.
:::
