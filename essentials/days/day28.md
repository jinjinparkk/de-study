# Day 28. 아키텍처 의사결정과 설계서

## 오늘의 한 줄

아키텍처는 정답을 고르는 일이 아니라 **요구사항에 비춰 무엇을 얻고 무엇을 포기하는지 정하고, 그 이유를 남기는 일**입니다. 대안을 두세 개 놓고 기준을 먼저 합의한 뒤 고르고, 결정은 ADR 한 장으로 기록합니다. 1년 뒤 "왜 이렇게 했어요?"에 문서가 대답하게 만드는 것이 목표입니다.

## 왜 중요한가

그룹 DW 1차 오픈 반년 뒤 새로 온 팀장이 "왜 ETL 도구를 안 쓰고 SQL로 변환했냐, 다시 바꾸자"고 합니다. 당시 결정 이유(원본 보관을 통한 재처리, 리니지, 인력 역량)가 회의록 어딘가에만 있어서 같은 논쟁을 처음부터 다시 합니다. Power BI 모델을 OBT로 바꾸자는 요청도 매 분기 돌아옵니다. **결정의 근거와 포기한 것**을 남기지 않으면 아키텍처는 사람이 바뀔 때마다 흔들립니다.

## 핵심 개념

### 1. 기능 요구사항과 비기능 요구사항

기능 요구사항은 "무엇을 보여 주나"(영업사원별 월 실적 대비 목표), 비기능 요구사항은 "어떤 조건에서"(아침 7시까지, 3년치, 영업사원은 자기 실적만)입니다. 아키텍처를 가르는 것은 대개 **비기능** 쪽입니다. 같은 대시보드라도 "하루 한 번"이면 배치 Import, "10분 이내"면 CDC + DirectQuery로 구조가 완전히 달라집니다. 비기능 요구사항은 측정 가능하게 적습니다. "빨라야 함"이 아니라 "주요 리포트 첫 화면 응답 목표 N초(측정 방법 명시)"처럼 씁니다.

### 2. 품질 속성과 트레이드오프

비기능 요구사항은 품질 속성(신선도, 성능, 정확성·감사성, 확장성, 비용, 운영 용이성, 보안)으로 묶입니다. 이 속성들은 서로 당깁니다. 신선도를 올리면 비용과 운영 복잡도가 오르고, 감사성(원본 보관)을 올리면 저장 비용이 듭니다. 아키텍트의 일은 **현업이 어느 속성을 더 중요하게 여기는지 먼저 합의**하고, 그 순서로 대안을 평가하는 것입니다. 기준을 나중에 정하면 결론에 기준을 맞추게 됩니다.

### 3. ADR: 결정 한 건 = 문서 한 장

ADR(Architecture Decision Record)은 결정 하나를 짧게 기록하는 문서입니다. Michael Nygard가 제안한 형식이 널리 쓰이며, 핵심 항목은 제목, 상태(제안/승인/대체됨), 맥락, 결정, 결과(얻는 것과 포기하는 것)입니다. 실무에서는 검토한 대안과 평가 기준을 덧붙입니다. ADR은 고치지 않고 쌓습니다. 결정이 바뀌면 새 ADR을 쓰고 옛 ADR의 상태를 "대체됨(ADR-00N)"으로 바꿉니다. 그래야 "언제, 왜 바뀌었나"가 남습니다.

### 4. 경영진·현업에게 설명하는 법

기술 용어가 아니라 **상대가 책임지는 것의 언어**로 바꿉니다. 경영진에게는 비용·위험·일정·되돌릴 수 있는지, 현업에게는 "언제 무엇을 볼 수 있고 무엇은 못 보는지"입니다. 형식은 늘 같습니다. 선택지 2~3개, 각각의 얻는 것과 잃는 것 한 줄, 추천안과 이유, 결정해 주셔야 할 것. "ELT가 모던합니다"는 설명이 아닙니다. "원본을 남겨 두면 로직이 틀렸을 때 원천 DB를 다시 건드리지 않고 고칠 수 있습니다. 대신 저장 비용이 듭니다"가 설명입니다.

### 5. 설계서 체계

ADR은 결정의 기록이고, 설계서는 결정의 결과물입니다. DW 프로젝트의 아키텍처 정의서는 대개 요구사항 요약(특히 비기능), 전체 구성도(레이어·흐름, Day 15), 데이터 아키텍처(주제영역·버스 매트릭스, Day 18·21), 적재 아키텍처(Day 22~24), BI 아키텍처(Day 26), 운영·보안·거버넌스, 그리고 ADR 목록으로 구성합니다. 상세 설계(테이블정의서·매핑정의서)는 이 정의서를 따릅니다.

### 대안 평가: 가중치를 먼저 합의하고 점수를 매긴다

적재 방식 결정의 평가표를 테이블로 둡니다. 가중치는 위 비기능 요구사항의 우선순위에서 나오고, 점수(1~5)는 PoC와 검토 회의 결과입니다. 숫자는 학습용 가상 값입니다.

```sql
CREATE SCHEMA IF NOT EXISTS lab;

CREATE TABLE lab.adr_crit (                -- 평가 기준과 가중치 (합 100)
  adr_id   VARCHAR(10) NOT NULL,
  crit_cd  VARCHAR(20) NOT NULL,
  crit_nm  VARCHAR(50) NOT NULL,
  wgt      NUMERIC(5)  NOT NULL,
  PRIMARY KEY (adr_id, crit_cd)
);
CREATE TABLE lab.adr_score (               -- 대안별 점수 (1~5)
  adr_id   VARCHAR(10) NOT NULL,
  opt_cd   VARCHAR(20) NOT NULL,
  crit_cd  VARCHAR(20) NOT NULL,
  score    NUMERIC(2)  NOT NULL,
  PRIMARY KEY (adr_id, opt_cd, crit_cd)
);
INSERT INTO lab.adr_crit VALUES
 ('ADR-001', 'AUDIT',  '감사성·재처리 (NFR-03)', 30),
 ('ADR-001', 'LINEAGE','리니지·변경 관리',        20),
 ('ADR-001', 'SKILL',  '팀 역량 적합성',          20),
 ('ADR-001', 'LOAD',   '원천 DB 부하',            15),
 ('ADR-001', 'COST',   '도입·운영 비용',          15);
INSERT INTO lab.adr_score VALUES
 ('ADR-001', 'ETL_TOOL', 'AUDIT', 2), ('ADR-001', 'ETL_TOOL', 'LINEAGE', 2), ('ADR-001', 'ETL_TOOL', 'SKILL', 3),
 ('ADR-001', 'ETL_TOOL', 'LOAD', 4),  ('ADR-001', 'ETL_TOOL', 'COST', 2),
 ('ADR-001', 'ELT_SQL',  'AUDIT', 5), ('ADR-001', 'ELT_SQL',  'LINEAGE', 4), ('ADR-001', 'ELT_SQL',  'SKILL', 4),
 ('ADR-001', 'ELT_SQL',  'LOAD', 4),  ('ADR-001', 'ELT_SQL',  'COST', 4),
 ('ADR-001', 'DB_LINK',  'AUDIT', 1), ('ADR-001', 'DB_LINK',  'LINEAGE', 2), ('ADR-001', 'DB_LINK',  'SKILL', 5),
 ('ADR-001', 'DB_LINK',  'LOAD', 1),  ('ADR-001', 'DB_LINK',  'COST', 5);

SELECT s.opt_cd, ROUND(SUM(s.score * c.wgt) / 5.0) AS wgt_score_100,
       STRING_AGG(c.crit_cd || '=' || s.score, ', ' ORDER BY c.wgt DESC) AS detail
  FROM lab.adr_score s JOIN lab.adr_crit c ON c.adr_id = s.adr_id AND c.crit_cd = s.crit_cd
 WHERE s.adr_id = 'ADR-001'
 GROUP BY s.opt_cd
 ORDER BY wgt_score_100 DESC;
```

| opt_cd | wgt_score_100 | 의미 |
|---|---|---|
| ELT_SQL | 86 | 원본 보관 + DW 내 SQL 변환 |
| DB_LINK | 52 | 기존처럼 DB 링크로 직접 INSERT |
| ETL_TOOL | 50 | 별도 ETL 도구에서 변환 후 적재 |

점수표는 결정을 대신하지 않습니다. 회의에서 "가중치를 바꾸면 결론이 바뀌는가"를 함께 보여 줘서 결정이 얼마나 단단한지 판단하게 하는 도구입니다(오늘의 과제 1).

### ADR-001. 그룹 DW 1차 적재 방식: ELT (원본 보관 + DW 내 SQL 변환)

| 항목 | 내용 |
|---|---|
| 상태 | 승인 (2026-01, 그룹 DW 아키텍처 검토 회의) |
| 맥락 | 원천은 계열사 Oracle ERP·WMS. 기존 복제는 DB 링크 직접 INSERT로 재실행 시 중복, 삭제 미반영(Day 22). 품질 부서는 적재 데이터의 원천 재현을 요구(NFR-03). 팀은 SQL·dbt에 익숙하고 ETL 도구 운영 경험이 적음. ERP 운영팀은 원천 부하 증가에 민감 |
| 검토 대안 | (1) ETL 도구에서 변환 후 적재 (2) ELT: 원천을 STG에 원본 그대로 증분 적재 후 DW 안에서 SQL로 변환 (3) 현행 DB 링크 유지·보완 |
| 결정 | (2) ELT. 추출은 워터마크 증분 + 키 비교 삭제 감지, STG는 원본 보관(보관 기간은 품질 부서와 별도 합의), 변환은 버전 관리되는 SQL(dbt 모델 포함)로 DW 안에서 수행. 민감 정보 마스킹이 필요한 컬럼은 추출 단계에서 처리(ETL 성격 예외) |
| 얻는 것 | 원천을 다시 건드리지 않는 재처리·백필, SQL 기반 리니지, 팀 역량에 맞는 개발 속도, 원천 부하는 증분 추출만 |
| 포기하는 것 | DW 저장·연산 비용 증가(STG 원본), ETL 도구의 GUI 모니터링 부재 → 배치 통제 테이블과 알림을 직접 구축(Day 24) |
| 재검토 조건 | 실시간(분 단위) 요구가 생기면 로그 기반 CDC 도입을 새 ADR로 검토 |

### ADR-002. Power BI 공통 모델: 스타 스키마 (OBT는 추출용 뷰로만)

| 항목 | 내용 |
|---|---|
| 상태 | 승인 (2026-02) |
| 맥락 | 영업팀은 "한 장짜리 테이블"을 선호. 그러나 요구사항에 목표 대비(월 × 사원 grain), 주문일·출고일 두 기준, 거래처 정정(Type 1) 반영이 있음. 2차에 물류·재고 팩트가 같은 차원을 쓸 예정(버스 매트릭스) |
| 검토 대안 | (1) 리포트별 OBT (2) 공통 차원 + 팩트 스타 스키마, BI 전용 뷰로 연결 (3) 스타 + 자주 쓰는 질문용 OBT 뷰 병행 |
| 결정 | (3). 공통 시맨틱 모델은 스타(차원 → 팩트 1:* 단방향, 날짜 테이블 지정, 역할 날짜는 비활성 관계). 엑셀 내보내기·단일 분석용으로만 스타 위에 OBT 뷰 제공, OBT에는 측정값을 따로 만들지 않음 |
| 얻는 것 | 목표·재고 등 grain이 다른 팩트를 같은 차원으로 연결, 지표 정의 한 곳 관리, 차원 정정이 차원 행만 갱신 |
| 포기하는 것 | 필드 목록이 여러 테이블로 나뉨 → 표시 폴더·업무 이름·숨김으로 보완, 사용자 교육 필요 |
| 재검토 조건 | 특정 분석이 OBT에서만 성능 목표를 만족한다는 측정 결과가 나오면 해당 분석 한정 예외 ADR |

### OBT의 비용을 숫자로 보여 주기

"OBT면 정정이 비싸다"를 현업에게 설명할 때 쓰는 근거 쿼리입니다. 미래종합병원 거래처명 정정(Day 19의 Type 1) 한 건이 각 구조에서 몇 행을 고치게 하는지 셉니다.

```sql
SELECT 'STAR: DIM_CUST' AS model, COUNT(*) AS upd_row_cnt
  FROM dw.dim_cust WHERE cust_no = 'C000102'
UNION ALL
SELECT 'OBT: 주문 라인', COUNT(*)
  FROM dw.fct_ord_line f JOIN dw.dim_cust c ON c.cust_sk = f.cust_sk WHERE c.cust_no = 'C000102'
UNION ALL
SELECT 'OBT: 출고 라인', COUNT(*)
  FROM dw.fct_ship_line f JOIN dw.dim_cust c ON c.cust_sk = f.cust_sk WHERE c.cust_no = 'C000102';
```

샘플에서는 미래종합병원 주문이 없어 스타 1행, OBT 0행입니다. 이처럼 샘플이 작으면 근거가 약해 보이므로, 실제 회의에서는 운영 데이터 기준 "거래처 정정 월평균 건수 × 거래처당 팩트 행 수"로 보여 줍니다. 핵심 메시지는 스타는 차원 크기, OBT는 팩트 크기에 비례한다는 것입니다.

## Before / After

| 항목 | Before | After |
|---|---|---|
| 결정 방식 | 회의에서 목소리 큰 쪽 | 비기능 요구사항 → 기준·가중치 합의 → 대안 평가 |
| 기록 | 회의록에 한 줄 | ADR (맥락, 대안, 결정, 얻는 것·포기하는 것, 재검토 조건) |
| 요구사항 | "빨라야 함", "실시간" | 측정 가능한 NFR (시각, 차이 0원, 확인 방법, 출처) |
| 설명 | 기술 용어 나열 | 상대의 책임 언어(비용·위험·일정·볼 수 있는 것) + 추천안 |
| 결정 변경 | 문서를 덮어씀 | 새 ADR + 옛 ADR "대체됨" |

## 시니어는 이렇게 판단한다

| 판단 지점 | 이럴 땐 A | 저럴 땐 B |
|---|---|---|
| ADR을 쓸까 | 되돌리기 비싸거나 여러 팀에 영향(적재 방식, BI 모델, 플랫폼) | 쉽게 되돌릴 수 있는 국소 결정(컬럼 순서)은 설계서에만 |
| 결정 시점 | 정보가 충분하고 미루면 일정이 막히면 지금 | 핵심 정보(원천 CDC 가능 여부)가 곧 나오면 "결정 기한"을 정하고 보류 |
| PoC | 대안 간 점수가 비슷하거나 성능·비용이 불확실하면 대표 쿼리로 PoC | 차이가 명확하면 PoC 없이 결정, 근거를 ADR에 |
| 현업 선호와 충돌 | 선호의 진짜 목적(쉽게 찾기)을 다른 수단으로 충족 | 목적 자체가 요구사항이면 예외를 허용하되 범위를 ADR로 제한 |
| 경영진 보고 | 선택지 2~3개 + 추천 + 결정 요청 사항 | 선택지가 하나뿐이면 "결정"이 아니라 "보고"로 다룸 |

## 흔한 실수 3가지

1. **결론을 먼저 정하고 기준을 맞추는 실수.** 점수표가 정당화 도구가 됩니다. 기준과 가중치는 대안을 보기 전에 현업과 합의합니다.
2. **"포기하는 것"을 비워 두는 실수.** 대가가 없는 결정은 없습니다. 포기한 것을 적어야 나중에 그 문제가 터졌을 때 "알고 고른 것"임을 보여 주고 보완책을 준비할 수 있습니다.
3. **비기능 요구사항을 형용사로 쓰는 실수.** "빠르게", "안정적으로"는 검증할 수 없습니다. 시각·건수·차이·확인 방법으로 씁니다.

## 셀프 체크 질문

**Q1. 정 과장이 "대시보드를 실시간으로 해 주세요"라고 합니다. 어떻게 요구사항으로 만들겠습니까?**

:::answer 모범 답안 보기
"실시간"이 어떤 업무 결정에 필요한지 묻습니다. 아침 회의에서 어제 실적을 보는 것이면 D+1 07:00 반영이면 충분하고, 월말 마감일에 오늘 주문을 보며 영업사원을 독려하는 것이면 마감일만 1시간 주기면 됩니다. 그 답을 "업무일 D 실적이 D+1 07:00까지, 월말 3영업일은 1시간 주기"처럼 측정 가능한 NFR로 적고, 각 수준의 비용(CDC 도입, 운영 인력, DirectQuery 성능 부담)을 함께 보여 줘 선택하게 합니다. 실시간은 기술 요구가 아니라 업무 요구에서 역산합니다.
:::

**Q2. ADR에 꼭 들어가야 하는 항목과 그 이유는 무엇입니까?**

:::answer 모범 답안 보기
맥락, 검토한 대안, 결정, 결과(얻는 것과 포기하는 것), 상태입니다. 맥락이 있어야 나중에 상황이 바뀌었는지 판단할 수 있고, 대안이 있어야 "그건 검토했나요?"에 답할 수 있으며, 포기하는 것이 있어야 그 약점이 드러났을 때 예정된 대가인지 판단하고 보완할 수 있습니다. 상태와 대체 관계는 결정의 이력을 남깁니다. 재검토 조건을 덧붙이면 언제 이 결정을 다시 열어야 하는지까지 정해 둘 수 있습니다.
:::

**Q3. 경영진에게 ELT 방식을 승인받아야 합니다. 3분 안에 어떻게 설명하겠습니까?**

:::answer 모범 답안 보기
선택지 세 개를 한 줄씩 말합니다. 현행 DB 링크 유지는 가장 싸지만 재실행 시 중복·삭제 누락으로 숫자 신뢰가 깨지는 문제가 남습니다. ETL 도구는 원천 부하가 낮지만 도구 비용과 운영 역량 확보가 필요하고, 변환 로직이 도구 안에 숨어 감사 대응이 어렵습니다. 추천안 ELT는 원천 원본을 DW에 남겨 로직 오류 때 원천을 다시 건드리지 않고 고칠 수 있고, 팀 역량에 맞아 일정 위험이 낮습니다. 대가는 DW 저장 비용 증가와 운영 모니터링 직접 구축입니다. 마지막으로 결정해 주셔야 할 것(원본 보관 기간의 비용 승인)을 명확히 말합니다.
:::

## 오늘의 과제

**과제 1.** 경영지원실이 "비용 가중치를 15에서 40으로 올리고, 감사성은 30에서 15, 리니지는 20에서 10으로 낮춰 다시 보자"고 합니다(역량 20, 부하 15 유지). 가중치를 바꿔 다시 계산하고 결론이 바뀌는지 확인하세요. 결과 모양은 `opt_cd, wgt_score_100` 3행입니다.

:::answer 해설 보기
가중치 합이 100인지 먼저 확인합니다(40 + 15 + 10 + 20 + 15 = 100). 가중치를 바꿔도 순위가 유지되면 결정이 단단하다는 근거가 되고, 바뀌면 어느 기준이 결정을 좌우하는지 드러납니다. 원본 테이블을 바꾸지 않도록 트랜잭션 안에서 계산하고 되돌립니다.

```sql
BEGIN;
UPDATE lab.adr_crit SET wgt = CASE crit_cd WHEN 'COST' THEN 40 WHEN 'AUDIT' THEN 15 WHEN 'LINEAGE' THEN 10 ELSE wgt END
 WHERE adr_id = 'ADR-001';

SELECT s.opt_cd, ROUND(SUM(s.score * c.wgt) / 5.0) AS wgt_score_100
  FROM lab.adr_score s JOIN lab.adr_crit c ON c.adr_id = s.adr_id AND c.crit_cd = s.crit_cd
 WHERE s.adr_id = 'ADR-001'
 GROUP BY s.opt_cd
 ORDER BY wgt_score_100 DESC;
ROLLBACK;
```

ELT_SQL 83, DB_LINK 70, ETL_TOOL 50입니다. 비용을 크게 올려도 ELT가 1순위지만, DB 링크와의 차이가 34점에서 13점으로 줄어듭니다. 이 결과를 보여 주며 "비용이 최우선이라면 DB 링크 보완안도 경쟁력이 있지만, 감사성(NFR-03)을 포기하는 것"이라고 설명하면 경영진이 무엇을 맞바꾸는지 보고 결정할 수 있습니다.
:::

**과제 2.** ADR-002의 근거 쿼리를 바른팜유통(C000301)으로 다시 돌려, 거래처명 정정 시 스타와 OBT에서 고쳐야 하는 행 수를 비교하세요. 결과 모양은 `model, upd_row_cnt` 3행이며 스타 1행, 주문 라인 2행, 출고 라인 3행입니다.

:::answer 해설 보기
바른팜유통은 SO2026030003 주문 2라인, 출고 3라인(같은 주문상세가 두 로트로 출고)이 있습니다. 스타는 차원 1행만 고치면 모든 팩트가 새 이름으로 보이고, OBT는 팩트 행마다 이름을 다시 써야 합니다.

```sql
SELECT 'STAR: DIM_CUST' AS model, COUNT(*) AS upd_row_cnt
  FROM dw.dim_cust WHERE cust_no = 'C000301'
UNION ALL
SELECT 'OBT: 주문 라인', COUNT(*)
  FROM dw.fct_ord_line f JOIN dw.dim_cust c ON c.cust_sk = f.cust_sk WHERE c.cust_no = 'C000301'
UNION ALL
SELECT 'OBT: 출고 라인', COUNT(*)
  FROM dw.fct_ship_line f JOIN dw.dim_cust c ON c.cust_sk = f.cust_sk WHERE c.cust_no = 'C000301';
```

거래처가 Type 2로 버전이 여럿이면 스타도 버전 수만큼 고치지만(Day 19의 Type 1 속성 전 버전 갱신), 그 수는 팩트 행 수와 비교할 수 없이 작습니다.
:::
