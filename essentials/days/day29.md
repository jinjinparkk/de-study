# Day 29. DW 프로젝트 리딩

## 오늘의 한 줄

DW 프로젝트를 이끄는 일은 **요구사항이 끝까지 추적되게 하고, 위험을 일찍 드러내고, 단계마다 "합의된 산출물"로 다음 단계의 문을 여는 일**입니다. 모델링 실력은 출발점일 뿐이고, 무엇을 언제 누구와 합의했는지가 프로젝트를 지킵니다.

## 왜 중요한가

설계 단계에서 정 과장이 "실적은 출고 기준"이라고 했는데 인터뷰 기록이 없었고, 개발은 주문 기준으로 끝났습니다. 테스트 단계에서야 차이가 드러나 마트와 리포트를 다시 만들었고, 그사이 ERP 운영팀의 CDC 권한 승인이 늦어진다는 위험은 아무도 관리 대장에 올리지 않아 이행 일정이 3주 밀렸습니다. **요구사항 추적, 위험 관리, 단계 게이트**가 없어서 생긴 일입니다.

## 핵심 개념

### 1. 단계와 산출물: 산출물이 다음 단계의 입장권

DW 구축 방법론은 회사마다 이름이 다르지만 대개 분석 → 설계 → 구축 → 테스트 → 이행의 흐름입니다. 핵심은 각 단계가 **합의된 산출물**로 끝나야 다음 단계가 시작된다는 것입니다. 분석이 끝났다는 것은 요구사항정의서에 현업이 서명했다는 뜻이고, 설계가 끝났다는 것은 매핑정의서가 리뷰를 통과했다는 뜻입니다.

| 단계 | 핵심 질문 | 주요 산출물 | 끝났다는 기준 |
|---|---|---|---|
| 분석 | 무엇을 왜 보나, 원천은 무엇인가 | 요구사항정의서(기능·비기능), 인터뷰 기록, 원천 시스템 분석서(프로파일링), 현행 리포트 목록 | 현업 서명, 지표 정의 초안 합의 |
| 설계 | 어떤 구조로 담나 | 아키텍처 정의서·ADR(Day 28), 버스 매트릭스, 논리·물리 ERD, 테이블정의서, 매핑정의서, 배치 설계서, 지표 사전 | 설계 리뷰 통과, 원천 담당 확인 |
| 구축 | 만들기 | 적재 프로그램, 마트·BI 뷰, 시맨틱 모델, 단위 테스트 결과 | 단위 테스트 통과, 코드 리뷰 |
| 테스트 | 숫자가 맞나, 운영이 되나 | 통합 테스트 시나리오·결과, 원천 대사 결과, 성능 테스트, 사용자 인수 테스트(UAT) | 대사 차이 0(또는 사유 확인), 현업 UAT 서명 |
| 이행 | 바꿔 끼우기 | 이행 계획서(초기 적재·기초재고·병행 운영), 운영 매뉴얼, 장애 대응 매뉴얼, 교육 자료 | 리허설 성공, 운영 이관 서명 |

### 2. 요구사항 정의: 문장 → 지표 → 추적

요구사항은 현업의 문장("영업사원별 목표 대비 실적을 보고 싶다")에서 출발해 **지표 정의**(매출금액 = 취소 제외 주문금액, 주문일 기준, 월 × 사원)로 바뀌고, 그 지표가 어느 테이블·측정값·테스트로 구현되는지 **추적**돼야 합니다. 이 연결표를 요구사항 추적 매트릭스(RTM, Requirements Traceability Matrix)라고 합니다. RTM이 있으면 "이 요구사항은 테스트됐나?", "이 테이블을 바꾸면 어느 요구사항이 영향받나?"에 바로 답합니다. 우선순위는 MoSCoW(Must/Should/Could/Won't)처럼 단순하게 매기고, 1차 범위 밖은 Won't로 **명시적으로** 적어 범위 논쟁을 줄입니다.

### 3. 일정: 위험이 큰 것을 앞에

DW 일정에서 늦어지는 곳은 대개 개발이 아니라 **원천 의존**입니다. 원천 접근 권한, 원천 데이터 품질, 마스터 코드 매핑(Day 13), 현업 의사결정(실적 귀속 기준)입니다. 그래서 원천 프로파일링과 핵심 결정은 분석 초반에 당기고, 한 주제영역(영업실적)을 끝까지 먼저 관통시키는 수직 슬라이스로 위험을 일찍 드러냅니다.

### 4. 위험 관리: 대장에 올리고, 주인을 정하고, 매주 본다

위험은 "일어날 수 있는 문제"이고 이슈는 "이미 일어난 문제"입니다. 위험 대장에는 위험, 발생 가능성, 영향, 대응(회피·완화·전가·수용), 담당, 기한, 상태를 적고 주간 회의에서 봅니다. 아키텍트가 특히 챙길 위험은 원천 변경(ERP 패치로 컬럼 변경), 마스터 불일치, 성능(운영 규모 데이터), 결정 지연입니다.

### 5. 현업 인터뷰: 화면이 아니라 결정을 묻는다

"어떤 화면을 원하세요?"로 시작하면 현재 엑셀의 복사본이 나옵니다. **"그 숫자를 보고 어떤 결정을 하십니까?"** 로 시작해야 grain, 기준 일자, 신선도, 보안이 나옵니다. 인터뷰는 질문지를 미리 보내고, 현재 쓰는 엑셀·리포트 실물을 받고, 끝나면 기록을 공유해 확인받습니다.

## 예시

### 1차 일정 골격 (주차는 가상)

```text

```

### 현업 인터뷰 질문 리스트

**한빛제약 영업기획팀 정 과장 (영업실적 대시보드 요청자)**

1. 이 대시보드를 보고 매주·매월 어떤 결정을 하십니까? 누가 함께 봅니까?
2. "매출"은 주문, 출고, 세금계산서 중 어느 시점입니까? 취소·반품·증정(0원 라인)은 어떻게 다룹니까?
3. 담당 영업사원이 바뀌면 지난 실적은 누구 것입니까? 주문을 받은 사원과 거래처 담당이 다를 때는요?
4. 목표는 어떤 단위(월·사원·품목)로, 누가, 언제 확정합니까? 목표가 중간에 바뀌기도 합니까?
5. 몇 시까지 어제 숫자가 보여야 합니까? 그 시각에 못 맞추면 전날 숫자와 일부 최신 숫자 중 무엇이 낫습니까?
6. 지금 쓰는 엑셀·보고서를 주실 수 있습니까? 그 숫자는 어느 화면에서 가져오십니까?
7. 영업사원은 다른 사람·다른 팀 실적을 봐도 됩니까?
8. 숫자가 ERP와 다르면 누구에게 먼저 묻습니까? 어느 쪽을 정답으로 봅니까?

**한빛로지스 물류운영팀 한 대리 (출고·재고 데이터 담당)**

1. 재고의 정답은 어느 화면·어느 시점입니까? 일 마감은 몇 시에 확정됩니까?
2. 한 주문상세가 여러 로트로 나뉘어 출고되는 경우가 얼마나 흔합니까? 부분 출고·출고 취소는 어떻게 기록됩니까?
3. 유효기한 임박 재고는 몇 개월 전부터 관리합니까? 그 기준은 품목마다 다릅니까?
4. 거래처 코드는 한빛제약 ERP와 같은 코드를 씁니까, WMS 자체 코드입니까? 매핑표가 있습니까?
5. 입고와 발주를 연결하는 번호가 WMS에 있습니까(Day 21의 끊어진 연결)?
6. 재고 실사 조정은 언제, 어떤 유형으로 기록됩니까?
7. 창고·로케이션이 새로 생기거나 바뀌는 일정이 있습니까?

**한빛정보기술 ERP 운영팀 (운영계 DB 담당, 변경 승인권)**

1. DW가 조회해도 되는 시간대와 허용 부하 기준이 있습니까? 읽기 전용 복제본이 있습니까?
2. 주문 헤더·상세의 수정일시는 모든 프로그램이 채웁니까? 상세만 바뀌는 화면이 있습니까?
3. 물리 삭제가 일어나는 테이블과 시점은 언제입니까? 삭제 이력이 남습니까?
4. 일 마감 완료를 알 수 있는 신호(테이블, 로그)가 있습니까?
5. 로그 기반 CDC나 트리거 도입에 대한 정책은 무엇입니까? 승인 절차와 소요 기간은요?
6. 향후 ERP 패치·컬럼 변경 계획이 있습니까? 변경 시 DW 팀에 사전 통보가 가능합니까?
7. 공통코드(상태·유형 코드) 테이블과 코드 변경 이력은 어디에 있습니까?

질문지는 인터뷰 전에 보내고, 끝나면 "확인된 사실 / 결정 필요 사항 / 후속 자료" 세 칸으로 기록을 정리해 당일 공유하고 회신을 받습니다. 결정 필요 사항은 위험 대장이나 ADR로 옮깁니다.

## Before / After

| 항목 | Before | After |
|---|---|---|
| 요구사항 | 회의 메모, "대시보드 만들어 주세요" | 요구사항정의서 + 지표 정의 + RTM, 범위 밖은 WONT로 명시 |
| 인터뷰 | "어떤 화면 원하세요?" | 결정·기준 일자·신선도·보안을 묻는 질문지, 기록 공유·확인 |
| 일정 | 개발 기간 중심 | 원천 권한·핵심 결정·코드 매핑을 앞에, 수직 슬라이스 |
| 위험 | 문제가 터진 뒤 보고 | 위험 대장(노출도·담당·기한) 주간 검토 |
| 단계 전환 | 일정이 되면 다음 단계 | 산출물 합의(서명·리뷰 통과)가 게이트 |

| 판단 지점 | 이럴 땐 A | 저럴 땐 B |
|---|---|---|
| 범위 추가 요청 | 1차 목표(SLA·대사)에 영향 없고 작으면 Should로 수용 | 원천·모델이 새로 필요하면 2차로 미루고 WONT + 합의 기록 |
| 현업 결정 지연 | 선택지와 숫자 차이를 표로 만들어 결정 기한과 함께 요청 | 기한을 넘기면 기본안으로 진행하고 그 사실을 공식 기록(위험 수용) |
| 방법론 | 그룹 표준 방법론이 있으면 그 산출물 이름을 따름 | 없으면 위 다섯 단계와 게이트만 최소로 정함. 산출물 수보다 합의가 중요 |
| 테스트 기준 | 금액 지표는 원천 대사 차이 0 + 사유 | 분석용 보조 지표는 허용 오차를 현업과 합의해 명시 |
| 이행 | 리포트가 적으면 일괄 전환 | 리포트·사용자가 많으면 병행 운영 기간에 구·신 숫자 비교 리포트 제공 |

## 흔한 실수 3가지

1. **인터뷰 기록을 확인받지 않는 실수.** "그렇게 말한 적 없다"가 테스트 단계에 나옵니다. 당일 공유하고 회신을 받습니다.
2. **원천 의존 작업을 뒤에 두는 실수.** 권한·품질·코드 매핑은 늦게 알수록 일정 전체를 밉니다. 분석 1주차에 시작합니다.
3. **범위 밖을 적지 않는 실수.** 적지 않은 것은 "언젠가 해 준다"로 들립니다. WONT와 합의자·일자를 남깁니다.

## 셀프 체크 질문

**Q1. DW 프로젝트의 단계별 핵심 산출물과, 각 단계가 "끝났다"는 기준을 말해 보세요.**

:::answer 모범 답안 보기
분석은 요구사항정의서(기능·비기능), 인터뷰 기록, 원천 분석서가 산출물이고 현업 서명과 지표 정의 초안 합의가 종료 기준입니다. 설계는 아키텍처 정의서·ADR, 버스 매트릭스, ERD, 테이블정의서, 매핑정의서, 배치 설계서, 지표 사전이고 설계 리뷰 통과와 원천 담당 확인이 기준입니다. 구축은 프로그램과 단위 테스트, 테스트는 통합·대사·성능·UAT 결과이며 대사 차이 0(또는 사유 확인)과 UAT 서명이 기준입니다. 이행은 이행 계획·운영 매뉴얼이고 리허설 성공과 운영 이관 서명이 기준입니다. 일정이 아니라 합의가 단계를 닫습니다.
:::

**Q2. 프로젝트 중반에 경영지원실이 "계열사 통합 매출도 이번에 넣어 달라"고 합니다. 어떻게 대응하겠습니까?**

:::answer 모범 답안 보기
먼저 요청의 목적과 시급성을 확인하고, 영향을 구체적으로 보여 줍니다. 계열사 ERP 원천 분석, 거래처·품목 코드 매핑(MDM), 회사 차원 추가, 대사 범위 확대가 필요하고 이는 1차 SLA와 일정에 영향을 줍니다. 선택지를 제시합니다. (1) 2차로 미루고 1차 모델이 확장 가능하다는 근거(버스 매트릭스, ADR-002)를 보여 줌 (2) 1차 범위에서 다른 Should 항목을 빼고 축소판으로 수용 (3) 일정·인력 추가. 결정은 요청자와 프로젝트 오너가 하고, 결과를 요구사항정의서(WONT 또는 범위 변경)와 위험 대장에 기록합니다.
:::

**Q3. 현업 인터뷰에서 꼭 물어야 하는 질문 다섯 가지를 들고 이유를 설명해 보세요.**

:::answer 모범 답안 보기
"이 숫자로 어떤 결정을 하나"는 grain과 우선순위를 정합니다. "매출은 어느 시점·어떤 조건인가"는 지표 정의와 기준 일자를 정합니다. "담당이 바뀌면 실적은 누구 것인가"는 SCD 유형을 정합니다(Day 19). "몇 시까지 보여야 하고, 못 맞추면 무엇이 나은가"는 SLA와 장애 시 표시 규칙을 정합니다(Day 24). "누가 무엇을 봐도 되나"는 행 수준 보안을 정합니다. 여기에 "지금 쓰는 엑셀을 달라"를 더하면 검증할 정답지를 얻습니다.
:::

## 오늘의 과제

**과제 1.** 요구사항 추적 점검 쿼리를 작성하세요. 우선순위가 MUST인 요구사항 중 테스트(TEST) 추적이 없는 것을 찾습니다. 결과 모양은 `req_id, req_desc` 2행(FR-02, NFR-02)입니다.

:::answer 해설 보기
테스트가 연결되지 않은 MUST 요구사항은 "만들었지만 맞는지 확인할 계획이 없는" 항목입니다. 이 쿼리를 테스트 단계 진입 게이트로 씁니다.

```sql
SELECT r.req_id, r.req_desc
  FROM lab.prj_req r
 WHERE r.prio_cd = 'MUST'
   AND NOT EXISTS (SELECT 1 FROM lab.prj_req_trace t WHERE t.req_id = r.req_id AND t.obj_tp_cd = 'TEST')
 ORDER BY r.req_id;
```

FR-02(목표 달성률)는 Day 26 과제 2의 SQL 기준표를, NFR-02(ERP 대사)는 Day 22·23의 대사 쿼리를 테스트 케이스로 등록하면 됩니다.
:::

**과제 2.** 영향도 분석입니다. FCT_ORD_LINE 구조를 바꿔야 할 때 영향받는 요구사항을 찾고, 그 요구사항들이 연결된 다른 구현물(측정값·작업·테스트)까지 함께 보여 주세요. 결과 모양은 `req_id, obj_tp_cd, obj_nm` 이며 FR-01의 TABLE·MEASURE·TEST 3행입니다.

:::answer 해설 보기
RTM을 거꾸로 읽으면 영향도 분석이 됩니다. 테이블 → 요구사항 → 그 요구사항의 모든 구현물 순으로 따라갑니다. 실무에서는 컬럼 리니지(Day 11)와 함께 써서 "어느 측정값이 그 컬럼을 쓰는지"까지 좁힙니다.

```sql
SELECT t.req_id, t.obj_tp_cd, t.obj_nm
  FROM lab.prj_req_trace t
 WHERE t.req_id IN (SELECT req_id FROM lab.prj_req_trace
                     WHERE obj_tp_cd = 'TABLE' AND obj_nm = 'FCT_ORD_LINE')
 ORDER BY t.req_id, t.obj_tp_cd;
```

FR-02·FR-03도 실제로는 FCT_ORD_LINE을 읽지만(측정값이 그 위에 있음) TABLE 추적이 빠져 있어 잡히지 않습니다. RTM은 빠짐없이 채울 때만 쓸모가 있으므로, 추적 누락 점검(TABLE 추적이 없는 FR)도 함께 돌립니다.
:::
