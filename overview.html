시작 전에 · dbt

dbt 한눈에

1~4일차에서 하나씩 배울 내용을 한 장의 지도로 먼저 봅니다. 여기서는 외우지 말고 "이런 부품이 있고, 이렇게 맞물리는구나"만 잡으세요.

읽는 데 약 30분 · 실습 없음

💡 dbt를 한 문장으로 dbt는 SELECT 문만 쓰면, 그걸 테이블·뷰로 만드는 DDL, 실행 순서, 테스트, 문서, 이력 관리를 대신 붙여 주는 도구입니다. 데이터를 계산하는 건 dbt가 아니라 웨어하우스(BigQuery, Snowflake, DuckDB…)입니다.

1. dbt는 어디에 있나

데이터가 원천에서 대시보드까지 가는 길을 그리면 이렇습니다. dbt는 웨어하우스 안에서 T(변환)만 맡습니다.

  원천                옮기기 (E·L)          웨어하우스 안 (T = dbt)                      쓰는 곳
  ─────               ────────────          ─────────────────────────────                ──────
  ERP · 앱 DB   ──┐
  광고 API      ──┼──▶  Fivetran      ──▶   raw  ──▶  staging  ──▶  marts   ──────▶   BI 대시보드
  로그 · CSV    ──┘     Airbyte              (원본    (정제)         (완성 표)          분석 · ML
                        직접 짠 스크립트       그대로)

  ◀──────────────────────── Airflow: 매일 몇 시에, 무엇 다음에 무엇을 (지휘자) ────────────────────────▶
                               └ Spark: 웨어하우스가 감당 못 할 크기일 때 따로 쓰는 계산 엔진

dbt가 하는 일

  • SELECT를 테이블·뷰로 만들기
  • 모델 사이 의존 관계를 읽고 순서대로 실행
  • 테스트 실행 (중복·NULL·허용값…)
  • 문서·리니지 그래프 만들기
  • 개발/운영 환경 나누기

dbt가 안 하는 일

  • 원천 시스템에서 데이터 가져오기 (E·L) → Fivetran, Airbyte 등
  • 정해진 시각에 자동 실행 (dbt Core 기준) → Airflow, cron 등
  • 데이터 저장·계산 → 웨어하우스
  • 대시보드 → BI 도구
🔁 프로시저 감각으로 옮기면 지금까지는 프로시저 하나가 E·T·L과 스케줄 일부까지 다 했습니다. 모던 데이터 스택에서는 이걸 도구별로 쪼갭니다. 가져오기는 EL 도구가, 변환은 dbt가, 언제 돌릴지는 Airflow가 맡습니다. 프로시저 안의 SQL 부분이 거의 그대로 dbt로 옮겨 온다고 보면 됩니다.

2. dbt run 하면 안에서 일어나는 일

제일 중요한 그림입니다. 내가 쓰는 건 SELECT뿐이고, 나머지는 dbt가 채웁니다.

  ① 내가 쓰는 파일                models/daily_sales.sql
                                  select order_date, count(*) as orders
                                  from {{ ref('stg_orders') }}            ← Jinja (중괄호 두 개)
                                  group by order_date
                                        │
                                        │  파싱: ref('stg_orders')를 보고
                                        │        "daily_sales는 stg_orders 다음"이라고 기록 → DAG
                                        ▼
  ② 컴파일 결과                   target/compiled/shop/models/daily_sales.sql
                                  select order_date, count(*) as orders
                                  from "dev"."main"."stg_orders"          ← 진짜 테이블 이름
                                  group by order_date
                                        │
                                        │  materialization(table)으로 감싸기
                                        ▼
  ③ 실제로 보내는 SQL             target/run/shop/models/daily_sales.sql
                                  create table "dev"."main"."daily_sales" as (
                                      select ... from "dev"."main"."stg_orders" ...
                                  )
                                        │
                                        │  profiles.yml의 연결 정보로 전송
                                        ▼
  ④ 웨어하우스가 실행             DuckDB / BigQuery / Snowflake ... (계산은 여기서)
단계누가프로시저 세계에서는
① SELECT 쓰기나프로시저 안의 SELECT 부분
② ref → 진짜 이름dbt스키마명·테이블명을 손으로 적음 (dm.daily_sales)
③ DDL로 감싸기dbtCREATE OR REPLACE TABLE … AS, DELETE + INSERT를 손으로 씀
④ 실행웨어하우스같음
✅ 디버깅할 때 오류가 나면 target/compiled/의 SQL을 복사해서 DB 콘솔에서 직접 돌려 보세요. 대부분 그걸로 원인이 보입니다. VS Code의 dbt Power User 확장을 쓰면 이 SQL을 옆 창에서 바로 볼 수 있습니다.

3. 프로젝트 폴더 = dbt의 전부

dbt 프로젝트는 그냥 폴더입니다. 파일이라 git으로 관리할 수 있습니다. 프로시저가 DB 안에 숨어 있던 것과 가장 크게 다른 점입니다.

  shop/                          ← dbt init 이 만든 프로젝트 폴더 (git 저장소)
  ├─ dbt_project.yml             ← 프로젝트 설정: 이름, 폴더별 기본 materialization       [1일차]
  ├─ models/                     ← 핵심. SELECT 파일 하나 = 모델 하나 = 테이블/뷰 하나
  │   ├─ staging/                    stg_*.sql  원본 1:1 정제                             [2일차]
  │   │   ├─ _sources.yml            원본 테이블 등록 (source)                            [2일차]
  │   │   └─ _stg_models.yml         컬럼 설명 + 테스트                                   [3일차]
  │   ├─ intermediate/               int_*.sql  중간 조립                                 [2일차]
  │   └─ marts/                      fct_* · dim_* · 완성 표                              [2일차]
  ├─ tests/                      ← 직접 쓰는 검증 SQL (singular test)                    [3일차]
  ├─ macros/                     ← 재사용 SQL 조각 (함수 같은 것)                         [4일차]
  ├─ seeds/                      ← 작은 CSV를 테이블로 (코드표 등)                        [2일차]
  ├─ snapshots/                  ← 변경 이력 (SCD2)                                       [4일차]
  └─ target/                     ← dbt가 만든 결과물 (컴파일된 SQL 등). git에 안 올림

  ~/.dbt/profiles.yml            ← 프로젝트 밖! DB 접속 정보·비밀번호. git에 안 올림       [1일차]

dbt_project.yml — 무엇을

프로젝트 이름, 모델 폴더 위치, "staging 폴더는 view, marts는 table" 같은 규칙. 팀 전체가 같이 쓰므로 git에 올립니다.

profiles.yml — 어디에

어느 DB에, 어떤 계정으로 붙을지. dev(내 개발용)와 prod(운영)를 나눠 둡니다. 비밀번호가 있어서 git에 안 올립니다.

4. ref · source · DAG — 순서를 dbt가 정하는 원리

모델 안에서 다른 테이블을 부를 때 이름을 직접 적지 않고 함수로 부릅니다.

  • {{ source('shop', 'raw_orders') }}: dbt 밖에서 들어온 원본을 부를 때
  • {{ ref('stg_orders') }}: dbt가 만든 다른 모델을 부를 때

dbt는 모든 파일에서 이 함수들을 모아 누가 누구를 쓰는지 그래프를 그립니다. 이게 DAG(방향이 있고 되돌아오지 않는 그래프)입니다.

  source                    staging                 intermediate              marts
  (원본, dbt 밖)            (view)                  (ephemeral)               (table)

  raw_customers ───▶   stg_customers ─────────────────────────────────────────┬──▶  dim_customers
                                                                               │         ▲
  raw_orders    ───▶   stg_orders    ──────────────────────────┬──▶  fct_orders ─────────┘
                                                                │
  raw_payments  ───▶   stg_payments  ───▶  int_order_payments ──┘

  dbt run 실행 순서:  ① stg_* 3개 (동시에)  →  ② fct_orders  →  ③ dim_customers
  (int_order_payments 는 ephemeral 이라 따로 만들어지지 않고 fct_orders SQL 안에 CTE 로 들어감)
  ※ 2일차 실습에서 실제로 만드는 그래프입니다. 1일차의 daily_sales 는 2일차에 이 구조로 바뀝니다.
이름을 직접 쓰면 (프로시저 방식)ref로 쓰면
실행 순서를 스케줄러에 사람이 적는다그래프를 보고 dbt가 정한다. 서로 상관없는 건 동시에 돌린다 (threads)
dev·prod 스키마명이 코드에 박혀 있다dev로 돌리면 dev 스키마, prod로 돌리면 prod 스키마로 자동으로 바뀐다
"이 표 바꾸면 어디가 영향받지?"를 grep으로 찾는다리니지 그래프에서 바로 보인다

그래프가 있으니 일부만 골라 실행할 수도 있습니다. 실무에서 매일 쓰는 문법입니다.

선택 문법뜻언제
-s stg_orders이 모델 하나만방금 고친 모델 확인
-s stg_orders+이 모델 + 이걸 쓰는 하위 모델 전부고친 게 아래에 미치는 영향까지 다시 만들 때
-s +daily_sales이 모델 + 이게 쓰는 상위 모델 전부이 표 하나를 처음부터 완전히 새로 만들 때
-s path:models/stagingstaging 폴더 전체계층 단위로 돌릴 때

5. 계층 — staging · intermediate · marts

프로시저 하나에 몰려 있던 단계를 역할별 층으로 나눕니다. 폴더 이름이 곧 규칙입니다.

  층              파일 이름         하는 일                                     보통 형태     누가 보나
  ──────────────  ───────────────  ──────────────────────────────────────────  ───────────  ────────────
  source          (등록만)          원본 테이블 위치 선언. SQL 없음               -            -
  staging         stg_원본명        원본 1개 ↔ 모델 1개. 이름 바꾸기, 형 변환,     view         개발자만
                                    소문자·공백 정리. JOIN·집계 안 함
  intermediate    int_설명          staging 여러 개 조립. JOIN, 중간 집계         ephemeral    개발자만
                                                                                 또는 view
  marts           fct_ · dim_       업무 단위 완성 표. 대시보드가 여기만 읽음      table        분석가 · BI
🔁 프로시저 감각으로 옮기면 1일차의 sp_build_daily_sales를 떠올리세요. -- 1) 정제의 tmp_orders가 staging, -- 2) 결제 합치기가 staging/intermediate, -- 3) 마트 적재가 marts입니다. 임시 테이블 하나하나가 파일 하나가 되고, 다른 프로시저도 그 파일을 가져다 쓸 수 있게 됩니다. LOWER(TRIM(status))를 프로시저마다 복사하던 일이 사라집니다.

fct와 dim: fct_(fact)는 주문·결제처럼 일어난 일이 행 하나인 표, dim_(dimension)은 고객·상품처럼 대상이 행 하나인 표입니다. 대시보드는 fct를 dim과 JOIN해서 "고객 등급별 매출" 같은 걸 만듭니다.

6. materialization — 같은 SELECT, 다른 저장 방식

SELECT는 그대로 두고 설정 한 줄로 어떻게 저장할지만 바꿉니다. 프로시저에서 손으로 쓰던 DDL·DML을 dbt가 대신 만들어 줍니다.

종류dbt가 만드는 SQL프로시저에서 쓰던 것언제배우는 날
viewcreate view … as select뷰가볍고 자주 바뀌는 staging1·2
tablecreate table … as select (매번 통째로 새로)TRUNCATE + INSERT, CREATE OR REPLACE대시보드가 읽는 marts1·2
ephemeral테이블을 안 만들고 쓰는 쪽 SQL에 CTE(with …)로 끼워 넣음임시 테이블, 서브쿼리잠깐 쓰는 중간 조립2
incremental처음엔 table, 이후엔 새 행만 merge / delete+insertMERGE, DELETE WHERE dt = p_date + INSERT매일 쌓이는 큰 표4
snapshot
(모델과 별도)		바뀐 행에 유효기간(dbt_valid_from/to)을 붙여 이력 보존SCD Type 2 프로시저고객 등급처럼 덮어쓰면 과거가 사라지는 값4
  설정하는 곳 (아래가 위를 덮어씀)

  dbt_project.yml          models: shop: staging: +materialized: view     ← 폴더 단위 기본값
        ▼                                 marts:   +materialized: table
  models/*.yml             - name: daily_sales  config: materialized: ...  ← 모델 단위
        ▼
  모델 파일 맨 위           {{ config(materialized='incremental') }}         ← 가장 우선

7. 테스트와 문서 — 품질을 코드에 붙이기

프로시저 세계에서는 "결과가 맞나?"를 문제가 터진 뒤에 압니다. dbt에서는 YAML에 기대 조건을 적어 두고 매번 같이 돌립니다.

  models/staging/_stg_models.yml                     dbt test 가 실제로 돌리는 SQL (대략)
  ──────────────────────────────                     ─────────────────────────────────────
  - name: stg_orders
    columns:
      - name: order_id
        data_tests:
          - unique                 ──────▶   select order_id from stg_orders
                                             group by order_id having count(*) > 1
          - not_null               ──────▶   select * from stg_orders where order_id is null
      - name: status
        data_tests:
          - accepted_values:       ──────▶   select * from stg_orders
              arguments:                     where status not in ('completed', 'returned', ...)
                values: [...]

  규칙: 결과가 0행이면 통과(PASS), 1행이라도 나오면 실패(FAIL)
종류무엇예
generic testYAML에 이름만 적는 기본 테스트unique, not_null, accepted_values, relationships(외래 키)
singular testtests/ 폴더에 직접 쓰는 SELECT. "나오면 안 되는 행"을 찾는 쿼리결제 합계가 음수인 주문
source freshness원본이 제때 들어왔는지"raw_orders 최신 행이 24시간보다 오래됐으면 경고"
contract모델 컬럼 이름·타입을 약속. 어기면 빌드 자체가 실패order_id는 반드시 bigint

같은 YAML에 description을 적으면 dbt docs generate가 문서 사이트 + 리니지 그래프를 만듭니다. 엑셀 테이블 정의서가 코드 옆으로 들어온 셈입니다.

8. 명령어 흐름 — 하루 작업은 이렇게 돈다

  개발할 때 (dev)                                              운영 (prod, 보통 Airflow가 실행)
  ────────────────                                              ────────────────────────────────
  모델 파일 수정
     │
     ├─▶ dbt compile -s 모델   SQL만 만들어 보기 (DB에 안 보냄)
     ├─▶ dbt show -s 모델      결과 몇 줄 미리 보기
     ├─▶ dbt build -s 모델+    만들고 + 테스트 + 하위까지
     │
     └─▶ git commit · push ─▶ 코드 리뷰 ─▶ main 병합 ──────▶  dbt build --target prod
                                                               (매일 새벽, 실패하면 알림)
명령하는 일배우는 날
dbt debug프로필·DB 연결 점검1
dbt run모델 만들기 (테스트 없음)1
dbt show결과 미리 보기 (테이블은 안 만듦)1
dbt compile컴파일된 SQL만 만들기1
dbt seedseeds/의 CSV를 테이블로 올리기2
dbt test테스트만 실행3
dbt buildseed → run → test → snapshot을 DAG 순서대로 섞어서 실행. 실무 기본3
dbt docs generate / serve문서 사이트 만들기 / 띄우기3
dbt snapshot스냅숏(SCD2)만 실행4
dbt depspackages.yml의 패키지 설치 (예: dbt_utils)4
  dbt build 가 run + test 보다 나은 이유

  stg_orders 만들기 ─▶ stg_orders 테스트 ─▶ ✗ 실패
                                              │
                                              └─▶ 이걸 쓰는 fct_orders, dim_customers 는 SKIP
                                                  (틀린 데이터가 대시보드까지 번지지 않음)

  dbt run 후 dbt test 를 따로 하면: 이미 dim_customers 까지 틀린 데이터로 다 만든 뒤에야 실패를 앎

9. Jinja와 매크로 — SQL에 변수와 함수를 더하기

{{ }}와 {% %}는 Jinja라는 템플릿 문법입니다. dbt는 SQL을 DB에 보내기 전에 이걸 먼저 풉니다(2번 그림의 ②).

문법뜻예프로시저에서는
{{ … }}값 넣기{{ ref('stg_orders') }}, {{ var('start_date') }}변수 p_date
{% if %}조건{% if is_incremental() %} where … {% endif %}IF … THEN
{% for %}반복으로 SQL 찍어 내기결제수단마다 sum(case when …) 컬럼 만들기동적 SQL 문자열 조립
{% macro %}재사용 함수{{ cents_to_won('amount') }}공통 함수, UDF
⚠️ 처음에 많이 하는 실수 Jinja는 DB가 아니라 dbt가 SQL을 만들기 전에 실행합니다. 그래서 Jinja 안에서 테이블의 값을 바로 읽을 수는 없습니다(읽으려면 run_query 같은 별도 기능이 필요합니다). "Jinja로 SQL 글자를 만든다 → 그 SQL을 DB가 실행한다", 두 단계로 생각하세요.

10. 환경 — dev와 prod를 나누는 방법

  ~/.dbt/profiles.yml
  shop:                          ← dbt_project.yml 의 profile: 'shop' 과 이름이 같아야 함
    target: dev                  ← 아무것도 안 쓰면 dev 로 실행
    outputs:
      dev:   path: dev.duckdb      threads: 1     ← 내 PC, 내 개인 스키마
      prod:  path: prod.duckdb     threads: 4     ← 운영

  dbt build                  →  dev 에 만들어짐  (마음껏 깨도 됨)
  dbt build --target prod    →  prod 에 만들어짐 (보통 사람이 아니라 Airflow·CI 가 실행)

같은 코드가 --target만 바꾸면 다른 곳에 만들어지는 건 ref() 덕분입니다. 코드에 스키마 이름을 직접 적지 않았으니까요. 실무에서는 개발자마다 dbt_eunjin 같은 개인 dev 스키마를 갖고, 운영 스키마는 자동화만 건드립니다.

11. 프로시저 ↔ dbt 한 장 비교

주제프로시저dbt
코드 위치DB 안폴더 안 파일 → git
작성 단위프로시저 하나에 여러 단계SELECT 하나 = 모델 하나
DDL·DML직접 씀materialization 설정으로 자동
실행 순서사람이 정함ref 그래프로 자동
재사용복사·붙여 넣기ref로 다른 모델 참조, 매크로
매개변수p_date DATEvar(), is_incremental()
품질 확인따로 짠 검증 쿼리, 혹은 없음테스트가 빌드에 포함
문서엑셀 정의서YAML → 문서 사이트 자동 생성
dev/prod스키마명을 코드에서 바꾸거나 DB를 따로 둠--target 하나로 전환
이력잘 안 남음git 커밋·코드 리뷰
스케줄DB 스케줄러 / 에이전트 잡dbt 밖 (Airflow 등) — 5·6일차

패턴별로 더 자세한 대응은 프로시저↔dbt 사전에 있습니다.

12. 7일 지도 — 이 그림의 어디를 언제 배우나

  1  큰 그림         ── 2번(dbt run 내부), 3번(폴더·profiles)  ── 첫 모델 3개, git
  2  모델·ref·계층    ── 4번(ref·source·DAG), 5번(계층), 6번(view·table·ephemeral)
  3  테스트·문서      ── 7번(테스트·freshness·contract), 8번(dbt build)
  4  Jinja·증분      ── 9번(Jinja·매크로), 6번(incremental·snapshot), 패키지
  ───────────────────────────────────────────────────────────────────────────
  5  Airflow 개념     ── 1번 그림의 "지휘자": DAG·Task·스케줄·백필
  6  Airflow + dbt    ── 8번 그림의 오른쪽(운영): Airflow가 dbt build --target prod 실행
  7  Spark            ── 1번 그림의 "큰 칼": 웨어하우스 밖에서 큰 데이터 계산
🧸 전체를 비유로

웨어하우스는 주방, raw는 막 들어온 식재료, dbt 모델은 단계별 레시피 카드, ref는 카드에 적힌 "이 카드 앞에 저 카드", 테스트는 단계마다 붙은 간 확인표, marts는 손님에게 나가는 완성 요리입니다.

Airflow는 "매일 새벽 5시에 카드 순서대로 요리 시작, 식재료가 안 왔으면 기다렸다가"라고 지시하는 주방장이고, Spark는 주방 화구로는 감당이 안 되는 대량 주문이 들어왔을 때 빌려 오는 대형 조리 설비입니다.

💡 이 페이지에서 꼭 가져갈 세 가지
  1. 내가 쓰는 건 SELECT뿐. DDL·순서·테스트는 dbt가, 계산은 웨어하우스가 한다.
  2. ref() 하나가 실행 순서, dev/prod 전환, 리니지를 모두 가능하게 한다.
  3. 막히면 target/compiled의 SQL을 열어 본다.
